# Research — Cover Letter Backend (Model, Storage, AI Generation, Template Matching)

## Research Basis

Novorésumé gates cover letters as a premium feature (Basic = "No Cover Letter"; Premium = "Matching Cover Letter"). Resume Now positions cover-letter building as a first-class product feature. Both signal that cover letters share design continuity with resumes. Novorésumé's AI cover-letter generator reuses resume data + job description, implying tightly linked backend models.

## What The Research Means For The Backend

- **Cover-letter and resume share a design system**: templates for cover letters are paired with resume templates. The backend should support this pairing (matching template IDs) so "matching cover letter" works without the user searching for the right template.
- **Cover-letter is its own document type** with its own structured model (recipient info, salutation, body paragraphs, closing), but it shares many backend patterns with resumes (save, autosave, versioning, preview, export).
- **AI cover-letter generation** must pull from the associated resume's structured data (name, experience highlights, skills) plus the job description to generate relevant, non-fabricated content. This is a cross-document AI query.
- **Premium gating** on cover-letter creation is a simple entitlement check (can this user create cover letters?); may be bundled or separate.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Cover-letter as a document type (parallel to resume) | Reuses save/version/export infrastructure |
| Matching template pairs (resume template → cover-letter template) | Visual continuity; premium value |
| Structured cover-letter model (recipient, salutation, body, closing) | Enables AI targeting for specific sections |
| AI cover-letter generation from resume data + job desc | Resume-aware, no duplicate data entry |
| Entitlement gating (premium required for cover-letter creation) | Monetization layer |
| Document-type filtering in workspace (Resumes / Cover Letters / All) | Organization alongside multi-language documents |

## Hidden Requirements Inferred

- Resume-to-cover-letter association (optional: which resume is this cover letter paired with?).
- AI cover-letter generation shares the same safety rules as resume AI: no fabrication, reviewable before acceptance, quota-tracked.
- Cover-letter-specific sections: recipient name, company name, job title, salutation, body (introduction, body paragraphs, closing), signature block.
- Template pairing data: `resume_template_id → matching_cover_letter_template_id`.

## Risks If Under-Specified

- Cover-letter model may be built as a simple free-text field, defeating AI and template-matching capabilities.
- AI cover-letter generation may fabricate experience that contradicts the resume if cross-document context is not properly linked.
- Premium gating may be inconsistent (cover letters free on one surface, premium on another).
- Template pairing may not be modeled, forcing users to manually find matching designs.

## Recommendation To Developers

- Model cover letters as structured documents (typed sections: recipient, salutation, body_paragraphs[], closing) sharing the same infrastructure as resumes.
- When generating AI cover letters, resolve the linked resume's structured data as context.
- Support a `template_pairing: { resume_template_id → cover_letter_template_id }` mapping in the template catalog.

## Open Questions

- MVP: manual cover-letter editor only, or AI-assisted as well?
- Should cover-letter and resume templates be auto-paired, user-selectable, or both?
- Should cover-letter be a separate document entity or an extension of the resume entity?
