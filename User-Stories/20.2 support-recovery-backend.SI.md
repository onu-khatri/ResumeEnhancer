# Supporting Information — Support Entry Metadata And Recovery Guidance Service

## Proposed APIs

- `GET /support/entry-points`
- `GET /support/contextual-help`

## Example Contextual Help Response

```json
{
  "context": "export_failure",
  "actions": [
    {
      "type": "self_service",
      "label": "Check export blockers"
    },
    {
      "type": "contact",
      "label": "Contact support"
    }
  ]
}
```

## Proposed Entities

- `SupportEntry`
- `HelpCategory`
- `SystemSetting`

## Suggested Technical Controls

- Config-driven workflow mapping
- Approved channel allowlist
- Generic fallback help payload

## Edge Cases

- Unknown workflow context is passed by the frontend (due to a bug, new workflow not yet configured, or an old client), and the service must return the `isFallback: true` generic entry rather than 404, ensuring users still see help options even for unmapped contexts.
- Region-specific support rule mismatch occurs when a user's locale implies one set of contact channels but the configured metadata is missing for that region; the service should fall back to the default region entry and not return an empty response.
- Support-channel metadata changed mid-session, meaning the frontend's cached support data may be stale during a support policy update; the service should support short TTL headers or ETags so the frontend can refresh without a full page reload.

## Test Focus

- Context mapping validity should be tested for all supported workflow keys to confirm each returns actions of the correct types and that no context returns an empty actions array.
- Fallback behavior should be tested by passing unknown, null, and malformed context values to verify the service always returns a valid payload with the `isFallback` flag set true.
- Safe handling of missing configuration should be tested by simulating a scenario where the support metadata store is empty or corrupted, confirming the service returns an error response that includes minimal static contact information in the body rather than a blank 500.

## Developer Notes

- Keep client-facing support metadata intentionally simple and stable; the response shape should have only the fields the frontend needs (context, actions array with type/label/description/target) and resist the temptation to add internal metadata fields that create tight coupling.
- Avoid exposing internal ticketing or operator-tool identifiers in client responses; any ID used for Zendesk, Intercom, or internal admin routing must be stripped at the API boundary before the response is sent to the browser.
