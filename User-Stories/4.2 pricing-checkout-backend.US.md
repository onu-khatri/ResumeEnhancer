## [BILL-BE-002] — Pricing Catalog, Checkout Session, And Return Verification Services

**Module:** Billing And Entitlements  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Free User, Active Job Seeker, Billing Platform, Product Support  
**Dependency:** EXP-BE-001, SUB-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform,  
I want canonical plan data, safe checkout-session orchestration, and reliable return verification,  
so that pricing remains consistent and entitlements change only when payment is actually confirmed.

### Description

This story covers the backend layer behind public pricing and in-product upgrade journeys. The service must provide canonical plan definitions for frontend display, create checkout sessions tied to a specific user and originating task, verify return state after checkout, and expose accurate entitlement truth. Resume-product billing is unusually trust-sensitive, so the backend must prevent ambiguous states such as “UI says premium but payment is not confirmed” or “checkout succeeded but the original export flow cannot be restored.”

### Scope

**Included In Scope**

- Plan catalog retrieval for pricing and upgrade surfaces.
- Checkout-session creation with origin context.
- Checkout return verification and normalized status response.
- Entitlement refresh after payment outcome.
- Commercial-state normalization for frontend use.

**Out Of Scope**

- Provider-specific ledger implementation details.
- Full subscription lifecycle management after activation.
- Finance reconciliation reporting.

### Preconditions

- Billing provider integration exists. Checkout-session creation and return verification depend on a working provider integration that can be called server-side without exposing secrets.
- Canonical plan/entitlement model exists. Plans, offers, and their feature matrices must already be defined so checkout can validate against a single source of commercial truth.
- Secure user session and ownership model exists. Checkout must be able to resolve the authenticated user and bind attempts to them, so ownership-safe correlation is possible from the first request.

### Detailed Workflow

1. Client requests plan catalog for pricing or upgrade display.
2. User initiates checkout for a selected offer from a known source context.
3. Backend validates offer availability and creates a provider checkout session.
4. Backend stores correlation data for user, plan, source context, and safe return handling.
5. User returns from provider flow.
6. Backend verifies checkout outcome and returns normalized status plus refreshed entitlement view.

### Functional Requirements

- The plan catalog service must expose commercially approved pricing metadata and feature matrices.
- Checkout session creation must validate the authenticated user, requested offer, and source context.
- The system must persist enough correlation data to restore meaningful return state.
- Return verification must distinguish success, cancellation, pending settlement, and failure.
- Entitlements must only change based on trusted backend/provider confirmation.
- The response must give frontend enough information to continue the original user task safely.

### Acceptance Criteria

**AC1 — Canonical Pricing Data**  
Given a client requests pricing data  
When the request is authorized for public or authenticated use  
Then the service returns a canonical, frontend-safe representation of current plans and features.

**AC2 — Checkout Session Safety**  
Given an authenticated user starts checkout  
When the selected offer and context are valid  
Then the service creates a checkout session tied to that user and returns a safe redirect payload.

**AC3 — Verified Return Outcome**  
Given the user returns from checkout  
When the backend verifies the provider state  
Then it returns normalized status and current entitlements without trusting client-only success markers.

**AC4 — Continuation Context**  
Given checkout originated from export, AI, analysis, or template unlock  
When return verification completes  
Then the service returns enough contextual metadata for the frontend to restore that journey.

**AC5 — Failure Integrity**  
Given checkout fails, is canceled, or remains pending  
When the frontend requests return verification  
Then the response accurately reflects the unresolved state and does not grant premium access.

### Business Rules

- Plans and feature matrices must be single-sourced. Every pricing page and entitlement check must read from the same canonical definitions so the UI never promises a capability the entitlement system does not actually grant.
- Commercial copy may vary by market, but capability truth must remain canonical. Wording, price, and currency can be localized, but the underlying feature matrix must stay consistent across all surfaces.
- Checkout correlation state must be temporary, ownership-safe, and auditable. Correlation records link a user to a checkout attempt and must never be reusable by another user or survive indefinitely.
- Entitlement grant is a backend authority concern, never a UI guess. The frontend must not flip entitlement state based on user perception; only trusted provider confirmation changes access.

### Validation Rules

- Requested offer must exist and be available to the current user/market. The backend must confirm the offer is real, not expired, and applicable to the user's market before creating a provider session.
- Source context type must be one of the supported premium-boundary origins. Only known origin types (export, AI, analysis, template unlock, etc.) are accepted, so continuation metadata stays interpretable.
- Return-verification requests must map to a known, user-owned checkout attempt. A return request that references an unknown or foreign attempt must be rejected rather than treated as a legitimate payment confirmation.

### Error Handling

- If plan catalog is temporarily unavailable, return a stable service-unavailable response suitable for pricing fallback UI. Pricing surfaces can render a cached or simplified fallback rather than a blank page.
- If checkout session creation fails after validation, do not create partial entitlement changes. A failed session must leave entitlement state untouched so the user's access level cannot drift.
- If provider return cannot be verified immediately, return a pending state and support retry polling. The client should poll or retry verification rather than assume success or failure on a transient provider delay.

### Security Considerations

- Do not expose provider secrets or raw callbacks directly to the client. Provider keys and webhook payloads stay server-side; the client only receives safe redirect URLs and normalized status.
- Correlation state must resist tampering and cross-user replay. Attempt IDs must be unguessable and bound to the owning user so one user cannot complete or reuse another's checkout.
- Return URLs and continuation routes must be allowlisted. Redirect targets must be validated against an allowlist to prevent open-redirect and phishing vectors.

### Data Model

> This section describes the expected entity structure with possible properties. It is a **business-requirements-level starting point** to drive technical modeling discussions, not a final database schema. Types, relationships, and constraints should be refined during technical design.

#### PlanDefinition

The canonical commercial capability bundle. Single source of truth for pricing and feature matrix truth.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `code` | string | Stable plan code, e.g. `basic`, `premium` |
| `displayName` | string | User-facing plan name |
| `billingModel` | enum | `free`, `one_time`, `subscription` |
| `features` | json | Canonical feature matrix, e.g. `pdfExport`, `docxExport`, `premiumTemplates` |
| `isPublic` | boolean | Whether shown on public pricing surfaces |
| `updatedAt` | datetime | |

#### OfferDefinition

A market/cohort-specific purchasable offer that resolves to a canonical plan.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `offerCode` | string | Purchasable offer code, e.g. `premium_quarter` |
| `planCode` | string | Reference to the canonical plan |
| `priceAmount` | number | Offer price |
| `currency` | string (ISO 4217) | Currency code |
| `duration` | string \| null | Time-box length for time-boxed offers |
| `market` | string \| null | Market/cohort availability scope |
| `isAvailable` | boolean | Whether currently purchasable |
| `expiresAt` | datetime \| null | Offer expiration, if any |

#### CheckoutAttempt

Ties a user, offer, provider session, and originating source context together so return state can be restored safely.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `userId` | string (uuid) | Authenticated user who initiated checkout |
| `offerCode` | string | Offer being purchased |
| `sourceContext` | json | Structured origin: `type`, `documentId`, `format`, etc. |
| `providerSessionId` | string \| null | Reference to the provider checkout session |
| `state` | enum | `initiated`, `redirected`, `returned_success_confirmed`, `returned_cancel`, `returned_failure`, `returned_pending` |
| `returnUrl` | string | Allowlisted return route |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

#### CheckoutReturnAudit

Tracks verification outcomes for support timelines and idempotent return handling.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `checkoutAttemptId` | string (uuid) | Owning checkout attempt |
| `outcome` | enum | Normalized result: `success`, `cancel`, `pending`, `failure` |
| `providerRawState` | string \| null | Provider's raw state captured for support/timeline reconstruction |
| `entitlementsRefreshed` | boolean | Whether the entitlement refresh completed |
| `createdAt` | datetime | |

```text
CheckoutAttempt (1) ──── (N) CheckoutReturnAudit
```

#### Design Notes

- Plan and feature truth are single-sourced from `PlanDefinition`/`OfferDefinition`; pricing pages render projections, never hand-maintained page constants.
- `CheckoutAttempt` persists the correlation between user, offer, source context, and provider session so the original task can be restored after payment.
- Entitlements change only after provider-verified success; return verification is idempotent to tolerate double-return or client retry.
- Continuation context is stored in structured form (`sourceContext`) rather than a bare redirect string so future premium entry points can be added without schema changes.

### Technical Notes

- Treat plan catalog responses as presentation-safe views built from entitlement truth rather than hand-maintained page constants.
- Store continuation context in structured form so future premium entry points can be added safely.
- Return verification should be idempotent.
