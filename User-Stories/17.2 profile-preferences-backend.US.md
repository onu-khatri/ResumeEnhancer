## [PROF-BE-001] — User Profile And Preferences Service

**Module:** Profile & Preferences  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** User Service  
**Dependency:** AUTH-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the user service,  
I want to provide secure profile and preference retrieval/update APIs for authenticated users,  
so that they can manage account-facing settings while the platform remains supportable, trustworthy, and coherent.

### Description

This story covers backend support for a settings area that includes profile details and product preferences. The service must separate identity-like profile information from user preference configuration where practical, enforce ownership and validation, and provide update responses that the frontend can handle with localized save states.

### Scope

**Included In Scope**

- Current-user profile retrieval.
- Current-user profile update.
- Current-user preference retrieval.
- Current-user preference update.

**Out Of Scope**

- Organization administration.
- Full billing/subscription data.
- Role management.
- External identity-provider management.

### Preconditions

- Authenticated session is valid and the auth middleware has resolved the current user identity before any profile or preference handler executes.
- User entity and preference model exist in the data layer, with the preference record created at user registration time with safe defaults so that a GET never returns null for a valid user.
- Allowed editable fields are approved and documented in a centralized allowlist that both the profile and preference update handlers reference, ensuring consistency across endpoints.
- The preference record is guaranteed to exist for every registered user, created with sensible defaults during account provisioning.

### Detailed Workflow

1. Settings UI requests current user profile and preferences.
2. Service returns owned account data only.
3. User updates profile or preferences.
4. Service validates incoming fields and saves approved changes.
5. Updated values are returned for immediate UI confirmation.

### Functional Requirements

- The service must expose current-user endpoints that avoid requiring raw user-id routing from the client.
- Profile fields and preference fields should be logically separated where that improves clarity and validation.
- Updates must support partial field changes without overwriting unrelated settings accidentally.
- The service must support auditability of meaningful account-setting changes where required.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authenticated user requests their settings data  
When the service processes the request  
Then it returns only that user’s allowed profile and preference fields.

**AC2 — Update Path**  
Given an authenticated user submits valid profile or preference changes  
When the service processes the request  
Then it persists only allowed fields and returns updated values.

**AC3 — Validation**  
Given invalid or unsupported field values are submitted  
When the service processes the request  
Then it rejects the invalid fields with structured validation details and preserves existing saved values.

**AC4 — Authorization**  
Given a user attempts to manipulate settings data outside their current-user scope  
When the request is processed  
Then the service denies access and does not expose restricted data.

**AC5 — Error Handling**  
Given persistence or downstream update logic fails  
When the failure occurs  
Then the service returns retry-safe operational errors without corrupting the prior saved state.

### Business Rules

- Users may manage only their own editable profile and preference data; the service must resolve user identity from the authenticated session and never accept a user-id parameter from the client for settings operations.
- Sensitive fields (such as email changes or deactivation requests) should require stricter validation, additional confirmation steps, and potentially re-authentication, depending on security policy.
- Settings changes should support self-service rather than requiring support for routine tasks, which means the API must accept partial, field-scoped updates and return clear errors for fields the user is not permitted to modify.
- When a settings update changes a field that has downstream implications (e.g., locale affecting template language defaults), the service should handle those implications atomically within the same request.

### Validation Rules

- Editable fields must be defined by an explicit allowlist maintained server-side; any field not present in the allowlist must be silently dropped from the update payload or explicitly rejected, never blindly persisted.
- Preference values must remain within supported enums/ranges; the service should validate editor preference against `["guided", "advanced"]`, locale against a supported locale list, and notification channel flags against recognized channel keys.
- Partial updates must not null out unrelated settings accidentally; the service must merge incoming fields into the existing state rather than replacing the entire record, and explicitly absent fields in a PATCH body must be left unchanged.
- Email format must be validated server-side even if the frontend also validates it, as client-side validation cannot be trusted as a security boundary.

### Error Handling

- Differentiate validation errors (HTTP 422 with field-level details), authorization failures (HTTP 403), not-found conditions (HTTP 404 for missing preference records), and transient persistence failures (HTTP 503 with retry-after hints), giving the frontend enough granularity to present appropriate per-section error UI.
- Preserve existing saved settings when an update fails — the service must never write partial or corrupted state during a failed transaction, and should roll back or never commit incomplete changes.
- Support action-level frontend error handling by returning structured field mapping in error responses, including which specific fields failed validation and a user-facing reason string for each, so the frontend can attach errors to individual form controls.
- Log all failed update attempts with enough context (user ID, fields attempted, failure reason) for operational debugging without logging the actual field values.

### Security Considerations

- Enforce current-user ownership on all settings endpoints by resolving user identity from the session token and using that as the sole data-scoping mechanism; never accept a user identifier from request parameters or bodies.
- Avoid returning unnecessary sensitive data in settings payloads — the `GET /users/me` response should exclude internal flags, role enumerations beyond what the UI needs, and any fields that could aid enumeration attacks.
- Audit meaningful settings changes (such as email, display name, locale, and preference toggles) where security or support needs justify it, but audit only field names changed, not old/new values, to limit the sensitivity of the audit trail itself.
- Rate-limit settings update endpoints to prevent abuse via rapid-fire modification attempts that could circumvent validation or audit logic.

#### Relationships

```
User ───1:1─── UserPreference (via userId)
User ───1:N─── AuditLog (via userId)
```

#### Business Notes

- Profile fields and preference fields are separated at the persistence layer to avoid accidental profile corruption during preference-only updates.
- The `AuditLog` records meaningful account-setting changes without storing new/old field values — only field names — to limit sensitive data exposure.
- Preference values use a backend enum allowlist; the `editorPreference` field, for example, accepts only `guided` or `advanced` and rejects unmapped values.
- Partial updates to `UserPreference` must merge into the existing record rather than replacing it, ensuring concurrent preference changes from different settings sections do not overwrite each other.
