## [TRACK-BE-001] — Job Tracker Data Model And Application Progress Services

**Module:** Job Tracking  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Active Job Seeker, Premium User, Product Support  
**Dependency:** DASH-BE-001, BILL-BE-002  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform,  
I want a private, user-owned job-tracking service with stage management and entitlement-aware limits,  
so that users can manage applications reliably and the product can support retention-oriented workspace behavior.

### Description

This story covers the backend model and APIs for lightweight job tracking. The service must let users create and manage application entries, move them through stages, associate them to owned resume documents, and respect any configured tracker limits. It should be intentionally simpler than a recruiting system and optimized for clarity, privacy, and reliable personal use.

### Scope

**Included In Scope**

- User-owned job application records.
- Supported stage transitions and archive state.
- Optional document association.
- Entitlement-aware tracker-card limits.
- List and summary retrieval for board/list frontend views.

**Out Of Scope**

- Team/shared boards.
- External job-source ingestion.
- Reminder delivery automation beyond stored dates.

### Preconditions

- User authentication and ownership model exist.
- Document summary lookup exists.
- Tracker entitlement policy exists.

### Detailed Workflow

1. Authenticated user requests tracker data.
2. Service returns owned jobs grouped or sortable by stage.
3. User creates a new job record.
4. Service validates required fields and entitlement limits.
5. User updates stage, notes, follow-up date, or document association.
6. Service persists changes and returns updated summary state.

### Functional Requirements

- The service must store private, user-owned application records.
- It must support create, read, update, archive, and reopen flows.
- Stage values must be normalized and predictable for UI rendering.
- Resume/document association must be validated against owned documents.
- If tracker-card limits exist, the service must enforce them consistently.
- List retrieval should support efficient workspace rendering, not require full-detail fetch for every card.

### Acceptance Criteria

**AC1 — Create Job Entry**  
Given an authenticated user below the allowed limit  
When they submit a valid job entry  
Then the service creates the record and returns a summary suitable for tracker rendering.

**AC2 — Update Stage**  
Given a user owns an existing job entry  
When they change its stage  
Then the service persists the new stage and returns the updated record.

**AC3 — Association Safety**  
Given a job entry is linked to a resume  
When the association is saved  
Then the referenced document must belong to the same user or the request is rejected.

**AC4 — Limit Enforcement**  
Given the user has reached the allowed active-card limit  
When they attempt to create another active card  
Then the service rejects the request with a clear entitlement/limit reason.

**AC5 — Privacy Integrity**  
Given one user requests another user’s tracker item  
When ownership does not match  
Then the service must not reveal the record.

### Business Rules

- Tracker data is private personal job-search information.
- Archived cards should not count as active if product policy says only active cards are limited.
- The stage model should stay stable enough for analytics and UX continuity.

### Validation Rules

- Company and role are required for creation.
- Stage must be one of the supported normalized values.
- Follow-up dates must be valid dates if provided.

### Error Handling

- Return stable validation errors for incomplete or malformed job data.
- Distinguish ownership failure, not-found, and entitlement-limit failure.
- Preserve idempotency expectations for retry-safe updates where practical.

### Security Considerations

- All endpoints must be ownership-scoped.
- Stored job URLs and notes should be treated as user-provided input requiring safe handling.
- Audit sensitive changes if internal support tooling may later inspect them.

### Analytics / Tracking

- `job_tracker_list_requested`
- `job_tracker_job_created`
- `job_tracker_stage_updated`
- `job_tracker_limit_denied`

### API Dependencies

- `PATCH /jobs/{id}`

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### JobApplication

A user-owned tracker card representing one job opportunity. Intentionally lightweight — not a recruiting pipeline.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | |
| `userId` | string (uuid) | Owning user |
| `company` | string | Company name (required) |
| `role` | string | Job title / role (required) |
| `jobUrl` | string | URL to the job posting or company career page |
| `location` | string | City, remote, or hybrid designation |
| `stage` | enum | Current application stage (see below) |
| `appliedDate` | date | When the application was submitted |
| `nextFollowUpAt` | date | Reminder date for follow-up |
| `notes` | text | Free-text notes about this opportunity |
| `relatedResumeId` | string (uuid) | The resume used for this application. Must belong to the same user. Null if not yet assigned. |
| `relatedCoverLetterId` | string (uuid) | The cover letter used. Null if not assigned. |
| `isArchived` | boolean | Whether this card is archived. Archived cards may be excluded from the active limit count (per plan policy). |
| `stageHistory` | json | Audit trail: array of `{ stage, timestamp }` recording each transition |
| `position` | integer | Order within the user's board for consistent rendering |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

#### Stage Enum

| Stage | Meaning | User action at this stage |
| --- | --- | --- |
| `saved` | Role identified, not yet applied | Prepare resume, research company, apply |
| `applied` | Application submitted | Wait for response, prepare for interview |
| `interviewing` | In any interview stage (phone, technical, onsite, final) | Prepare, attend, send thank-you |
| `offer` | Offer received | Negotiate, decide |
| `archived` | Rejected, withdrawn, or expired | Review lessons learned |

#### Stage Transitions

Valid moves and their audit trail behavior:

```text
saved → applied (user submits application)
saved → archived (role closed or user decided not to apply)
applied → interviewing (received interview invitation)
applied → archived (rejected or no response after long wait)
interviewing → offer (accepted)
interviewing → archived (rejected or withdrew)
offer → archived (offer declined or expired)
archived → saved (user reopens — card becomes active again)
```

Each transition appends an entry to `stageHistory`: `{ "from": "applied", "to": "interviewing", "timestamp": "2026-08-20T10:30:00Z" }`.

#### Card Limit Enforcement

| Plan | Active Card Limit | Archived Card Behavior |
| --- | --- | --- |
| Free | 3 (from Novorésumé reference) | Archived cards do not count toward the active limit |
| Premium | Unlimited | N/A |

When a free user reaches their active limit:

- `POST /jobs` returns HTTP 402 or 403 with error code `TRACKER_LIMIT_REACHED`
- Response includes `{ activeCount: 3, activeLimit: 3, message: "Upgrade to Premium for unlimited tracking" }`
- Archived cards can still be viewed, reopened (which counts them as active again), or permanently deleted

#### Retrieval Contract

`GET /jobs` returns a lightweight summary for board rendering:

```json
{
  "items": [
    {
      "id": "job_123",
      "company": "Acme Corp",
      "role": "Frontend Engineer",
      "stage": "applied",
      "location": "Remote",
      "nextFollowUpAt": "2026-08-19",
      "relatedResumeId": "res_01",
      "relatedCoverLetterId": "cl_01",
      "position": 0
    }
  ],
  "activeCount": 4,
  "activeLimit": -1,
  "stageSummary": {
    "saved": 2,
    "applied": 3,
    "interviewing": 1,
    "offer": 0
  }
}
```

#### Relationships

```text
User (1) ──── (N) JobApplication
Resume (1) ──── (N) JobApplication (via relatedResumeId — soft link, optional)
CoverLetter (1) ──── (N) JobApplication (via relatedCoverLetterId — optional)
```

The resume and cover-letter links are soft references. If the linked document is deleted, `relatedResumeId` / `relatedCoverLetterId` are set to null on the job card. The card itself is not deleted.

### Technical Notes

- Prefer lightweight card-summary responses plus optional detail payloads.
- Model limit evaluation centrally with other entitlements.
- Keep room for future reminders or analytics without expanding MVP field complexity too early.
