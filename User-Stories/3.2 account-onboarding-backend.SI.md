# Supporting Information — Account Registration And Session Bootstrap

## Proposed APIs

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/logout`
- `POST /auth/verify-email`
- `POST /auth/verify-email/resend`
- `GET /bootstrap`

## Request And Response Notes

### `POST /auth/register`

Request fields:

- `firstName`
- `lastName`
- `email`
- `password`
- `termsConsent`
- `privacyConsent`
- `marketingConsent`
- `source`
- `selectedTemplateId`

Suggested response fields:

- `userId`
- `sessionState`
- `emailVerificationState`
- `defaultPlanCode`
- `nextAction`
- `workspaceRoute`
- `featureEntitlements`

### Suggested Status Codes

- `201` account created
- `409` duplicate identity or safe equivalent
- `422` validation failure
- `429` throttled
- `503` dependent service degraded

## Proposed Entities

## Entity Responsibilities

| Entity | Responsibility |
| --- | --- |
| `User` | primary account record and lifecycle status |
| `AuthenticationIdentity` | credential-bearing identity and verification state |
| `Session` | active login context, device metadata, expiry |
| `ConsentRecord` | evidence of legal and optional marketing consent |
| `UserPreference` | locale and onboarding-related defaults |
| `Plan` | pricing/feature package definition |
| `Entitlement` | effective capability access state |
| `AuditLog` | security, support, and compliance traceability |

## Suggested Transaction Boundary

- transactional:
  - create user
  - create auth identity
  - create consent record
  - assign default plan
  - create session
- async:
  - queue verification email
  - queue welcome email
  - publish analytics event

## Suggested Background Jobs

- Verification email send
- Welcome email send
- Signup analytics forwarder
- Failed-email retry

## Validation Matrix

| Scenario | Expected Server Behavior |
| --- | --- |
| Duplicate email with different casing | normalize and reject duplicate |
| Missing required consent | reject with validation code |
| Valid account but email queue down | return success with queue-failed event |
| Retry after response loss | avoid duplicate account creation |

## Edge Cases

- Duplicate submit within the same second. Two nearly simultaneous submissions must resolve to a single account via idempotency or a unique constraint rather than producing duplicates.
- Email provider timeout. A slow email provider must not block the synchronous registration response; the send is queued and retried asynchronously.
- Session created before downstream cache is warm. Bootstrap data may be briefly stale after session creation, so the flow must tolerate and eventually refresh that data.
- Database commit succeeds but HTTP response is interrupted. The client may retry, so the service must detect the already-existing account and return a safe, consistent result.
- Selected template ID no longer exists by bootstrap time. If the chosen template was removed between selection and bootstrap, the service must fall back to a default route rather than fail.

## Test Focus

- Idempotent registration behavior. Verify a retried request does not create a second user or duplicate consent/session records.
- Race between duplicate signup attempts. Exercise concurrent submissions to confirm uniqueness holds under contention.
- Audit log completeness. Confirm security-relevant events (account created, consent accepted, session created) are all recorded.
- Partial side-effect failures. Simulate email-queue failure and verify the account remains usable with a resend path.
- Session creation and bootstrap route correctness. Verify sessions are issued and the returned route matches the originating source context.

## Developer Notes

- If using a modular monolith, keep registration orchestration in an application service. A single orchestration point keeps the workflow explicit and testable.
- Hide password hashing behind a port or dedicated domain service. This isolates the hashing algorithm so it can be upgraded without touching orchestration.
- Use a unique index on normalized email and handle constraint violations gracefully. The constraint is the final defense against duplicates; violations must map to a clean conflict response.
