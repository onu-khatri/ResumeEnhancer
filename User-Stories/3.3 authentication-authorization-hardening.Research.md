# Research — Production Authentication And Authorization Hardening

## Research Date

2026-09-13

## Repository Evidence

### Observed

- Program.cs configures AddAuthorization and UseAuthorization but not AddAuthentication or UseAuthentication.
- AuthTokenService emits a custom HMAC-signed access-token string, not a JWT.
- Auth routes have registration, refresh, logout, verification resend, and bootstrap, but no login or password-management routes.
- AuthenticationIdentity has PasswordHash and email-verification state, but no lockout, password-history, reset, or verification-challenge records.
- User.IsDeactivated exists without Auth enforcement.
- Resume endpoints read X-User-Id and X-Audit-UserId headers.
- GlobalExceptionHandler writes exception and inner-exception messages.
- InMemoryRegistrationThrottle is process-local and registration-only.
- Existing Auth integration tests do not cover login or JWT authorization.
- The registration validator has a 12-character minimum plus upper/lower/digit/special requirements; five-character alphanumeric would weaken it.

### Inferred

- There is no effective backend JWT authentication boundary for newly mapped endpoints.
- Client identity headers create impersonation/audit risk.
- Additional lifecycle state is needed for lockout, history, reset, and verification completion.
- Guest access should be explicit, while new endpoints default to protected.

## External Evidence

- Microsoft requires JWT bearer configuration and authentication middleware before endpoints that depend on authenticated users: https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0
- Microsoft supports policy-based authorization and fallback policies to protect endpoints without explicit authorization metadata: https://learn.microsoft.com/en-us/aspnet/core/security/authorization/introduction?view=aspnetcore-10.0 and https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authorization.authorizationoptions.fallbackpolicy?view=aspnetcore-10.0
- Microsoft documents AddProblemDetails and safe API error middleware: https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling-api?view=aspnetcore-10.0
- OWASP recommends secure session storage/transport and warns against browser localStorage for authentication tokens: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html and https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html
- OWASP recommends adaptive password hashing such as Argon2id, bcrypt, or PBKDF2: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- OWASP recommends explicit CSRF protection for cookie-authenticated state changes: https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
- RFC 8725 defines JWT best practices, including algorithm allowlisting and rejection of unsecured JWTs: https://www.rfc-editor.org/rfc/rfc8725.html
- RFC 9700 recommends refresh-token expiration, revocation, and rotation as appropriate: https://www.rfc-editor.org/rfc/rfc9700.html

## Recommended Decisions

- Preserve the current 12-character baseline; do not reduce it to five characters.
- Allow supported special characters and prioritize length and breached-password screening.
- Retain two previous password hashes and reject reuse.
- Add enumeration-safe forgot/reset flows with hashed single-use challenges.
- Add authenticated password change and session-family revocation.
- Add email-verification completion.
- Use framework-managed JWT bearer authentication and a fail-closed fallback policy.
- Make guest access explicit.
