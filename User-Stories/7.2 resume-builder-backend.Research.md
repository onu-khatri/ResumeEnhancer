# Research — Resume Builder Backend (CRUD, Sections, Ordering, Validation)

## Research Basis

Both competitors provide a structured, section-based builder — not a free-form document editor. The backend implications are significant: resumes are modeled as structured data with typed sections, repeatable items, ordering, visibility, and versioning. Novorésumé's help-center documentation on template switching, layout reordering, and document management confirms that the backend must support content/style separation and robust document organization.

## What The Research Means For The Backend

- The resume data model must be **structured**: typed sections (header, summary, experience, education, skills, etc.), each with typed fields and optional repeatable items. Not a free-text blob.
- **Content and design must be separated** in the data model. Content belongs to the resume entity; template/theme/style is a separate reference. This enables template switching without content loss and theme customization independent of content.
- **Ordering is first-class state**: section order within the document and item order within sections must be persisted and respected by both preview and export rendering.
- **Visibility is first-class state**: sections can be hidden without losing their content.
- **Document organization** (views/filters, tags) requires metadata fields on the document model beyond just title and content.
- **Document capacity limits** (e.g., 10 docs free, 50+ paid) are enforced at the backend.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Structured section model (typed sections + repeatable items) | Enables AI targeting, ATS analysis, validation, and structured export |
| Content/style separation | Enables template switching, theming, and layout changes without losing content |
| Section and item ordering persistence | Supports reorder operations and consistent preview/export rendering |
| Section visibility (show/hide) | Users must hide sections without deleting content |
| Document metadata (title, type, language, tags, template ref) | Drives organization views and filtering |
| Optimistic concurrency / versioning | Prevents conflict overwrites between sessions |
| Partial update support | Editing one section should not require rewriting the entire document |
| Document limits enforcement | Backend enforces per-plan caps, not client-side |

## Hidden Requirements Inferred

- Autosave endpoint with conflict detection (version-token-based).
- Reorder endpoint that atomically updates position indices.
- Duplicate document endpoint (creates a new document with the same content but a new ID and optional new metadata like language).
- Content validation endpoint (is this document ready for export/analysis?).
- Section schema configuration (which sections exist, which are repeatable, which are required).

## Risks If Under-Specified

- Engineers may store resume content as one JSON blob, making partial updates, reordering, and section-level validation difficult.
- Content/style may be stored together, making template switching an expensive content-migration task instead of a style-reference change.
- Document IDs may not carry enough metadata (language, type, tags) for the organization views the frontend needs.
- Optimistic concurrency may be absent, leading to last-write-wins data loss between multiple tabs.

## Recommendation To Developers

- Model resumes as structured documents with typed sections, separate from template/style metadata.
- Use a position/order model that supports atomic reorder (gap-based ordering or explicit position indices).
- Support partial PATCH updates per section so autosave is efficient and conflict-scope is narrow.
- Design the resume model to be **content-only**; template_id and theme_id are references, not embedded data.

## Open Questions

- How is ordering persisted (ordinal positions, linked-list, or gap-based)?
- Should hidden sections and deleted sections be recoverable (soft-delete)?
- What is the autosave frequency, and is it section-scoped or document-scoped?
