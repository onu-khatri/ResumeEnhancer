# Supporting Information - Theme Accessibility Remediation Across The Frontend

## Audit Boundary

The implementation audit covers all frontend source files below `application/WebSolution/websolution.client/src`. At story creation, the inventory contains 73 `.tsx` and `.css` source files; 27 contain direct palette utilities or explicit foreground/background declarations. The implementation must re-run the inventory rather than assume these counts remain static.

## Theme Model

| Theme | Root selector | Current risk to remove |
| --- | --- | --- |
| Light | default `:root` | hard-coded dark surfaces or light foregrounds bypassing the token set |
| Midnight | `:root[data-theme='midnight']` | separate `body.dark` and `dark:` behavior diverging from root tokens |
| Forest | `:root[data-theme='forest']` | light-theme-oriented `dark:` fallbacks that do not express Forest intent |

The root theme attribute must define the semantic contract. Theme-specific values may differ, but component code must consume roles, not palette shades.

## Required Semantic Token Roles

| Token family | Required roles |
| --- | --- |
| Surfaces | canvas, raised, subtle, overlay/control background |
| Text | primary, heading, muted, inverse, placeholder, disabled |
| Borders and focus | default border, strong border, focus ring, focus offset |
| Actions | primary foreground/background, secondary, ghost, destructive, disabled |
| Feedback | success, warning, danger, information, premium/locked foreground/background/border |
| Selection | selected, checked, hover, active, invalid, read-only where applicable |

## Component-State Matrix

| Surface family | Components and locations | Required states |
| --- | --- | --- |
| Global and shell | `index.css`, theme provider, shell navigation, theme selector, login, not-found | all themes, links, selection, focus, disabled selector where applicable |
| Actions | `Button`, removable pill actions, sortable table actions, feature actions | primary, outline, ghost, subtle, hover, focus-visible, disabled |
| Text-entry controls | input, textarea, autocomplete, select, native select in shell | label, value, placeholder, description, invalid, hover, focus, disabled, open listbox/options |
| Choice controls | checkbox, radio group, listbox option | unchecked, checked/selected, focus, invalid where supported, disabled |
| Content containers | cards, panels, pagination, tables, builder cards/sidebars, dashboard lists, preview columns/sections/timeline | text/surface, border/surface, hover/selected, focusable descendants |
| Feedback and async | inline alert, empty state, error state, request state, skeleton/status | informational, warning, error, entitlement/locked, loading |
| Feature pages | dashboard, builder, preview, resume shell, work experience, public/fallback pages | all visible state variants and responsive layouts that alter backgrounds |

## Source Review Procedure

1. Enumerate all `.tsx` and `.css` files in `src` and identify direct foreground, background, border, ring, outline, shadow, opacity, and palette utility usage.
2. For each occurrence, classify it as semantic-token migration, valid non-UI asset/exception, or obsolete styling.
3. Define the intended adjacent foreground/background pair for every semantic role in each supported theme.
4. Correct shared primitives before feature consumers, then correct feature-specific surfaces that require a new role.
5. Re-run the source inventory. Any retained direct color must have a documented rationale, affected themes, calculated contrast, and owner.

## Verification Strategy

- Add a deterministic contrast utility or equivalent standards-based check to test the approved token pairs without relying on rounded display values.
- Add a theme fixture that renders the shared component-state matrix for Light, Midnight, and Forest.
- Test provider persistence and synchronization alongside the color contract so remediation does not alter preference behavior.
- Perform a route-level visual audit for every theme, including desktop and narrow layouts where a changed surface can become adjacent to a different background.
- Record the audit result by source file, component/state, theme, tested color pair, ratio, and any permitted exception.

## Completion Evidence

The pull request must include:

- the final source-audit inventory;
- automated test output for theme contrast and existing frontend behavior;
- a completed theme/component/state audit matrix;
- visual evidence or a reproducible review procedure for all three themes; and
- an explicit list of any WCAG-exempt inactive controls or non-application-controlled UI.
