# Supporting Information — Billing Operations Summary, Transaction, And Refund Retrieval Services

## Proposed APIs

- `GET /admin/billing/summary`
- `GET /admin/billing/transactions`
- `GET /admin/billing/refunds`

## Example Transaction Summary

```json
{
  "transactionId": "pay_123",
  "subscriptionId": "sub_123",
  "status": "paid",
  "amount": 23.85
}
```

## Proposed Entities

- `Subscription`
- `Payment`
- `Refund`
- `Invoice`
- `AuditLog`

## Suggested Technical Controls

- Support/finance visibility scopes: enforce distinct read scopes so support agents see less than finance operators where policy requires.
- Filter validation: constrain queries to supported fields and ranges, rejecting unbounded or arbitrary scans.
- Curated response shaping: map raw provider state into stable, privacy-aware product fields before returning data.

## Edge Cases

- Payment success with failed entitlement sync: the service must surface both payment and entitlement state so operators can detect the mismatch.
- Refund initiated but not settled: distinguish requested, processing, and settled refund states so operators do not mistake intent for completion.
- Large finance event history: retrieval must paginate and filter efficiently to avoid unbounded scans.

## Test Focus

- Scope enforcement: verify operators receive only records within their finance/support scope.
- Filter behavior: confirm supported filters return correct, efficient results.
- Partial-source failure handling: ensure a delayed or down source yields a stable partial response where approved.

## Developer Notes

- Treat these APIs as internal operations views, not external billing-provider mirrors, so contracts reflect product semantics rather than provider specifics.
- Keep fields curated for internal use and privacy-aware, excluding full card details and provider tokens by design.
