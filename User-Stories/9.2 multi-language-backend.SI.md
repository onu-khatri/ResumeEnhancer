# Supporting Information — Language-Aware Document Metadata And Variant Management Services

## Suggested Entities

| Entity | Purpose |
| --- | --- |
| `SupportedLanguage` | approved language catalog |
| `DocumentLanguageMeta` | language identity attached to document |
| `DocumentVariantFamily` | optional grouping for related variants |

- `SupportedLanguage` is the authoritative allowlist of languages the product can author, keyed by `code` with a display `label` and optional `isDefault` and `isRtl` flags. New languages must be added here before any document can be created in them, which keeps the catalog auditable and prevents unsupported-language drift.
- `DocumentLanguageMeta` is the denormalized language identity attached to a document summary so workspace and builder queries do not require a join per document. It carries the `code`, `label`, `isDefault`, and an optional `variantFamilyId` to preserve relationship context.
- `DocumentVariantFamily` is an optional aggregate that groups documents which are intentionally the "same" content in different languages, so the UI can show related variants without forcing the association early if it is not needed.

  "isRtl": false,

```json
{
  "sourceDocumentId": "res_123",
  "languageCode": "de",
  "mode": "duplicate_as_variant"
}
```

## Suggested Summary Contract Fields

- `documentId`
  - Primary identifier used for navigation and subsequent mutations.
- `documentType`
  - `resume` or `cover_letter`, used to render the correct workspace treatment.
- `title`
  - Display title that may be near-identical across variants, so it is always paired with the language label.
- `languageCode`
  - The canonical language code used for filtering and API queries.
- `languageLabel`
  - Human-readable language name surfaced directly in cards and headers.
- `variantFamilyId`
  - Optional grouping key linking related language variants, null when the document is standalone.
- `relatedVariantCount`
  - Precomputed count so list UIs can show "2 variants" without additional per-row queries.

## Edge Cases

- User creates multiple variants in the same language.
  - The system must allow multiple documents in one language even when they share a family, so uniqueness must never be enforced on the `(familyId, languageCode)` pair.
- Source document deleted while duplicate request is in flight.
  - The duplication must fail cleanly with a not-found response rather than creating a half-copied variant, and the client must be able to recover gracefully.
- Locale pack exists for UI labels but content-specific defaults do not.
  - The backend must distinguish interface localization from content defaults and fall back to the default language where content conventions are unavailable.
- Future RTL languages added after MVP assumptions.
  - Entity and rendering designs must not assume left-to-right flow, so future RTL support does not require a schema migration.

## Testing Focus

- Ownership checks during duplication.
  - Verify a user cannot duplicate a document they do not own, and that ownership is enforced on both source and created variant.
- Unsupported language validation.
  - Assert that variant creation with an unknown language code is rejected against the `SupportedLanguage` catalog.
- Summary exposure in workspace lists.
  - Confirm language fields appear correctly in the workspace summary payload and stay consistent after variant creation.
- Variant-family relationship stability.
  - Verify family ids and related counts remain correct when variants are created, deleted, or archived.

## Developer Notes

- Keep language metadata easy to join into existing summary queries.
  - Storing denormalized language fields on the document summary avoids per-row joins and keeps workspace list latency low.
- Avoid coupling supported-language catalog to account-region logic unless required later.
  - The language catalog is a product capability concern, not a billing or region concern, so keep them decoupled to avoid accidental restrictions.
- If variant-family modeling feels heavy for MVP, return simple `sourceDocumentId` plus `languageCode` relationships first and evolve carefully.
  - A lightweight `sourceDocumentId` link can deliver variant UI without a full family aggregate, and can be upgraded later without a disruptive migration.
