## [PRIV-BE-001] — Privacy Request, Data Export, And Account Deletion Initiation Services

**Module:** Privacy & Account Deletion  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Privacy Service  
**Dependency:** AUTH-BE-001, BILL-BE-001, PROF-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the privacy service,  
I want to accept and track supported privacy-related user requests such as data export and account deletion initiation,  
so that the platform can honor user data rights in a supportable, policy-aware, and trustworthy way.

### Description

This story covers the backend support for user-facing privacy actions. The service must provide metadata about available privacy actions, accept supported requests, enforce policy constraints, and return stable states that the frontend can communicate clearly. It should support cases where full deletion is immediate, delayed, or support-mediated depending on product policy.

### Scope

**Included In Scope**

- Privacy action metadata retrieval.
- Data export request initiation.
- Account deletion request initiation.
- Request-state creation and tracking.

**Out Of Scope**

- Full back-office privacy case handling.
- Legal-policy authoring.
- Enterprise retention exceptions.

### Preconditions

- Privacy and deletion policy is defined, including which actions are self-service, which require support, what retention rules apply, and under what conditions deletion can be blocked (e.g., active subscription).
- User authentication is valid for self-service actions; re-authentication requirements for destructive actions should be specified before implementation so the endpoint can enforce an elevated confirmation level when policy demands it.
- Request-state storage exists with a defined lifecycle (pending, processing, completed, blocked, requires escalation, failed) so the service has a consistent state machine rather than ad-hoc boolean flags.

### Detailed Workflow

1. Frontend requests available privacy-action metadata.
2. Service returns supported actions and policy-aware guidance metadata.
3. User initiates data export or account deletion.
4. Service validates policy requirements and creates a request record or executes supported initiation behavior.
5. Service returns accepted, pending, blocked, or escalation-required state.

### Functional Requirements

- The service must expose privacy-action options in a frontend-consumable form.
- Data export initiation must create a trackable request or job state.
- Account deletion initiation must respect policy constraints such as billing or retention dependencies.
- Request outcomes must distinguish:
  - accepted
  - pending
  - blocked by policy
  - requires support escalation
- The service must support a future where deletion may not mean immediate erasure of every record.

### Acceptance Criteria

**AC1 — Happy Path Data Export**  
Given an authenticated user requests data export  
When the service processes the request  
Then it accepts the request, creates a trackable state, and returns a frontend-consumable result.

**AC2 — Happy Path Deletion Initiation**  
Given an authenticated user initiates account deletion under allowed policy conditions  
When the service processes the request  
Then it accepts or schedules the request and returns clear next-step state.

**AC3 — Policy Constraint Handling**  
Given deletion or export cannot proceed immediately due to policy constraints  
When the service processes the request  
Then it returns a structured blocked or escalation-required outcome rather than a generic failure.

**AC4 — Authorization And Safety**  
Given an unauthenticated or invalid user context attempts a privacy action  
When the request is processed  
Then the service denies the request safely.

**AC5 — Error Handling**  
Given request creation or policy-resolution logic fails  
When the failure occurs  
Then the service returns stable operational errors without creating ambiguous privacy-request state.

### Business Rules

- Privacy requests are trust-sensitive and must be tracked explicitly with a stateful request record; they should never be handled as a fire-and-forget operation because the user needs to know whether their request was accepted, is in progress, or was blocked.
- Account deletion may have policy-driven delays (cooling-off periods, support review requirements) or retained-data exceptions (billing records, legal holds) that must be represented honestly through the `retentionNote` field, not hidden from the user or the frontend.
- Support escalation may be required for some requests or account states (e.g., deletion with an active subscription, export for accounts flagged for compliance review); the service must return `requires_escalation` with a clear reason rather than silently blocking and returning a generic error.

### Validation Rules

- Only supported privacy actions may be initiated, validated against a defined action allowlist (e.g., `data_export`, `account_deletion`), rejecting any unrecognized action key with a clear validation error.
- Policy prerequisites must be validated before acceptance; for account deletion, check active subscription status, pending billing obligations, and any legal or compliance flags before marking the request as accepted.
- Duplicate or excessively repeated requests may require throttling or reuse of active request state — if a user already has a `pending` or `processing` PrivacyRequest for the same type, return the existing request state rather than creating a duplicate, and rate-limit to prevent abuse.

### Error Handling

- Distinguish unsupported-action errors (422 with the action key), blocked-by-policy errors (422 with a structured blocked reason and retention note), unauthorized (403), and transient operational failures (503) so the frontend can route each outcome to the appropriate UI state.
- Preserve stable prior request state if new request creation fails; a failed creation attempt must not invalidate, delete, or corrupt an existing pending request for the same user and action type.
- Return frontend-mappable request status semantics so the frontend can render status labels, next-step guidance, and support escalation paths without parsing internal codes or free-text status strings.

### Security Considerations

- Re-authentication or stronger confirmation policy may apply for destructive requests; the service must support a mechanism to validate that the user has passed an elevated auth check before accepting an account deletion request, such as requiring a fresh token with a higher assurance level.
- Privacy request data must be strictly user-scoped; no endpoint should return or allow modification of another user's privacy requests, and queries must always filter by the authenticated user's ID from the session.
- Request tracking and auditability are important for trust and compliance; every privacy request state transition must produce an audit log entry recording who initiated it and when, creating a verifiable trail for privacy audits and support investigations.

### Data Model

#### Entity: PrivacyRequest

| Property | Type | Description |
| --- | --- | --- |
| `id` | `string (UUID)` | Unique request identifier |
| `userId` | `string (UUID)` | FK to owning User |
| `type` | `enum` | Request type: `data_export`, `account_deletion` |
| `status` | `enum` | Lifecycle status: `pending`, `processing`, `completed`, `blocked`, `requires_escalation`, `failed` |
| `blockedReason` | `string?` | Policy reason if status is `blocked` |
| `escalationReason` | `string?` | Why support involvement is required |
| `requestedAt` | `datetime` | When the user submitted the request |
| `completedAt` | `datetime?` | When the request was fulfilled |
| `retentionNote` | `string?` | Policy-aware explanation of data that may be retained post-deletion (billing records, legal holds) |

#### Business Notes

- Privacy requests follow an explicit lifecycle; status transitions must be enforced (e.g., a `completed` request cannot move back to `pending`).
- Account deletion may be `blocked` when an active paid subscription exists — the service must surface the reason clearly so the frontend can guide the user to cancel the subscription first.
- The `retentionNote` field is critical for trust: it must honestly explain which data is retained post-deletion and why (legal, billing, or compliance reasons), using policy-approved wording rather than generic boilerplate.
- Duplicate or rapid-repeat privacy requests should be throttled; if an active `pending` or `processing` PrivacyRequest already exists for the same user and type, the service should return the existing request state rather than creating a duplicate.
