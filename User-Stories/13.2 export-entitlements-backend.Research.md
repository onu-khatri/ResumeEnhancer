# Research — Export Generation Backend And Entitlement Enforcement

## Research Basis

Export generation and entitlement enforcement are tightly coupled backend concerns. The selected competitors confirm that export is the monetization gate, and the backend must reliably distinguish "premium-gated" from "content-not-ready" from "generation-failed" — presenting each differently to the user. Competitor evidence also confirms that data is retained after plan expiry (content kept, export restricted) and that both one-time and recurring billing models exist, so the backend must support both.

## What The Research Means For The Backend

- **Entitlement enforcement is a backend concern**: the export endpoint must evaluate plan state (not client flags) before generating output. Client-side locks are a convenience indicator; the real gate is server-side.
- **Four response states are needed** for the export endpoint:
  1. Blocked — content validation failed (resume incomplete or invalid)
  2. Blocked — plan does not allow (upgrade required, with which formats are locked)
  3. Success — artifact generated and available for download
  4. Failed — generation error (technical, retryable, not a plan issue)
- **"Preview premium, pay to download"** means the builder must allow premium-flagged content in the preview but block export — i.e., export generation must check whether any *content* uses premium-only features, not just whether the *user* is premium.
- **Data-after-expiry**: content stays; export capability is reduced to free-tier level. Backend must distinguish "content exists" from "content is exportable at current plan level."
- **Pay-once vs. recurring**: the backend must support time-boxed Premium (start/end date) regardless of whether we choose one-time or subscription billing — both models need an expiry date on premium access.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Centralized entitlement engine | Single source of truth for plan + capability checks |
| Export validation (content readiness) | Separate from plan-gating; different error messages |
| Export-plan-gate (format availability per plan) | Server-enforced, not client-trusted |
| Premium-content detection in export | If user used premium features in preview, block export if not paid |
| Export job lifecycle (queued/generating/ready/failed) | Reliable artifact generation with status polling |
| Artifact lifecycle management | Time-limited download URLs, cleanup |
| Idempotent generation | No duplicate artifacts on retry/re-click |
| Data-retention policy enforcement | Content kept after expiry; export downgraded to free-tier rules |

## Hidden Requirements Inferred

- Plan definition that maps capabilities to format access, page counts, and feature availability.
- Document metadata flagging that tracks whether premium-only features were used (for the "preview premium / pay to download" gate).
- Export rendering engine that can produce PDF and potentially DOCX from structured resume data + template.
- Checkout webhook handling that triggers entitlement activation (near-instant, or with clear grace period).
- Support-tooling: support must be able to see "what plan does this user have" and "were any premium features used in this document."

## Risks If Under-Specified

- Engineers may trust the client for entitlement decisions, creating a bypass vector.
- "Export blocked" and "export failed" responses may be indistinguishable, causing confusion and support load.
- Premium-feature usage in preview may not be flagged, allowing free users to effectively use (but not download from) premium features with no incentive to upgrade.
- Artifact download URLs may not expire, creating a content-leakage vector.

## Recommendation To Developers

- Build a central `IEntitlementService` or equivalent that answers "can user X perform action Y on resource Z" for export, template, AI, and analysis.
- Make export generation idempotent: same input produces same (cached) artifact, but re-triggered by content changes.
- Design the export rendering engine to be format-agnostic: structured document → PDF or DOCX renderer with shared logic.

## Open Questions

- Which formats in MVP (PDF only, or PDF + DOCX)?
- Should export be synchronous (wait for generation) or async (return job ID, poll)?
- How long should artifact download links be valid?
- Should "watermarked free PDF" be a monetization lever?
