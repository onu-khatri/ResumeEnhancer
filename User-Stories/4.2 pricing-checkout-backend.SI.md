# Supporting Information — Pricing Catalog, Checkout Session, And Return Verification Services

## Suggested Service Responsibilities

- Plan catalog projection
- Offer validation
- Checkout-session creation
- Checkout-attempt persistence
- Return verification and normalization
- Entitlement refresh handoff

## Example API Shapes

### `GET /plans`

```json
{
  "plans": [
    {
      "code": "basic",
      "displayName": "Basic",
      "billingModel": "free",
      "features": {
        "pdfExport": false,
        "docxExport": false,
        "premiumTemplates": false
      }
    }
  ]
}
```

### `POST /billing/checkout`

```json
{
  "offerCode": "premium_quarter",
  "sourceContext": {
    "type": "export",
    "documentId": "res_123",
    "format": "pdf"
  }
}
```

### `GET /billing/checkout-return`

```json
{
  "status": "success",
  "entitlementsRefreshed": true,
  "continuation": {
    "type": "export",
    "route": "/app/resumes/res_123/export"
  }
}
```

## Persistence Suggestions

| Entity | Purpose |
| --- | --- |
| `PlanDefinition` | canonical commercial capability bundle |
| `OfferDefinition` | market/cohort-specific purchasable offer |
| `CheckoutAttempt` | ties user, offer, provider session, and source context |
| `CheckoutReturnAudit` | tracks verification outcomes |

## State Model

- `initiated`
- `redirected`
- `returned_success_pending_refresh`
- `returned_success_confirmed`
- `returned_cancel`
- `returned_failure`
- `returned_pending`

## Edge Cases

- User returns twice from the same checkout attempt. Verification must be idempotent so a second return does not double-grant entitlements or corrupt state.
- Provider shows success but webhook/state sync is delayed. The backend must return a pending state and allow polling until the provider confirms, without prematurely granting access.
- Offer expires between pricing view and checkout creation. Checkout creation must re-validate availability so an expired offer is rejected rather than silently honored.
- User starts checkout for AI lock but returns after document was deleted. Return verification must tolerate a missing originating document and degrade to a safe continuation route.

## Testing Focus

- Idempotent return verification. Confirm repeated verification requests produce a consistent outcome and no duplicate entitlement changes.
- Cross-user replay rejection. Verify one user cannot reference or complete another user's checkout attempt.
- Plan catalog consistency with entitlement checks. Confirm the plan feature matrix matches what the entitlement system actually grants.
- Safe degradation when provider verification is slow. Verify pending states and polling behave correctly under delayed provider responses.

## Developer Notes

- Prefer structured `sourceContext` over route strings only. Structured origin data lets the backend reconstruct the exact journey and adds new entry points later.
- Keep plan catalog generation close to entitlement policy definitions. Generating the catalog from entitlement truth prevents drift between pricing and access.
- Audit checkout transitions because billing disputes often require timeline reconstruction. A durable transition log lets support explain exactly what happened at each step.
