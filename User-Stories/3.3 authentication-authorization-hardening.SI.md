# Supporting Information — Production Authentication And Authorization Hardening

## Boundary

Backend only:

WebSolution.Server -> ModulesComposition -> AuthModule.Web -> AuthModule.SL -> AuthModule.PL

ProfilingModule remains the owner of users, roles, access profiles, and deactivation state.

## Current Evidence And Required Work

| Current state | Required work |
| --- | --- |
| Program configures authorization but not authentication | Register JWT bearer authentication |
| UseAuthorization exists without UseAuthentication | Add authentication before authorization |
| AuthTokenService emits custom HMAC text | Issue/validate JWTs through framework handlers |
| Endpoints lack auth metadata | Add fallback policy and explicit anonymous/protected metadata |
| Resume endpoints read X-User-Id and X-Audit-UserId | Derive identity from claims/trusted service auth |
| No login/password lifecycle contracts | Add AM, SL, Web, and PL slices |
| Only current password hash exists | Add hashed history and previous-two comparison |
| IsDeactivated/EmailVerified are not enforced | Add status and verification checks |
| Exception handler exposes exception data | Use redacted ProblemDetails |
| Throttle is process-local and registration-only | Add distributed limits across sensitive flows |

## Route Matrix

- Anonymous: homepage, approved discovery reads, existing Auth onboarding endpoints, new login/verification/reset endpoints, bootstrap.
- Authenticated: resume operations, private profile, billing reads, workspace operations.
- Policy/ownership protected: resume ownership, user administration, roles, access profiles, billing mutations, template mutations, admin operations.

## Contracts

Add LoginRequest, ChangePasswordRequest, ForgotPasswordRequest, ResetPasswordRequest, VerifyEmailRequest, and an authenticated identity response for GET /api/v1/auth/me. Authoritative user identity comes from the authenticated principal.

## Password And Challenge Persistence

Add password-history records containing UserId, PasswordHash, and CreatedAtUtc. Compare proposed passwords with the current and previous two hashes; update current hash and history transactionally.

Add password-reset and email-verification challenge records containing UserId, TokenHash, expiry, used timestamp, and safe request metadata. Store only hashes; challenges are random, short-lived, single-use, and invalidated after use.

Password change/reset revokes refresh-session families. Account disablement and compromise response revoke applicable sessions.

## Authorization

Configure JWT bearer validation, issuer/audience/signature/algorithm/lifetime checks, fallback authentication, explicit AllowAnonymous for the guest list, named policies for administration/billing/capabilities, and resource authorization for owned data. Never trust client-provided subject headers.

## Tests

Cover login/enumeration, JWT validation, middleware order, fallback/guest routes, 401/403, roles/capabilities/ownership, forged headers, account states, email verification, password policy/history, reset-token expiry/reuse, session revocation, refresh replay/concurrency, distributed throttling, CORS/HTTPS/cookies/CSRF, ProblemDetails redaction, and key rotation.
