# Research — Template Selection And Existing Resume Import

## Research Basis

The selected competitors make two different promises to new users: "start with a polished design" and "start from what you already have." Both are critical because some users are beginning from zero, while others already have a resume that needs modernization or optimization.

## Competitive Interpretation

### Template Systems

- Templates are not just images; they are entry points into a design system plus authoring workflow.
- Public competitor pages organize templates by style, use case, and ATS compatibility — suggesting **metadata-rich catalogs** that can drive filters, previews, and entitlement decisions.
- Template gating (8 free / 16 premium) is an explicit monetization lever that must be communicated before the user invests effort in a locked template.
- Template switching after creation is an expected capability that depends on **content/style separation**.

### Import Systems

- Existing-resume upload is both a convenience feature and an acquisition bridge for users who do not want to start over.
- Support content about accepted formats (.doc, .docx, PDF, RTF, TXT) implies file-ingestion rules must be explicit and format coverage deliberate.
- Parsing is never perfect, so a **review step** is necessary even if not heavily marketed.
- Import should yield structured, editable sections — not an opaque text block.

## Product Interpretation

- Template-first and import-first are both essential entry patterns.
- Template metadata needs richness to drive preview, category filtering, ATS-safe labeling, and entitlement states.
- Import cannot be treated as a blind ingestion path; users need a structured parse review step with confidence indicators.

## Hidden Requirements Inferred

- Categorized, filterable, metadata-rich template catalog.
- Template preview (visual + metadata) before commitment.
- Entitlement-aware template response (free vs. premium templates flagged).
- File scanning and parser pipeline supporting multiple formats.
- Parse confidence indicators (sections detected, fields mapped, ambiguous areas flagged).
- Draft creation from parsed structure (not a raw text blob).
- Template change API that preserves content and only updates style properties.

## Risks If Under-Specified

- Engineers may build a gallery with pretty images but insufficient metadata to support real product behavior (filtering, entitlement, preview).
- Import could create opaque text dumps instead of editable structured sections.
- Free vs premium template state could become inconsistent between browse, preview, and create-draft actions.
- Template switching after creation may not be supported if content/style are not separated from the start.

## Recommendation To Developers

- Treat template catalog as product data with metadata (category, ATS-safe flag, premium flag, min/max pages, supported sections), not static assets only.
- Keep parse review editable and explicit; show the user what mapped where.
- Do not assume uploaded files are safe, parseable, or structurally consistent.
- Build the template-switch API on the content/style separation model from day one, even if the feature is used minimally in MVP.

## Open Questions

- Should MVP include profession and seniority filters or only style/category filters?
- Should import create a new draft always or optionally merge into an existing draft?
- Should image-only PDF support be attempted in MVP?
- How many templates in MVP (free + premium), and what metadata fields are required per template?
