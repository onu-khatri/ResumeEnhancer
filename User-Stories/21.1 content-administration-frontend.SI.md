# Supporting Information — Content Administration Interface For Templates, Examples, And Public Resources

## Suggested Screens

- Content list view
- Content metadata detail panel
- Publication state change confirmation

## Suggested Components

- Content table/list
- Type/category filters
- Status badge
- Metadata edit form
- Confirmation dialog

## Design Token Guidance

### Typography

- Content names and states should be immediately legible, using type weight and hierarchy so operators can scan the inventory without effort.
- State and category labels should remain distinct from item titles so a published state is never confused with the item's name.

### Color

- Status colors should communicate publication state clearly, using restrained semantic hues (e.g., neutral for draft, positive for published) rather than decorative variety.
- Color must never be the only signal for state, so text or icons reinforce meaning for accessible, low-ambiguity scanning.

### Spacing

- Support table readability and safe interaction spacing, keeping rows comfortably separated while remaining dense enough for operational scanning.
- Group high-impact controls away from routine ones so a publication change is not accidentally triggered.

## API And Entity Map

- APIs: `GET /admin/content`, `PATCH /admin/content/{id}`
- Entities: `ContentItem`, `Template`, `Example`

## Edge Cases

- Large mixed-content inventory: the UI must stay responsive and filterable when thousands of items span multiple content families, using pagination or virtualized lists.
- Draft item missing required publication metadata: the interface should flag the incomplete item and prevent an invalid publish rather than silently failing.
- Permission-limited manager views: a manager with a restricted scope should see a cleanly filtered list rather than hidden rows that suggest missing data.

## Test Focus

- Status update safety: verify that a publication-state change is confirmed, validated, and reflected only after backend success.
- Filter and list usability: confirm type/status/category filters return expected subsets and preserve context across updates.
- Permission-denied behavior: ensure blocked managers see a clear denial state distinct from load or empty states.

## Developer Notes

- Model content-type metadata consistently even if different content families have different fields, so the UI can share list, filter, and edit components across asset types rather than forking per family.
- Keep public and internal status representations clearly separated, since a status valid internally (e.g., `needs_review`) may have no meaning on the public site and must not leak there.
