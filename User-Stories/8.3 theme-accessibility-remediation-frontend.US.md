## [THEME-FE-002] - Theme Accessibility Remediation Across The Frontend

**Module:** Frontend Foundation and Theme Infrastructure  
**Layer:** Frontend  
**Priority:** Must Have  
**Persona:** All application users, including users with low vision or color-vision deficiencies  
**Dependency:** THEME-FE-001, PROF-FE-001, shared frontend foundation  
**Source Classification:** Documented, Observed

### User Story

As a user who selects Light, Midnight, or Forest,
I want every application surface and control to use colors appropriate to my selected theme,
so that I can read content, understand state, and complete tasks without inaccessible foreground, background, border, or focus combinations.

### Description

The current application theme provider supports `light`, `midnight`, and `forest`, but the frontend has theme-token usage mixed with direct palette utilities and a Midnight-only `dark` path. This can produce dark text on dark backgrounds, light text on light backgrounds, and state indicators that no longer meet contrast requirements when the active theme changes. This story establishes a complete, repeatable remediation of the application color system rather than one-off fixes on reported screens.

### Scope

**Included In Scope**

- Every application-controlled frontend source surface under `application/WebSolution/websolution.client/src`, including shared UI, pages, application shell, resume dashboard, builder, preview, and fallback states.
- The supported `light`, `midnight`, and `forest` themes.
- Shared semantic tokens for canvas, raised and subtle surfaces, text, headings, muted text, borders, accents, status feedback, focus, selected, disabled, and validation states.
- Every shared component and form control, including buttons, inputs, textareas, selects, autocomplete, checkbox, radio group, cards, lists, tables, pagination, removable pills, alerts, empty states, errors, and loading/skeleton states.
- Default, hover, keyboard focus, selected, checked, invalid, read-only where supported, and disabled/inactive states.
- Automated contrast regression coverage and a repeatable visual audit of each supported theme.

**Out Of Scope**

- Changing the product's supported theme names or adding new themes.
- Redesigning the resume document customization catalogue, premium entitlement rules, or ATS-safe policy.
- Browser-native or third-party UI that the application does not style; any such exception must be identified and documented.

### Functional Requirements

- The active theme must be the authoritative source of application color behavior; a component must not depend on a Midnight-only styling path to remain readable.
- UI colors must resolve through documented semantic tokens or a documented, tested exception. Direct palette values must not silently bypass the active theme.
- Every supported theme must provide complete foreground/background, border/surface, icon/surface, and focus/surface combinations for all rendered component states.
- Error, warning, success, selection, and premium/locked states must remain understandable without color alone.
- Theme selection and persisted profile preference behavior must remain unchanged.

### Acceptance Criteria

**AC1 - Complete Theme Coverage**  
Given Light, Midnight, or Forest is selected  
When a user visits any application route and interacts with every supported component state  
Then every application-controlled foreground, background, border, icon, and focus treatment resolves to the selected theme's approved semantic token set.

**AC2 - Text Contrast**  
Given any supported theme and an application-controlled text pair  
When its rendered foreground and intended background are evaluated  
Then normal text, including labels, descriptions, validation messages, placeholders, and hover/focus text, meets at least 4.5:1 contrast, and qualifying large text meets at least 3:1.

**AC3 - Control And State Contrast**  
Given any supported theme and an operable form control, action, icon, or state indicator  
When its visible boundary, selected/checked/invalid state, or keyboard-focus treatment is evaluated against adjacent colors  
Then the required visual information meets at least 3:1 contrast and does not rely on color alone to convey meaning.

**AC4 - Full Frontend Audit**  
Given the frontend source inventory is reviewed  
When color declarations and utility classes are assessed across all source files  
Then each application-visible color use is migrated to semantic tokens or recorded as an approved exception with its contrast rationale and verification evidence.

**AC5 - Regression Protection**  
Given a future token, component, or theme change  
When the frontend verification suite runs  
Then automated contrast checks cover the approved theme token pairs and component-state matrix, and the change fails verification when a required pair falls below its WCAG threshold.

**AC6 - Preserved Theme Behavior**  
Given a user changes or synchronizes their theme preference  
When the provider applies Light, Midnight, or Forest  
Then the selected theme remains persisted and all corrected surfaces update without changing business behavior or user content.

### Business Rules

- Accessibility conformance is required for every supported theme, not only the default theme.
- An inactive control may use the WCAG inactive-control exception only when it is genuinely non-operable; the exception must not be used for an otherwise interactive state.
- Color is supplementary, not the sole carrier of error, selection, warning, entitlement, or other meaning.
- Shared primitives are the first remediation point. Feature-specific components may add a semantic token only when the shared system does not express the required intent.

### Validation Rules

- Normal text requires a minimum 4.5:1 contrast ratio; large text requires a minimum 3:1 contrast ratio.
- Required visual identification of an operable UI control, its state, and its focus indicator requires a minimum 3:1 contrast ratio against adjacent colors.
- A computed ratio must meet the threshold before rounding.
- Every supported theme must pass the same component-state matrix before the work is complete.

### Error Handling

- If a persisted or remote theme value is unsupported, retain the existing safe fallback behavior and do not apply a partial palette.
- If a component cannot resolve a required semantic token during development, treat it as a verification failure rather than silently falling back to a hard-coded color.

### Accessibility Requirements

- Meet the repository's WCAG 2.2 AA baseline for text and non-text contrast in every supported theme.
- Preserve keyboard-visible focus across controls after token migration.
- Preserve accessible names and text alternatives already supplied by shared controls; color remediation must not remove them.

### React UI Implementation Notes

- Consolidate theme behavior around the root theme attribute and semantic CSS custom properties; avoid styling branches that only understand Midnight.
- Update shared primitives before consuming feature surfaces so common controls receive consistent corrections.
- Keep theme selection, persistence, and profile synchronization interfaces stable.

### Definition Of Ready For Engineering

- The complete source and component-state audit matrix is available in the supporting information.
- Approved semantic color roles and contrast pairs are defined for Light, Midnight, and Forest.
- The implementation team has selected a repeatable automated contrast verification method compatible with the existing frontend test toolchain.

### Definition Of Done

- All application-controlled frontend surfaces have been audited for every supported theme.
- Required text, non-text control, state, and focus contrast pairs pass WCAG 2.2 AA thresholds.
- Direct palette use is removed, tokenized, or documented as a verified exception.
- Automated regression coverage and theme-by-theme visual audit evidence are present.
- Existing theme persistence and preference synchronization continue to work.
