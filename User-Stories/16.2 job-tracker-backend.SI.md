# Supporting Information — Job Tracker Data Model And Application Progress Services

## Suggested Entities

| Entity | Purpose |
| --- | --- |
| `JobApplication` | core user-owned tracker record |
| `JobApplicationNote` | optional future extension if note history is needed |
| `JobTrackerLimitPolicy` | resolved active-card allowance from entitlements |

- `JobApplication` is the primary record and must carry ownership, stage, company/role, optional job URL, an optional `relatedDocumentId`, and a follow-up date. It is the authorization root for all tracker mutations.
- `JobApplicationNote` is deferred and exists only as a forward-compatible concept so the schema does not need to be redesigned when note history is introduced.
- `JobTrackerLimitPolicy` is a resolved value computed from the user's entitlements and applied at read and write time, so the enforced cap is never hardcoded in the API.

## Example API Shapes

### `GET /jobs`

```json
{
  "items": [
    {
      "id": "job_123",
      "company": "Acme Corp",
      "role": "Frontend Engineer",
      "stage": "applied",
      "relatedDocumentId": "res_01",
      "nextFollowUpAt": "2026-08-19"

  ],
  "activeCount": 4,
  "activeLimit": 10
}
```

### `POST /jobs`

```json
{
  "company": "Acme Corp",
  "role": "Frontend Engineer",
  "stage": "saved",
  "jobUrl": "https://example.com/jobs/123",
  "relatedDocumentId": "res_01"
}
```

## Normalized Stage Suggestions

- `saved`
  - The user bookmarked the opportunity but has not started applying.
- `applying`
  - The user is actively preparing or in progress with the application.
- `applied`
  - The application has been submitted.
- `interviewing`
  - The user is in an interview process.
- `offer`
  - An offer has been received.
- `rejected`
  - The application was declined.
- `archived`
  - The record is hidden from active views but retained for history.

## Edge Cases

- Card limit reached but archived cards exist.
  - Archived cards must not count against the active limit, and the enforcement must distinguish active from archived when checking the cap.
- Related document deleted or ownership transferred.
  - A job referencing a deleted or inaccessible document must degrade to an unlinked state or reject an invalid association rather than exposing another user's data.
- Duplicate jobs at the same company/role entered intentionally.
  - Users may legitimately apply to similar roles, so uniqueness must not be enforced on company/role and duplicates must be allowed.
- Long notes causing oversized board payloads.
  - Note fields must be bounded or excluded from list payloads so large notes do not bloat board responses.

## Testing Focus

- Ownership isolation.
  - Verify a user cannot read or mutate another user's job records.
- Limit enforcement for active versus archived items.
  - Assert archived cards do not count against the cap and that active-card limits are enforced on creation.
- Association validation against document ownership.
  - Confirm `relatedDocumentId` references are validated for existence and ownership.
- Stable ordering for board/list rendering.
  - Verify list responses are ordered deterministically so board rendering is stable across requests.

## Developer Notes

- Consider returning both grouped and flat representations only if clearly needed; otherwise keep the API simple and let frontend group by stage.
  - A flat list keeps the contract minimal and lets the frontend render board or list views from one source without server-side grouping complexity.
- Keep note and reminder expansion paths possible without forcing them into MVP schema design.
  - Design the record so note history and reminders can be added later without a breaking migration, but do not build them prematurely.
