# Supporting Information — Content Inventory, Metadata, And Publication State Services

## Proposed APIs

- `GET /admin/content`
- `PATCH /admin/content/{id}`

## Example Content Summary

```json
{
  "id": "tpl_123",
  "type": "template",
  "status": "published",
  "category": "professional"
}
```

## Proposed Entities

- `ContentItem`
- `Template`
- `Example`
- `AuditLog`

## Suggested Technical Controls

- Content-type filter support: constrain list queries to supported content families so operators can isolate templates, examples, and guides efficiently.
- Publication-state transition validation: enforce an approved state machine so invalid transitions such as `archived` directly to `published` are rejected server-side.
- Content-management role gating: ensure only authorized roles can reach inventory and mutation endpoints, with read and write scopes enforced independently.

## Edge Cases

- Invalid publication state transition: the service must reject the change with a structured policy error and leave the item in its prior state.
- Mixed content families with different metadata schemas: the API must return a stable common summary while keeping family-specific fields optional and clearly scoped.
- Permission-limited content managers: a scoped manager must only see items within their boundary, with no indication of the existence of hidden items.

## Test Focus

- Metadata validation: verify only approved fields and enum values are accepted and persisted.
- Publication-state audit logging: confirm every state change writes an attributable before/after audit entry.
- Filterable inventory retrieval: ensure type, status, and category filters return correct, efficient results.

## Developer Notes

- Keep content-item summary contracts stable across multiple public asset families, so the frontend can rely on a single list contract.
- Separate public render concerns from internal content-management concerns, so admin metadata never leaks into the public rendering path.
