# Research — Shared Frontend Foundation For React Product Experience

## Why This Pack Is Needed

The current backlog now has solid feature-level frontend stories, but without a shared foundation the implementation can still drift. Different engineers may build polished local screens that do not feel like one product. This pack closes that gap by defining the baseline system that future stories inherit.

## Research Basis

This pack is primarily **[INFERRED]** and **[RECOMMENDED]** rather than competitor-specific because public competitor sites show outcomes, not their internal frontend conventions. Still, the selected references reveal one important truth: the better products feel coherent across onboarding, builder, templates, AI, analysis, and pricing. That coherence is not accidental.

## What Public Product Quality Implies

- Consistent spacing, hierarchy, and shell patterns are likely defined somewhere internally. Novorésumé's public tools and Resume Now's guided-builder flow feel like one system, which signals a shared design-language foundation rather than per-page ad-hoc styling.
- Shared state patterns reduce confusion as users move between builder, AI, analysis, and billing. Both competitors transition visitors from marketing pages into tools without an abrupt visual or interaction break, implying reusable loading, error, and feedback states.
- Premium/upgrade messaging is most effective when it feels like part of the product instead of an interruption from another system. Resume Now's pricing pages integrate into the same product story, suggesting monetization surfaces share the same shell and design language rather than being bolted on.

## Product Interpretation

- We should not let each feature team invent its own layout, state styling, or interaction rules. The coherence visible in Novorésumé and Resume Now is the product of enforced shared conventions, not accidental similarity.
- React architecture should reflect product boundaries:
  - shell
  - feature modules
  - shared primitives
  - async state handling
- A foundation pack makes feature stories cleaner because they can reference shared assumptions instead of repeating them. It also mirrors what the competitors' polish implies: a single design system driving every surface.

## Risks If This Is Missing

- The public site and authenticated app may feel like different products. Novorésumé notably splits its marketing shell from its builder shell, but both still read as one brand — losing that coherence would make our public and app surfaces feel disconnected.
- Repeated patterns such as loading, errors, locks, drawers, modals, and action bars may become inconsistent. Resume Now's guided flow shows these states are used frequently enough that inconsistency would be immediately noticeable to users.
- React code may drift into duplicated containers, duplicated primitives, and ad-hoc state handling. Without a baseline, each feature re-implements the same patterns, slowing delivery and increasing bug surface.
- QA and design review become slower because there is no standard to validate against. Reviewers have no shared checklist, so every screen requires bespoke judgment instead of comparison to a known foundation.

## Recommended Interpretation For This Project

- Treat this pack as the baseline for all future FE stories.
- Keep feature stories focused on feature-specific behavior and only restate foundation rules when a deviation is intentional.
- Use this pack to guide both design review and implementation review.

## Open Questions

- Will the team adopt CSS variables, CSS modules, Tailwind, or another token-delivery mechanism?
- Will the app shell be sidebar-first, top-nav-first, or hybrid by breakpoint?
- Which shared state-management approach will the React app standardize on for async feature flows?
