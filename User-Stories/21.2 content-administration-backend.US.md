## [CONT-BE-001] — Content Inventory, Metadata, And Publication State Services

**Module:** Content Administration  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Content Service  
**Dependency:** ADM-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the content service,  
I want to expose internal APIs for content inventory retrieval, metadata updates, and publication-state management,  
so that public-facing templates, examples, and resource assets can be operated safely and consistently.

### Description

This story covers backend support for internal content administration. The service must return content inventory across supported families, expose publication state and metadata, and allow authorized updates to approved fields. It should support operational content maintenance without requiring engineering-only interventions for every metadata change.

### Scope

**Included In Scope**

- Internal content inventory retrieval.
- Content-type metadata retrieval.
- Publication status updates.
- Category/tag metadata updates.

**Out Of Scope**

- Full CMS body editing.
- SEO management suite.
- Public rendering engine.

### Preconditions

- Content item model exists, defining the shared catalog fields (type, status, category, premium flag) that every asset family participates in.
- Publication status model is approved, so operators and the service share a common understanding of valid states and the transitions between them.
- Content-management roles exist with a defined permission scope that separates managers who can edit metadata from those who cannot.

### Detailed Workflow

1. Authorized content manager requests content inventory.
2. Service validates content-management permissions.
3. Service returns content summaries and metadata.
4. Manager updates approved metadata or publication state.
5. Service validates and persists changes and records audit information.

### Functional Requirements

- Content inventory APIs must support mixed content families while remaining filterable by type.
- Publication-state changes must be explicit and auditable.
- Metadata updates must be constrained to approved editable fields.
- Retrieval payloads should support operational filtering by type, category, and state.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authorized content manager requests content inventory  
When the service processes the request  
Then it returns content summaries with type, state, and supported metadata.

**AC2 — Metadata Update**  
Given an authorized content manager updates allowed metadata fields  
When the service processes the request  
Then it validates and persists only supported changes and returns updated state.

**AC3 — Publication State Change**  
Given an authorized manager changes a publication state  
When the service processes the request  
Then it applies the change safely and records an audit trail.

**AC4 — Authorization And Validation**  
Given a manager lacks permission or submits invalid metadata/state transitions  
When the request is processed  
Then the service rejects the action without corrupting content state.

### Business Rules

- Content inventory is an operational growth asset: the templates, examples, and guides it catalogs are the acquisition surface that drives onboarding and conversion, so treating them as first-class managed assets is necessary.
- Publication states and premium/public metadata must stay aligned with real product behavior; an item marked published but not actually reachable, or marked premium while free, erodes trust in the acquisition funnel.
- Content state changes should be auditable so the team can trace who changed a public asset and when, which matters during incident investigation and content reviews.

### Validation Rules

- Only supported content types, statuses, categories, and editable fields may be used; the service must reject unknown enum values rather than silently persisting ambiguous metadata.
- Publication transitions must respect approved state rules, for example preventing a jump from `archived` directly to `published` without an explicit intermediate step where policy requires it.
- Managers may only access allowed content scopes, so an operator restricted to a subset of content families cannot read or modify items outside their assigned boundary.

### Error Handling

- Distinguish authorization, validation, not-found, and persistence failures so the frontend can render the correct recovery path instead of a single generic error.
- Prevent partial publication-state updates when related validation fails, keeping the content item in its prior consistent state rather than a half-applied one.
- Return frontend-mappable policy errors for blocked changes so operators understand why a transition was refused and what to do next.

### Security Considerations

- Content-management APIs must be role-protected so only authorized managers can reach inventory and mutation endpoints; read access itself should still be gated behind an internal session.
- Unpublished or internal-only content metadata must not leak through wrong scopes, since exposing draft or premium-gated details would undermine the public catalog and reveal strategy.
- Publication changes must be auditable, recording the acting operator and before/after state so sensitive edits are attributable.

### Analytics / Tracking

- `content_inventory_requested`
- `content_metadata_updated`
- `content_publication_state_changed`

### API Dependencies

- `GET /admin/content`
- `PATCH /admin/content/{id}`

### Data Model

This service operates over a content inventory that unifies several public-facing asset families behind a common catalog abstraction. The entities below support retrieval, metadata updates, and publication-state transitions while keeping template and example specifics separate from the generic `ContentItem` wrapper.

#### ContentItem

The generic catalog wrapper that all public-facing assets participate in, holding shared status and classification fields regardless of asset family.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable unique identifier for the content item. |
| `type` | enum | Asset family: `template`, `example`, `guide`, or `resource`. |
| `status` | enum | Publication state such as `draft`, `published`, or `archived`. |
| `category` | string | Primary classification label used for filtering and discovery. |
| `tags` | string[] | Additional free-form classification tags. |
| `isPremium` | boolean | Whether the item participates in premium-only positioning. |
| `createdAt` | datetime | Creation timestamp. |
| `updatedAt` | datetime | Last modification timestamp. |

#### Template

A resume or cover-letter template that participates in the content inventory while carrying template-specific metadata.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable template identifier. |
| `contentItemId` | string | Link back to the owning `ContentItem` catalog entry. |
| `kind` | enum | `resume` or `cover_letter`. |
| `style` | string | Visual style label such as `modern`, `creative`, or `academic`. |
| `isAtsFriendly` | boolean | Whether the template is optimized for applicant-tracking systems. |

#### Example

A sample resume, cover letter, or guidance asset used for acquisition and onboarding.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable example identifier. |
| `contentItemId` | string | Link back to the owning `ContentItem` catalog entry. |
| `contentType` | enum | The asset kind the example demonstrates (`resume`, `cover_letter`, `guide`). |
| `title` | string | Human-readable example title. |

#### AuditLog

Records sensitive content-management actions for traceability.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable audit entry identifier. |
| `actorId` | string | Operator who performed the action. |
| `action` | enum | Action performed such as `metadata_updated` or `status_changed`. |
| `targetType` | string | Type of entity affected. |
| `targetId` | string | Identifier of the entity affected. |
| `before` | json | Snapshot of prior state where relevant. |
| `after` | json | Snapshot of resulting state where relevant. |
| `timestamp` | datetime | When the action occurred. |

#### Example JSON

```json
{
  "id": "tpl_123",
  "type": "template",
  "status": "published",
  "category": "professional",
  "tags": ["ats", "minimal"],
  "isPremium": true
}
```

#### Relationships

```text
ContentItem 1 ─── 1 Template     (template catalog entry)
ContentItem 1 ─── 1 Example      (example catalog entry)
ContentItem 1 ─── * AuditLog     (content actions audited)
```

#### Business Notes

- `ContentItem` is the shared inventory anchor; `Template` and `Example` enrich it with family-specific fields rather than duplicating status.
- Publication state lives on `ContentItem` so all asset families share the same transition rules.
- Audit entries must capture before/after snapshots for sensitive status and premium-flag changes.
