# Research — Multi-Language Document Management Backend

## Research Basis

Novorésumé's help-center documentation on multi-language documents explicitly states: each document version is independent, no synchronization between languages, and up to 144 documents for Premium users. This is explicitly a **manual versioning model**, not automatic translation. The backend must treat language as a first-class document property and support organization via metadata (tags, type filters).

## What The Research Means For The Backend

- **Language is a document-level property**, not a per-section value. Each document has one language code.
- **No cross-language sync logic is needed** — this simplifies the backend. A "Spanish version" is a new document with `languageCode: "es"` and its own content.
- **Duplication is how variants are created**: the user duplicates their English resume, changes the language to Spanish, and rewrites content.
- **Document organization requires metadata**: `languageCode`, `tags[]`, `documentType` (resume/cover_letter) must be queryable/filterable.
- **Localized section labels** must be served per document's language — the backend needs a mapping of `sectionType → label` per supported language.
- **Document capacity limits** must account for multi-language users: an English + Spanish + German user uses 3 slots.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| `languageCode` on document | First-class property for filtering and label localization |
| `tags[]` on document | User-defined tags for organization (language, role, market) |
| Document duplication endpoint | Copies content with new language metadata |
| Localized section label catalog | Serves correct labels per document language |
| Document capacity enforcement | Respects per-plan limits; multi-language users consume more slots |
| Views/filters by type and tags | Supports the "My Documents" organizational pattern |

## Hidden Requirements Inferred

- Supported-languages list (which `languageCode` values are valid).
- Section-label translations per language (e.g., `"experience" → "Experiencia"` for `es`).
- Tag management CRUD (create/edit/delete tags, apply to documents).
- RTL detection and block — if RTL languages are not yet supported, the backend should reject document creation with RTL language codes and return a clear error.

## Risks If Under-Specified

- Language may be stored inconsistently or not at all, preventing filtering and organization.
- Without tags, users with 5+ language variants have no way to organize or find documents.
- Section labels may display in the wrong language if the localization mapping is not served per document.
- Document limits may not account for the higher slot usage of multilingual users.

## Recommendation To Developers

- Add `languageCode` (ISO 639-1) and `tags` (array of strings or tag IDs) to the document model from day one.
- Provide a document duplication endpoint that accepts `languageCode` override.
- Serve localized section labels based on the document's language setting.
- Block unsupported languages at the API level with a clear error message (e.g., "Right-to-Left languages are not yet supported").

## Open Questions

- Which languages are supported in MVP? Should unsupported languages be blocked or allowed with a "labels may not localize" warning?
- How are tags modeled — simple string array, or a dedicated tag entity with user-specific tag sets?
- Should section-label localization use a static config or be editable by the user (Novorésumé allows manual label translation)?
