# Supporting Information — Moderation Case Retrieval And Abuse Review Services

## Proposed APIs

- `GET /admin/moderation/cases`
- `PATCH /admin/moderation/cases/{id}`

## Example Moderation Case

```json
{
  "id": "mod_123",
  "category": "ai_policy",
  "severity": "medium",
  "status": "open"
}
```

## Proposed Entities

- `ModerationCase`
- `AuditLog`
- `Role`
- `AccessProfile`

## Suggested Technical Controls

- Case taxonomy allowlist: restrict category, severity, and status to approved values, rejecting anything outside the taxonomy.
- Controlled state-transition rules: enforce an approved lifecycle so only valid next states can be applied.
- Trust/safety scope enforcement: gate case access and mutation behind stricter authorization than general admin data.

## Edge Cases

- Case references deleted artifact: the service must tolerate dangling references and still render reviewable, curated context.
- Two operators attempt to resolve same case: detect concurrent updates and surface a conflict rather than silently overwriting one resolution.
- High-severity cases require stricter visibility: enforce elevated scope so critical cases are only visible to appropriately cleared reviewers.

## Test Focus

- Authorization: verify only cleared operators can access and mutate cases.
- State transition validation: confirm only approved transitions are accepted.
- Sensitive-data minimization: ensure responses exclude raw content and unnecessary PII.
- Audit completeness: verify every view and status change is recorded.

## Developer Notes

- Keep case payloads curated and avoid overexposure of raw signals, returning summaries over full source content.
- Treat trust/safety operations as a higher-sensitivity admin domain than ordinary content management, applying tighter controls throughout.
