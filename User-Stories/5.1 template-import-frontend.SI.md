## Design Token Guidance

### Typography

- Start-choice headings should feel editorial and inviting.
- Template metadata should stay concise and scannable.
- Parse-review helper text should prioritize clarity over density.

### Color

- Template gallery can carry slightly richer visual energy than auth or settings screens because preview assets are central.
- Premium locks should use a refined accent style, not harsh warning colors.
- Import progress states should use a neutral-to-positive progression scale, reserving error colors only for actual failure.

### Spacing

- Template card grid needs breathable spacing to maintain a curated feel.
- Upload and parse states require clear separation between status text and actions.
- Parse review fields should not be cramped; users need confidence correcting machine-extracted content.

## Example Parse Result Shape

```json
{
  "importJobId": "imp_123",
  "status": "review_ready",
  "warnings": [
    "Could not confidently detect end date for one job entry."
  ],
  "sections": [
    {
      "type": "experience",
      "confidence": "medium",
      "items": []
    }
  ]

```

## Edge Cases

- Import extracts duplicate sections
  - A parser may produce two experience blocks or overlapping entries, so the review screen must let the user merge, remove, or reorder duplicates before draft creation. Surfacing duplicates clearly prevents a confusing, bloated draft from being committed silently.
- Upload completes but parse stalls
  - If the file uploads but parsing never reaches `review_ready`, the UI must show a stuck-phase state with retry or support guidance rather than an indefinite spinner. The user needs a way to escape without losing the uploaded file.
- Premium template selected by free user
  - The gallery must clearly mark a template as premium and present the upgrade path at selection time, not silently allow a choice that later fails. The chosen intent should survive so the user can complete the upgrade and continue where they left off.
- File is scan-safe but structurally unreadable
  - A file can pass security scanning yet contain no extractable structure, so the UI must distinguish "safe but unparseable" from "blocked" and offer manual entry or a re-upload path. The messaging must not imply the user's file is malicious when it is simply unsupported.

## Test Focus

- File drag-drop and click-upload
  - Verify both the drag-drop and native file-picker paths produce the same upload state and validation behavior, including rejected file types.
- Unsupported format handling
  - Confirm unsupported extensions and MIME types are blocked with clear, actionable messaging before any network request is sent.
- Parse review correction flow
  - Exercise editing extracted fields, resolving warnings, and confirming the draft, ensuring corrections persist into the created resume.
- Template selection continuity into builder
  - Assert that choosing a template and then completing signup or import lands the user in the builder with the selected template preserved.

## Developer Notes

- Keep upload and parse as separate user-visible phases.
  - Uploading a file and parsing its contents are distinct operations with different failure modes, so modeling them separately gives users accurate progress and lets each phase retry independently. A single monolithic "import" state hides where a failure actually occurred.
- Parse review should avoid exposing raw parser internals, but should expose enough uncertainty for user correction.
  - The review screen must translate low-level parser signals into plain-language warnings and confidence indicators rather than dumping internal fields. Users need to trust and correct the result without understanding the parsing engine.

## Professional UI Notes

- The template area should feel like a curated product catalog, not a file browser.
- The import experience should feel reliable and methodical, not experimental.
