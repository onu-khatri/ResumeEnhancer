## [THEME-BE-001] — Theme Capability, Appearance State, And Layout Ordering Services

**Module:** Builder Customization  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Active Job Seeker, Premium User, Rendering System  
**Dependency:** RES-BE-001, EXP-BE-001, BILL-BE-002  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform,  
I want structured theme/layout capabilities and persisted customization state,  
so that appearance changes remain safe, entitlement-aware, and consistent across preview and export.

### Description

This story covers the backend support for appearance customization and layout ordering. The service must expose the allowed customization options for a given document/template, persist selected appearance state, validate supported combinations, and store layout ordering changes in a way the renderer can trust. This is a core architectural requirement because competitor behavior makes it clear that content and appearance must remain separated if template switching and premium customization are to remain stable.

### Scope

**Included In Scope**

- Template/document customization capability retrieval.
- Persisted appearance settings.
- Persisted layout ordering state.
- Validation against template support and entitlements.

**Out Of Scope**

- Graphic design editor engine.
- User-authored custom templates.
- Full freeform coordinate-based layout.

### Preconditions

- Structured document model exists.
- Rendering pipeline accepts appearance/layout inputs.
- Entitlement policy for customization exists.

### Detailed Workflow

1. Client requests customization capabilities for a document.
2. Backend resolves template support, appearance options, and entitlement visibility.
3. User submits appearance or layout changes.
4. Backend validates combinations and persists supported state.
5. Preview and export consumers use the same stored customization truth.

### Functional Requirements

- The service must return a normalized capability set for themes, fonts, styles, and layout ordering.
- Appearance state must be stored independently from core content fields.
- Layout ordering changes must map to the structured document model deterministically.
- Unsupported, non-entitled, or ATS-disallowed combinations must be rejected or normalized according to product policy.
- Persisted customization must be consumable by both preview and export paths.

### Acceptance Criteria

**AC1 — Capability Retrieval**  
Given a document and template  
When customization metadata is requested  
Then the response includes the supported appearance and layout capabilities for that context.

**AC2 — Appearance Persistence**  
Given a valid customization update  
When it is submitted  
Then the service stores the selected appearance state without mutating document content.

**AC3 — Layout Ordering Persistence**  
Given a valid reorder request  
When it is submitted  
Then the resulting order is stored deterministically and returned for subsequent loads.

**AC4 — Policy Enforcement**  
Given a user selects a premium-only or unsupported option  
When the request is processed  
Then the service rejects or constrains it according to entitlement/template rules.

**AC5 — Rendering Consistency**  
Given a document has stored customization  
When preview or export consumes it  
Then both paths can rely on the same normalized state model.

### Business Rules

- Customization truth is part of document presentation state.
- Content and appearance must stay decoupled.
- Capability exposure may differ by template and plan.

### Validation Rules

- Theme/font/style identifiers must exist in the allowed capability set.
- Layout reorder targets must reference valid sections/items.
- ATS-safe constraints must be centrally enforced where applicable.

### Error Handling

- Return stable validation responses for unsupported customization combinations.
- If a reorder mutation would create invalid state, reject it without partial persistence.
- Preserve prior valid customization state when new updates fail.

### Security Considerations

- Entitlement validation must not rely on the client.
- Internal template capability definitions must not be exposed beyond public-safe allowed sets.

### Analytics / Tracking

- `customization_capabilities_requested`
- `customization_updated`
- `layout_order_updated`
- `customization_denied_by_policy`

### API Dependencies

- `GET /documents/{id}/customization`
- `PATCH /documents/{id}/customization`
- `PATCH /documents/{id}/layout-order`
- `GET /entitlements/me`

### Data Requirements

- Document id
- Template id
- Capability schema version
- Appearance state object
- Layout ordering object
- Entitlement constraints

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

> Theme/customization is modeled as **references to tokens** (fontId, themeId, backgroundId, etc.) stored on the document, not as inline style strings. This separation from content enables template switching without content loss and allows the rendering engine to apply appearance consistently across preview and export.

#### CustomizationCapabilitySet

Defines what a given template supports for customization. Queried per document/template combination.

| Property | Type | Description |
| --- | --- | --- |
| `templateId` | string (uuid) | Which template this capability set applies to |
| `fonts` | json[] | Array of `{ id, name, category, isPremium, isAtsSafe }` — available fonts |
| `colorThemes` | json[] | Array of `{ id, name, primaryColor, accentColor, isPremium, isAtsSafe }` |
| `backgroundStyles` | json[] | Array of `{ id, name, previewUrl, isPremium, isAtsSafe }` — null if not supported |
| `pictureStyles` | json[] | Array of `{ id, name, shape, border, isPremium, isAtsSafe }` |
| `ratingStyles` | json[] | Array of `{ id, name, icon, isPremium, isAtsSafe }` |
| `iconSets` | json[] | Array of `{ id, name, previewUrl, isPremium, isAtsSafe }` |
| `layoutOrdering` | json | `{ sectionReorder: boolean, itemReorder: boolean, isPremium: boolean }` |

#### Theme Controls Taxonomy (From Competitor Research)

| Control | Basic (Free) | Premium | ATS-Safe Constraint |
| --- | --- | --- | --- |
| Fonts | 3–5 standard | 10–15 total | Web-safe, sans-serif preferred |
| Color themes | 20–30 | 60–80 | High contrast enforced |
| Background styles | None | Creative patterns | Blocked in ATS-safe mode |
| Picture styles | 1 (standard) | 3–4 (circle, rounded, border) | Blocked in ATS-safe mode |
| Rating styles | Text only | Bar/dot/star visual | Replaced with text in ATS-safe mode |
| Icon sets | None | Interests & causes | Replaced with text labels in ATS-safe mode |
| Layout reorder | Predefined | Custom drag-and-drop | Section headings must remain standard |

#### DocumentCustomizationState

The persisted appearance choices for a specific document. Stored as a separate entity, not embedded in resume content.

| Property | Type | Description |
| --- | --- | --- |
| `documentId` | string (uuid) | Which document this customization applies to (resume or cover letter) |
| `fontId` | string | Selected font from the capability set |
| `colorThemeId` | string | Selected color theme |
| `backgroundStyleId` | string | Selected background; null if not used |
| `pictureStyleId` | string | Selected picture style; null if not used |
| `ratingStyleId` | string | Selected rating style; null if not used |
| `iconSetId` | string | Selected icon set; null if not used |
| `schemaVersion` | string | Version of the customization schema — protects against capability-set changes breaking stored state |
| `updatedAt` | datetime | |

#### DocumentLayoutOrder

The persisted section and item ordering for a specific document.

| Property | Type | Description |
| --- | --- | --- |
| `documentId` | string (uuid) | Which document this ordering applies to |
| `sectionOrder` | string[] | Ordered list of section IDs — defines the document's section sequence |
| `itemOrders` | json | `{ "sectionId": ["itemId1", "itemId2", ...], ... }` — per-section item sequences |
| `version` | integer | Monotonic counter for conflict detection on reorder operations |
| `updatedAt` | datetime | |

#### Relationships

```text
Template (1) ──── (1) CustomizationCapabilitySet
Resume (1) ──── (1) DocumentCustomizationState
Resume (1) ──── (1) DocumentLayoutOrder
CoverLetter (1) ──── (1) DocumentCustomizationState
CoverLetter (1) ──── (1) DocumentLayoutOrder
```

#### Premium-Feature Detection For Export

If a document's `DocumentCustomizationState` references a premium `fontId`, `colorThemeId`, or other premium token, and the user is on a free plan, the export gate must detect this and return `premium_features_used` → upgrade required. This prevents free users from "previewing" premium designs and exporting them without payment — it is the same gate as the export domain's "preview premium, pay to download" model.

### Technical Notes

- Prefer schema-driven customization objects over ad hoc flags.
- Keep capability definitions aligned with rendering-engine support to avoid dead options.
- Version customization schema carefully because export compatibility depends on it.
