## Design Token Guidance

### Typography

- Page title: large display or heading style with strong clarity
- Supporting copy: medium body style with high readability
- Form labels: smaller but high-contrast label style
- Error text: compact body style with clear emphasis, never tiny

### Color

- Background should use soft contrast between page surface and form card surface.
- Primary accent should communicate trust and progress, not entertainment styling.
- Error color must be readable on light surfaces and paired with icon/text, not color alone.
- Success/info states should remain restrained and product-like.

### Spacing

- Use generous outer page padding on desktop.
- Keep consistent vertical rhythm between fields, helper text, and consent copy.
- Preserve enough space between primary and secondary actions to avoid accidental taps.

### Radius / Shadow

- Form container should use subtle elevation, not heavy marketing-card styling.
- Inputs and buttons should share a common radius system for cohesion.

## Detailed API Contract Notes

### `POST /auth/register`

Request example:

```json
{
  "firstName": "Anup",
  "lastName": "Singh",
  "email": "user@example.com",
  "password": "strong-password",
  "termsConsent": true,
  "privacyConsent": true,
  "marketingConsent": false,
  "source": "template_detail",
  "selectedTemplateId": "tpl_modern_01"
}
```

Response example:

```json
{
  "userId": "usr_123",
  "sessionState": "active",
  "emailVerificationState": "pending",
  "nextAction": "bootstrap",
  "workspaceRoute": "/app/templates?selected=tpl_modern_01"
}
```

### `GET /bootstrap`

## Validation Matrix

| Scenario | Expected UI Behavior | Expected API Behavior |
| --- | --- | --- |
| Missing email | inline error, no submit | request not sent |
| Duplicate email | preserve form, offer sign-in/reset | `409` or mapped safe code |
| Weak password | inline helper and error | `422` or mapped validation |
| Missing consent | block submit | request not sent |
| Bootstrap failure | keep signed-in state, show retry | `5xx` handled gracefully |

## State Matrix

| State | Trigger | Visual Treatment | Allowed Actions |
| --- | --- | --- | --- |
| Idle | page load | clean form | edit, sign in |
| Dirty | user input | normal form | edit, submit |
| Invalid | local validation fails | inline errors | edit |
| Submitting | submit pressed | spinner, disabled CTA | none |
| Partial Success | account created, bootstrap failed | info banner, retry CTA | retry, dashboard |
| Success | bootstrap complete | redirect | continue |
| Failure | API error | alert and preserved values | retry |

## Edge Cases

- Duplicate email
  - The form must preserve the user's entered values, including name and consent, while steering them toward sign-in or password reset. The message must remain privacy-safe so it neither confirms nor denies account existence to an attacker probing addresses.
- User refreshes during submit
  - A mid-flight refresh can orphan the request, so the app must reconcile a possibly-created account on the next load rather than blindly re-submitting. The refresh-safe source context must survive so the user still lands on the correct post-signup route.
- Verification email delivery delay
  - The reminder banner must remain dismissible and non-blocking, and the user must still be able to enter the builder. A resend action should be available without punishing the user for the provider's latency.
- Session issued but builder bootstrap fails
  - The user is authenticated but routing metadata is missing, so the partial-success state offers retry and workspace fallback. The account must never be treated as failed when only the bootstrap step broke.
- Existing authenticated session reaches register screen in a stale tab
  - The register screen must detect an active session on mount and redirect to the workspace or bootstrap target instead of rendering the signup form. This avoids a confusing duplicate-account path in a forgotten tab.
- Source references a deleted or unpublished template
  - A template intent that no longer resolves must degrade to the generic builder entry rather than throwing an error or landing on a dead template page. The selected-template continuation is dropped gracefully, not catastrophically.
- Browser blocks cookies after successful registration
  - If the session cannot be persisted due to blocked cookies, the app should surface a clear explanation and retry guidance. The account itself may exist, so re-registering is never the correct recovery path.

## Test Focus

- Keyboard-only completion
  - Verify that tab order, focus visibility, error-summary focus, and screen-reader announcements work end to end without a mouse. This includes validating that consent rows and helper text remain reachable by keyboard.
- Mobile portrait completion
  - Confirm the single-column layout, thumb-friendly tap targets, and sticky CTA behavior do not obscure fields or break submission. Test across common narrow viewport widths and with the virtual keyboard open.
- Retry after transient `500`
  - Simulate an operational backend failure and confirm values are preserved, the error is explanatory, and a retry succeeds without duplicating the account. Verify the submit guard releases correctly after recovery.
- Analytics payload accuracy
  - Assert that every onboarding event carries the correct source page, template intent, and plan context. Ensure transport is not dropped when a redirect happens immediately after the completion event.
- Redirect matrix from homepage, pricing, template, and premium-lock entry points
  - Exercise every entry source and confirm each lands on its intended destination. Template and premium-lock continuations must reappear after the signup round trip.
- Focus management after failed submit
  - Confirm that a failed submit moves focus to the form-level error summary and that individual field errors are announced. Focus must not be lost to a silent state.
- Preservation of source intent after server validation failure
  - Submit invalid data, receive a server validation response, and verify the source context and template intent survive the round trip so the user is not silently dropped to a generic path.

## Developer Notes

- Prefer a small state machine for submit, failure, partial-success, and success instead of many booleans.
  - Modeling submit flow as explicit states (`idle`, `submitting`, `failure`, `partialSuccess`, `success`) prevents contradictory flag combinations such as "submitting and failed." Transitions become auditable and easier to test.
- Keep analytics transport resilient to redirect timing.
  - Completion events must be flushed or sent before the redirect fires so they are not lost when the document unloads. Use a transport that survives navigation or capture the event before triggering the route change.
- Never clear all form state on operational failure; only clear fields if security policy requires it.
  - Preserving non-sensitive values reduces friction on retry, but password and any credential-equivalent fields must follow the security policy's clearing rule. Distinguish operational failure from validation failure in state handling.

## Professional UI Notes

- Avoid default auth-page aesthetics with oversized generic illustrations and weak spacing.
- Keep the experience intentionally product-oriented and conversion-focused.
