# Supporting Information — Resume Checker And Job Match Review Workspace

## Suggested Screens

- Analysis launcher
- Score report view
- Keyword gap view
- Job-match rerun state
- Premium-lock explanation state

## Suggested Components

- Score card
- Category breakdown chart
- Recommendation list
- Keyword diff chip
- Rerun CTA
- Resume-version freshness banner

## Design Token Guidance

### Typography

- Score headline should be prominent but not oversized to the point of feeling gamified.
- Recommendation text should favor clarity and scannability.
- Section labels and category labels must stay consistent across report views.

### Color

- Analytical surfaces should use calm, trustworthy neutrals.
- Score and severity colors must be consistent and interpretable.
- Charts should degrade gracefully to text-first patterns for accessibility and mobile.

### Spacing

- Give enough separation between score summary and detailed findings.
- Recommendation cards should be easy to scan in sequence.
- Job-description input and launch controls should not crowd the report region.

## API And Entity Map

- APIs: `POST /analysis/resume`, `POST /analysis/job-match`, `GET /analysis/{id}`
  - The two analysis entry points cover the generic resume check and the job-description-driven match respectively, while the GET endpoint returns a previously computed report for reload and sharing. The UI selects the entry point based on whether a job description is present.
- Entities: `ResumeAnalysis`, `ATSAnalysis`, `JobDescription`, `JobMatch`
  - `ResumeAnalysis` is the base report, `ATSAnalysis` holds formatting-specific findings, `JobDescription` is the optional target input, and `JobMatch` captures the keyword-alignment results against that description.

## Edge Cases

- Low-confidence parse from imported resume
  - If the source resume came from a low-confidence import, the analysis must flag that its input may be incomplete so the user does not over-trust the score.
- Extremely long job description
  - Very large descriptions may slow scoring or overflow the UI, so the input must be bounded and the report must render summaries rather than echoing the full text.
- Resume updated while analysis is running
  - The report may be based on an older version, so a freshness banner must indicate when the analyzed version differs from the current draft.
- User reruns analysis before first report is fully read
  - Rerunning should not silently discard the prior report, and the UI must avoid confusion between an in-progress run and an already-shown result.

## Test Focus

- Analysis refresh after edits
  - Verify the freshness banner appears after edits and that a rerun reflects the current resume version.
- Empty-state messaging
  - Confirm empty or incomplete resumes produce clear guidance rather than a misleading score.
- Score comparison clarity
  - Assert that comparing a new run against a previous one is visually clear and unambiguous.
- Stale-result banner behavior
  - Verify the banner appears only when the analyzed version is actually stale and disappears after a fresh run.

## Developer Notes

- Keep report sections linkable to builder sections where possible.
  - Recommendations should deep-link to the relevant resume section so users can act on feedback without hunting through the builder.
- Use explicit report mode identifiers so the frontend knows whether to show job-description-specific language.
  - A stable mode discriminator (`resume` vs `job_match`) prevents the UI from guessing and ensures the right copy and sections render for each analysis type.

## Professional UI Notes

- The report should feel like a thoughtful review surface, not a flashy score generator.
- Prioritize trust, clarity, and editability over decorative data visualization.
