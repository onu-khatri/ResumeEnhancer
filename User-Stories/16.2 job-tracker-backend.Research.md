# Research — Job Tracker Backend (Cards, Stages, Associations, Limits)

## Research Basis

Novorésumé's Kanban-style job tracker provides the primary public signal. It is a premium feature with a card limit (3 cards basic, unlimited premium), simple stage progression, and connections to resume documents. The backend must model a lightweight personal tracking system — not an enterprise ATS.

| --- | --- | --- | --- | --- |

## What The Research Means For The Backend

- Job cards are **lightweight entities**: company, role, stage, dates, notes, optional resume association. Not a heavyweight CRM pipeline.
- **Stage progression** is a state-machine: saved → applied → interviewing → offer → archived. Moves should have timestamps for audit/analytics.
- **Card limits** are per-plan: the backend enforces a maximum card count for free users and rejects card creation beyond the limit.
- **Resume association**: a job card may reference a resume document, creating a link between "which resume did I use for this application?"
- Job tracker is a **personal, private workspace** — no sharing, no team features, no recruiter-side pipeline.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Job-card CRUD with stage, dates, notes, resume link | Personal application tracking |
| Stage state machine (enforced stages, transition logging) | Data integrity and analytics |
| Per-plan card-count limit enforcement | Free = capped; Premium = unlimited |
| Resume-to-job-card association (soft link) | Connects tracker to document workspace |
| Job-card reorder and stage-move atomic operations | Clean UX on drag-and-drop |
| Audit trail for stage changes | Supportability and analytics |

## Hidden Requirements Inferred

- Job-card ordering within a stage (position index).
- Stage definition (which stages exist — hardcoded in MVP, configurable later).
- Reminder/note storage per card (optional structured notes or free-text).
- Optional job-description storage (if the user pasted a job description for job-match analysis, it may be stored with the card).

## Risks If Under-Specified

- The job-tracker model may grow into an overbuilt CRM-style pipeline with unnecessary complexity.
- Card limits may be enforced inconsistently or only on the client.
- Resume association may reference a document the user no longer has access to (deleted or archived).
- Stage transitions may be unrestricted, allowing illogical moves (e.g., offer → saved).

## Recommendation To Developers

- Keep the job-card model simple: id, userId, company, role, stage, applicationDate, notes, resumeId, position, timestamps. Add fields only when proven needed.
- Enforce card limits at the API layer (create-card endpoint checks count vs. plan limit).
- Model stage as an enum with a defined progression path (or at minimum log all transitions).
- Soft-link to resume documents; handle deleted-resume gracefully (nullify the association).

## Open Questions

- Should stages be hardcoded (saved/applied/interviewing/offer/archived) or user-configurable?
- Should job cards be archivable (soft-delete) rather than permanently deletable?
- Should reminders/notifications for follow-ups be part of the job-tracker backend or a separate notification domain?
