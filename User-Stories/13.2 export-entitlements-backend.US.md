## [BILL-BE-001] — Export Processing, Billing Checkout, And Entitlement Evaluation

**Module:** Export & Billing  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Billing Service, Export Service  
**Dependency:** RES-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform backend,  
I want to evaluate plan entitlements, process checkout, and generate export artifacts securely,  
so that users receive the right document formats and the business can monetize fairly and reliably.

### Description

This story covers the server-side behavior behind export eligibility, checkout initiation, payment-result processing, subscription activation, and secure artifact delivery. Export and billing must be related but not tightly tangled: a user may be allowed to export immediately, may need to upgrade first, or may need to retry after a generation failure.

### Scope

**Included In Scope**

- Entitlement evaluation for export requests.
- Checkout-session creation.
- Payment webhook processing.
- Subscription and entitlement activation.
- Export-job creation and artifact retrieval.
- Secure artifact delivery and retention.

**Out Of Scope**

- Full billing portal UI.
- Manual finance admin operations.
- Tax engine complexity beyond required provider integration.
- Bulk export packaging.

### Preconditions

- Billing provider is configured.
- Plan catalog exists.
- Rendering pipeline is available.
- Secure storage for export artifacts is available.
- Webhook endpoint and reconciliation job path are configured.

### Functional Workflow

1. User requests export of a resume in a chosen format.
2. Service evaluates entitlement.
3. If entitled, export job is created and rendering starts or is queued.
4. If not entitled, checkout session is created.
5. Payment provider redirects or processes payment.
6. Webhook or verified return updates subscription state.
7. Entitlements are activated.
8. User retries export or auto-resumes if product supports that behavior.
9. Artifact is stored securely and returned through signed retrieval path.

### Functional Requirements

- Entitlement evaluation must be server-authoritative.
- Export requests must not trust client-provided plan or price data.
- Payment events must be idempotent.
- Export artifact retrieval must be secure and time-bound.
- Subscription activation must propagate quickly enough for post-upgrade export continuity.
- Export responses must differentiate validation blockers, entitlement locks, queued generation, ready artifact, and recoverable generation failure so the frontend can present the correct state.
- Checkout/session creation must support return-to-export continuation without losing the initiating resume, format, or workflow context.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a user with valid entitlement requests an export  
When the request is processed  
Then an export job is created, rendered, stored, and made available through a secure retrieval path.

**AC2 — Checkout Path**  
Given a user lacks entitlement for the requested export  
When they start checkout and payment succeeds  
Then the subscription is activated and the entitlement is usable without manual intervention.

**AC6 — Post-Checkout Continuation**  
Given the user begins checkout from an export attempt  
When checkout completes successfully  
Then the backend provides enough continuation state for the frontend to resume the export flow without forcing the user to reconstruct the request context.

**AC3 — Validation And Billing Safety**  
Given the plan, price, resume state, or request payload is invalid  
When checkout or export is attempted  
Then the service rejects it safely and avoids duplicate charges or duplicate entitlements.

**AC4 — Error Handling**  
Given payment callback, entitlement activation, or export rendering partially fails  
When the issue occurs  
Then the system records the state, retries where appropriate, and exposes support-friendly diagnostics.

**AC5 — Idempotency**  
Given duplicate payment callbacks or duplicate export requests occur  
When the service receives them  
Then it preserves a correct single source of truth and avoids double-processing.

### Business Rules

- Entitlements determine formats, template access, AI quota, and analysis depth.
- Payment events must be idempotent.
- Export artifacts require retention and cleanup policy.
- Checkout success must not automatically imply export success; rendering may still fail independently.

### Validation Rules

- Verify requested format against plan and feature flags.
- Validate checkout amounts against server-side plan catalog.
- Reject stale or replayed payment callbacks.
- Reject export requests for deleted or unauthorized resumes.

### Error Handling

- Separate payment failures from export failures.
- Use webhook reconciliation for final subscription state.
- Preserve audit trails for refunds, renewals, and cancellations.
- Allow safe retry of export after a render failure when billing already succeeded earlier.
- Keep validation-blocked export responses distinct from plan-lock responses so the frontend can route the user either back to editing or into upgrade UX.

### Security Considerations

- Use signed download URLs and encrypted billing tokens or provider references.
- Never trust client-side price or plan identifiers alone.
- Store minimal payment-provider data required for reconciliation.

#### Export Block Reason Flow

The export service evaluates these checks in order:

1. **Content validation**: is the resume complete enough to export? → `content_not_ready`
2. **Premium-feature detection**: does the resume use premium features (e.g., a premium template, premium font, premium layout) while the user is on a free plan? → `premium_features_used` (the "preview premium, pay to download" gate)
3. **Plan entitlement**: does the plan allow this format? → `plan_restricted`
4. **Generation**: render the artifact → `queued` → `generating` → `ready` or `failed`

#### Relationships

```text
Plan (1) ──── (N) Subscription
Plan (1) ──── (N) Payment
User (1) ──── (N) Subscription (one active, many historical)
User (1) ──── (N) Payment
User (1) ──── (N) Export
Resume (1) ──── (N) Export
Subscription (1) ──── (1) Payment (activating payment)
```

#### After-Expiry Policy

When a pay-once Premium subscription expires:
- `Subscription.status` → `expired`
- All user content (resumes, sections, items, cover letters) is **preserved** — no data is deleted.
- Export capability reverts to free-tier rules (format and feature restrictions re-apply).
- AI credits drop to free-tier limits.
- ATS/job-match depth reverts to free-tier (summary only).
- Job tracker card limit drops to free-tier count; excess cards remain viewable but not editable.
