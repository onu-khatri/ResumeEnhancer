## [ADM-BE-001] — Role, Access Profile, And Admin User Management Services

**Module:** Admin & RBAC  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Admin Service  
**Dependency:** AUTH-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the admin service,  
I want to expose secure user, role, and access-profile management APIs with strong authorization and auditability,  
so that internal operators can manage platform access safely and consistently.

### Description

This story covers the backend services required for the foundational admin/RBAC surface. The service must return user summaries, role definitions, access-profile definitions, and allow authorized assignment changes. It must protect against privilege mistakes, enforce operator authorization, and record sensitive changes in an auditable way.

### Scope

**Included In Scope**

- Admin user summary retrieval.
- Role retrieval.
- Access-profile retrieval.
- User role/access assignment changes.
- Authorization and audit enforcement for admin actions.

**Out Of Scope**

- Finance/reporting operations.
- Content moderation tooling.
- Feature-flag management.

### Preconditions

- Role and access model exists, defining roles, access profiles, and how they map to users so assignments have a concrete schema to validate against.
- Admin authorization rules exist, establishing which operators may view user data and which may perform assignment mutations.
- Audit logging infrastructure exists so every sensitive access change can be recorded with before/after state.

### Detailed Workflow

1. Authorized operator requests admin user or access data.
2. Service validates admin permission scope.
3. Service returns allowed summary and definition payloads.
4. Operator submits a role/access assignment change.
5. Service validates the change, applies it, and records an audit trail.

### Functional Requirements

- Admin APIs must be isolated from end-user account APIs.
- Role and access assignments must be validated against supported definitions.
- Service must support fine-grained authorization so not every admin can perform every action.
- Sensitive access changes must be auditable.
- Retrieval payloads should support operational UX without overexposing sensitive data.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authorized admin requests user, role, or access-profile data  
When the service processes the request  
Then it returns the requested summaries and definitions within the admin’s authorization scope.

**AC2 — Assignment Update**  
Given an authorized admin submits a valid user-role or access-profile change  
When the service processes the request  
Then it applies the change, returns updated assignment state, and writes an audit record.

**AC3 — Authorization Boundary**  
Given an operator lacks permission for a requested action  
When the request is processed  
Then the service denies the action and does not reveal protected data beyond what policy allows.

**AC4 — Validation**  
Given an invalid or unsupported assignment is submitted  
When the request is processed  
Then the service rejects it with structured validation or policy error information.

**AC5 — Error Handling**  
Given persistence or audit logging fails during a sensitive change  
When the issue occurs  
Then the system returns a safe operational failure and avoids partial or ambiguous assignment state.

### Business Rules

- Internal access must be role-based and support more than one admin-like persona, so support agents, finance operators, and super admins can be given appropriately scoped capabilities.
- Access changes are sensitive business actions and must be auditable, because a wrong assignment can expose private user data or allow destructive operations.
- The system should be designed for configurable roles/access profiles rather than hard-coded role checks only, so new roles can be added without code changes.

### Validation Rules

- Only supported roles and access profiles may be assigned; the service must reject references to unknown or deactivated definitions.
- Assignment changes must obey policy constraints such as protected system roles, preventing removal of the last super admin or assignment of incompatible profiles.
- Retrieval queries must respect admin visibility scope, so an operator only sees users and roles within their own boundary.

### Error Handling

- Distinguish permission denial, validation failure, not-found, and transient service issues so each is handled and communicated differently.
- Prevent partial assignment application when audit or persistence requirements fail, avoiding a state where access changed but no audit record exists.
- Return frontend-mappable policy errors for blocked operations so the admin UI can explain why an action was refused.

### Security Considerations

- Enforce strict admin authorization boundaries, treating every mutation as a potentially privileged operation that must be re-checked at the server.
- Audit all sensitive access changes, including the acting admin, the target user, and before/after assignment state.
- Minimize sensitive data exposure in admin summary payloads, avoiding full identity details where a summary identifier is enough for operational use.

### Analytics / Tracking

- `admin_user_list_requested`
- `admin_role_assignment_updated`
- `admin_policy_denied`

### API Dependencies

- `GET /admin/users`
- `GET /admin/roles`
- `GET /admin/access-profiles`
- `PATCH /admin/users/{id}/roles`

### Data Model

Admin/RBAC rests on a small, explicit set of entities that separate identity (`User`) from access control (`Role`, `AccessProfile`, `UserRole`). This separation lets operators assign and revoke privileges without editing user identity records, and keeps every sensitive assignment auditable.

#### User

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable user identifier. |
| `email` | string | Login/contact email. |
| `displayName` | string | Human-readable name. |
| `status` | enum | Account state such as `active`, `suspended`, or `deleted`. |
| `createdAt` | datetime | Account creation timestamp. |

#### Role

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable role identifier. |
| `name` | string | Unique role name such as `super_admin` or `support_agent`. |
| `description` | string | Human-readable role description. |
| `permissions` | string[] | Permission keys granted by the role. |
| `isSystem` | boolean | Whether the role is protected from casual modification. |

#### AccessProfile

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable access profile identifier. |
| `name` | string | Unique profile name. |
| `description` | string | Human-readable profile description. |
| `scopeRules` | json | Visibility/scope constraints for the profile. |

#### UserRole

| Property | Type | Description |
| --- | --- | --- |
| `userId` | string | User receiving the assignment. |
| `roleId` | string | Role being assigned. |
| `accessProfileId` | string | Access profile linked to the assignment. |
| `assignedAt` | datetime | When the assignment was created. |

#### AuditLog

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable audit entry identifier. |
| `actorId` | string | Admin who performed the change. |
| `action` | enum | `role_assigned`, `role_revoked`, etc. |
| `targetUserId` | string | User whose access changed. |
| `before` | json | Pre-change assignment state. |
| `after` | json | Post-change assignment state. |
| `timestamp` | datetime | When the action occurred. |

#### Example JSON

```json
{
  "userId": "usr_22",
  "roles": ["support_agent"],
  "accessProfiles": ["support_limited"]
}
```

#### Relationships

```text
User * ─── * Role                  (via UserRole assignment)
UserRole * ─── 1 AccessProfile     (scoped visibility)
User 1 ─── * AuditLog              (access changes audited)
```

#### Business Notes

- `Role` carries permission keys while `AccessProfile` carries data-visibility scope; together they enable fine-grained but understandable access control.
- `isSystem` protects foundational roles from accidental removal or reassignment.
- Every assignment mutation must produce an `AuditLog` entry capturing before/after state.
