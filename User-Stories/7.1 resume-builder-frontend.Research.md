# Research — Section-Based Resume Builder With Live Preview

## Why This Story Is Core

Across all selected competitor research, the resume builder is the real product. Templates, AI, ATS checks, and pricing all matter, but the builder is the place where user value is actually created. A weak builder requirement will cause downstream confusion in export, AI, validation, and monetization stories.

## Competitive Interpretation

### Novorésumé Signals

- The product presents itself as an app-like editor rather than a static form.
- Live preview and drag-and-drop messaging imply a highly interactive, stateful frontend.
- Content/style separation is proven by the "template switching without content loss" help documentation.
- A reusable "My Content" library (content separated from design) makes duplication and tailoring effortless — user reviews confirm this as a key premium and retention feature.
- "My Documents" with Views and Tags confirms that document organization (beyond just editing) is a first-class concern.

### Resume Now Signals

- The guided section-by-section flow (choose template → answer questions) suggests builder UX should help users progress even if they are not confident writers.
- Save, edit later, and formatting controls imply a persisted document workspace, not a one-time wizard.
- Proofreading and improvement loops suggest the builder is the hub for other tools.

## Product Interpretation

- The builder should be section-first, not raw document-first.
- Preview and formatting controls are central value, not nice-to-have.
- Save-state clarity matters because resume writing is iterative and interruption-prone.
- The builder must unify content editing, validation, and downstream readiness.
- Content/style separation is a **foundational architecture requirement** — not just a UX preference — because template switching, theming, and customization depend on it.
- Document organization (tagging, views) should be considered in the builder ecosystem planning even if implementation is phased.

## Screen Decomposition

| Area | Purpose | Required Capabilities |
| --- | --- | --- |
| Builder Shell | keep user oriented | section nav, primary actions, status |
| Section Editor | edit structured data | forms, repeatable items, validation |
| Preview Canvas | show rendered resume | pagination, layout update, locked style hints |
| Status Layer | communicate draft state | saving, saved, failed, conflict |
| Action Layer | route into adjacent tasks | export, analysis, AI, template/theme change |

## Hidden Requirements Inferred

- Stable section schemas and versioned templates.
- Preview-rendering logic that can translate structured data into display output.
- Autosave and optimistic concurrency.
- Repeatable-item ordering model.
- Validation model that distinguishes content quality from hard blockers.
- Content/style separation enabling template switching without data loss.
- Reusable "content library" data model enabling one-click duplication/tailoring.

## Risks If Under-Specified

- Engineers may build a large generic form with no true workspace behavior.
- Preview may drift from export output if rendering contract is vague.
- Autosave may overwrite data or mislead users if state transitions are not defined.
- Reorder and visibility actions may become inconsistent between edit panel and preview.
- Without content/style separation from the start, template switching and theming become expensive to retrofit.

## Recommendation To Developers

- Treat the builder as a stateful application surface with explicit save and conflict states.
- Keep the document data model structured from the start; avoid storing only an opaque text blob.
- Ensure preview and export share the same rendering assumptions as much as feasible.
- Model content and design as separate concerns in the data layer (structured sections vs. template/theme metadata).
- Design a reusable content model that supports easy duplication — enabling the tailoring flow that user reviews value most.

## Open Questions

- Is drag-and-drop part of MVP on mobile, or only move up/down controls?
- Should version history be exposed in MVP or only stored internally?
- How much formatting customization belongs in the core builder versus a separate appearance panel?
- Should "My Content" reusable library be part of MVP, or deferred (knowing it delays the tailoring differentiation)?
- Should document Views and Tags (organization) be part of the builder domain or a separate workspace domain?
