## [CL-FE-001] — Cover Letter Builder With Resume-Aware Start Flow

**Module:** Cover Letter  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** Job Seeker, Premium Subscriber, Career Changer  
**Dependency:** CL-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a user preparing a full application package,  
I want to create and customize a cover letter using my resume data, matching templates, and optional AI assistance,  
so that I can produce a consistent and role-relevant companion document without starting from zero.

### Description

This story covers the cover-letter creation experience, which extends the platform from a resume builder into an application-package platform. Research from both selected competitors shows that cover letters are not treated as side assets; they are closely linked to resume creation, styling, and premium value. The frontend should therefore support resume-aware creation, matching template cues, optional AI-assisted drafting, editing, and preparation for export.

**Research context:** Novorésumé gates cover letters as premium-only (Basic = "No Cover Letter"; Premium = "Matching Cover Letter") and offers 16 matching cover-letter templates paired with resume templates. AI cover-letter generation pulls data from the user's resume + job description. Resume Now also positions a full cover-letter builder. The research confirms that cover letters are a natural companion product that increases application-package completeness and premium value.

### Scope

**Included In Scope**

- Cover-letter creation entry point.
- Start from scratch or from existing resume context.
- Matching template and styling relationship to resume.
- Editable cover-letter body and key sections.
- Resume-to-cover-letter prefill or context awareness.

**Out Of Scope**

- Deep expert review services.
- Shared external collaboration.
- Public cover-letter sharing links.

### Preconditions

- User is authenticated.
  The cover-letter builder is a private, account-bound workspace, so a valid session token must be present before any create or edit action is allowed. Unauthenticated users who reach the cover-letter entry point should be redirected to login with a return path back to the intended flow.
- Resume data or resume selection flow exists if resume-aware start is used.
  When the user chooses to create a cover letter from an existing resume, the system needs access to that resume's parsed content (section data, contact info, skills, experience summaries) to prefill relevant fields. A resume-picker UI must be available so the user can select which of their saved resumes to use as the source context.
- Cover-letter templates or styles are available.
  The template catalog must include cover-letter-specific designs that pair visually with resume templates. At minimum, 16 matching cover-letter templates (per the Novorésumé research baseline) should be queryable via the templates API so the user can see and select a cohesive look for their application package.
- Export path exists or is defined by entitlement logic.
  The user's ability to export the cover letter as PDF, DOCX, or plain text must be known before they invest effort in writing. If cover-letter export is premium-gated, the UI must surface that restriction early so the user understands the value proposition of upgrading.

### Detailed Workflow

1. User enters cover-letter creation from dashboard, builder, or upgrade flow.
2. User selects one of the following paths:
   - start from scratch
   - create from selected resume
   - create from resume + job description context
3. System opens cover-letter editor with template/style context.
4. User edits sections such as greeting, opening, body, and closing.
5. User optionally uses AI to draft or improve portions.
6. User previews or prepares for export as part of the application package flow.

### Functional Requirements

- The cover-letter flow must feel related to the resume flow, not like a separate unrelated product.
- Users must be able to start from resume context to avoid re-entering core information.
- The UI should make it clear that a cover letter complements the resume rather than repeats it.
- Matching visual style between resume and cover letter should be supported where product design allows.
- The editor must allow manual editing even when AI or resume-based prefill is used.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a user wants a cover letter after or alongside resume creation  
When they start the flow from an existing resume  
Then the editor opens with relevant context and allows the user to create or refine a cover letter.

**AC2 — Start Options**  
Given a user does not want to start from scratch  
When they select a resume-aware start path  
Then the UI uses resume data or context where allowed and clearly shows what was prefilled or generated.

**AC3 — Editing And Matching Style**  
Given a user is editing a cover letter  
When they choose a matching template or style relationship with their resume  
Then the UI preserves that relationship without making the cover letter impossible to customize.

**AC4 — Error Handling**  
Given prefill, AI, or template-loading steps fail  
When the failure occurs  
Then the user can still proceed with manual editing instead of losing the entire cover-letter path.

**AC5 — Responsive And Accessible Behavior**  
Given the cover-letter editor is used across device sizes  
When the user edits and previews content  
Then the interface remains usable, readable, and keyboard accessible.

### Business Rules

- A cover letter should complement, not duplicate, the resume.
  The cover letter must add narrative value — explaining motivation, connecting experience to the specific role, and expressing interest — rather than restating bullet points already listed in the resume. If resume-aware prefill is used, it should pull in contact info and key facts but leave room for the user to craft a personalized message.
- Resume-aware start should reduce work but not remove user control.
  Prefilling a cover letter from resume data is a convenience feature, not an automation that produces a finished letter. Every prefilled field must remain editable, and the UI must not imply that the prefill output is ready to send without user review and customization.
- Cover-letter access may be premium-gated depending on final plan design (Novorésumé: Basic = no cover letter; Premium = matching cover letter).
  The product's monetization model may restrict cover-letter creation and export to paid tiers. If gated, free users who encounter the feature through navigation or upsell CTAs must see a clear explanation of what they gain by upgrading, and they must retain their current context rather than being blocked outright.
- Matching style should be offered as a convenience, not a hard lock.
  When a user selects a cover-letter template that matches their resume template, the pairing should be a recommendation, not an enforced constraint. Users must be free to mix templates if they prefer, and the UI must not silently overwrite their cover-letter template choice when they change their resume template later.
- AI generation for cover letters must follow the same safety rules as resume AI: no fabrication, reviewable, quota-tracked.
  AI-drafted cover-letter text must not invent skills, job titles, or achievements that the user did not provide. Generated content must be clearly labeled as AI-assisted, must be editable before saving, and must count against the same usage quota system as resume AI to ensure fair and predictable limits.

### Validation Rules

- Required opening/closing structure rules must be defined by product policy.
- Character limits and formatting rules should support professional letter standards.
- Resume-prefill must not silently overwrite manual edits once the user has started editing.

### Error Handling

- Distinguish template-loading, prefill, and AI-related failures.
  Each failure domain must produce a distinct error state with its own recovery path. A template-load failure should let the user continue editing with a default style; a prefill failure should fall back to a blank letter with a notice that resume data could not be loaded; an AI generation failure should leave the editor intact and allow the user to retry or proceed manually without losing unsaved text.
- Preserve draft edits during transient issues.
  If a network interruption occurs while the user is typing or has unsaved changes, the UI must retain the in-progress draft content. An autosave mechanism or local-storage buffer should protect against data loss, and any error overlay or modal must not discard the user's current work when dismissed.
- Allow fallback to manual letter editing if resume-context features fail.
  The cover-letter creation path must never become fully blocked because a dependent feature (resume data fetch, template query, AI service) is unavailable. The user must always have a clear path to start or continue a manual letter, even if enhanced features are temporarily degraded.
- When the cover-letter export endpoint returns an error, surface the specific export-format failure rather than a generic message.
  A PDF generation failure and a DOCX rendering failure may have different causes and resolutions, so the error message should name the affected format and suggest an alternative export option when available.

### Security Considerations

- Only use resume data from user-owned or explicitly selected documents.
- Do not expose internal resume data fields unnecessarily in cover-letter start UIs.
- Maintain the same private-document handling standard as the resume builder.

- Cover letter id
- Resume reference where applicable
- Template/style metadata
- Draft content state

### UX Notes

- Users should feel they are building an application set, not a disconnected second document.
- Resume-context start should reduce repetition and increase confidence.
- Cover-letter guidance should help users understand purpose and tone.

### UI/UX Design Requirements

- The editor should feel familiar to resume users while still respecting letter-writing structure.
- Visual hierarchy should help users see:
  - which resume the letter is connected to
  - which template/style is active
  - where the letter body begins and ends
- Matching-style affordances should feel premium and cohesive.

### React UI Implementation Notes

- Reuse as much editor-shell and save-state patterning as possible from the resume builder without forcing the cover-letter UI into an unnatural section model.
- Keep resume-context start logic separate from pure editor rendering so users can recover if prefill fails.

### Layout And Responsive Requirements

- Desktop:
  - support editor and preview or structured guidance side by side where useful
- Tablet:
  - allow a simplified split or toggle view
- Mobile:
  - prioritize focused editing with optional preview mode

### Visual And Interaction Requirements

- The cover-letter editor should feel slightly more narrative and letter-oriented than the resume builder.
- Resume-to-cover-letter relationship should be visible but not visually dominant.
- AI and prefill interactions should be clearly labeled so users know what content came from where.

### Definition Of Ready For Engineering

- Cover-letter structure model is approved.
- Resume-aware start rules are approved.
- Template/style relationship is approved.

### Definition of Done

- Users can create, edit, and continue cover letters with or without resume context.
- Matching style and fallback behaviors are implemented.
- Responsive and accessible editor behavior is verified.
