## [SAFE-BE-001] — Moderation Case Retrieval And Abuse Review Services

**Module:** Moderation & Abuse Prevention  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Trust & Safety Service  
**Dependency:** OBS-BE-001, ADM-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the trust and safety service,  
I want to provide authorized internal retrieval and controlled status management for moderation and abuse-review cases,  
so that operators can investigate suspicious or policy-sensitive activity safely and consistently.

### Description

This story covers backend support for internal moderation and abuse-review operations. The service must expose case lists, category/severity/status metadata, and allowed state transitions where supported. It should support review of AI-related, upload-related, account-related, or billing-related abuse signals without exposing more data than needed.

### Scope

**Included In Scope**

- Moderation case retrieval.
- Filtering by supported case metadata.
- Controlled case status updates where approved.
- Authorization and audit for trust/safety review actions.

**Out Of Scope**

- Automated abuse-detection algorithms.
- External reporting intake.
- Content moderation provider orchestration details.

### Preconditions

- Moderation/abuse case model exists, capturing category, severity, status, and minimal target metadata for review.
- Trust/safety authorization model exists so access to these sensitive records is more restricted than ordinary admin data.
- Case-state lifecycle is approved, defining the valid transitions between open, under-review, resolved, and dismissed states.

### Detailed Workflow

1. Authorized operator requests moderation case list or case detail.
2. Service validates trust/safety scope.
3. Service returns supported case data and current status.
4. Operator submits a permitted status change if allowed.
5. Service validates, applies, and audits the change.

### Functional Requirements

- The service must support explicit case categories and severity metadata.
- Case retrieval must be filterable by supported operational dimensions.
- Status transitions must be controlled and policy-aware.
- Trust/safety views must minimize exposed PII and sensitive content while still supporting review.
- Access to moderation data may be more restricted than general admin data.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authorized trust/safety operator requests moderation cases  
When the service processes the request  
Then it returns approved case data within the operator’s scope.

**AC2 — Filtering**  
Given supported category or status filters are used  
When the request is processed  
Then the service returns matching cases predictably and efficiently.

**AC3 — Controlled Status Update**  
Given an authorized operator submits a permitted case-state transition  
When the service processes the request  
Then it applies the change and records an audit event.

**AC4 — Authorization And Validation**  
Given an unauthorized operator or invalid state transition is submitted  
When the request is processed  
Then the service rejects the action safely and preserves current case truth.

### Business Rules

- Moderation and abuse-review operations require stronger access control than normal product administration in many cases, because case data can include policy-sensitive content and personal signals.
- Case-state transitions should remain policy-driven and auditable, ensuring every resolution or dismissal follows an approved lifecycle and is traceable.
- Review payloads should be intentionally scoped to what the operator needs, so raw uploads or full user details are not returned to every reviewer.

### Validation Rules

- Only supported categories, severities, and state transitions may be used; the service must reject anything outside the approved case taxonomy.
- Operator role/scope must be enforced so reviewers can only see and act on cases within their assigned categories.
- Unknown case ids or unsupported transitions must be rejected with structured errors rather than silently ignored.

### Error Handling

- Distinguish authorization, invalid filter, invalid transition, and persistence failures so each class maps to a distinct frontend state.
- Prevent ambiguous case-state changes when audit or persistence steps fail, so a case never ends up in an untracked state.
- Return stable frontend-mappable policy errors so operators understand exactly why an update was refused.

### Security Considerations

- Trust/safety case data is sensitive and must be tightly scoped, with stronger gating than general admin data.
- Case retrieval and mutation may itself require audit logging, capturing who viewed or changed a case for accountability.
- Avoid exposing unnecessary raw content or PII in internal responses, preferring curated summaries over full source signals.

### Analytics / Tracking

- `moderation_cases_requested`
- `moderation_case_state_changed`
- `moderation_access_denied`

### API Dependencies

- `GET /admin/moderation/cases`
- `PATCH /admin/moderation/cases/{id}`

### Data Model

Moderation operations center on a `ModerationCase` that packages an abuse or policy flag with category, severity, and workflow status. The model intentionally minimizes stored raw content, keeping just enough context for operators to review decisions safely.

#### ModerationCase

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable case identifier. |
| `category` | enum | Flag type such as `ai_policy`, `signup`, `upload`, or `billing`. |
| `severity` | enum | `low`, `medium`, `high`, `critical`. |
| `status` | enum | `open`, `under_review`, `resolved`, `dismissed`. |
| `targetType` | string | Kind of entity flagged (`user`, `file`, `generation`, etc.). |
| `targetId` | string | Identifier of the flagged entity. |
| `summary` | string | Curated, PII-minimized description for review. |
| `createdAt` | datetime | When the case was created. |
| `updatedAt` | datetime | Last status/state update timestamp. |

#### AuditLog

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable audit entry identifier. |
| `actorId` | string | Trust/safety operator who acted. |
| `action` | enum | `case_viewed`, `status_changed`, etc. |
| `caseId` | string | Related moderation case. |
| `before` | json | Pre-change case state. |
| `after` | json | Post-change case state. |
| `timestamp` | datetime | When the action occurred. |

#### Role

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable role identifier. |
| `name` | string | Role name such as `trust_safety_operator`. |
| `permissions` | string[] | Permission keys for moderation actions. |

#### AccessProfile

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable access profile identifier. |
| `name` | string | Profile name. |
| `scopeRules` | json | Which case categories/severities the operator may view. |

#### Example JSON

```json
{
  "id": "mod_123",
  "category": "ai_policy",
  "severity": "medium",
  "status": "open",
  "targetType": "generation"
}
```

#### Relationships

```text
ModerationCase 1 ─── * AuditLog                 (review actions audited)
Role * ─── * AccessProfile                      (operator scope)
ModerationCase * ─── * Role/AccessProfile       (scoped visibility)
```

#### Business Notes

- `ModerationCase` is the single source of truth for a flag's handling state; raw signals should be summarized into `summary` rather than exposed directly.
- `Role` and `AccessProfile` gate both who may view cases and which categories they may see.
- Every status transition and case view is recorded in `AuditLog` for accountability.
