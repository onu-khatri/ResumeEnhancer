## [LANG-BE-001] — Language-Aware Document Metadata And Variant Management Services

**Module:** Builder And Workspace  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** International Job Seeker, Multilingual Professional, Product Support  
**Dependency:** RES-BE-001, COV-BE-001, DASH-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform,  
I want document records to carry supported language metadata and variant relationships,  
so that multilingual users can manage distinct application documents safely without false translation assumptions.

### Description

This story covers the backend support for multi-language document management. Public competitor guidance shows that language-specific documents are separate records, not one mutable document that auto-translates. The backend must therefore model language as a first-class document attribute, support controlled variant creation, expose supported language metadata, and preserve clear relationships between related drafts where appropriate.

### Scope

**Included In Scope**

- Supported language catalog retrieval.
- Language metadata on resume and cover-letter records.
- Duplicate/create flows for language variants.
- Variant relationship metadata for workspace and builder display.

**Out Of Scope**

- Automatic translation generation.
- Full RTL rendering pipeline if not approved.
- Linguistic quality scoring.

### Preconditions

- Supported language list is approved.
- Resume and cover-letter data models can carry metadata changes.
- Workspace/document summary APIs can expose language fields.

### Detailed Workflow

1. Client requests supported language options.
2. User creates a new document or duplicates an existing one into a supported language.
3. Backend validates language support and ownership of any source document.
4. Service creates a new document record with the chosen language metadata.
5. Workspace and builder requests return language and variant metadata for display.

### Functional Requirements

- The service must expose an explicit supported-language catalog.
- Every language-aware document must store a normalized language code.
- Variant creation must create a distinct document record, not mutate the source document language in place unless that behavior is separately approved.
- Related-language metadata should be queryable for workspace and builder use.
- The service must not imply automatic translation if only metadata/structure duplication occurs.

### Acceptance Criteria

**AC1 — Supported Language Catalog**  
Given a client requests supported languages  
When the request succeeds  
Then the service returns the allowed language codes and display names for document creation.

**AC2 — Variant Creation**  
Given a user owns an existing document  
When they duplicate it into another supported language  
Then the service creates a new document with the selected language metadata and distinct identity.

**AC3 — Summary Exposure**  
Given a user requests workspace or document detail data  
When language-aware documents exist  
Then the response includes language metadata suitable for clear UI display.

**AC4 — Unsupported Language Rejection**  
Given a user requests an unsupported language  
When the create or duplicate action is submitted  
Then the service rejects it with a clear validation response.

**AC5 — Ownership Safety**  
Given a user attempts variant creation from a document they do not own  
When the request is processed  
Then the service must reject the operation without exposing the source record.

### Business Rules

- Language is part of document identity.
- Variant relationships are informative and organizational; they do not imply sync.
- Supported languages must be explicit and product-approved.

### Validation Rules

- Language code must match the supported catalog.
- Source-document duplication must pass ownership checks.
- Variant relationship references must not create invalid cycles or broken links.

### Error Handling

- Return stable validation errors for unsupported languages.
- If variant creation fails after partial persistence begins, rollback or mark the operation safely to avoid orphaned broken drafts.
- Separate ownership denial from generic not-found behavior according to security policy.

### Security Considerations

- Language metadata must not weaken document ownership or privacy rules.
- Locale/resource responses should be safe for authenticated and/or public use depending on product design.

### Analytics / Tracking

- `language_catalog_requested`
- `language_variant_created`
- `language_variant_rejected`

### API Dependencies

- `GET /localization/languages`
- `POST /documents`
- `POST /documents/{id}/duplicate`
- `GET /documents/{id}`
- `GET /workspace/documents`

### Data Requirements

- Document id
- Source document id if duplicated
- Language code
- Language display metadata
- Variant family or relationship identifiers

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### SupportedLanguage

The product-approved catalog of supported document languages. This is a controlled list; adding a language is a product decision, not a user action.

| Property | Type | Description |
| --- | --- | --- |
| `code` | string (ISO 639-1) | `en`, `de`, `fr`, `es`, `da`, etc. |
| `label` | string | Display name: "English," "German," "French" |
| `isRtl` | boolean | Whether this language uses right-to-left text. If the product does not yet support RTL, RTL languages are listed but marked `isSupported: false`. |
| `isSupported` | boolean | Whether document creation is allowed in this language. Allows the catalog to show aspirational languages without enabling broken experiences. |
| `sortOrder` | integer | Display order in the language selector |

#### DocumentLanguageMetadata

Attached to each document (resume or cover letter) as part of the document record. The `Resume` entity defined in the builder domain carries `languageCode` as a top-level field. This model expands on what that field implies.

| Field on Document | Type | Description |
| --- | --- | --- |
| `languageCode` | string (ISO 639-1) | Must match a code in `SupportedLanguage` where `isSupported = true` |
| `sectionLabels` | json | Override map for section headings: `{ "experience": "Berufserfahrung", "education": "Ausbildung" }`. Populated with product defaults at creation time; optionally user-editable (Novorésumé pattern). |
| `sourceDocumentId` | string (uuid) | If this document was created by duplicating another document for a different language, stores the source. Null for original documents. |
| `variantFamilyId` | string (uuid) | Groups related language variants. All variants created from the same source share a family ID. Simplifies workspace filtering. Null for standalone documents. |

```json

  },
  "de": {

    "summary": "Berufliches Profil",
    "experience": "Berufserfahrung",
    "education": "Ausbildung",
```

When a document is created with a given `languageCode`, the default labels are applied. Users may override individual labels (Novorésumé allows manual label translation in the builder).

#### Variant Creation Flow

```text
User has resume in English (res_123, languageCode = "en")
  → clicks "Create Spanish Version"
  → POST /documents { sourceDocumentId: "res_123", languageCode: "es" }
  → Backend:
    1. Validates ownership of res_123
    2. Validates "es" is in SupportedLanguage with isSupported = true
    3. Duplicates content (sections, items), assigns new document ID (res_456)
    4. Sets res_456.languageCode = "es", res_456.sourceDocumentId = "res_123"
    5. Assigns variantFamilyId (same for both, or creates new family if source has none)
    6. Applies Spanish section labels from localization catalog
    7. Returns new document
```

#### Document Capacity And Multi-Language

Users with Premium get a document capacity (e.g., 72–144 docs). Each language variant consumes one slot. A user with English, Spanish, and German variants of one resume uses 3 slots. The workspace should surface usage clearly.

#### Explicit Non-Behaviors (From Competitor Research)

- Documents in different languages **do not sync** — editing the English version does not update the Spanish version.
- Changing the `languageCode` of an existing document is allowed only if the document has no content (empty draft), or via explicit duplication, to prevent inconsistency between content language and label language.
- Machine translation is not provided or implied. Users write content in the target language.

### Technical Notes

- Prefer normalized language codes and explicit labels over free-text language names.
- Keep variant relationships simple enough for workspace display without forcing a complex graph model.
- Reuse existing document-duplication flows where possible.

### Definition Of Ready For Engineering

- Supported language list and codes are approved.
- Duplicate-versus-create behavior is agreed.
- Workspace summary contract can expose language metadata.

### Definition of Done

- Supported language metadata is exposed.
- Distinct language variants can be created safely.
- Workspace and builder consumers can render language identity from backend truth.
