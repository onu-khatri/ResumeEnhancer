# Research — Review Summary Aggregation And Read-Only Share Link Services

## Research Basis

While the selected competitors do not publicly expose the exact same share-link model, the research strongly supports a backend review layer that aggregates readiness signals before export and a controlled handoff mechanism if the product wants safe external viewing.

## Backend Interpretation

- A review-summary endpoint can unify validation and analysis outputs into one contract — Resume Now's pricing page lists ATS check and resume-check as separate features, implying multiple quality signals. On the backend, these should be aggregated into a single review-summary endpoint so the frontend never stitches together disparate quality APIs. This also allows the service to normalize signal severity (blocker vs. warning) consistently.
- Share links require a separate external projection and strong revocation controls — neither Novorésumé nor Resume Now expose public share links, so there is no direct competitor precedent to follow. This means we must design the external projection carefully: it should be a stripped-down, read-only view that excludes all internal metadata, and revocation must be immediate and auditable since we are inventing a capability competitors haven't shipped.
- This should remain a controlled handoff feature, not a collaboration system — the backend must not introduce comment storage, annotation endpoints, or multi-user access models. Competitor analysis shows resume builders are single-user tools, and expanding into collaboration would require a fundamentally different data model and permission system.

## Risks If Under-Specified

- Frontend stitches review state from too many endpoints inconsistently — if there is no aggregation layer, the frontend must call validation, ATS analysis, and export readiness APIs separately, assemble the results, and decide what counts as a blocker versus a warning. Resume Now's bundled proofread/check experience suggests users expect one coherent result, not a patchwork of individual checks.
- Shared links may expose too much information or ambiguous version state — without a dedicated external projection, there is a risk that the regular document API is reused for sharing, leaking owner metadata, editing controls, or internal status flags. Additionally, without version binding, a share link may show live content that changes after the user intended to share a specific version.
- Teams may accidentally drift into collaboration tooling complexity — if the share-link endpoint is too flexible, developers may extend it into a general-purpose document access API that grows comment threads, multi-user permissions, and real-time presence. The backend API design must explicitly constrain itself to read-only handoff to prevent this drift.

## Recommended Scope Interpretation

- Provide review aggregation plus explicit read-only share-link management — the backend should focus on two clear services: a review-summary endpoint that normalizes quality signals into one contract, and a share-link CRUD with strong ownership checks and an external projection. Resume Now's consolidated proofread/check flow supports the review aggregation need, while the share-link feature fills a gap competitors haven't addressed.
- Defer comments, annotations, and recruiter workflows — no competitor evidence supports these features in a resume-builder context, and they would require separate data models, notification systems, and permission schemes. Keeping the backend focused on review + read-only sharing ensures the codebase doesn't accumulate infrastructure debt for unused collaboration features.
