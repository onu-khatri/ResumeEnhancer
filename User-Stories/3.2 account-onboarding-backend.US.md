## [AUTH-BE-001] — Account Registration And Session Bootstrap

**Module:** Authentication & Onboarding  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Authentication Service  
**Dependency:** None  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the authentication service,  
I want to register users, issue sessions, assign default entitlements, and initialize starter bootstrap data,  
so that new users can securely begin creating resumes immediately after signup.

### Description

This story covers the server-side orchestration behind first-time registration. It is not only an insert into a `User` table. The service must validate and normalize user input, store legal consent evidence, create secure credentials, issue an authenticated session, assign a default plan or entitlement set, queue verification email, and return enough structured data for the frontend to route the user into the correct first workspace state.

### Scope

**Included In Scope**

- Email/password registration.
- Email normalization and uniqueness checks.
- Password hashing.
- Legal and marketing consent persistence.
- Session creation.
- Default plan assignment.
- Bootstrap routing response.
- Verification email enqueue.
- Audit logging for security-sensitive actions.

**Out Of Scope**

- Social login identity creation.
- MFA enrollment.
- Team or enterprise account provisioning.
- Billing checkout during signup.

### Preconditions

- Database is available. The core account, identity, consent, and session writes rely on a transactional store so a failed step cannot leave a partial account.
- Email infrastructure or job queue is available. Verification and welcome emails are dispatched asynchronously, so a queue or broker must accept messages without blocking the synchronous registration path.
- Starter template configuration exists. The bootstrap route may reference a selected or default template, so starter assets must already be provisioned and published.
- Default plan configuration exists. A default free/starter plan and its capability set must be defined so every new account receives a deterministic entitlement baseline.
- Session signing keys or cookie secrets are active. Session issuance requires valid signing material, and missing or expired keys would leave users unable to establish a session after signup.
- Rate limiting and abuse protection are enabled. Registration is a public abuse target, so throttling and bot protections must be active before traffic arrives.

### Functional Workflow

1. Receive registration request with identity fields, consent flags, and source metadata.
2. Validate schema and apply throttling checks.
3. Normalize email and trim supported text fields.
4. Check for existing account conflicts.
5. Hash password using approved algorithm.
6. Persist user, auth identity, consent record, preferences, and default plan assignment.
7. Create authenticated session.
8. Queue verification email and welcome side effects.
9. Return a structured bootstrap payload including next route and entitlement summary.

### Functional Requirements

- Registration must be idempotent enough to avoid duplicate account creation under retry scenarios.
- Consent version IDs must be resolved server-side, not trusted from the client.
- The API must support source attribution so post-signup continuation remains accurate.
- Session issuance must happen in the same user journey as registration, unless policy intentionally requires a second login.
- The response must be compact but sufficient for frontend route selection and banner decisions.
- The bootstrap response must preserve the triggering context from homepage, pricing, template-selection, or premium-lock entry paths.
- The bootstrap response must support frontend partial-success handling by distinguishing:
  - account created and session active
  - account created but verification email queue delayed
  - account created but bootstrap continuation degraded
- The response must expose enough state for the frontend to decide whether to show a verification reminder, template continuation, or safe default workspace route.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid registration request  
When the service processes it  
Then it creates the user, stores consent metadata, creates a session, assigns the default plan, queues verification email, and returns bootstrap payload including the correct continuation route for the original source context.

**AC2 — Validation**  
Given the email is malformed, already claimed, or required consent is absent  
When the request is processed  
Then the service rejects the request with structured validation or conflict errors and does not create partial data.

**AC3 — Partial Side-Effect Failure**  
Given user creation and session creation succeed but email dispatch enqueue fails  
When the workflow completes  
Then the account remains usable, the failure is logged, and a resend path remains available.

**AC4 — Concurrency And Retry Safety**  
Given the client retries the same request due to network uncertainty  
When the service receives duplicates close together  
Then it avoids creating duplicate accounts and returns a consistent result or safe conflict response.

**AC5 — Security And Abuse Protection**  
Given repeated suspicious signup attempts occur  
When thresholds are exceeded  
Then the service applies throttling or abuse controls and records an auditable event.

### Business Rules

- User email must be unique per normalized email within the applicable account scope. Uniqueness is enforced on the normalized (trimmed/lowercased) value so casing or trailing-space variants cannot create duplicate accounts.
- Consent version and timestamp must be stored. Legal acceptance must reference the exact document version the user saw, so compliance can be demonstrated even after terms change.
- Email verification readiness must exist even if hard enforcement is deferred. The system must be able to verify emails and report verification state from day one, even if product policy does not block unverified accounts initially.
- Free or starter entitlement is assigned by default unless invite or campaign logic overrides it. The default assignment guarantees every new account has a usable capability baseline without extra configuration.
- Marketing consent must remain separate from legal acceptance. Declining marketing must never be conflated with rejecting required legal terms, and each must be stored independently.
- Verification email failure must not roll back successful account creation. A failed email dispatch must leave a working account plus a resend path, rather than leaving the user in a limbo state.

### Validation Rules

- Enforce normalized email uniqueness. Normalize first (trim, lowercase), then check for conflicts, returning a structured conflict rather than a raw database error.
- Enforce password policy server-side. Minimum length, complexity, and breach-list checks must run server-side because client-side rules alone are trivially bypassed.
- Reject malformed or unsupported source identifiers. Only known acquisition sources are accepted so continuation routing stays accurate and untrusted values cannot inject bad route data.
- Reject missing legal consent. Required terms and privacy acceptance must be present and true; optional marketing consent may be absent or false.
- Reject empty-after-trim names. Names that become empty after trimming must fail with field-scoped messages so the account is not created with unusable identity data.

### Error Handling

- Return stable machine-readable error codes. Fixed, documented codes let the frontend map each failure to a specific recovery path without string matching.
- Avoid partial record duplication. Idempotency keys or unique constraints must ensure a retried request does not create a second account or duplicate consent/session rows.
- Make email send and analytics side effects retryable. Side effects that fail must be queued for retry or logged, never silently dropped, so eventual delivery and tracking are preserved.
- If session creation fails after user creation, return a recoverable flow and log a critical inconsistency event. The account must still be usable via a later login, and support must be able to diagnose the gap.
- If bootstrap route calculation fails, return a safe default app route instead of hard failure where possible. A degraded route hint is better than stranding a successfully-created user at a dead end.
- Return distinguishable operational states for:
  - validation failure
  - throttling
  - duplicate identity
  - bootstrap degraded but recoverable
  - verification side-effect delayed

### Security Considerations

- Hash passwords with modern adaptive hashing. Use a current adaptive algorithm (e.g., Argon2id or bcrypt) with per-user salts and appropriate cost factors; never store or log plaintext credentials.
- Protect auth endpoints with rate limiting. Registration, login, and resend endpoints must be throttled per IP and per identifier to blunt credential-stuffing and enumeration attempts.
- Store session and consent changes in audit logs. Security-relevant lifecycle events must be durable and tamper-evident for support, security review, and compliance needs.
- Use secure cookie settings or equivalent token handling. Sessions must use `HttpOnly`, `Secure`, and `SameSite` attributes (or equivalent token safeguards) to resist theft and CSRF.
- Avoid account-enumeration leaks where policy requires it. Error messaging and timing should not reveal whether an email is already registered beyond what product policy permits.
- Never log raw password or full legal text payloads. Logging must capture only hashes or event metadata, never sensitive input values, to avoid secondary exposure in log systems.

#### Design Notes

- Core records (user, identity, consent, session, plan assignment) should commit within a single transaction boundary so retries never produce partial accounts.
- `AuthenticationIdentity` is separated from `User` so verification state and credentials live independently of the profile, enabling future multi-identity login.
- Consent is versioned (`versionId` resolved server-side) so legal acceptance remains provable even if the terms document changes later.
- Entitlements are resolved into an effective capability set, keeping the bootstrap response compact and letting plan changes propagate without a frontend contract change.
- Email dispatch, welcome mail, and analytics are async side effects and must never roll back successful account creation.

### Response Contract Expectations

- Response must include `sessionState`, `emailVerificationState`, `defaultPlanCode`, and `workspaceRoute` or equivalent next-step data.
- Validation errors must be field-addressable.
- Operational failures must be distinguishable from validation failures.
- Response should also support `source`, `selectedTemplateId`, `nextAction`, and optional `bannerMessages` or equivalent UX-driving metadata.
- The contract must support frontend rendering of partial-success states without requiring a second exploratory API call.
