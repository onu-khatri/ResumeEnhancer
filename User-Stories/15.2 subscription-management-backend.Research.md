# Research — Subscription State, Invoice Retrieval, And Self-Service Billing Actions

## Research Basis

Public competitor pricing, help, and terms content show that subscription and plan management continue after checkout and need clear user-facing representation. A backend service must exist to normalize billing-provider truth into safe, understandable account-state data.

## Requirement Interpretation

- Billing state must be normalized into a user-safe account view — Resume Now's terms-of-use page describes recurring billing and cancellation behavior, but those legal documents are not user-friendly summaries. The backend must translate provider-level statuses and billing events into a structured, frontend-ready contract that answers the user's key questions (plan, status, next billing date, what actions are available) without requiring the frontend to parse provider-specific codes.
- Self-service actions must be backend-approved per state — Novorésumé's help article on membership questions shows that users need to understand their options after purchase, and Resume Now's contact-us page references dashboard cancellation. The backend must be the gatekeeper: it computes which actions are valid for the current subscription state and returns that list, rather than trusting the frontend to decide.
- Invoice/receipt access is part of a mature billing-management experience — both competitors' support content implies that users should be able to access their billing history. Resume Now's terms reference billing records, and standard SaaS expectations include downloadable receipts. The backend must provide a scoped, paginated invoice endpoint that returns user-readable summaries.

## Risks If Under-Specified

- FE shows wrong or incomplete billing actions — if the backend doesn't provide an explicit `allowedActions` list, the frontend will inevitably derive action availability from status labels (e.g., "if status is active, show cancel button"). This creates a hidden dependency on billing rules that will break when new statuses are added, when plan types have different cancellation policies, or when the billing model changes.
- Users misunderstand cancellation or expiry outcomes — Resume Now's recurring-subscription model and Novorésumé's pay-once model produce fundamentally different post-cancellation behavior. Without a backend that returns explicit outcome messaging (access-until date, feature-loss summary), the frontend cannot explain the consequences accurately and users will act on incorrect assumptions.
- Support must manually interpret provider state too often — if the backend passes through raw provider statuses or error codes to the frontend, support teams become the translation layer between what the billing provider says and what the user understands. A normalization layer in the backend eliminates this recurring support cost.

## Recommended Backend Interpretation

- Return canonical plan/status/timing plus allowed actions in one stable contract — the `GET /billing/subscription` endpoint should return everything the frontend needs to render the billing management page in a single response: plan details, current status, period timing, allowed actions, and included features. Resume Now's bundled billing dashboard and Novorésumé's consolidated membership help content both suggest that users want one place to understand their billing situation, and the API should mirror that consolidation.
- Keep invoice/receipt history user-readable but safely abstracted from raw provider data — invoices should return user-facing fields (amount, currency, date, period covered, receipt link) rather than provider-specific identifiers or internal payment-gateway references. If the billing provider offers a hosted receipt page, the API should return that URL directly so the frontend can link to it without proxying the receipt content.
