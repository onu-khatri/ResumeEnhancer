## Design Token Guidance

### Typography

- Case type and status need immediate readability, so category and workflow state are legible at a glance in a dense queue.
- Severity and category labels should be distinct from the case summary so operators can triage quickly.

### Color

- Severity should be clear and semantic without overwhelming the UI, using calm severity hues rather than alert-heavy styling on every row.
- Color must be reinforced by text or icons so severity is never conveyed by color alone.

### Spacing

- Dense case lists still need good scan separation and readable detail layout, keeping rows scannable without sacrificing detail readability.
- Separate the list from the detail panel so reviewers can move between overview and detail without losing context.

## API And Entity Map

- APIs: `GET /admin/moderation/cases`, `PATCH /admin/moderation/cases/{id}`
- Entities: `ModerationCase`, `AuditLog`

## Edge Cases

- Large queue with mixed categories: the queue must remain responsive and filterable when many cases span multiple flag types.
- Operator lacks access to some case categories: restricted cases must be filtered out cleanly rather than shown as broken rows.
- Status changed elsewhere while case is open: the UI should surface a stale-state conflict rather than silently overwriting a newer status.

## Test Focus

- Severity/status clarity: verify severity and workflow state are visually unambiguous in list and detail.
- Filter usability: confirm category and status filters return the expected case subsets.
- Permission boundaries: ensure operators only see cases within their assigned scope.
- Update failure handling: verify a failed status change preserves context and does not show false success.

## Developer Notes

- Keep case payloads intentionally minimal until review patterns stabilize, exposing only what reviewers need to decide.
- Treat sensitive internal review data carefully in list and detail views, avoiding raw content or PII in summary rows.
