## [DISC-BE-001] — Public Discovery Catalog And Funnel-Metadata Services

**Module:** Public Discovery And Acquisition  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** New Visitor, Job Seeker, Growth Team  
**Dependency:** CONT-BE-001, TPLADM-BE-001  
**Source Classification:** Observed, Inferred, Recommended

### User Story

As the platform,  
I want public-safe catalogs for templates, examples, and discovery categories,  
so that acquisition pages can load fast, stay consistent with product truth, and route visitors into meaningful entry flows.

### Description

This story covers backend support for public discovery surfaces. The service must provide published-only, public-safe metadata for templates, examples, categories, ATS-related labels, and continuation targets. It should separate internal inventory truth from public presentation truth, because acquisition surfaces need stable contracts without leaking draft or internal operational data.

### Scope

**Included In Scope**

- Published public template catalog.
- Published public example catalog.
- Category and filter metadata.
- Public-safe CTA/continuation metadata.

**Out Of Scope**

- CMS authoring backend.
- Full article/content rendering engine.
- Personalized recommendation logic.

### Preconditions

- Public/published asset states are modeled. Every template and example must carry an explicit publication state (draft, published, withdrawn) so the public projection can reliably filter to approved assets only.
- Template/content administration metadata exists. The admin-side inventory must already hold the titles, summaries, categories, and thumbnails that the public catalog projects from, so discovery does not maintain a parallel content source.
- Funnel continuation targets are defined. Onboarding and start-flow entry points must be agreed before the catalog goes live, because each asset embeds a CTA that routes visitors into those specific flows.

### Detailed Workflow

1. Public page requests discovery catalog or category slice.
2. Service returns published assets and public-safe metadata only.
3. Client filters or routes by category, ATS label, role, or document type.
4. Client uses returned continuation metadata to route the visitor into signup or start flow.

### Functional Requirements

- Public catalog endpoints must return only published assets approved for public discovery.
- Response payloads must be optimized for browsing, not internal editing.
- Category/filter metadata must stay consistent with the assets returned.
- CTA/continuation fields must support downstream source-context preservation.
- The service should support performant category slicing without requiring the frontend to download the entire universe unnecessarily.

### Acceptance Criteria

**AC1 — Public-Safe Catalog**  
Given a public client requests templates or examples  
When the service responds  
Then only public-safe, published asset metadata is returned.

**AC2 — Category Consistency**  
Given assets have category or ATS labels  
When discovery data is requested  
Then filter/category metadata aligns with actual public assets.

**AC3 — Continuation Metadata**  
Given a public asset can lead to signup or product entry  
When the frontend consumes catalog data  
Then the response includes the source-context metadata needed for the next step.

**AC4 — Unpublished Asset Protection**  
Given an asset is internal, draft, or withdrawn  
When public catalogs are requested  
Then that asset is not exposed.

**AC5 — Degraded Availability**  
Given one discovery subset is temporarily unavailable  
When the request partially fails  
Then the service can still return stable error/empty-state semantics without leaking internal data.

### Business Rules

- Public discovery data must be derived from approved published truth. Public endpoints should never read directly from the internal editing inventory; they project from it so draft and withdrawn assets are structurally impossible to leak.
- Public catalog labels must match product behavior closely enough to preserve trust. If a template is labeled "ATS-friendly," that claim must reflect the actual template characteristics users experience, not marketing shorthand.
- Public discovery contracts should remain stable for marketing/SEO surfaces. Changing slugs, category keys, or CTA shapes breaks campaign URLs and search rankings, so these are versioned public contracts rather than internal implementation details.

### Validation Rules

- Category slugs and filter keys must be known/approved. Unknown or stale filter values must not crash the catalog; they should degrade to an empty result or a safe fallback rather than produce an internal error.
- CTA continuation targets must map to valid product entry points. Every embedded CTA must resolve to a real onboarding or start flow, since an invalid target strands a ready-to-convert visitor.
- Public asset payloads must not include internal moderation or draft metadata. The projection must strip admin-only fields at the boundary so the shape itself enforces public safety.

### Error Handling

- Return stable empty results for valid-but-empty categories. A category that currently has zero live assets is a legitimate state and should render an empty state, not a server error.
- Return safe not-found behavior for unknown asset slugs. Unknown or withdrawn slugs should produce a presentation-safe 404-equivalent without revealing whether the asset ever existed internally.
- Keep public API errors presentation-safe and non-revealing. Public error bodies must never include stack traces, internal identifiers, or admin-only state, since they are visible to anonymous visitors and bots.

### Security Considerations

- Do not expose internal notes, unpublished states, premium operations metadata, or admin-only identifiers. The public projection is the security boundary; anything not explicitly approved for public view must be absent from the response, not merely hidden by the frontend.
- Rate-limiting and caching strategy should protect public endpoints from abuse while preserving performance. Public discovery is unauthenticated and therefore a target for scraping and abuse, so throttling and edge caching must be designed in from the start.

### Data Model

> This section describes the expected entity structure with possible properties. It is a **business-requirements-level starting point** to drive technical modeling discussions, not a final database schema. Types, relationships, and constraints should be refined during technical design.

#### PublicTemplate

A public-safe projection of a template asset approved for public discovery. It derives from internal inventory truth but exposes only presentation-safe fields, never draft or moderation metadata.

| Property | Type | Description |
| --- | --- | --- |
| `slug` | string | Stable public identifier used in campaign URLs and shareable category views; versioned carefully so old links keep resolving |
| `title` | string | Public-facing display name |
| `summary` | string | Short description shown on gallery cards |
| `categories` | string[] | Ordered list of category slugs the asset belongs to |
| `thumbnailUrl` | string | Public CDN reference to the preview image; may be temporarily absent while processing |
| `atsLabel` | string \| null | Trust label such as `ats-friendly`; absent when not applicable |
| `atsExplanation` | string \| null | Short human-readable explanation of what the ATS label means for this asset |
| `cta` | object | Embedded continuation target metadata — see PublicAssetCta |
| `publishedAt` | datetime | When the asset became publicly discoverable |

#### PublicExample

A public-safe projection of a role-based example (e.g., "Nurse resume example") surfaced for pre-signup browsing and search-funnel landing.

| Property | Type | Description |
| --- | --- | --- |
| `slug` | string | Stable public identifier |
| `title` | string | Public-facing example title |
| `summary` | string | Short description of what the example demonstrates |
| `role` | string | Target job title/role this example is relevant to |
| `categories` | string[] | Category slugs such as role, industry, or document type |
| `thumbnailUrl` | string | Public preview reference |
| `cta` | object | Embedded continuation target metadata |
| `publishedAt` | datetime | When the example became publicly discoverable |

#### DiscoveryCategory

A curated category or filter group used on discovery pages to organize templates and examples.

| Property | Type | Description |
| --- | --- | --- |
| `slug` | string | Stable filter key used in URLs and query params |
| `label` | string | User-visible category name |
| `description` | string | Optional explanatory copy shown on category landing pages |
| `assetCount` | integer | Derived count of live published assets in this category; kept consistent with actual published assets |
| `isActive` | boolean | Whether the category should currently appear on discovery surfaces |

#### PublicAssetCta

The continuation target metadata embedded in each public asset so the frontend can route a visitor into onboarding or a start flow without a second lookup. May be embedded rather than a separate table.

| Property | Type | Description |
| --- | --- | --- |
| `type` | enum | `use_template`, `start_example`, `import_resume`, `signup` |
| `target` | string | Product entry route with preserved source context (e.g., `/signup?source=template&asset=...`) |

#### Example Response Shape

```json
{
  "items": [
    {
      "slug": "modern-ats-template",
      "title": "Modern ATS Resume Template",
      "assetType": "template",
      "categories": ["ats-friendly", "modern"],
      "thumbnailUrl": "/public-assets/templates/modern-ats.jpg",
      "atsLabel": "ats-friendly",
      "atsExplanation": "Single-column layout that passes most ATS parsing checks.",
      "cta": {
        "type": "use_template",
        "target": "/signup?source=template&asset=modern-ats-template"
      }
    }
  ]
}
```

#### Relationships

```text
Template (1) ──── (N) Category (via category slugs on the asset)
Example (1) ──── (N) Category
PublicTemplate (1) ──── (1) PublicAssetCta (embedded continuation target)
PublicExample (1) ──── (1) PublicAssetCta (embedded continuation target)
```

#### Design Notes

- Public projections are derived from internal inventory truth but intentionally narrower; they must never expose draft, moderation, admin-only, or premium-operation internals.
- `slug` is the stable public identity. Slugs should be treated as a published contract and versioned carefully so old campaign URLs continue to resolve.
- Category `assetCount` must stay consistent with live published assets, either computed at projection time or kept in sync on publish/unpublish events.
- Embedding `cta` on each asset keeps a single catalog response sufficient for the frontend to route the visitor onward, preserving acquisition continuity.

### Technical Notes

- Prefer dedicated public projections rather than exposing internal entities directly.
- Public endpoints should be cache-friendly and resilient to catalog growth.

### Definition Of Ready For Engineering

### Definition of Done
