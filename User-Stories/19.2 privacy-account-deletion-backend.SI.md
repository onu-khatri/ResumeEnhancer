# Supporting Information — Privacy Request, Data Export, And Account Deletion Initiation Services

## Proposed APIs

- `GET /privacy/options`
- `POST /privacy/data-export`
- `POST /privacy/account-deletion`

## Example Privacy Options Response

```json
{
  "supportedActions": [
    "data_export",
    "account_deletion"
  ]
}
```

## Proposed Entities

- `PrivacyRequest`
- `User`
- `Subscription`
- `AuditLog`

## Suggested Technical Controls

- Request-state lifecycle
- Policy rule checks
- Re-auth requirement hooks where needed

## Edge Cases

- User requests deletion with active paid state, requiring the service to detect the active subscription, block the deletion with a structured reason referencing the subscription, and provide clear guidance through the `blockedReason` field so the frontend can show a link to the cancellation flow.
- Repeated export requests before the previous one completes should either be throttled (rate-limited) or return the existing pending request state to prevent resource waste and duplicate export jobs.
- Policy requires support/manual review where the service cannot automatically accept a privacy request and must return `requires_escalation` with a specific reason, at which point the frontend presents a support contact path rather than a dead end.

## Test Focus

- Policy-aware blocked states should be tested for each defined block reason (active subscription, pending billing, compliance hold) to confirm the correct status and `blockedReason` are returned, not a generic failure.
- Request deduplication or throttling should verify that rapid duplicate submissions return the existing request state and that rate limits are enforced without blocking legitimate first-time requests.
- User ownership and audit coverage should confirm that privacy request data is never cross-visible between users and that each state transition writes a complete audit trail entry.

## Developer Notes

- Keep privacy-request state explicit enough that support and frontend can understand it; avoid storing critical lifecycle information in free-text notes that require manual interpretation, and use structured status, blockedReason, and retentionNote fields instead.
- Avoid representing nuanced policy outcomes as simple boolean success/failure; a privacy request can be accepted, accepted-with-conditions, blocked, or escalated, and collapsing these into a single true/false flag would force the frontend to guess what happened.
