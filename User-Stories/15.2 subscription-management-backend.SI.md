# Supporting Information — Subscription State, Invoice Retrieval, And Self-Service Billing Actions

## Proposed APIs

- `GET /billing/subscription`
- `GET /billing/invoices`
- `POST /billing/cancel`

## Example Subscription Response

```json
{
  "planCode": "PREMIUM_MONTH",
  "status": "active",
  "expiresAt": "2026-09-14T00:00:00Z",
  "allowedActions": ["cancel"]
}
```

- `Subscription`

## Suggested Technical Controls

- Allowed-action computation layer
- User-scoped invoice queries
- Billing action audit logging

## Edge Cases

- Subscription pending cancellation but still active — when a user cancels with `cancelAtPeriodEnd: true`, the subscription status transitions to `pending_cancellation` but the user retains full access until `currentPeriodEnd`. The API must return both the status and the access-until date so the frontend can correctly communicate "your access ends on [date]" rather than showing the subscription as already expired.
- Provider confirms payment but local state update is delayed — if a payment webhook event is processed successfully by the billing provider but the local database update fails or is delayed, a subsequent subscription-state request could return stale data (e.g., showing `past_due` when the payment was actually received). The service must reconcile with the provider on state-read requests when inconsistency is detected, or use idempotent webhook processing to prevent drift.
- No invoice history for newly upgraded user — a user who just completed checkout will have no invoices yet (the first invoice may take minutes to hours to appear depending on the provider's billing cycle). The invoice endpoint must return an empty list rather than an error, and the response should include a flag or timestamp indicating when the first invoice is expected.

## Test Focus

- Canonical state rendering support — verify that every subscription status returned by the API includes all required fields (planCode, status, period timing, allowedActions, features), that the allowedActions list matches business rules for that status, and that the response schema is stable across plan types and billing models.
- Allowed-action correctness — test that active subscriptions return `["cancel"]`, that pending_cancellation subscriptions return an empty or reduced list (no duplicate cancel), that expired subscriptions return `["renew", "upgrade"]`, and that free-tier subscriptions return `["upgrade"]` but not `["cancel"]`. These rules must be verified per billing model.
- Cancellation state transitions — verify the full lifecycle: `active` → (cancel requested) → `pending_cancellation` → (period end passed) → `expired` or `cancelled`. Test both immediate-cancel and end-of-term-cancel policies, and confirm that the API response correctly reflects which model applies.
- Invoice ownership enforcement — verify that User A cannot retrieve User B's invoices, that unauthenticated requests are rejected, and that invoice queries are automatically scoped to the authenticated user without the client specifying a user ID parameter.

## Developer Notes

- Avoid leaking raw provider-specific status complexity directly to the frontend — billing providers often have dozens of internal status codes (e.g., Stripe's `trialing`, `incomplete`, `incomplete_expired`, `past_due`, `unpaid`). These should be mapped to a smaller set of user-facing status values (`active`, `pending_cancellation`, `cancelled`, `expired`, `past_due`) in the API layer so the frontend never needs to understand provider-specific semantics.
- Treat subscription-state endpoints as a normalization layer for user-facing truth — the backend's subscription API is not a pass-through to the billing provider; it is a translation layer that enriches provider data with internal metadata (plan features, allowed actions) and filters out sensitive details (payment method internals, provider-specific error codes). This normalization should happen in a dedicated service or middleware, not scattered across route handlers.
