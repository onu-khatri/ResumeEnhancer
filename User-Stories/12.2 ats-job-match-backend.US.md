## [ATS-BE-001] — Resume Analysis And Job Match Scoring Engine

**Module:** ATS Analysis & Job Matching  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Analysis Service  
**Dependency:** IMP-BE-001, AI-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the analysis service,  
I want to score resume quality and compare resumes to job descriptions,  
so that the platform can return actionable feedback and prioritized improvement guidance.

### Description

This story covers the backend engine for resume scoring, ATS-style checks, and job-description matching. The service must work on a stable snapshot of resume content, compute structured score categories, identify gaps or warnings, and return recommendations that the frontend can explain without pretending to replicate any competitor's proprietary algorithm.

### Scope

**Included In Scope**

- General resume analysis.
- Job-description match analysis.
- Category scoring.
- Recommendation generation.
- Snapshotting against resume version and job-description input.
- Persisted analysis history.

**Out Of Scope**

- Recruiter-side ranking of many resumes.
- ML training infrastructure.
- Multi-language support unless explicitly approved.
- Admin authoring UI for analysis rules.

### Preconditions

- Resume content is accessible in normalized form.
- Analysis rules and thresholds are configured.
- Storage exists for analysis runs and result artifacts.
- Resume version or snapshot ID can be resolved.

### Functional Workflow

1. Receive request for generic analysis or job match.
2. Validate resume readiness and optional job-description payload.
3. Build a content snapshot tied to resume version.
4. Run configured analysis rules and scoring groups.
5. If job description is provided, extract keywords and compare against resume snapshot.
6. Produce overall score, category scores, findings, and recommendations.
7. Persist analysis result and return response.

### Functional Requirements

- Scores must be reproducible against a snapshot of the input data.
- The engine must support multiple report modes with shared and mode-specific logic.
- Recommendations must be structured, not just plain-text paragraphs.
- Rule groups must be configurable over time without rewriting the entire service.
- The service must support partial or degraded outcomes when one sub-check fails but others succeed.
- Result payloads must expose report mode, resume-version snapshot, and freshness-relevant metadata so the frontend can identify stale results after later resume edits.
- Recommendation payloads must be structured enough for grouped UI rendering by severity, category, or action type.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid resume and job description  
When analysis runs  
Then the service stores and returns overall scores, category scores, missing-keyword insights, and recommendation items.

**AC2 — Validation**  
Given the resume lacks minimum content or the job description is too short  
When analysis is requested  
Then the service rejects the run with specific validation feedback.

**AC3 — Error Handling**  
Given a rule engine or dependent parser fails  
When analysis cannot fully complete  
Then the service returns partial or failed status predictably and logs diagnostics.

**AC4 — Traceability**  
Given a score is generated  
When support or QA inspects the run  
Then the system can show which rule groups contributed to the result.

**AC5 — Snapshot Integrity**  
Given the underlying resume changes after analysis started  
When the report is returned  
Then the analysis remains tied to the original snapshot and is not silently recalculated against newer content.

**AC6 — Frontend Freshness Support**  
Given a report is retrieved after the resume has since changed  
When the frontend compares current resume version to analyzed version  
Then the API contract makes that mismatch detectable without inference.

### Business Rules

- Scores are heuristics, not guarantees of hiring success.
- Rule groups must be configurable.
- Analysis results should be tied to resume version and job-description snapshot.
- The engine must not claim competitor-scoring parity.

### Validation Rules

- Require a minimum amount of resume text for meaningful scoring.
- Cap job-description size.
- Reject unsupported languages until explicitly supported.
- Reject duplicate in-flight requests when policy requires throttling or deduplication.

### Error Handling

- Support synchronous and queued analysis paths where appropriate.
- Preserve previous successful result when a rerun fails.
- Make reruns create new analysis records instead of mutating history.
- Surface degraded-subsystem outcomes clearly.
- Return stable report status or mode metadata so the frontend can distinguish completed, partial, failed, and stale-display scenarios.

### Security Considerations

- Restrict access to analysis artifacts by owner and admin/support role.
- Protect against abuse through rate limits and payload caps.
- Redact sensitive diagnostics from client-facing responses.

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### ResumeAnalysis

The top-level analysis run record. One analysis run evaluates one resume at a specific version, optionally against a job description.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique analysis run identifier |
| `userId` | string (uuid) | Owning user |
| `resumeId` | string (uuid) | Resume evaluated |
| `resumeVersion` | integer | Snapshot: resume version at analysis time. Used for stale-result detection. |
| `mode` | enum | `resume_check` (general quality/ATS) or `job_match` (against a specific job description) |
| `jobDescriptionId` | string (uuid) | Reference to JobDescription entity; null for `resume_check` mode |
| `overallScore` | integer | Aggregate score (0–100) |
| `status` | enum | `queued`, `processing`, `completed`, `partial`, `failed` |
| `contentSnapshot` | json | The structured resume content used for this analysis (immutable copy for reproducibility and audit) |
| `categoryScores` | json | Per-category sub-scores — shape depends on mode (see below) |
| `findings` | json | Array of finding objects with category, severity, message, and action |
| `recommendations` | json | Array of recommendation objects with category, priority, actionType, targetSection, and description |
| `engineVersion` | string | Version of the scoring engine used, for reproducibility and debugging |
| `createdAt` | datetime | |
| `completedAt` | datetime | |

#### CategoryScore Shape (Resume Check Mode)

```json
{
  "jobMatch": { "score": 78, "label": "Keywords & Relevance" },
  "formatStructure": { "score": 85, "label": "Format & Structure" },
  "contentQuality": { "score": 72, "label": "Content Quality" },
  "sectionOrganization": { "score": 90, "label": "Section Organization" },
  "technicalElements": { "score": 95, "label": "Technical Elements" }
}
```

#### CategoryScore Shape (Job Match Mode)

```json
{
  "hardRequirements": { "score": 80, "label": "Hard Requirements" },
  "skillsAlignment": { "score": 65, "label": "Skills Alignment" },
  "seniorityFit": { "score": 70, "label": "Seniority Fit" },
  "industryMatch": { "score": 55, "label": "Industry Match" },
  "careerTrajectory": { "score": 75, "label": "Career Trajectory" }
}
```

#### Finding Object

| Property | Type | Description |
| --- | --- | --- |
| `code` | string | Stable finding identifier (e.g., `missing_education_section`, `low_keyword_density`) |
| `category` | string | Which scoring category this finding belongs to |
| `severity` | enum | `blocker` (prevents valid export/analysis), `warning` (weakens quality), `info` (suggestion) |
| `message` | string | Human-readable description of the issue |
| `targetSectionId` | string | Which resume section the finding relates to (for UI deep-linking) |
| `action` | string | What to do: `fix_in_resume`, `address_in_cover_letter`, `consider_adding`, `verify_information` |

#### Recommendation Object

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | |
| `priority` | integer | 1 (highest) to N — sort order for display |
| `category` | string | |
| `actionType` | string | `add_section`, `improve_bullets`, `add_keywords`, `reorder_sections`, `fix_dates` |
| `targetSectionId` | string | |
| `description` | string | Concrete, actionable instruction |
| `exampleText` | string | Optional example of the improvement |

#### JobDescription

Stores the pasted job description used for job-match analysis.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | |
| `userId` | string (uuid) | Owning user |
| `rawText` | text | Full pasted text (retained for re-runs) |
| `normalizedText` | text | Cleaned/normalized version used for analysis |
| `extractedKeywords` | json | Keywords, skills, qualifications extracted by the NLP pipeline |
| `extractedRole` | string | Detected job title/role |
| `source` | string | `manual_paste`, `linkedin_url`, `indeed_url` |
| `createdAt` | datetime | |

#### Relationships

```text
User (1) ──── (N) ResumeAnalysis
Resume (1) ──── (N) ResumeAnalysis (one per version-run)
JobDescription (1) ──── (N) ResumeAnalysis (one job desc can be used across multiple runs)
ResumeAnalysis (1) ──── (N) Finding
ResumeAnalysis (1) ──── (N) Recommendation
```

#### Depth Gating (Free vs. Premium)

| Tier | Score | Category breakdown | Findings | Recommendations |
| --- | --- | --- | --- | --- |
| Free | Overall score only | Top-level category scores (no detail) | Top 3 findings only | Top 3, generic |
| Premium | Overall + detailed | Full per-category breakdown with specifics | All findings, actionable | All, prioritized, with examples |

The same analysis run produces both views — the backend filters the response depth based on the user's plan entitlement at request time.

### Definition Of Ready For Engineering

- Score category model is approved.
- Snapshot strategy is approved.
- Recommendation schema is approved.

### Definition of Done

- Scoring outputs are stable, explainable, and version-linked.
- Rule changes are configurable and testable.
- Analysis throughput, traceability, and failure modes are observable.
