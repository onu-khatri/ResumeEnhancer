## [IMP-BE-001] — Template Catalog And Resume Import Parsing Pipeline

**Module:** Templates & Import  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Template Service, Import Service  
**Dependency:** RES-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform backend,  
I want to serve template metadata and process uploaded resumes into structured draft data,  
so that users can either start from a design or convert an existing document into editable content.

### Description

This story covers two tightly related backend responsibilities: template-catalog delivery and resume-import orchestration. The template service must expose a filterable, entitlement-aware catalog. The import service must securely ingest files, scan them, parse supported formats, produce structured section output with confidence markers, and convert that output into a draft when the user confirms.

### Scope

**Included In Scope**

- Template listing and detail endpoints.
- Entitlement-aware template metadata.
- Resume upload intake.
- File scanning.
- Parse job orchestration and status reporting.
- Parse-result persistence.
- Draft creation from approved parse result.

**Out Of Scope**

- Template publishing/admin workflows.
- OCR-heavy document recovery for poor scans unless explicitly approved.
- Bulk or batch import.
- Import merge into an existing draft if not in MVP.

### Preconditions

- Template records exist.
- Secure object storage is available.
- File scan subsystem is available.
- Parser subsystem is available for configured file types.
- Resume draft creation API exists.

### Functional Workflow

1. Client requests template catalog with optional filters.
2. Template service returns active templates plus plan-lock metadata.
3. Client uploads resume file.
4. Import service stores file in quarantine or secure temporary storage.
5. Scan job validates file safety.
6. Parse job extracts text and maps content to structured sections.
7. Result is stored with warnings and confidence.
8. On user confirmation, service creates a draft resume based on parse output and selected template if applicable.

### Functional Requirements

- Template catalog must include enough metadata for gallery, preview, and entitlement behavior.
- Import must be asynchronous where processing time is unpredictable.
- Raw uploaded files must not be exposed directly to the frontend.
- Parse output must distinguish structured data from warnings and unresolved items.
- Draft creation from parse result must be explicit, traceable, and retry-safe.
- Template catalog responses must support frontend filter and card states such as category, premium lock, and preview availability.
- Import-job statuses must be explicit enough for the frontend to render phase-by-phase progress such as uploading, scanning, parsing, review-ready, and failed.
- Create-draft operations must support confirmed parse data after user review, including corrected or normalized field values where the UI allows edits before draft creation.

### Acceptance Criteria

**AC1 — Template Catalog**  
Given a template listing request  
When the service returns results  
Then each item includes category, preview asset, supported sections, publication status, and entitlement flags.

**AC2 — Import Happy Path**  
Given a supported uploaded file  
When scanning and parsing succeed  
Then a structured parse result is stored and made available for user review.

**AC3 — Validation And Security**  
Given an oversized, unsupported, password-protected, or unsafe file  
When the service inspects it  
Then the import is rejected before parsing and the reason is recorded.

**AC4 — Partial Parse**  
Given parsing extracts only part of the resume reliably  
When processing completes  
Then the service returns partial structured data with warnings and confidence levels instead of pretending the result is complete.

**AC5 — Draft Creation**  
Given a user confirms a parse result  
When the create-draft action is called  
Then the service creates a new editable resume draft and links it to the import job.

**AC6 — Reviewed Parse Continuation**  
Given the user edits parsed values in the review UI before confirming  
When the create-draft action is called  
Then the service uses the approved reviewed values rather than ignoring user corrections.

### Business Rules

- Template availability depends on plan entitlement and publication state.
- Import jobs must be isolated per user.
- Uploaded source files must have defined retention limits.
- Parse results should be immutable snapshots once review-ready.

### Validation Rules

- Enforce configured file types and size caps.
- Reject password-protected or unreadable documents unless explicitly supported.
- Normalize extracted dates, text blocks, and section types.
- Reject create-draft requests for import jobs not owned by the requesting user.

### Error Handling

- Use asynchronous job states for slower parses.
- Preserve raw parser diagnostics for support use without exposing them directly to users.
- Return stable import status values.
- Ensure failed draft creation can be retried without duplicate resumes when idempotency key is present.
- Distinguish scan failure, parse failure, and draft-creation failure so the frontend can present the correct fallback path.

### Security Considerations

- Virus scan before parse.
- Signed URL access only for raw upload storage if internal services need it.
- Delete or expire raw uploads according to retention policy.
- Enforce ownership and anti-abuse controls on import jobs.

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### Template

Defines a resume or cover-letter template. Templates are product catalog data, persisted and queryable — not static assets.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | |
| `code` | string | Stable machine-readable identifier (e.g., `tpl_modern_executive`) |
| `name` | string | Display name: "Executive", "Modern", "Minimalist" |
| `documentType` | enum | `resume`, `cover_letter` |
| `category` | enum | `modern`, `creative`, `traditional`, `simple`, `student`, `graduate`, `functional`, `hybrid`, `executive`, `tech`, `cv` |
| `isPremium` | boolean | Whether this template requires a paid plan |
| `isAtsSafe` | boolean | Whether this template follows ATS-friendly rules (single-column, standard headings, no tables/graphics) |
| `previewImageUrl` | string | Thumbnail/preview image URL for gallery and template picker |
| `supportedPages` | json | `{ min: 1, max: 10 }` — page range this template supports |
| `supportedSections` | string[] | Which section types this template supports (e.g., `["header","summary","experience","education","skills"]`) |
| `pairedCoverLetterId` | string (uuid) | Matching cover-letter template ID (for "matching set" feature); null if none |
| `defaultTheme` | json | Default theme configuration: `{ fontId, colorThemeId, backgroundId }` |
| `layoutSchemaVersion` | string | Version of the rendering engine this template targets (for compatibility checks) |
| `isActive` | boolean | Publication state; inactive templates are hidden from the catalog |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

#### Template Capability Constraints

Each template declares which sections it can render and which customization options it supports. These constraints feed into the theme/customization and builder domains:

| Constraint | Purpose |
| --- | --- |
| `supportedSections[]` | Builder shows only sections the template can render |
| `supportedPages.min/max` | Block creation/export beyond supported page count |
| `isAtsSafe` | Enforce ATS-safe customization boundaries (block creative backgrounds, rating styles, icons in ATS-safe mode) |
| `defaultTheme` | Initial appearance when a user creates a draft with this template |

#### ImportJob

Tracks the lifecycle of an uploaded resume file through scanning, parsing, and draft creation.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | |
| `userId` | string (uuid) | Owning user |
| `sourceFileName` | string | Original filename as uploaded |
| `sourceFileType` | string | Detected MIME type / extension: `pdf`, `docx`, `doc`, `rtf`, `txt` |
| `sourceFileSize` | integer | File size in bytes |
| `sourceStorageKey` | string | Reference to the quarantined file in secure object storage |
| `status` | enum | `queued`, `scanning`, `parsing`, `review_ready`, `failed`, `consumed` |
| `scanOutcome` | enum | `clean`, `flagged`, `rejected` |
| `scanDetails` | json | Scanner diagnostics (for support use, not exposed to users directly) |
| `parseResult` | json | Structured extraction: array of `{ sectionType, items[], confidence, warnings[] }` |
| `parseConfidence` | enum | `high`, `medium`, `low` — overall quality indicator for user display |
| `parseWarnings` | string[] | Non-blocking issues found: `"dates could not be normalized"`, `"image-only PDF — text extraction may be incomplete"` |
| `createdResumeId` | string (uuid) | The resume created from this import (populated when status = `consumed`) |
| `createdAt` | datetime | |
| `consumedAt` | datetime | When user confirmed and draft was created |

#### Parse Result Structure

```json
{
  "sections": [
    {
      "detectedType": "header",
      "confidence": "high",
      "items": [
        {
          "data": {
            "fullName": "John Doe",
            "email": "john@example.com",
            "phone": "+1-555-0100"
          },
          "warnings": []
        }
      ]
    },
    {
      "detectedType": "experience",
      "confidence": "medium",
      "items": [
        {
          "data": {
            "jobTitle": "Software Engineer",
            "companyName": "Acme Corp",
            "startDate": "2020-01",
            "endDate": "2024-03",
            "isCurrent": false,
            "bullets": ["Built REST APIs..."]
          },
          "warnings": ["endDate could not be verified — check the original"]
        }
      ]
    }
  ],
  "unrecognizedText": "Any text that couldn't be assigned to a section"
}
```

#### Import Status Flow

```text
upload → queued → scanning → [scan fails? → failed]
                              → [scan passes → parsing] → [parse fails? → failed]
                                                          → [parse succeeds → review_ready]
                                                                              → [user confirms → consumed]
                                                                              → [user rejects → failed]
```

#### File Acceptance Rules

| Accepted | Rejected |
| --- | --- |
| `.doc`, `.docx`, `PDF` (text-based), `RTF`, `TXT` | Password-protected PDFs, image-only PDFs (scan-based without OCR), files exceeding max size, corrupted/unreadable files, files flagged by malware/virus scan |
