## [LANG-FE-001] — Multi-Language Resume And Cover Letter Authoring Experience

**Module:** Builder And Workspace  
**Layer:** Frontend  
**Priority:** Could Have  
**Persona:** International Job Seeker, Multilingual Professional, Returning User  
**Dependency:** LANG-BE-001, RES-FE-001, COV-FE-001, DASH-FE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As a multilingual user preparing applications for different markets,  
I want to create and manage language-specific document versions with localized labels and clear separation,  
so that I can tailor resumes and cover letters without confusing one language draft with another.

### Description

This story covers the frontend experience for language-aware document creation and management. Public Novorésumé help content explicitly documents multi-language documents as separate versions that do not auto-sync across languages. That signal matters because it prevents a misleading assumption that translation is automatic. The frontend must help users create a document in a chosen language, understand that each language version is its own editable asset, and manage those versions safely in builder and workspace flows.

### Scope

**Included In Scope**

- Choose a document language during creation or duplication.
- Language-specific document labeling in workspace and editor.
- Localized section labels and helper text where supported.
- Clear management of separate language variants.

**Out Of Scope**

- Automatic translation of resume content.
- Full right-to-left support if not approved for MVP.
- Machine-translation quality tooling.

### Preconditions

- Supported language list exists.
  Product stakeholders must have approved a finite, explicit list of ISO language codes and display names that the platform will support in its initial release. This list drives the language-selection dropdown, determines which localized section labels are available, and defines the boundary of honest versus unsupported-language messaging.
- Backend supports language-specific document metadata.
  The document model must include a persisted language code field, and the API must accept and return this field in document creation, duplication, and retrieval responses. Without this backend support, the frontend cannot display language badges, filter by language, or enforce variant-creation rules.
- Product has approved initial localization coverage.
  The team must have decided which UI elements will be localized (e.g., section labels, helper text, tooltips, placeholder copy) and which will remain in the default language. Partial localization must be clearly communicated to avoid the impression that the entire product is fully translated when only builder chrome is covered.

### Detailed Workflow

1. User starts a new resume or duplicates an existing one for another market.
2. The UI asks for or displays the document language.
3. The user enters a language-specific editor where labels and defaults reflect that choice.
4. The workspace shows the language variant clearly so the user can distinguish it from other versions.
5. The user returns later and selects the correct language draft without confusion.

### Functional Requirements

- Users must be able to identify the language of each document quickly in workspace and editor.
- Language choice must be explicit at document-creation or language-variant-creation time.
- The UI must make it clear that language variants are separate drafts, not auto-synced translations.
- Section labels and selected guidance content should localize where supported.
- Unsupported languages must be handled honestly rather than partially implied.

### Acceptance Criteria

**AC1 — Language Selection**  
Given a user creates or duplicates a document  
When language selection is supported  
Then they can choose a supported language and see it applied to the new draft.

**AC2 — Variant Clarity**  
Given a user has multiple drafts for different languages  
When they view workspace or document headers  
Then each draft shows its language clearly enough to avoid accidental editing of the wrong version.

**AC3 — Localized Builder Chrome**  
Given a document is in a supported language  
When the user opens the builder  
Then section labels and supported helper UI reflect that language setting.

**AC4 — Separation Of Drafts**  
Given a user edits one language version  
When they save changes  
Then the UI does not imply that another language version changed automatically.

**AC5 — Unsupported-Language Handling**  
Given a user requests a not-yet-supported language or unsupported behavior such as RTL  
When the system cannot fulfill it  
Then the UI communicates the limitation clearly.

### Business Rules

- Each language version is its own managed document.
  A resume authored in English and its French variant are two independent documents with their own IDs, edit histories, and export states. The platform must never auto-sync content between language versions, even if they were created via duplication. This rule prevents the dangerous user assumption that editing one language draft will automatically update another.
- Language support must be explicit and finite in MVP.
  The initial release must support a curated, tested set of languages rather than an open-ended list that implies partial or untested support. Adding a new language requires backend metadata updates, localization coverage, and QA validation, so the frontend must not offer a free-text language field that creates false expectations.
- Localization of interface chrome does not imply automatic content translation.
  Displaying section labels and helper text in the selected language is a chrome-level convenience, not a content-translation feature. The UI must make this distinction visible so that users do not expect the platform to translate their bullet points, summaries, or job descriptions when they switch document language.

### Validation Rules

- Only supported languages may be selected.
- Language switching must preserve unsaved-change safeguards.
- Localized labels must map to supported section vocabulary only.

### Error Handling

- If localized metadata fails to load, preserve document editing with a safe fallback language or error notice as approved.
  When the localization resource bundle for the selected language cannot be fetched (e.g., CDN failure, missing translation file), the builder must fall back to the default language labels rather than crashing or rendering empty section headers. An unobtrusive notice should inform the user that localized labels are temporarily unavailable, but content editing must continue uninterrupted.
- If creating a language variant fails, do not leave the user uncertain whether a new document was created.
  A failed variant-creation request (timeout, server error, quota limit) must result in a clear error message that confirms no document was created and that the user's original draft remains untouched. The UI must never show a phantom document card that disappears on refresh, as this erodes trust in the workspace.
- If the user selects an unsupported language code (e.g., via a stale or manipulated client state), the system must reject it gracefully.
  The language-selection control should only offer approved language codes, but if an unsupported code arrives at the frontend, the UI must treat it as an error state and redirect the user to a supported default rather than rendering a broken editor with missing or garbled labels.

### Security Considerations

- Language variants follow the same ownership and privacy rules as all other documents.
- Locale-based routing must not bypass authorization checks.

### Data Requirements

- Document type

### UX Notes

- The UI should reduce fear of overwriting the wrong language version.
- Language markers should be practical and visible, not buried in settings.

### UI/UX Design Requirements

- Show language badges or labels in workspace cards, document header, and variant-selection surfaces.
- Keep language choice close to document identity, not buried deep in configuration menus.
- Use plain explanatory copy to distinguish “new language version” from “translate automatically”.

### React UI Implementation Notes

- Keep document language in top-level editor state because many labels depend on it.
- Reuse duplication and workspace patterns instead of inventing a separate parallel flow.
- Use lazy-loaded locale resources when possible to avoid bloating core editor bundles.

### Layout And Responsive Requirements

- Desktop:
  - language badge visible in header and workspace card
- Mobile:
  - compact badge or meta row still required

### Visual And Interaction Requirements

- Language identity should be visible at a glance.
- Variant creation should feel like a document-management action, not a risky destructive change.

### Definition Of Ready For Engineering

- Supported languages are approved.
- Localized builder label coverage is defined.
- Variant-creation rules are agreed.

### Definition of Done

- Users can create and manage supported language variants clearly.
- Builder/workspace show language identity consistently.
- Non-supported language scenarios are handled honestly.
