## [DASH-BE-001] — Saved Documents Index And Workspace Management APIs

**Module:** Dashboard & Workspace  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Document Service  
**Dependency:** AUTH-BE-001, RES-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the document service,  
I want to provide lightweight document-index APIs and safe management operations for user-owned resumes and cover letters,  
so that users can reliably return to, organize, and continue working on saved documents.

### Description

This story covers the backend support for the authenticated workspace. The service must return efficient document summary data, allow user-owned documents to be renamed or duplicated, support document-type filtering and search metadata, and preserve ownership and continuity rules. It should avoid forcing full editor payload retrieval for workspace-level actions.

### Scope

**Included In Scope**

- Document summary listing.
- Filtering by document type.
- Searchable metadata fields.
- Rename operation.
- Duplicate operation.
- Archive/delete initiation behavior.

**Out Of Scope**

- Full editor payload delivery.
- Team sharing.
- Public sharing links.
- Billing history.

### Preconditions

- Authenticated user session is valid. All workspace listing and management operations run under a resolved identity so ownership can be enforced on every request.
- Resume and cover-letter entities or document-type entities exist. The underlying document records must already be persisted by their respective builder/editor flows so the workspace can summarize them.
- Ownership rules are established. A clear owner field must exist on each document type so the service can scope queries and deny cross-user access deterministically.

### Detailed Workflow

1. Workspace requests a summary list of user-owned documents.
2. Service returns document metadata optimized for list rendering.
3. User triggers rename, duplicate, or archive/delete-related action.
4. Service validates ownership and applies the requested action safely.
5. Updated summary state is returned or available for refresh.

### Functional Requirements

- The system must support a lightweight document summary model separate from full document content payloads.
- The summary model must support resume and cover-letter document types.
- Duplicate operations must preserve source relationships or lineage metadata where useful.
- The service must support sorting and filtering fields without requiring full document loads.
- Archive/delete behavior must be intentional and recoverability-aware based on product rules.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid authenticated user  
When the workspace requests their document list  
Then the service returns only that user’s document summaries with enough metadata for workspace rendering.

**AC2 — Rename**  
Given a user renames one of their documents  
When the request is processed  
Then the service persists the new title subject to validation rules and returns updated summary data.

**AC3 — Duplicate**  
Given a user duplicates one of their documents  
When the request is processed  
Then the service creates a new user-owned document copy with a valid default title and preserved editable content lineage as required.

**AC4 — Authorization**  
Given a user attempts to manage a document they do not own  
When the request is processed  
Then the service denies the operation and does not reveal protected metadata.

**AC5 — Error Handling**  
Given a list or management request fails due to transient or data-related issues  
When the failure occurs  
Then the service returns stable, frontend-mappable error responses without corrupting existing document state.

### Business Rules

- Users may only access and manage documents they own unless a future sharing model explicitly changes this. Ownership is the default authorization boundary and must not be relaxed implicitly.
- Duplicated documents must be independently editable after creation. A duplicate is a full copy with its own identity, so edits to the copy never affect the source and vice versa.
- Summary-list performance must be optimized for workspace use, not tied to full builder payload size. The list should return only metadata so large libraries remain fast and responsive.
- Archive and delete policies must align with product’s recoverability decisions. Whether documents are soft-deleted, archived, or hard-deleted must match the product's recoverability stance and be applied consistently.

### Validation Rules

- Title changes must enforce max length and disallowed character rules. Renames must reject over-length or unsafe titles so summary rendering and file export never break on unexpected input.
- Duplicate operations must apply deterministic default naming where necessary. Copies should receive a predictable default title (e.g., "… (Copy)") and resolve collisions deterministically instead of failing.
- Filters and search results must be scoped strictly to owned documents. Filter and search parameters must never widen the result set beyond the requesting user's own documents.

### Error Handling

- Distinguish unauthorized, not-found, validation, and transient service failures. Each class needs a distinct, frontend-mappable response so the UI can show the right recovery action instead of a generic error.
- Avoid partial duplicate creation if downstream steps fail. Duplication must be atomic or compensating so a failure never leaves a half-created copy behind.
- Preserve original documents unchanged when duplication fails. The source document must remain intact regardless of any copy failure, so users never lose data during a duplicate attempt.

### Security Considerations

- Enforce object-level authorization on all document summary and management endpoints. Every operation must verify the requesting user owns the target document, and listing must filter by owner at the query level.
- Do not expose internal document lineage or deleted-state details beyond what the UI needs. Lineage metadata and archive state are internal concerns and should not leak protected information through responses.
- Log management actions for support and audit use where appropriate. Rename, duplicate, and archive events should be auditable so support can reconstruct document history when disputes arise.

### Analytics / Tracking

- `workspace_documents_listed`
- `document_renamed`
- `document_duplicated`
- `document_archive_requested`

### API Dependencies

- `GET /documents`
- `PATCH /documents/{id}`
- `POST /documents/{id}/duplicate`
- `DELETE /documents/{id}` or archive equivalent

### Data Model

> This section describes the expected entity structure with possible properties. It is a **business-requirements-level starting point** to drive technical modeling discussions, not a final database schema. Types, relationships, and constraints should be refined during technical design.

#### DocumentSummary

A lightweight list-oriented projection used by the workspace. It is deliberately separate from full editor content payloads so listing stays fast as libraries grow.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `ownerUserId` | string (uuid) | Owning user account |
| `type` | enum | `resume`, `cover_letter` |
| `title` | string | User-facing document name |
| `lastUpdatedAt` | datetime | Most recent edit timestamp, used for sort ordering |
| `templateId` | string (uuid) \| null | Style reference used for thumbnail rendering |
| `status` | enum | `draft`, `ready`, `archived` — lifecycle state |
| `sourceDocumentId` | string (uuid) \| null | Lineage: originating document if this one is a duplicate |

#### Resume

The resume content entity. The full builder model (sections, items, versioning) is defined in the Resume Builder story; only workspace-relevant fields are summarized here.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `ownerUserId` | string (uuid) | Owning user account |
| `title` | string | Editable document title |
| `status` | enum | `draft`, `ready`, `archived` |
| `version` | integer | Monotonic version counter used by the builder |
| `updatedAt` | datetime | Last mutation timestamp |

#### CoverLetter

The cover-letter content entity. Full content details belong to the Cover Letter story; only workspace-relevant fields are summarized here.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `ownerUserId` | string (uuid) | Owning user account |
| `title` | string | Editable document title |
| `status` | enum | `draft`, `ready`, `archived` |
| `content` | json | Cover-letter content payload (details in the Cover Letter story) |
| `updatedAt` | datetime | Last mutation timestamp |

#### AuditLog

Traceability for workspace management actions used by support and audit.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `actorUserId` | string (uuid) | Subject who performed the action |
| `eventType` | string | e.g. `document_renamed`, `document_duplicated`, `document_archive_requested` |
| `documentId` | string (uuid) \| null | Affected document, when applicable |
| `payload` | json | Structured metadata |
| `createdAt` | datetime | |

#### Relationships

```text
User (1) ──── (N) Resume
User (1) ──── (N) CoverLetter
Resume (1) ──── (1) DocumentSummary (list projection)
CoverLetter (1) ──── (1) DocumentSummary (list projection)
Resume (1) ──── (N) Resume (duplicate lineage via sourceDocumentId)
User (1) ──── (N) AuditLog
```

#### Design Notes

- `DocumentSummary` is a dedicated list projection, not the full editor payload, so workspace listing stays fast as libraries grow.
- Resume and CoverLetter share a common workspace treatment (list, rename, duplicate, archive) even though their content models differ; `DocumentSummary` provides the unified surface.
- Duplicate lineage (`sourceDocumentId`) is preserved internally to support tailoring traceability without burdening the UI.
- Ownership is enforced per document; every summary and management endpoint must scope results strictly to the requesting user.
