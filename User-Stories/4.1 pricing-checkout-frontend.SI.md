# Supporting Information — Pricing, Upgrade, And Checkout Continuity Experience

## Suggested Screens

- Public pricing page
- In-product upgrade dialog
- Checkout-return processing state
- Checkout-return success state
- Checkout-return canceled/error state

## Design Token Guidance

- Pricing pages should feel high-trust and editorial rather than flashy.
- Use one strong premium accent color plus a neutral information palette.
- Keep legal/renewal copy legible with smaller but still accessible text styles.
- Distinguish “current plan”, “recommended plan”, and “locked capability” with border, label, and background token differences instead of multiple competing highlights.

## Interaction Guidance

- Preserve continuation context in URL-safe state plus backend verification.
- Avoid trapping users in pricing after a canceled checkout; always offer return to original work.
- Show exactly one primary CTA per return state.

## Example Frontend State Shape

```ts
type UpgradeContext =
  | { type: "export"; documentId: string; format: "pdf" | "docx" }
  | { type: "template_unlock"; templateId: string }
  | { type: "ai_limit"; tool: string }
  | { type: "analysis_limit"; reportMode: "ats" | "job_match" };

type CheckoutReturnState = {
  status: "success" | "cancel" | "pending" | "failure";
  upgradeContext?: UpgradeContext;
  entitlementRefreshRequired: boolean;
  continuationRoute?: string;
};
```

## Edge Cases

- User completes checkout in another tab and returns later.
  - The return state must be durable enough that a delayed or cross-tab return still reconciles the correct entitlement outcome. The UI should refresh entitlements on focus/return rather than relying only on the immediate callback.
- Entitlement is active but export generation still fails operationally.
  - A paid user must never see a pricing block for what is actually a technical failure; the frontend must distinguish the two and route to a retry/error path instead of an upgrade prompt.
- User opens stale pricing page while plan matrix changed.
  - A cached or previously loaded plan set may no longer match the server, so the frontend must refresh or invalidate and avoid offering withdrawn plans or outdated prices.
- User starts checkout from premium template selection, then returns after that template was unpublished.
  - The continuation context now references a removed entity, so the UI must degrade to a safe workspace destination and explain that the original item is no longer available.

## Testing Focus

- Continuation from every major premium boundary.
  - Exercise export, template unlock, AI limit, and analysis limit entry points to confirm each returns to the correct destination with the right plan messaging.
- Mobile readability of comparison content.
  - Verify plan cards and the feature matrix remain legible on narrow screens without dense, unreadable tables or clipped copy.
- Delayed entitlement confirmation handling.
  - Simulate a pending activation and confirm the UI shows an honest processing state and recovers once confirmation arrives, without a false success.
- Consistency between public pricing copy and in-product upgrade copy.
  - Assert that feature names, plan names, and lock explanations match across surfaces so users are not confused by contradictory wording.

## Developer Notes

- Keep pricing rendering data-driven so plan changes do not require layout rewrites.
  - The plan matrix should render from canonical data structures rather than hardcoded card markup, so adding or reordering plans is a configuration change, not a frontend refactor.
- Reuse entitlement badges and trust-copy patterns across pricing, export, and settings surfaces.
  - Shared components and copy fragments prevent drift and keep the commercial story consistent wherever it appears.
- Route guards should not assume checkout success until entitlement refresh completes.
  - A returned checkout is not proof of activation, so any guard that gates premium features must verify the entitlement state from the backend before granting access.
