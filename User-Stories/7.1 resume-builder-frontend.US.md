## [RES-FE-001] — Section-Based Resume Builder With Live Preview

**Module:** Resume Builder  
**Layer:** Frontend  
**Priority:** Must Have  
**Persona:** Job Seeker, Student, Experienced Professional  
**Dependency:** RES-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a resume author,  
I want to edit resume sections in a guided builder with live preview,  
so that I can create a polished document without having to manually format a document in Word or another editor.

### Description

This story covers the main authenticated authoring workspace for resumes. The builder must support editing structured sections, previewing the rendered document in near real time, reordering content, hiding and showing sections, surfacing validation, and communicating save state clearly. The builder is the center of the product and must behave like an application workspace, not a long static form.

### Scope

**Included In Scope**

- Resume builder workspace shell.
- Core sections: header, summary, experience, education, skills.
- Section create/edit/delete/hide/reorder interactions.
- Live preview updates.
- Save state display and autosave feedback.
- Validation highlights that affect export or analysis readiness.

**Out Of Scope**

- Full cover-letter editor.
- Template-administration tools.
- Deep version-history UI.
- Collaborative multi-user editing UI.

### Preconditions

- User is authenticated — the builder workspace is a gated, authenticated-only experience that requires a valid session token and active user profile.
- A resume draft exists or can be created on entry — the system must either fetch an existing draft by ID or gracefully initialize a new one with default section scaffolding and metadata.
- Template and theme metadata are available — the preview renderer needs complete template configuration (fonts, spacing, colors, layout rules) loaded before the first paint to avoid layout flicker.
- Resume payload includes section order and visibility state — the backend contract must return explicit ordering and `visible`/`hidden` flags per section so the UI can reconstruct the authoring state without guesswork.
- Autosave contract is available from backend — the frontend needs a well-defined API contract covering debounce window, conflict-detection tokens (e.g., `ETag` or version stamp), and error-response shapes for retry logic.

### Detailed Workflow

1. User opens an existing draft or creates a new one.
2. Builder loads layout shell with section navigation, edit panel, and preview area.
3. User selects a section such as `Experience`.
4. Section form opens with existing entries or empty-state guidance.
5. User adds, updates, reorders, or hides items.
6. Preview updates after debounced local state change or confirmed save, depending on architecture.
7. Autosave status transitions through `saving`, `saved`, or `retry needed`.
8. If validation blockers exist, the builder shows them near the section and in any global summary.
9. User can continue editing, switch sections, preview formatting results, and eventually export or analyze.

### Functional Requirements

- The builder must preserve a clear separation between structured data editing and rendered-document preview.
- The main workspace must keep section context visible while editing.
- The builder must support multiple items per repeatable section such as experience and education.
- Section ordering must be explicit and user-controlled.
- Optional sections must be hideable without deleting content.
- The preview must reflect both content and template-driven layout choices.
- The builder must communicate whether changes are saved, still saving, or failed to save.

### Section Behavior Requirements

| Section | Required In MVP | Repeatable | Key Behavior |
| --- | --- | --- | --- |
| Header / Personal Info | Yes | No | contact details and role headline |
| Summary | Yes | No | free text with length guidance |
| Experience | Yes | Yes | date range, bullets, current-role state |
| Education | Yes | Yes | degree, institution, date range |
| Skills | Yes | Yes or grouped | tag/list model with category support later |
| Projects | Phase 2 or configuration-based | Yes | link and contribution details |
| Certifications | Phase 2 or configuration-based | Yes | credential and issuer |

### UI State Requirements

- **Loading:** skeleton or progressive load while draft and template metadata arrive.
- **Ready:** content editable and preview visible.
- **Saving:** non-blocking save indicator, duplicate mutations coalesced.
- **Saved:** confirmation state with timestamp or subtle saved label.
- **Validation warning:** section marked as incomplete or low quality.
- **Save failure:** visible error with retry path that does not discard local edits.
- **Conflict:** stale data warning if backend detects version mismatch.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a user opens a draft in the builder  
When they edit header, summary, experience, education, and skills  
Then the preview updates without full-page refresh and the system persists those changes through save or autosave.

**AC2 — Section Management**  
Given a user adds, hides, deletes, or reorders sections and section items  
When the action completes  
Then the builder reflects the new order or visibility in both the editing interface and preview.

**AC3 — Validation**  
Given required fields are incomplete or dates are logically invalid  
When the user attempts actions that depend on valid content, such as export readiness checks  
Then the UI highlights the affected section and explains what must be corrected.

**AC4 — Error Handling**  
Given autosave or section update fails  
When the failure happens  
Then the save indicator changes to an error state, local edits remain intact, and the user can retry.

**AC5 — Conflict Handling**  
Given the same resume is edited from another tab or device  
When the builder submits stale version data  
Then the UI communicates a conflict state and blocks silent overwrites.

**AC6 — Responsiveness And Accessibility**  
Given the builder is used on desktop, tablet, or mobile  
When the user navigates sections, fields, and controls  
Then the layout adapts appropriately and remains keyboard and screen-reader accessible.

### Business Rules

- Core sections must be available in MVP — header, summary, experience, education, and skills sections are non-negotiable and must ship as fully functional editing surfaces before any Phase 2 sections are considered.
- Users may hide optional sections without deleting content — hiding a section should toggle its visibility flag in the payload while preserving all user-entered data so the content can be restored later without re-entry.
- The builder must preserve structure even when the template presentation changes — switching templates should only affect visual rendering (fonts, colors, layout) but never alter the underlying section data, ordering, or item relationships.
- Premium-only formatting controls must show locked states when relevant — controls gated behind a paid plan should render as intentionally locked (with a clear upgrade path) rather than appearing broken or missing, so free users understand what they could unlock.
- Delete actions for repeatable items should require lightweight confirmation only when data loss risk is meaningful — removing an empty or default entry can be immediate, but deleting an entry with substantial content should surface an undo-capable or confirmation prompt to prevent accidental loss.

### Validation Rules

- Section title and free-text lengths must be bounded by configuration — character limits should be driven by a shared configuration source (not hardcoded) so that templates with different space constraints can impose different limits without frontend redeployment.
- Dates cannot be logically impossible — end dates must be chronologically after start dates, future-only date ranges must be flagged for non-current roles, and date gaps exceeding configurable thresholds should raise warnings.
- Current-role or current-study toggles must disable incompatible end-date requirements — when a user marks a position as "current," the end-date field should become disabled or hidden, and validation should skip end-date checks for that entry to avoid blocking saves with a meaningless requirement.
- Contact fields must use valid format types — email must match a standard email regex, phone must accept international formats, and URL-type fields (LinkedIn, portfolio) must pass URL validation without being mandatory unless configured as required fields.
- Required export blockers must be distinct from optional quality suggestions — the validation engine must tag each issue with a severity level so the UI can render red/error styling for content that prevents export versus amber/warning styling for suggestions that improve quality but don't block output.

### Error Handling

- Distinguish local draft errors from server sync errors — validation problems (e.g., missing required fields, invalid date ranges) should surface inline near the offending field, while network or server errors should appear in a global save-status indicator with clear retry affordances so the user knows whether the issue is with their content or with connectivity.
- Preserve unsaved local state during transient failures — if an autosave or manual save fails due to a network blip, all local edits must remain in the editor exactly as the user left them; the save-status indicator should shift to a "retry needed" state but never clear or revert the user's work.
- Show non-blocking warnings for optional content quality issues — quality hints (e.g., "summary is shorter than recommended," "consider adding metrics to this experience bullet") should appear as dismissible, non-blocking banners or inline tips that never prevent navigation, saving, or export.
- Prevent duplicate reorder requests while one is pending — if a drag-and-drop or explicit reorder action is in flight, the UI must disable further reorder interactions until the server confirms the new order or returns an error, preventing race conditions that could corrupt section sequencing.

### Security Considerations

- Sanitize rich text or formatted text input before rendering preview — any user-supplied text that passes through a rich-text editor or supports HTML-like formatting must be sanitized (e.g., via DOMPurify or equivalent) before being rendered in the preview pane to prevent stored XSS attacks that could execute in another user's or admin's session.
- Prevent unsafe markup injection in any preview surface — the preview renderer must treat all resume content as untrusted data and apply strict output encoding; template variables must never be interpolated into raw HTML without context-aware escaping, and any third-party template engine must be evaluated for injection risks before integration.
- Respect object ownership checks for every save-related mutation — the frontend must send the correct resume ID and version token with every PATCH/POST request, and must handle 403/404 responses by clearly informing the user they lack access rather than silently swallowing the error or exposing confusing technical messages.

### Data Requirements

- Resume metadata
- Resume version token
- Section list and section-item records
- Template and theme configuration
- Entitlement state for locked controls

### UX Notes

- Keep the preview visible whenever screen size allows.
- Make save state explicit: saving, saved, retry needed.
- Favor guided structured editing over free-form full-document editing for MVP.
- Surface quality hints near the related section, not only in a global error area.

### UI/UX Design Requirements

- The builder must feel like a modern document workspace, not a long stacked form.
- The overall interface should communicate confidence, precision, and editability.
- Use a clear three-part mental model where possible:
  - navigation or section index
  - editing surface
  - preview/document output
- Visual hierarchy must help users answer three questions at all times:
  - where am I editing
  - what changed
  - is my work saved
- The preview must look polished enough that users trust it as the future export representation.
- The editing experience should reduce anxiety for non-designers by making structure and guidance visible.

### React UI Implementation Notes

- Build the workspace using composable React feature components rather than one monolithic screen component.
- Separate local editing state, autosave state, and preview-render state so the UI does not jitter on every keystroke.
- Prefer feature-level hooks for:
  - section selection
  - draft mutation
  - autosave status
  - conflict detection
- Render repeatable items as stable keyed components to reduce focus loss during edits and reorder actions.
- Keep preview rendering isolated enough that template switches or section edits do not unnecessarily rerender the whole workspace.

### Layout And Responsive Requirements

- Desktop:
  - split workspace with persistent preview if viewport allows
  - section navigation should remain reachable without excessive scrolling
- Tablet:
  - preview may collapse into toggle, tab, or slide-over state
- Mobile:
  - edit-first experience with optional preview mode
  - reorder controls should use explicit move actions if drag and drop becomes unreliable

### Visual And Interaction Requirements

- Save-status indicator must remain consistently visible.
- Active section should be visually distinct in both navigation and form surface.
- Repeatable items such as experience entries should be presented as structured cards or rows with obvious edit boundaries.
- Empty states must encourage action with examples or guidance, not just "No data."
- Validation blockers should use severity-based styling:
  - error for export blockers
  - warning for quality improvements
- Use subtle workspace motion for panel changes and preview updates, but avoid distracting animations during typing.

### Design-System Expectations

- Use consistent spacing, radius, shadows, and typography tokens across the workspace.
- Avoid default browser styling for builder controls.
- Locked premium controls should look intentionally unavailable, not broken.

### Accessibility Notes

- Reorder actions must have keyboard-accessible alternatives.
- Section list must expose expanded/collapsed and selected states to assistive technology.
- Save-status changes should be announced when important.

### Definition Of Ready For Engineering

- Core section schemas are approved.
- Preview-rendering contract is approved.
- Autosave behavior and debounce strategy are agreed.
- Conflict response shape is defined by backend.

### Definition of Done

- Builder handles core sections end to end.
- Accessibility, autosave, preview, and conflict behaviors are tested.
- Export-blocking validations are wired into the UI.
- Mobile and desktop layouts are verified.
