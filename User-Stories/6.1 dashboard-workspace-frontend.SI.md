# Supporting Information — Saved Documents Workspace And Resume Management

## Suggested Screens

- Main workspace dashboard
- Empty documents state
- Populated documents state
- Rename dialog
- Archive/delete confirmation state

## Suggested Components

- Workspace header
- Document card or row
- Search field
- Filter chips or tabs
- Sort menu
- Empty-state panel
- Inline action menu

## Frontend Component Inventory

| Component | Responsibility | Reusability |
| --- | --- | --- |
| `WorkspaceShell` | page framing for authenticated home | shared |
| `DocumentCollection` | list/grid of saved documents | shared |
| `DocumentCard` | single document summary with actions | shared |
| `DocumentTypeTabs` | switch resume/cover-letter/all | shared |
| `WorkspaceEmptyState` | no-documents guidance | shared |
| `DocumentActionMenu` | rename/duplicate/archive actions | shared |

## Design Token Guidance

### Typography

- Page heading should feel clear and task-oriented.
- Document titles must be visually primary inside each card/row.
- Metadata such as last updated should use a subdued but readable style.

### Color

- Use calm neutral surfaces with subtle differentiation between document types where needed.
- Action states such as archive/delete should be semantically distinct but restrained.

### Spacing

- Preserve generous spacing between create actions and document collection.
- Cards/rows must remain scannable without dense metadata stacking.

## API And Entity Map

- APIs: `GET /documents`, `PATCH /documents/{id}`, `POST /documents/{id}/duplicate`
  - The dashboard reads a lightweight document summary list and mutates only metadata such as title or archived state, never full document content. Duplication is a dedicated endpoint so the workspace can copy without loading the full edit payload.
- Entities: `Resume`, `CoverLetter`, `Tag`, `DocumentSummary`
  - `DocumentSummary` is the projection the dashboard consumes, carrying title, type, updated-at, and status without section content. `Tag` supports future organization features while `Resume` and `CoverLetter` remain the underlying document types surfaced through the same collection.

## Edge Cases

- User has many similarly named tailored resumes.
  - Near-identical titles make identification hard, so each card must surface enough differentiating metadata such as last-updated time, template, or an optional subtitle. Search and sort must remain usable when titles collide.
- A document was deleted or archived from another session.
  - The current tab may hold a stale list entry, so the UI must reconcile a missing or archived document gracefully when an action returns a not-found or conflict result, without leaving a ghost card.
- Search returns no results while documents still exist.
  - The empty-results state must be distinct from the truly-empty workspace state and offer a way to clear filters, otherwise users may believe their documents were lost.
- Resume and cover-letter counts differ significantly.
  - The type tabs and counts must render accurate per-type totals and not imply a balanced collection; each tab should remain meaningful even when one document type is empty.

## Test Focus

- Empty vs populated states
  - Verify the first-run empty state, the populated collection, and the filtered-empty state render distinctly and each offer appropriate next actions.
- Rename and duplicate actions
  - Confirm metadata mutations persist, optimistic UI rolls back on failure, and duplicate creates a distinct document without mutating the original.
- Filter and search accuracy
  - Assert type filters and search matching are correct across resume, cover-letter, and combined views, including case and partial matches.
- Mobile action discoverability
  - Verify inline action menus remain reachable and unambiguous on small screens where hover-based menus are unavailable.

## Developer Notes

- Keep dashboard payload lighter than full document-edit payloads.
  - The workspace should request a summary projection rather than full section trees, reducing latency and payload size for lists that may grow large over time.
- Model document type, last updated, and lightweight status fields consistently for future analytics and organization features.
  - A stable, well-typed `DocumentSummary` shape keeps workspace, search, and future organization features sharing one source of truth instead of drifting into parallel ad-hoc shapes.
