# Research — Theme, Layout, and Customization Backend

## Research Basis

Novorésumé's documented theme feature, layout reorder, and pricing differentiation around fonts/colors/layout provide clear signals that the backend must support a **tokenized appearance model** — a layer of visual properties (font, color theme, backgrounds, styles) that applies to content without altering it, and a **layout order model** that defines section and item positioning.

## What The Research Means For The Backend

- **Appearance is a separate concern** from content. The backend should model theme settings (fontId, colorThemeId, backgroundId, pictureStyleId, ratingStyleId, iconMode) as a distinct object or set of references on the document, not embedded in section content.
- **Layout order is persisted state**: sectionOrder and per-section itemOrder must be independently stored and updated. Reorder operations should be atomic.
- **Entitlement enforcement**: premium-only theme options are blocked server-side (not just hidden in the UI). The backend returns available options based on plan and enforces at save time.
- **ATS-safe constraints**: some theme options should be blocked or flagged when the document is in an ATS-friendly mode (e.g., creative backgrounds, rating styles, icons may break ATS parsing). The backend should enforce these constraints.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Tokenized theme model (font, color, background, picture style, rating style, icon mode) | Separates appearance from content; enables safe theme switching |
| Section and item order persistence | Supports reorder operations with atomic updates |
| Entitlement enforcement on customization depth | Premium fonts/themes/styles gated server-side |
| ATS-Safe constraint enforcement | Prevents ATS-breaking styles from being saved/exported when in ATS-safe mode |
| Theme option catalog API | Returns available fonts, themes, backgrounds, etc. with premium/ats-safe flags |
| Customization save as partial update | Changing theme should not resend the full document |

## Hidden Requirements Inferred

- Default theme per template (what font/colors are set when a new draft is created with a given template).
- Theme inheritance: changing the font on a document should not reset the color theme.
- Theme "reset" capability (revert to template default).
- Premium-option detection in document: if a document *uses* premium theme options, the export gate must detect this (even if the user is currently on a free plan but previewed premium features).

## Risks If Under-Specified

- Theme options may be stored as inline style strings in content, making it impossible to change themes without re-editing every section.
- ATS-safe constraints may be ignored at the backend, letting users save and export documents with ATS-breaking visual elements.
- Premium options may be client-toggled but not server-verified, creating a bypass.
- Layout reorder may conflict with concurrent edits if not handled atomically.

## Recommendation To Developers

- Model theme as a separate `ThemeProfile` or equivalent object on the document, with typed references (not free-form strings).
- Enforce premium and ATS-safe constraints at the API save boundary.
- Use atomic position updates for reorder (e.g., send new position array, validate, persist in one transaction).

## Open Questions

- Which theme options are MVP (fonts + colors) vs. post-MVP (backgrounds, picture styles, rating styles, icons)?
- Should ATS-safe mode be a user toggle or a per-template property?
- Should theme changes trigger a re-render cache invalidation on the preview/export engine?
