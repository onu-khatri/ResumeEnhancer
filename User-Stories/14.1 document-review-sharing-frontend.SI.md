## Design Token Guidance

- The review surface should feel clean, serious, and confidence-oriented.
- Use warning/error semantics sparingly and clearly, reserving strong emphasis for true blockers.
- Sharing controls should visually communicate caution and trust.

## Edge Cases

- User creates share link, edits document, then share becomes stale by version policy — if version binding is active, the share link was created against version N, and the user subsequently edits to version N+1, the shared view still shows version N. The UI must detect this mismatch and warn the user that the share link is stale, offering a regenerate action to update the shared version to match the current state.
- Share is disabled while someone still has an old link — if a viewer has the shared document open when the owner revokes the link, the viewer's next interaction (refresh, navigation) must show a clear "link no longer available" message. The UI on the owner's side should confirm revocation without implying the viewer was notified — this is an asynchronous trust boundary.
- Review summary says ready but export entitlement is missing — if the review signals confirm the document is error-free but the user lacks export entitlement (e.g., free-tier user hitting an export limit), the UI must explain the gap: the document is ready, but the user needs to upgrade to complete the export. This prevents the confusing experience of "everything looks good but I can't proceed."

## Testing Focus

- Version freshness messaging — verify that the `PreviewFreshnessBanner` appears when the review summary is stale relative to the latest saved version, that the banner communicates the staleness clearly without alarmist language, and that the regenerate/refresh action resolves the staleness.
- Read-only share-language clarity — test that every UI element related to sharing (tooltips, confirmation dialogs, copy-success messages) explicitly states that shared access is view-only and that the shared URL can be opened by anyone who has it. Users should never be able to misinterpret sharing as granting editing access or restricting the audience.
- Continuity between review, builder, and export — verify that navigating from review to edit (and back) preserves document context, that the export action is reachable from review regardless of readiness status, and that the browser back button works predictably within this three-node flow.

## Developer Notes

- Consider binding share links to a document snapshot or version if product wants stronger trust later — version binding creates a clear contract: "this is what I shared, and it won't change." This is architecturally cleaner than live-state sharing because it eliminates the staleness problem and gives the owner explicit control over when the shared view updates. However, it requires snapshot storage or version-referenced rendering.
- Keep shared-document rendering separate from authenticated editor controls — the shared view component tree should be intentionally distinct from the authenticated document viewer. This prevents accidental inclusion of edit buttons, export controls, or metadata panels in the shared view. A separate route (`/share/{token}`) with a dedicated rendering path achieves this cleanly.
