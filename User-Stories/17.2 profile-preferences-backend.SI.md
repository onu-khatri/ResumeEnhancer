# Supporting Information — User Profile And Preferences Service

## Proposed APIs

- `GET /users/me`
- `PATCH /users/me`
- `GET /users/me/preferences`
- `PATCH /users/me/preferences`

## Example Preferences Payload

```json
{
  "locale": "en-US",
  "marketingConsent": false,
  "editorPreference": "guided"
}
```

## Proposed Entities

- `User`
- `UserPreference`
- `AuditLog`

## Suggested Technical Controls

- Current-user identity resolution from session
- Editable-field allowlist
- Partial update handling with safe defaults

## Edge Cases

- Concurrent updates from multiple tabs could produce race conditions if the frontend sends a full record replacement instead of a field-level merge, potentially overwriting changes made in another tab since the last GET.
- Deprecated preference values from older clients (e.g., a preference enum value that was removed in a newer API version) must be handled gracefully — the service should either migrate the value server-side or return a validation error with guidance, not crash or silently corrupt data.
- Settings save succeeds partially in downstream systems (e.g., profile written to primary DB but audit log fails), requiring a decision on whether the partial success is committed, rolled back, or flagged for eventual consistency.

## Test Focus

- Current-user authorization must be tested by attempting to access or modify another user's settings data through manipulated request parameters or forged identities, confirming the service rejects all such attempts.
- Partial update safety should verify that sending a PATCH with only `displayName` does not alter `locale`, `timezone`, or any preference field, and that the response reflects only the changed field plus the full merged state.
- Validation mapping for frontend section forms requires that field-level errors in the API response include the exact field path (e.g., `displayName`, `preferences.editorPreference`) so the frontend can place error messages beside the correct form controls.
- Audit coverage should confirm that `profile_updated` and `preferences_updated` audit entries are created with the correct changed-fields metadata and without logging sensitive field values.

## Developer Notes

- Keep settings APIs stable and intentionally narrow; avoid turning them into a generic user-admin surface by exposing internal fields, role enumerations, or system flags that the settings UI does not need and that could create security exposure or tight coupling between frontend and backend internals.
- Separate identity/profile concerns from product-behavior preferences where possible, using distinct database columns or even separate tables so that engineers working on one do not accidentally affect the other during schema migrations or query changes.
