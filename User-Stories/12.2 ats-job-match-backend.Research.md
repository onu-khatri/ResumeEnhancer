# Research — ATS Analysis And Job Match Backend

## Research Basis

Novorésumé's ATS checker and job matcher provide the richest public signal about what a backend analysis engine is expected to deliver: structured, categorized scoring with concrete findings, not a black-box number. The five ATS scoring areas and five job-match categories describe a backend that evaluates resumes across multiple independent dimensions and returns the results as a version-linked, explainable report.

## What The Research Means For The Backend

- Analysis is not a single endpoint returning a number. It requires a **multi-dimensional scoring engine** that evaluates separate rule groups and returns independent sub-scores plus categorized findings.
- Results must be **version-linked**: each analysis run is associated with the specific resume version it evaluated. When content changes, results must be flagged stale.
- The **two-tier model** (free summary / premium detail) means the backend must support result depth gating — the same analysis run can serve different detail levels based on entitlement.
- **Job-description ingestion**: the backend must accept, store (temporarily or per-run), and process job-description text as context for the job-match pipeline.
- **Performance**: A resume check may run in < 1 minute per the Novorésumé UX promise; backend must be designed for a tolerable latency window (sync or async with polling).
- **Privacy**: standalone tools (no-signup) must support auto-deletion of uploaded data. Logged-in analysis must keep data under the user's account privacy policy.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Multi-rule scoring engine | Each scoring area is an independent evaluator with its own rules/checks |
| Version-linked analysis runs | Detect stale results after content changes |
| Depth-gating (free vs. premium detail) | Same run produces summary (free) or detailed findings (premium) |
| Job description context processing | Extract role, skills, requirements, seniority from pasted text |
| Category-level recommendations with severity | Each finding has a category, priority, and action |
| Privacy / auto-delete for standalone | Trust signal and compliance for no-signup tools |
| Rerun support | New run supersedes old, results are not overwritten silently |
| Provider/engine abstraction | Scoring rules may be rule-based, heuristic, or AI-driven; backend should support multiple engines |

## Hidden Requirements Inferred

- Resume parser/structural analyzer that can detect section types, heading labels, and list structures.
- Keyword-extraction engine for job descriptions.
- Rule configuration (which rules fire, thresholds, severity mapping) — ideally configurable without deploys.
- Asynchronous analysis for longer jobs (queued → running → complete → failed).
- Audit trail for each analysis run (what was scored, when, what the results were).

## Risks If Under-Specified

- Engineers may build a single numeric-score endpoint with no breakdown, making results unactionable.
- Scoring may drift from reality — claims of "ATS safe" must be defensible (reference: Novorésumé's explicit HR survey citation of 82.3% ATS usage).
- Without version-linking, users may apply an outdated analysis to an edited resume.
- Job-description processing may fail on unusual formatting (LinkedIn/Indeed copy-paste with extraneous content).

## Recommendation To Developers

- Design analysis as a pipeline: parse resume structure → evaluate rule groups in parallel → aggregate scores → format findings by category → store as version-linked run → return depth-appropriate response.
- Use rule-engine patterns so that scoring categories can be independently developed, tested, and tuned.
- Treat "rerun" as creating a new analysis record — never overwrite the old one.
- Distinguish "engine error" (scoring rules failed) from "provider error" (AI provider for NL analysis failed) in error payloads.

## Open Questions

- Hybrid rule-based + NLP scoring, or purely rule-based in MVP?
- Should analysis be synchronous (blocking response) or asynchronous (queued with polling)?
- Should the score reflect a weighted composite of sub-scores, or remain independently displayed?
- What is the free-tier result depth (score only, summary findings, or all detail)?
