## [AUTH-FE-001] — Guided Account Onboarding

**Module:** Authentication & Onboarding  
**Layer:** Frontend  
**Priority:** Must Have  
**Persona:** New User, Job Seeker  
**Dependency:** AUTH-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a new user,  
I want to create an account through a short guided flow,  
so that I can enter the resume builder with minimal friction and without losing the action that brought me there.

### Description

This story covers the complete first-use registration experience from a public CTA to a functional in-app starting point. The user may arrive from the homepage, pricing page, template gallery, or a premium-lock prompt. The UI must preserve that source context, capture the minimum viable account data, explain legal consent, handle failures gracefully, and redirect the user to the correct first step in the product.

The intent is not to build a generic auth form. The onboarding experience is part of the resume-creation journey, so the frontend must optimize for speed to value, continuity, and trust.

### Scope

**Included In Scope**

- Registration entry from homepage, pricing page, template gallery, and upgrade prompt.
- Email/password signup form.
- Legal consent capture.
- Optional marketing consent capture.
- Inline validation and submit-state handling.
- Post-signup redirect to template selection, starter draft, or other approved entry state.
- Email verification reminder state if verification is not hard-blocking.

**Out Of Scope**

- Social login UI.
- MFA setup UI.
- Enterprise invitation flows.
- Deep profile-completion wizard.

### Preconditions

- The user is not authenticated.
  - If an authenticated session already exists in a stale tab, the register screen must be bypassed and the user routed to the workspace or bootstrap target instead, so a second account is never offered to a signed-in user. The frontend should detect this state on mount and redirect before the form renders.
- Public routes expose one or more primary onboarding CTAs.
  - These CTAs carry the source context that drives post-signup routing, so each entry point must attach a consistent, enumerated source value before opening the flow. Without this, the redirect matrix cannot decide where to land the user and template intent would be lost.
- Terms of service and privacy policy URLs are published.
  - Legal consent is a hard requirement, so the links must resolve to live, versioned documents whose identifiers can be recorded with the consent timestamp. If the URLs are missing, the form cannot legally complete and the submit path must remain blocked.
- Bootstrap route logic is available from backend or app configuration.
  - The bootstrap response is what converts a successful signup into a concrete next action, so its shape and failure modes must be agreed before the form ships. The frontend needs a defined fallback when bootstrap is unavailable or slow.
- At least one valid starter template or starter path exists.
  - The onboarding promise is "start free and keep building," which requires a destination that always exists. If all starter templates are unpublished or deleted, the flow must degrade to a generic builder entry rather than dead-ending.

### Detailed Workflow

1. The visitor clicks `Create Resume`, `Start Free`, `Use This Template`, or equivalent CTA.
2. The app records source context such as `homepage`, `pricing`, `template_detail`, or `premium_lock`.
3. The registration screen or modal opens with clear value copy and minimal fields.
4. The user enters first name, last name, email, password, and consent selections.
5. Client-side validation runs on blur and on submit.
6. The user submits the form.
7. The submit CTA enters loading state and duplicate submit is blocked.
8. On success, the app receives active session state plus bootstrap-routing metadata.
9. The app redirects the user to:
   - template gallery if they started from generic CTA
   - a selected template confirmation if they started from a specific template
   - premium-explanation or checkout-return continuation if the action originated from a locked capability
10. If email verification is pending but not blocking, a dismissible reminder is shown after landing.

### Functional Requirements

- The registration form must collect only fields required to create an account and lawfully store consent.
- The onboarding flow must preserve source context through refresh-safe frontend state or server-returned bootstrap data.
- The app must support both full-page and modal presentation if product later chooses either pattern.
- The UI must not require payment details for free account creation.
- The user must be able to navigate to sign-in and forgot-password without losing already entered registration values, unless security policy says otherwise.
- If the user started with a chosen template, that template intent must survive signup and reappear after login.

### Field And Control Requirements

| Field / Control | Type | Required | Validation / Rules | Behavior |
| --- | --- | --- | --- | --- |
| First Name | Text | Yes | 1-50 chars; trim leading/trailing spaces | Error shown below field |
| Last Name | Text | Yes | 1-50 chars; trim leading/trailing spaces | Error shown below field |
| Email | Email | Yes | valid email shape; normalized before submit | Preserve value on server error |
| Password | Password | Yes | 8-64 chars; must satisfy server policy | Show helper text before failure |
| Terms Consent | Checkbox | Yes | must be checked | Link to terms opens in new tab or approved route |
| Privacy Consent | Checkbox or combined legal copy | Yes | must be explicitly acknowledged | Copy must be auditable |
| Marketing Consent | Checkbox | No | optional; default false unless legal guidance differs | Independent from terms consent |
| Submit CTA | Button | Yes | disabled during submit | Label changes during submit |
| Secondary CTA | Link/Button | No | sign in path | Must retain source attribution |

### UI State Requirements

- **Idle:** empty form or prefilled state if user returned from interrupted path.
- **Dirty:** user has started typing.
- **Client-invalid:** one or more fields invalid; submit blocked or allowed with inline errors based on design.
- **Submitting:** loader visible, duplicate submit blocked, controls disabled except safe navigation if allowed.
- **Success:** auth established and redirect begins.
- **Partial success:** account created but bootstrap fails; show recoverable transition state.
- **Failure:** validation or operational error shown without clearing non-sensitive values.
- **Offline:** detect lack of network and show retry guidance.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a visitor clicks a public onboarding CTA  
When they submit valid registration details  
Then the account is created, the user is signed in, and they are redirected to the correct first in-app route based on their source context.

**AC2 — Template Continuation**  
Given a visitor starts onboarding from a specific resume template  
When registration succeeds  
Then the app preserves the chosen template and lands the user on the selected-template start flow instead of the generic dashboard.

**AC3 — Validation**  
Given the user enters an invalid email, weak password, or missing required consent  
When they try to submit  
Then the form blocks completion, highlights the exact controls with issues, and announces errors accessibly.

**AC4 — Partial Success**  
Given the account is created successfully but bootstrap data fails to load  
When the app receives that state  
Then the user remains authenticated, sees a safe retry path, and is not asked to re-register.

**AC5 — Error Handling**  
Given the registration request fails due to network, throttling, or backend error  
When the failure occurs  
Then the UI preserves user-entered values except password if security policy clears it, explains the issue, and allows retry without losing source context.

**AC6 — Accessibility And Mobile**  
Given the flow is used on keyboard-only, screen reader, tablet, or mobile portrait  
When the user moves through the form and errors  
Then focus order, labels, error announcements, hit targets, and layout remain usable and WCAG 2.2 AA aligned.

**AC7 — Analytics**  
Given the user starts, submits, completes, fails, or abandons onboarding  
When those transitions occur  
Then analytics events are sent with source page, template intent, and plan context when available.

### Business Rules

- Account creation requires acceptance of terms and privacy policy.
  - Consent must be captured as an explicit, auditable action tied to the specific document versions presented at the time of signup. The system must record a consent timestamp and the document version identifiers so legal teams can later prove informed agreement.
- Free users must be able to reach a usable builder entry point.
  - Registration is the gateway to the core resume-building value, so a completed signup must never dead-end behind an unreachable route or an unfulfilled dependency. The bootstrap destination for a free user must always resolve to a working builder, template gallery, or starter draft.
- Social sign-in is phase-ready but not required for MVP.
  - Email/password onboarding is sufficient for launch, but the flow should not be architected in a way that makes adding social providers a large rewrite later. Keeping authentication concerns isolated behind a provider interface preserves the option without shipping it now.
- The system must not auto-enroll a user in marketing communication without explicit consent.
  - Marketing consent defaults to false and is fully independent of the terms and privacy consent required to create the account. A user who declines marketing must not be treated differently in the core product experience.
- A user who begins from a chosen template must not lose that intent after signup.
  - Template intent is part of the source context and must survive registration, including through refresh, server validation errors, and email verification. The selected template identifier travels with the account handoff and reappears in the bootstrap destination.
- Email verification may be soft-blocking for editing and hard-blocking for selected actions if configured later.
  - The MVP can allow entry into the builder while verification is pending, but the design must leave room to gate specific actions later. Verification state must be surfaced clearly so users understand what they can and cannot do until confirmed.

### Validation Rules

- Email is required, trimmed, and must be well formed.
  - Normalization should lowercase the local/domain portion before submission and strip accidental surrounding whitespace. The client should apply a lightweight shape check on blur and defer final authority on deliverability to the server.
- Password must be 8 to 64 characters and satisfy server policy.
  - Client-side checks mirror the server policy so users get immediate guidance rather than a delayed rejection. Helper text should state the length bounds and any complexity requirements before the user submits.
- Consent controls required by legal policy must be explicit and auditable.
  - Terms and privacy acknowledgment cannot be implied by scrolling or by default-checking the box. The submit action is blocked until both required consent controls are affirmatively checked.
- Name fields must reject unsupported control characters and empty-after-trim values.
  - Values that are only whitespace are treated as empty and fail validation. Control characters and other non-printing input are stripped or rejected to keep stored identity data clean.
- Submit must be blocked while request is in flight.
  - The submit CTA enters a disabled/loading state and the form ignores repeated submits, preventing duplicate account-creation requests. This guard protects against both double-click and keyboard-triggered re-submits.

### Error Handling

- Show field-level and form-level errors separately.
  - Field errors attach to the specific control that failed, while a form-level alert summarizes the overall failure and receives focus after submit. This separation keeps users from scanning an undifferentiated wall of text when only one field is wrong.
- Prevent double submit while request is in progress.
  - The loading state disables the primary CTA and any enter-key submission path until the request resolves, so a network retry cannot accidentally create two accounts. The guard applies even if the backend is slow rather than fully down.
- Route already-registered emails to sign-in or reset-password actions without disclosing more than policy allows.
  - The messaging must follow the security team's guidance on account-enumeration risk. In most cases the UI should present a neutral, helpful prompt that links to sign-in or password reset without confirming or denying the email's existence.
- If bootstrap fails after registration, show `Try again` and `Go to workspace` fallback actions if session exists.
  - A partial-success state keeps the user authenticated while offering a retry of the bootstrap call and a safe escape to the workspace. The user must never be asked to re-register simply because the routing metadata failed to load.
- If the backend returns throttling, show wait guidance instead of a generic error.
  - Rate-limit responses should be mapped to a clear "please wait and try again" message with a suggested retry window when the backend provides one. This reduces support burden and discourages rapid retry loops that worsen throttling.

### Security Considerations

- Protect against CSRF, brute-force, and credential stuffing.
  - The signup request must carry CSRF protection and be routed through backend rate limiting and lockout policies, with the frontend respecting throttling signals. These controls are shared with the auth backend so a single policy governs all entry points.
- Avoid revealing whether an email already exists beyond safe UX guidance.
  - Error copy must be neutral and must not confirm or deny account existence, because enumeration feeds credential-stuffing and phishing. The frontend should treat "already registered" and "invalid" responses through the same privacy-preserving messaging path unless policy explicitly authorizes otherwise.
- Record consent timestamps.
  - The frontend must send the consent selections with a reference to the exact legal document version shown, and the backend stores the acceptance timestamp. This produces the auditable trail needed for compliance and dispute resolution.
- Never store raw passwords or expose them in telemetry.
  - Passwords are handled only in the transport to the server and are never written to local storage, analytics events, or error payloads. On failure, the password field is cleared unless policy permits otherwise, precisely to avoid accidental retention.
- Sanitize and validate source-route parameters before using them in redirect logic.
  - Any source or return-path value originating from the URL must be treated as untrusted input and validated against an allowlist before it is used to construct a redirect. This prevents open-redirect attacks that could send a newly registered user to a malicious destination.

### Data Requirements

- User identity fields
- Consent flags and document-version references
- Session state
- Locale and source attribution
- Selected template intent
- Optional marketing consent preference

### UX Notes

- Keep the form short and builder-oriented.
- The primary headline should explain the user outcome, not just "Create account."
- Keep helper text visible before failure when possible to reduce trial-and-error.
- If the user is entering from a premium lock, explain what happens next after signup.

### UI/UX Design Requirements

- The page must feel product-grade rather than like a generic auth template.
- Use a two-zone layout on desktop:
  - left or top zone for brand/value framing
  - main zone for focused registration form
- The form container should remain visually compact, centered, and easy to scan.
- Visual hierarchy must prioritize:
  - page title
  - short value statement
  - primary submit CTA
  - trust/legal copy
- Error states must be calm and precise, not alarming or overly dense.
- The design should communicate "start free and continue building" rather than "create an account for a generic app."
- Use a clean, modern visual direction with strong spacing rhythm, subtle surface contrast, and restrained accent color usage.

### React UI Implementation Notes

- Implement the form as a controlled React form with field-level error state and form-level submission state.
- Keep route-source and selected-template context in page state plus durable navigation state so refresh and redirect handling are predictable.
- Use reusable presentational components for:
  - input field
  - password field
  - consent row
  - alert banner
  - loading CTA
- Avoid deeply nesting business logic inside field components; keep orchestration in the page container or feature hook.
- Support suspense-friendly bootstrap loading patterns after successful registration.

### Layout And Responsive Requirements

- Desktop:
  - form width should stay narrow enough for quick completion
  - supporting value content may appear alongside the form
- Tablet:
  - supporting content may collapse above the form
- Mobile:
  - single-column layout
  - sticky primary CTA only if it does not obscure fields
  - field spacing and tap targets must support thumb use

### Visual And Interaction Requirements

- Primary CTA must have clear default, hover, focus, loading, disabled, and success-transition states.
- Form inputs must use visible labels, not placeholder-only identification.
- Password requirements should appear as supportive helper text before failure, then escalate into validation styling when needed.
- Legal consent copy must remain readable and not feel buried beneath the fold on common laptop sizes.
- Use subtle transition and opacity changes for loading and validation, not decorative motion.

### Accessibility Notes

- Every field must have a persistent visible or programmatically associated label.
- Validation messages must be announced to assistive technology.
- Error summary should receive focus after failed submit.
- Color alone must not communicate invalid state.

### Definition Of Ready For Engineering

- Legal copy and document URLs are approved.
- Redirect matrix by entry source is approved by product/design.
- Password policy is finalized.
- Bootstrap response shape is available.

### Definition of Done

- Responsive and accessible UI is implemented.
- Validation, error, and analytics states are covered by tests.
- Design and copy are approved for MVP launch.
- Source attribution survives register-to-builder handoff.
- Partial-success and bootstrap-retry states are implemented and tested.
