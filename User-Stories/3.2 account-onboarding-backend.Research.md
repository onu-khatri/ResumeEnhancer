# Research — Account Registration And Session Bootstrap

## Research Basis

The selected competitors do not publicly document their internal auth architecture, but their public product behavior strongly implies a richer registration workflow than a simple account insert. Users can start quickly, save documents, return later, recover access, and continue document work. That visible behavior requires orchestration, durability, and supportability.

## What The Competitors Imply Technically

### Novorésumé Implications

- If users can start free without payment friction, the platform needs a default free entitlement assignment path.
- If builder entry feels immediate, session issuance and bootstrap routing must be fast and reliable.
- If account data persists across tools, onboarding must create records usable by multiple modules from the start.

### Resume Now Implications

- Support pages show the product expects users to return to stored documents later.
- Recovery guidance implies traceable auth events, session behavior, and customer-service diagnosability.
- Multiple paid and free capabilities imply plan assignment or entitlement resolution early in the lifecycle.

## Hidden Backend Capabilities Inferred

- Email normalization and uniqueness enforcement. Competitor products treat an email as a single durable identity across login, recovery, and billing, which requires normalized uniqueness rather than case-sensitive string comparison.
- Password hashing and auth identity management. Visible login and recovery flows imply credentials are stored securely and identities are managed separately from profile data.
- Consent versioning and legal audit storage. Privacy-policy references (Resume Now) and paid offerings imply legal acceptance must be provable later, so consent must be versioned and timestamped.
- Session creation and expiry handling. Novorésumé's start-free entry and Resume Now's support flows both assume durable sessions that can be created at signup and later invalidated or expired.
- Default plan and entitlement assignment. Immediate access to builder tools implies a free/starter entitlement is assigned automatically so users are never left with zero capabilities.
- Source-aware bootstrap routing. Funnels from templates or pricing must preserve their origin so the user lands in the right first-run context rather than a generic dashboard.
- Async email dispatch and retry. Verification and welcome emails must not block account creation, so dispatch is asynchronous with retry on failure.
- Audit and support traceability. Resume Now's contact/support pages imply the platform can reconstruct account and billing history, requiring durable audit events.

## Engineering Interpretation

- A real product cannot rely on client-only onboarding.
- Session creation and initial workspace bootstrap must be robust enough for a smooth first-use journey.
- Consent and auditability are required from day one.
- Registration should be implemented as an application workflow, not a single repository call.

## Consequences If Under-Specified

- Duplicate users during retries or double-click submit scenarios.
- Users successfully created but unable to enter the builder due to thin bootstrap contracts.
- Compliance gaps if legal acceptance cannot be proven later.
- Support burden if account creation failures are not distinguishable from email-delivery failures.

## Requirement Implications

- Backend must support partial workflow recovery. A real onboarding flow spans multiple steps (account, session, email, bootstrap), so the backend must recover cleanly when only some steps succeed.
- Verification email failure cannot block account usability unless policy explicitly requires that behavior. Novorésumé's start-free promise implies users should not be stranded if an email fails to send.
- Session issuance should return feature entitlements and route hints. The response must tell the frontend where the user goes next and what they can do, in a single round-trip.
- Frontend should not need multiple extra round-trips to decide where the user goes next. A rich bootstrap payload mirrors the immediate-to-builder experience competitors promise.

## Suggested Error Taxonomy

| Error Code | Meaning | Frontend Use |
| --- | --- | --- |
| `AUTH_EMAIL_IN_USE` | account likely exists | offer sign in or reset |
| `AUTH_WEAK_PASSWORD` | password rejected | show inline rules |
| `AUTH_RATE_LIMITED` | too many attempts | show wait guidance |
| `AUTH_BOOTSTRAP_UNAVAILABLE` | account created but next route unavailable | retry bootstrap |
| `AUTH_VERIFICATION_QUEUE_FAILED` | account created, email dispatch delayed | show resend later |

## Recommendation To Developers

- Use a transaction boundary for core account, identity, consent, and session records. Keeping these writes atomic prevents the partial-account states that produce duplicate users and support pain.
- Move email sending and analytics to async side effects. Email and analytics are non-critical relative to account usability and must not block or roll back registration.
- Version bootstrap response shape so future onboarding additions do not break old clients. A versioned contract lets onboarding evolve without forcing simultaneous frontend/backend releases.
- Model partial success intentionally because it is a normal distributed-system scenario. Design for degraded-but-recoverable states instead of assuming every step always succeeds.

## Open Questions

- Should bootstrap create a default draft automatically or only return starter options?
- Should multi-session support be in MVP?
- Should email verification state live on `User` only or also on a separate identity record?
- Should abuse detection be synchronous only or include post-fact risk scoring?
