## [BILL-FE-002] — Pricing, Upgrade, And Checkout Continuity Experience

**Module:** Billing And Entitlements  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** Free User, Active Job Seeker, Returning Paid User  
**Dependency:** BILL-BE-002, EXP-FE-001, SUB-FE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a user evaluating or encountering a premium boundary,  
I want clear pricing, honest upgrade messaging, and a checkout-return flow that preserves my task,  
so that I can understand what I am paying for and continue my work without confusion.

### Description

This story covers the public and in-product pricing/upgrade experience before subscription management begins. The selected competitors show that monetization in this category is highly sensitive because users often reach the paywall after investing time, effort, and hope into a resume. The frontend must therefore explain plan value, differentiate free versus premium clearly, and preserve the user’s original task when they return from checkout. This is not only a sales page problem. It is a continuity and trust problem.

### Scope

**Included In Scope**

- Public pricing page and plan comparison experience.
- In-product upgrade prompts from export, premium template, AI, or analysis boundaries.
- Checkout launch and return-state continuity.
- Clear messaging for pay-once, subscription, or hybrid model chosen by product leadership.
- Honest display of feature limits, plan inclusions, and upgrade outcomes.

**Out Of Scope**

- Billing-provider hosted checkout UI internals.
- Post-purchase invoice history page.
- Finance-operator tooling.

### Preconditions

- Canonical plan and entitlement definitions exist.
  - The pricing UI must render from a single source of truth for plan codes, billing cadence, and feature inclusion, so the public page and in-product prompts never drift apart. Without canonical definitions, the consistency guarantee required by AC5 cannot be met.
- Checkout session creation endpoint exists.
  - The frontend relies on a backend endpoint that returns a provider handoff, so its contract and error cases must be defined before the upgrade prompt ships. The endpoint must also accept and echo the source context needed for return-state restoration.
- Product leadership has approved the commercial model language.
  - The exact wording for pay-once versus subscription, renewal, and cancellation must be approved before rendering, because ambiguous language is a legal and trust risk. The frontend renders approved copy rather than inventing commercial promises.

### Detailed Workflow

1. User opens the pricing page or hits a premium boundary in product.
2. The UI explains the relevant locked capability, current plan, and meaningful premium value.
3. The user compares plans and chooses an upgrade option.
4. The app creates a checkout session while preserving source context such as export, template unlock, or AI usage.
5. The user returns from checkout success, cancellation, or interruption.
6. The app restores the original task context and shows the updated commercial state clearly.

### Functional Requirements

- Pricing UI must explain plans in capability terms, not only marketing labels.
- The same entitlement story must appear consistently across pricing page, upgrade modal, and return state.
- Upgrade prompts must explain why the user is blocked and what becomes available after payment.
- Checkout return must preserve task continuity for export, template choice, AI action, or analysis rerun.
- The UI must differentiate canceled checkout, failed checkout, successful payment, and delayed entitlement activation.
- If the product uses pay-once time-boxed premium, the copy must explicitly avoid recurring-language ambiguity.
- If the product uses subscription renewal, the renewal and cancellation language must be visible before purchase.

### Acceptance Criteria

**AC1 — Pricing Clarity**  
Given a user opens pricing  
When plan data loads  
Then the UI clearly distinguishes free versus paid capabilities, commercial duration, and relevant feature limits.

**AC2 — Contextual Upgrade Prompt**  
Given a user triggers a premium boundary from export, AI, analysis, or premium template usage  
When the prompt appears  
Then it explains the blocked action, the reason for the block, and the specific value of upgrading.

**AC3 — Checkout Continuity**  
Given the user starts checkout from a task-specific context  
When they return from checkout  
Then the app restores them to the correct destination with updated plan messaging and safe retry/continue actions.

**AC4 — Honest State Handling**  
Given checkout is canceled, fails, or entitlement confirmation is delayed  
When the user returns  
Then the UI presents the correct commercial state without falsely implying successful unlock.

**AC5 — Consistency Across Surfaces**  
Given a feature appears as paid on pricing  
When the same feature is encountered in-product  
Then the naming, promise, and lock explanation remain materially consistent.

### Business Rules

- Pricing language must be single-sourced and commercially consistent.
  - Plan names, feature descriptions, and lock explanations must be sourced from shared configuration so the public page, upgrade modal, and return state never contradict one another. This single-sourcing is what lets AC5's cross-surface consistency be enforced mechanically rather than by manual review.
- A technical export failure must not be presented as a pricing block.
  - If an export fails for a rendering or operational reason, the UI must show a technical error with retry, not an upgrade prompt, so the user is not misled into paying for a problem payment cannot fix. The frontend must distinguish the error type before choosing which message to render.
- A pricing block must not look like a generic system error.
  - An entitlement lock is a business state, so it should be styled and worded as clear, calm guidance about unlocking value, not as a red error banner. Conflating the two erodes trust and confuses users about whether something is actually broken.
- Upgrade should happen at the point of value, not before basic product trust is earned.
  - The prompt should appear when the user is attempting a premium capability they already understand, not as an immediate wall on first launch. This sequencing respects the job seeker's investment in their resume before asking for money.

### Validation Rules

- Only available plans and offers may be shown for the user's market/cohort.
  - The frontend must filter the plan matrix to offers actually available to the user's region and cohort, hiding stale or withdrawn plans. A plan that is not purchasable must never be presented as selectable.
- Return-state tokens must be validated before restoring checkout context.
  - Any token or session id coming back from the checkout provider is untrusted and must be verified by the backend before the UI trusts its claimed status. The client must not render a success state based solely on a client-supplied parameter.
- Stale or unsupported offer references must degrade gracefully.
  - If the continuation context references a template or offer that was since removed, the UI must fall back to a safe workspace destination rather than crashing. Graceful degradation preserves the user's account state even when the original task is no longer actionable.

### Error Handling

- If plan data fails to load, show a recoverable pricing-state error with support fallback.
  - The pricing page must degrade to a clear error with a retry action and a support path, not a blank or partially populated comparison that could mislead the user. Plan data is non-optional, so a failed load blocks pricing decisions until recovery.
- If checkout session creation fails, preserve current work and allow retry.
  - The user's in-progress task must remain untouched when the checkout handoff cannot be created, and the retry must not duplicate or corrupt prior state. The continuation context stays intact so a second attempt resumes the same intent.
- If return verification is pending, show an intermediate "processing purchase" state rather than a false success.
  - Entitlement activation can lag behind payment, so the UI must show an honest pending state that re-checks status instead of declaring success prematurely. This prevents the user from attempting an action that is not yet unlocked.

### Security Considerations

- Do not expose raw billing-provider identifiers in UI state.
  - Provider session ids and checkout tokens should remain server-side or opaque, never embedded in readable form in the URL or client state where they could be leaked or replayed. The client should only ever see the minimal handle it needs to resume the flow.
- Return-state restoration must validate ownership and prevent open redirects.
  - The continuation destination must be verified against the current user's entitlements and against an allowlisted route set so an attacker cannot craft a return URL that redirects elsewhere. Ownership checks ensure one user cannot restore another user's checkout context.
- Client must not self-grant entitlements before backend confirmation.
  - The frontend must never optimistically flip a feature to unlocked based on a client-side signal; it must wait for the backend to confirm entitlement activation. Self-granting would allow bypassing the paywall entirely.

### UX Notes

- The pricing experience should reduce anxiety, not create it.
- Users must understand “what do I get?” and “what happens next?” quickly.
- In-product upgrade prompts should feel contextual, not like generic ad interruptions.

### UI/UX Design Requirements

- Use clear visual hierarchy between free and premium plans without dark patterns.
- Keep feature comparison readable on both desktop and mobile.
- Represent blocked actions with calm, practical language and immediate next steps.
- Success return states should feel reassuring and action-oriented, especially near export.

### React UI Implementation Notes

- Model pricing data, checkout launch state, and return-state restoration separately.
- Keep upgrade surfaces configurable by trigger type so export, template, and AI prompts can share a common foundation without identical copy.
- Use route-safe continuation state rather than brittle in-memory assumptions only.

### Layout And Responsive Requirements

- Desktop:
  - pricing comparison grid with sticky summary CTA acceptable
  - contextual upgrade dialog or side panel for in-app prompts
- Mobile:
  - stacked plan cards with concise benefit summaries
  - checkout return state must remain readable without dense tables

### Visual And Interaction Requirements

- Locked features should be visible but not hostile.
- Selected plan emphasis should come from contrast, spacing, and information grouping rather than gimmicky urgency patterns.
- Use subtle motion when restoring post-checkout state so the transition feels intentional.

### Definition Of Ready For Engineering

- Pricing model and plan matrix are approved.
- Checkout return states are defined.
- Legal/commercial review of user-facing billing language is complete.

### Definition of Done

- Users can compare plans, start checkout, and return to their original task with accurate state.
- Upgrade prompts are contextual and consistent.
- Error, cancellation, and delayed-confirmation states are implemented and tested.
