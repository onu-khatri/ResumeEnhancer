# Supporting Information — Support, Recovery, And Account Assistance Experience

## Suggested Screens

- Support/help hub
- Contextual help drawer/panel
- Recovery action cards

## Suggested Components

- Help entry button/link
- Contextual help card
- Support channel list
- Privacy/help route card
- Fallback support banner

## Frontend Component Inventory

| Component | Responsibility | Reusability |
| --- | --- | --- |
| `SupportEntry` | entry point from contextual surfaces | shared |
| `SupportHub` | central help/recovery page | shared |
| `ContextualHelpPanel` | workflow-specific help surface | shared |
| `SupportChannelCard` | phone/email/chat/self-service option | shared |
| `RecoveryActionList` | structured next-step cards | shared |

## Design Token Guidance

### Typography

- Headings should be calm and direct.
- Support action labels should be concise and easy to scan.

### Color

- Support surfaces should use trust-oriented neutrals with restrained semantic accents.
- Error/failure context should not make the help surface feel alarming or punitive.

### Spacing

- Action cards should have enough separation to reduce cognitive overload in stressful moments.
- Keep core actions above the fold when possible.

## API And Entity Map

- APIs: `GET /support/entry-points`, `GET /support/contextual-help`
- Entities: `SupportEntry`, `HelpCategory`

## Edge Cases

- Support content service unavailable, meaning the dynamic contextual help API returns an error; the frontend must degrade gracefully to the static fallback contact information so users still see a support path rather than an error screen.
- Context mapping not found for the current workflow, requiring the frontend to fall back to the generic (isFallback: true) support entry, which should still present sensible default actions like "contact support" and "visit help center" rather than an empty state.
- Privacy/legal link varies by region, so the frontend must resolve region-specific URLs from the backend metadata rather than hard-coding a single privacy policy link that may be incorrect for users in different jurisdictions.

## Test Focus

- Contextual help mapping should be tested by passing each supported workflow context key and verifying the returned actions are appropriate to that context, not generic or misrouted.
- Static fallback visibility should be tested by intentionally breaking the contextual help endpoint and confirming the fallback contact/help information is still rendered on screen.
- Mobile readability should be tested to confirm that support action cards, contact details, and self-service links remain readable and tappable on small screens under potentially stressful conditions.
- High-stress workflow support entry should be tested by simulating entry from a failed export, failed payment, or expired session state and verifying the help surface offers relevant, calming next steps.

## Developer Notes

- Keep help content and support-channel metadata configurable enough for policy changes so that support hours, email addresses, and phone numbers can be updated via the backend metadata endpoint rather than requiring a frontend deployment.
- Ensure fallback support contact details are resilient and not dependent on a fragile dynamic fetch, meaning the static fallback contact information should be bundled with the frontend build or served from a highly available CDN rather than fetched from the same API that renders contextual help.
