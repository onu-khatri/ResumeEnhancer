## Proposed Entities

- `Resume`
  - Top-level document aggregate holding identity, title, template linkage, current version, and status. It is the authorization root for all section and item mutations.
- `ResumeVersion`
  - Immutable or semi-immutable saved version record that enables optimistic concurrency and lets a draft be restored to an earlier state. Each mutation bumps the version and stores a checkpoint.
- `ResumeSection`
  - A typed section within a resume carrying type, order, and visibility. It groups repeatable items and drives builder navigation and export ordering.
- `ResumeSectionItem`
  - A single repeatable entry inside a section, such as one experience or education record, holding the field data the builder edits.
- `ShareLink`
  - Public or private sharing capability reserved for a later phase, linking an external token to a specific resume version for viewing.

## Entity Responsibilities

| Entity | Responsibility |
| --- | --- |
| `Resume` | top-level document metadata and authorization root |
| `ResumeVersion` | immutable or semi-immutable saved version record for concurrency and history |

## Suggested Technical Controls

- Optimistic concurrency token
  - Every mutation carries the `version` the client last saw, and the server rejects the write with a conflict code when it does not match, preventing silent overwrite across tabs or sessions.
- Background preview/render cache refresh
  - Preview images or rendered output are regenerated asynchronously so save latency stays low and the render work is not on the critical edit path.
- Soft-delete flags
  - Deletion marks records as removed rather than physically destroying them, preserving history and enabling recovery or audit.
- Row-level ownership checks
  - Every read and write is filtered by the owning user at the data layer so one user can never access another's resume regardless of id guessing.

## Conflict Response Example

```json
{
  "errorCode": "RESUME_VERSION_CONFLICT",
  "latestVersion": 13,
  "requiresRefresh": true
}
```

- The conflict response must return the latest version so the client can offer a refresh-and-reapply path. The `requiresRefresh` flag tells the frontend whether a full reload is needed or a targeted merge is possible.

## Edge Cases

- Two tabs edit the same section
  - Both tabs send the same base version; the second write must receive a conflict response and prompt the user to refresh or resolve rather than silently overwriting the first tab's changes.
- Resume deleted while open
  - Mutations against a soft-deleted resume must return a not-found or deleted status so the open editor can stop autosaving and inform the user instead of recreating the document.
- Autosave race with template switch
  - A pending autosave for the old template can land after the template switch, so the server must validate that section content is compatible with the current template version and reject stale writes.
- Item reorder arrives after section delete
  - A reorder targeting a now-deleted section must be rejected cleanly with a conflict/not-found rather than silently recreating the section.

## Test Focus

- Conflict response handling
  - Verify stale-version writes are rejected with the correct code and latest version, and that the client-facing flow can recover.
- Partial update validation
  - Assert that section-specific payloads are validated against their schema and incompatible content is rejected without corrupting the draft.
- Save throughput under rapid keystrokes
  - Confirm autosave can coalesce rapid mutations without dropping the final state or exceeding rate limits.
- Visibility and reorder persistence
  - Verify section visibility and ordering changes persist and are reflected in subsequent reads and export ordering.

## Developer Notes

- Choose between normalized relational storage and JSON-backed storage deliberately; both can work, but query and validation needs favor structured modeling.
  - Structured section and item tables make validation, versioning, and partial updates simpler to enforce at the service boundary than a single opaque JSON blob.
- Keep section-schema validation close to application service boundaries so all mutation paths reuse it.
  - Centralizing schema validation means every create, update, reorder, and import path enforces the same rules, avoiding drift between endpoints.
