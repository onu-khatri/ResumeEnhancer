## [NOTIF-BE-001] — Notification Event Delivery And Preference Enforcement Service

**Module:** Notifications  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Notification Service  
**Dependency:** AUTH-BE-001, PROF-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the notification service,  
I want to store, retrieve, and manage user-specific notification events while enforcing communication preference rules,  
so that operational product events are delivered consistently and users can control supported communication categories.

### Description

This story covers backend support for in-product notification delivery and preference-aware communication behavior. The service must model notification categories, user ownership, read state, and preference rules. It should support operational events such as export completion, billing activation, verification reminders, and supportable alerts without forcing the UI to infer meaning from unrelated system logs.

### Scope

**Included In Scope**

- In-app notification record creation and retrieval.
- Read/unread update handling.
- Preference persistence for supported communication categories.
- Category-based filtering and routing metadata.

**Out Of Scope**

- Full email campaign engine.
- Push-notification provider integration.
- Admin broadcast tooling.

### Preconditions

- Authenticated user identity is available so that every notification read, write, and preference operation can be scoped to the owning user without any ambiguity about who the notification belongs to.
- Notification event taxonomy is defined, with a fixed set of categories (such as export, billing, account, document, verification, security) that both the backend and frontend share, so events are created and rendered consistently.
- Preference categories are defined, including which categories are mandatory (non-suppressible) and which are user-configurable, before preference-enforcement logic can be implemented.

### Detailed Workflow

1. A product event triggers notification creation.
2. Service evaluates whether the event is mandatory or preference-controlled.
3. Service stores the in-app notification and any delivery metadata.
4. Frontend requests current user notifications.
5. User marks items as read or updates preferences.

### Functional Requirements

- Notifications must be scoped strictly to the owning user.
- Event categories must be explicit so the frontend can render meaningful grouping and status.
- The service must support both mandatory operational events and user-configurable categories where policy allows.
- Notification payloads must include sufficient deep-link metadata for product continuation.
- Preference rules must be enforceable without blocking mandatory account/security/billing communication.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid user event that should create an in-app notification  
When the service processes it  
Then the notification is stored with category, summary metadata, and current read state.

**AC2 — Retrieval**  
Given an authenticated user requests notifications  
When the service processes the request  
Then it returns only that user’s notifications with stable category and status information.

**AC3 — Preference Enforcement**  
Given a user has disabled a configurable communication category  
When a non-mandatory event in that category is generated  
Then the service respects the preference while still allowing mandatory operational categories to flow.

**AC4 — Read State**  
Given a user marks a notification as read  
When the request is processed  
Then the service updates only that user-owned item and returns consistent state.

**AC5 — Error Handling**  
Given storage or preference resolution fails  
When the issue occurs  
Then the service returns stable operational failures without corrupting prior notification state.

### Business Rules

- Mandatory operational notices cannot be suppressed by optional preference settings when policy forbids it; categories such as security, billing, and account-critical events must always be delivered regardless of a user's opt-out state.
- Notification categories must be understandable to both product teams and end-user interfaces, using stable, human-meaningful category keys rather than opaque internal event codes that require a mapping layer to interpret.
- Read/unread is user-specific state, meaning a single notification's read status is per-user and must never be shared or globally mutated across users, even for the same underlying event.

### Validation Rules

- Preference updates must be limited to supported categories, rejecting any category key not present in the defined taxonomy with a structured validation error rather than silently persisting unknown values.
- Notification ownership must be enforced on read-state updates, meaning the service resolves the notification by ID and verifies it belongs to the authenticated user before mutating read state, returning 404 or 403 for foreign or missing records.
- Deep-link metadata must reference supported destinations only, validating that the `target.type` and `target.id` combination points to a recognized resource type so the frontend cannot be handed arbitrary or malicious navigation targets.

### Error Handling

- Distinguish authorization (403), validation (422), and transient delivery/storage failures (503 with retry hints) so the frontend can render appropriate error states for each class of problem instead of a generic failure.
- Preserve stored notification history when read-state updates fail, ensuring a failed PATCH to mark a notification read never deletes or corrupts the underlying notification record.
- Avoid creating duplicate notifications for the same event when deduplication is appropriate, using a deduplication key (such as event type + resource ID) so repeated export-ready or billing events do not spam the user with identical notices.

### Security Considerations

- Enforce user isolation on notification retrieval and updates, ensuring queries always filter by the authenticated user's ID and never expose another user's notification feed through ID enumeration or missing where-clauses.
- Avoid storing sensitive payload data beyond what is needed for user-facing summaries; the notification record should hold only a concise summary and deep-link metadata, not raw event payloads, PII, or internal system details that could be exposed through the API.
- Protect mandatory account/security notices from accidental suppression by making the `mandatory` flag authoritative server-side and preventing preference updates from ever removing or disabling mandatory categories, regardless of client input.

### Analytics / Tracking

### Data Model

#### Entity: Notification

| Property | Type | Description |
| --- | --- | --- |
| `id` | `string (UUID)` | Unique notification identifier |
| `userId` | `string (UUID)` | FK to owning User |
| `category` | `enum` | Event category: `export`, `billing`, `account`, `document`, `verification`, `security` |
| `summary` | `string` | User-facing one-line event description |
| `read` | `boolean` | Whether the user has seen this notification |
| `createdAt` | `datetime` | When the notification was generated |
| `target` | `json` | Deep-link metadata (`type` + `id`) for navigation |
| `mandatory` | `boolean` | Whether this is a mandatory operational notice |
| `dedupKey` | `string?` | Optional key for deduplicating repeatable events |

```json
{
  "id": "ntf_1001",
  "userId": "usr_abc123",
  "category": "export",
  "summary": "Your PDF export is ready.",
  "read": false,
  "createdAt": "2026-08-14T12:30:00Z",
  "target": {
    "type": "export",
    "id": "exp_456"
  },
  "mandatory": true,
  "dedupKey": "export:exp_456:ready"
}
```

#### Entity: UserPreference (Notification Scope)

| Property | Type | Description |
| --- | --- | --- |
| `userId` | `string (UUID)` | FK to User |
| `notificationCategories` | `json` | Per-category enablement flags (only for non-mandatory categories) |

```json
{
  "userId": "usr_abc123",
  "notificationCategories": {
    "export": true,
    "document": true,
    "marketing": false
  }
}
```

#### Entity: AuditLog

| Property | Type | Description |
| --- | --- | --- |
| `id` | `string (UUID)` | Unique log entry identifier |
| `userId` | `string (UUID)` | FK to User whose notification state changed |
| `action` | `string` | Action type: `notification_read`, `preference_updated` |
| `changedFields` | `json` | Array of changed property names |
| `timestamp` | `datetime` | When the change occurred |

#### Relationships

```
User ───1:N─── Notification (via userId)
User ───1:1─── UserPreference (notification scope)
User ───1:N─── AuditLog (via userId)
```

#### Business Notes

- Mandatory operational notifications (`mandatory: true`) bypass user preference suppression entirely; categories like `billing`, `security`, and `account` may be non-optional per compliance policy.
- The `dedupKey` prevents duplicate notifications for the same logical event (e.g., multiple export-ready signals for the same export) — the service should upsert based on this key.
- The notification `target` object supports deep linking into product workflows; the frontend resolves `type` and `id` to a navigable route only after verifying the current user still has access to that resource.
- Notification preference data shares the `UserPreference` entity with the broader profile-preferences service but is logically scoped to notification-category flags to keep concerns separated.
