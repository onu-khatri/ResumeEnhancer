# Supporting Information — Notification Event Delivery And Preference Enforcement Service

## Proposed APIs

- `GET /notifications`
- `PATCH /notifications/{id}`
- `PATCH /notifications/preferences`

## Example Notification Payload

```json
{
  "id": "ntf_123",
  "category": "export",
  "summary": "Your PDF export is ready.",
  "read": false,
  "createdAt": "2026-08-14T12:30:00Z",
  "target": {
    "type": "export",
    "id": "exp_123"
  }
}
```

## Proposed Entities

- `Notification`
- `UserPreference`
- `AuditLog`

## Suggested Technical Controls

- Category allowlist
- User-specific read-state updates
- Deduplication keys for repeatable events

## Edge Cases

- Duplicate export-ready events can fire when the export job signals completion more than once (e.g., a retry or idempotent webhook), requiring a deduplication key to prevent two identical "export ready" notifications for the same export resource.
- Notification references deleted document — a notification pointing to a document the user subsequently deleted must resolve gracefully at read time, with the backend either omitting the deep link or the frontend handling a stale-target state.
- Preferences updated while events are being generated can race, where a user disables a category at the same moment an event in that category is created; the service must define a clear ordering so the preference change takes effect deterministically.

## Test Focus

- Ownership enforcement should be tested by attempting to retrieve or mark another user's notification as read, verifying the service returns 403/404 and no cross-user data is ever returned.
- Preference suppression rules should verify that a disabled non-mandatory category blocks event creation while mandatory categories (security, billing) continue to flow regardless of user opt-out state.
- Mandatory-category behavior should be tested to confirm that no client-side or API-side preference update can disable a mandatory category and that the `mandatory` flag is enforced server-side.
- Deep-link metadata integrity should be tested to confirm that `target.type` and `target.id` combinations are validated against a supported-resource allowlist before being persisted.

## Developer Notes

- Keep category taxonomy centralized and shared with frontend display mapping so that adding or renaming a category requires a change in a single shared source of truth rather than scattered backend and frontend constants that drift apart.
- Avoid coupling stored notification summaries too tightly to transient wording that changes frequently; store stable summary fragments or structured event data and let the frontend compose final display text, so a copy tweak does not require rewriting historical records.
