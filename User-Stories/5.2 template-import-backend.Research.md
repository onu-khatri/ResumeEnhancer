# Research — Template Catalog Backend And Resume Parsing/Import

## Research Basis

Template-first and import-first are the two essential entry paths. The backend must serve a structured, metadata-rich template catalog that supports filtering, preview, entitlement decisions, and draft creation. For import, the backend must ingest multiple file formats, extract structured resume data, and present a reviewable parse result.

## What The Research Means For The Backend

### Template Catalog Backend

- Templates are **product data**, not static assets. Each template needs metadata fields: id, name, category, style, ATS-safe flag, premium flag, preview thumbnail, supported sections, min/max pages.
- The template list endpoint must be **entitlement-aware**: free users see premium templates marked as locked, not hidden (so they can be aspirational).
- Template application to a draft is a style-reference update — it changes the template_id on the document; it does not modify content.

### Import/Parsing Backend

- Must accept `.doc`, `.docx`, PDF, RTF, and TXT as documented by Resume Now's support content. PDF is the hardest (image-only vs. text-based); TXT is the easiest.
- Parsing must produce **structured output** (sections detected, fields mapped, confidence per mapping), not a raw text blob — the imported data goes into the structured resume model.
- A **parse review step** is required: the user must see what was extracted, correct errors, and confirm before the draft is created.
- File size and type validation happens before parsing.

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Template catalog API with metadata | Drives gallery, filters, previews, and entitlement decisions |
| Entitlement-aware template listing | Free users see premium templates as locked, not hidden |
| Template application = style reference change | Content unchanged; pagination may shift |
| Multi-format file ingestion pipeline | Supports .doc, .docx, PDF, RTF, TXT |
| Structured parse output with confidence | Reviewable before draft creation |
| File validation (type, size, malware scan) | Security and user experience |

## Hidden Requirements Inferred

- Template versioning (if templates are updated, existing documents reference a specific version or auto-update).
- Parse caching (same file shouldn't re-parse on every preview).
- Entitlement consistency: the same premium/free flag served by the catalog API must match the flag used by the draft-creation and template-switch logic.
- ATS-safe template constraints (which sections/styles are allowed/disallowed per template).

## Risks If Under-Specified

- Template catalog may be built as a static image gallery with no structured metadata — making filtering and entitlement impossible.
- Import may return a single text field, losing all section structure and defeating the purpose of a structured builder.
- Parse results may be trusted as accurate without a review step, leading to messy drafts.
- PDF parsing may fail silently on scanned/image-based documents.

## Recommendation To Developers

- Build template catalog as a structured data API, not a file server. Each template is a record in a database/config.
- Design the import pipeline as: validate file → extract text (format-dependent) → NLP/rule-based section detection → confidence-scored mapping → return structured result for user review → create draft on confirmation.
- Don't trust client-side entitlement checks — enforce template premium/free status server-side on draft creation and template switch.

## Open Questions

- How many template metadata fields in MVP?
- PDF parsing: text-only, or attempt OCR for image-based PDFs? (MVP: text-only likely safer.)
- Should import support image-based resume files like PNG/JPG?
- Should parse results be editable as structured data or as a free-text correction view?
