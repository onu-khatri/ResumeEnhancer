## [SUB-BE-001] — Subscription State, Invoice Retrieval, And Self-Service Billing Actions

**Module:** Subscription Management  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Billing Service  
**Dependency:** BILL-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the billing service,  
I want to expose accurate subscription state, invoice summaries, and supported self-service billing actions,  
so that users can understand and manage their plan without ambiguity and the frontend can present trustworthy billing controls.

### Description

This story covers backend support for the post-checkout billing-management experience. The service must provide canonical subscription state, allowed actions, invoice summary retrieval, and safe action handling such as cancellation or plan-change entry. It should support different billing models without forcing the frontend to infer commercial rules from raw status flags alone.

### Scope

**Included In Scope**

- Current subscription state retrieval.
- Allowed billing action metadata.
- Invoice/receipt summary retrieval.
- Self-service cancel action or equivalent.

**Out Of Scope**

- Full finance ledgers.
- Tax handling.
- Enterprise contract billing.

### Preconditions

- Billing provider integration exists — a payment processor (e.g., Stripe) and its webhook infrastructure must be integrated and stable, providing the source-of-truth for subscription state, payment events, and invoice generation. The backend service layers on top of the provider, not in place of it.
- Subscription and entitlement models exist — the product must have defined what plans exist, what features each plan includes, and how entitlements map to subscription statuses before the management API can return canonical state. Without this schema, the service has no structure to normalize against.
- Billing policy for cancellation/expiry is approved — the product team must have decided whether cancellation takes effect immediately or at period end, what happens to user data after expiry, and whether proration or refunds are offered. These policy decisions directly shape the `allowedActions` computation and cancellation response.

### Detailed Workflow

1. Frontend requests current billing/subscription state.
2. Service returns canonical plan, status, timing, and allowed-action data.
3. Frontend requests invoice or receipt summaries if needed.
4. User initiates a supported billing action such as cancellation.
5. Service processes the request and returns updated state or next-step metadata.

### Functional Requirements

- Subscription state responses must be descriptive enough for user-facing rendering without hidden rule inference.
- The service must support allowed-action metadata so the frontend shows only valid self-service actions.
- Invoice or receipt summaries should be user-consumable and not require raw provider detail exposure.
- Cancellation or plan-management actions must update state predictably and be auditable.
- The service must support both immediate-effect and end-of-term behavior where policy differs.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authenticated user requests current subscription state  
When the service processes the request  
Then it returns current plan, status, timing, and allowed-action data accurately.

**AC2 — Invoice Retrieval**  
Given a user requests invoice or receipt summaries  
When the service processes the request  
Then it returns only that user’s allowed billing-history metadata.

**AC3 — Self-Service Action**  
Given a user initiates a supported cancellation or billing-management action  
When the service processes it  
Then it applies the correct policy, records the outcome, and returns updated or pending state clearly.

**AC4 — Authorization And Safety**  
Given a user attempts a billing action they are not allowed to perform  
When the service processes the request  
Then it denies the action safely and does not change billing state.

**AC5 — Error Handling**  
Given provider communication or persistence fails during a management action  
When the failure occurs  
Then the service returns a stable operational error without creating ambiguous subscription state.

### Business Rules

- Billing state must be driven by canonical backend and provider truth — the backend is the single source of truth for subscription status; the UI must never derive billing state from cached or local data. Any discrepancy between the provider and local records must be resolved in favor of provider truth, with the local state updated accordingly.
- Self-service actions must match policy-approved user capabilities — not every subscription status permits every action. For example, a user already pending cancellation should not see a second cancel button. The backend must compute `allowedActions` per request based on current status, plan type, and billing model to prevent impossible or harmful actions.
- The frontend should not need to guess commercial rules from raw provider statuses — the service must abstract provider-specific status codes (which may be opaque, numerous, or provider-dependent) into a small set of well-documented, user-facing status values and action lists. This keeps billing logic centralized in the backend.
- Subscription changes and cancellations are auditable business events — every state-changing operation (creation, plan change, cancellation, payment) must produce an immutable `AuditLog` entry so that support teams can reconstruct billing history without querying raw provider logs.

### Validation Rules

- Requests must be scoped to the current authenticated user — the service must extract the user identity from the authenticated session and scope all subscription queries, invoice retrievals, and management actions to that user only. Cross-user billing access must be impossible at the API level.
- Management actions must be validated against allowed-action rules — before executing a cancellation or plan change, the service must re-compute the allowed actions for the current subscription state and reject the request if the action is not permitted. This prevents race conditions where state changes between page load and action submission.
- Invoice retrieval must return only supported history scope — the invoice endpoint must enforce a reasonable lookback window (e.g., last 24 months) and pagination to avoid unbounded queries. It must also verify that each returned invoice belongs to the requesting user.

### Error Handling

- Distinguish unauthorized, unsupported-action, provider, and transient persistence failures — each failure category needs a distinct HTTP status and error code so the frontend can show appropriate messaging: 403 for unauthorized access, 422 for an action not in the allowed list, 502 for provider communication failure, and 503 for transient internal errors.
- Preserve prior billing truth if an action fails mid-flight — if a cancellation request reaches the provider but the local database update fails, the service must reconcile by re-fetching provider state rather than leaving the database in a state that contradicts the provider. Never update local state before confirming the provider accepted the change.
- Return a clear pending state when final provider outcome is asynchronous — some billing operations (like cancellations that take effect at period end) produce an intermediate state where the action is acknowledged but not yet final. The service must return this pending state with clear timing information so the frontend can explain to the user exactly what will happen and when.

### Security Considerations

- Billing history and state must be strictly user-owned — every billing API endpoint must authenticate the user and verify that the requested resource (subscription, invoice, payment) belongs to that user. No endpoint should accept a user ID as a parameter from the client; it must always be derived from the session.
- Raw provider secrets or unnecessary payment details must never be exposed — the API must never return full payment method numbers, provider API keys, or internal payment gateway tokens. Only masked references (e.g., `card_****1234`) and receipt URLs are acceptable in user-facing responses.
- Sensitive billing changes must be audit-logged — every cancellation, plan change, and payment event must produce an immutable audit record containing the user ID, event type, timestamp, and relevant metadata. These logs must be write-once and must not be user-deletable.

### Data Model

#### Entity Definitions

**Subscription** — The authoritative record of a user's current billing relationship.

| Property | Type | Description |
| --- | --- | --- |
| `id` | UUID | Subscription identifier |
| `userId` | UUID | The owning user |
| `planCode` | string | Canonical plan identifier (e.g., `PREMIUM_MONTH`) |
| `status` | enum(`active`, `pending_cancellation`, `cancelled`, `expired`, `past_due`) | Current subscription lifecycle state |
| `currentPeriodStart` | datetime | Start of the current billing period |
| `currentPeriodEnd` | datetime | End of the current billing period |
| `cancelAtPeriodEnd` | boolean | Whether cancellation will take effect at period end rather than immediately |
| `allowedActions` | array\<string\> | Backend-computed list of actions the user may perform right now (e.g., `["cancel"]`) |
| `createdAt` | datetime | When the subscription was created |
| `updatedAt` | datetime | When the subscription state last changed |

**Plan** — The product definition for a billing tier.

| Property | Type | Description |
| --- | --- | --- |
| `code` | string | Unique plan identifier |
| `name` | string | Human-readable plan name |
| `billingModel` | enum(`recurring`, `time_boxed`) | Whether the plan renews automatically or is pay-once with expiry |
| `features` | array\<string\> | Included capability identifiers |
| `tier` | integer | Ordering rank for upgrade/downgrade logic |

**Invoice** — A user-facing record of a billing event.

| Property | Type | Description |
| --- | --- | --- |
| `id` | UUID | Invoice identifier |
| `userId` | UUID | The billed user |
| `subscriptionId` | UUID | The associated subscription |
| `amount` | decimal | Charged amount in the billing currency |
| `currency` | string | ISO 4217 currency code |
| `status` | enum(`paid`, `open`, `void`) | Payment status of the invoice |
| `invoiceDate` | datetime | When the invoice was generated |
| `periodStart` | datetime | Start of the service period covered |
| `periodEnd` | datetime | End of the service period covered |
| `receiptUrl` | string \| null | Link to a downloadable receipt, if provided by the billing provider |

**Payment** — A record of a completed payment transaction.

| Property | Type | Description |
| --- | --- | --- |
| `id` | UUID | Payment identifier |
| `invoiceId` | UUID | The invoice this payment satisfies |
| `userId` | UUID | The paying user |
| `amount` | decimal | Amount paid |
| `paymentMethod` | string | Masked payment method reference (e.g., `card_****1234`) |
| `paidAt` | datetime | When payment was completed |

**AuditLog** — An immutable record of a billing-relevant event.

| Property | Type | Description |
| --- | --- | --- |
| `id` | UUID | Log entry identifier |
| `userId` | UUID | The user whose billing context was affected |
| `event` | string | Event type (e.g., `subscription_cancelled`, `invoice_paid`) |
| `details` | json | Structured event payload |
| `occurredAt` | datetime | When the event happened |

#### Relationships

```
User ──1:1──> Subscription (current active relationship)
Subscription ──*:1──> Plan (plan defines the tier)
Subscription ──1:*──> Invoice (billing history)
Invoice ──1:0..*──> Payment (payments against an invoice)
User ──1:*──> AuditLog (all billing events scoped to user)
```

- A user has exactly one active `Subscription` at any time (free tier is represented as a subscription with a free `planCode`).
- `Plan.features` is the source of truth for what the user's current tier includes; the frontend reads this to render the "included features" list without hardcoding plan details.
- `Invoice` records are immutable once paid and are retained for the user's billing history even after subscription cancellation.
- `Payment` records contain only masked payment-method references — full card numbers or provider tokens are never stored in the application database.

#### Business-Level Design Notes

- The `allowedActions` array is computed server-side on each request based on the current subscription status, plan type, and billing policy. The frontend must never derive action availability from `status` alone — doing so would duplicate business rules and risk drift.
- The `cancelAtPeriodEnd` flag supports two cancellation models: immediate effect (access ends now) and end-of-term effect (access continues until the paid period expires). The billing policy determines which model applies per plan type.
- The `billingModel` field on `Plan` captures the fundamental difference between recurring-subscription plans (like Resume Now's model) and pay-once/time-boxed plans (like Novorésumé's model). This distinction drives renewal messaging, cancellation behavior, and expiry communication throughout the UI.
- `AuditLog` entries must be created for every state-changing billing action — subscription creation, cancellation, plan change, invoice payment, and provider webhook events. These are the authoritative record for support investigations and compliance needs.
