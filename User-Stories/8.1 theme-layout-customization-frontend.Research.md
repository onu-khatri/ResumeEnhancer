# Research — Theme, Appearance, And Custom Layout Editing Experience

## Research Basis

The strongest public customization signals come from Novorésumé's documented theme feature, layout-adjustment help content, and pricing differentiation around fonts/themes/layout. These matter because customization is not a cosmetic afterthought — it is a meaningful premium value surface that must still protect content integrity and ATS safety.

## What The Research Means

- Users expect to personalize presentation **after** content exists — customization is not a one-time-at-creation decision.
- Content must survive appearance changes without re-entry or corruption (confirmed by Novorésumé's documented template-switching and theme behavior).
- Some customization controls must be bounded by **ATS-safe rules** (e.g., block tables, non-standard headings, complex graphics in ATS-friendly mode).
- Customization depth is **commercially meaningful**: the 8→16 templates, 30→74 themes, 3→12 fonts ladder is a concrete, explainable premium value proposition.
- Novorésumé's feature list (fonts, color themes, backgrounds, picture styles, rating styles, icons, specialized sections) provides a proven taxonomy of customization controls.

## Requirement Interpretation

- Separate content-edit and appearance-edit experiences (different panels/regions in the builder).
- Provide **live preview** because appearance decisions are inherently visual.
- Use explicit locking and explanation for premium or unsupported options (Novorésumé's white-star pattern).
- Enforce ATS-safe boundaries — if a user is in an ATS-friendly template mode, prevent unsupported customization choices from corrupting ATS readability.

## Risks If Under-Specified

- Teams may scatter appearance controls randomly throughout the builder instead of in a dedicated customization surface.
- Preview/export mismatch risk rises if customization metadata is not modeled cleanly.
- ATS-unsafe options may be exposed with no guardrails, directly contradicting the "ATS-friendly" product promise.
- Premium/free boundaries may be unclear — users shouldn't discover a lock only *after* investing time in a custom theme.

## Recommended Scope Interpretation

- Focus MVP on tokenized theme controls (fonts, colors, accents) plus bounded layout ordering.
- Include ATS-safe constraint enforcement as a first-class concern.
- Defer freeform design tooling, user-authored templates, and advanced visual flourishes (backgrounds, rating styles) to post-MVP.
- Premium gating should be visible but aspirational — locked options should show a preview thumbnail and clearly state "available on Premium."

## Open Questions

- Which customization controls are MVP vs. post-MVP (fonts/colors in MVP; backgrounds/icons later)?
- How strictly do we enforce ATS-safe constraints — hard block, soft warn, or user choice with a warning?
- Should we use a "preview premium, pay to use" gate for premium customization options (mirroring the export gate)?
