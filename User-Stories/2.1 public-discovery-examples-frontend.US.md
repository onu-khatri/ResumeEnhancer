## [DISC-FE-001] — Public Template Discovery, Example Browsing, And Funnel Entry Experience

**Module:** Public Discovery And Acquisition  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** New Visitor, Job Seeker, Career Changer  
**Dependency:** DISC-BE-001, ONB-FE-001, TMP-FE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a public visitor exploring whether the platform can help me,  
I want to browse templates, examples, and role-relevant entry content before creating an account,  
so that I can build confidence, find a suitable starting point, and enter the product through a meaningful funnel.

### Description

This story covers the public-facing discovery surfaces that attract and convert users before they reach the authenticated product. The selected references strongly show that template galleries, ATS-friendly template categories, examples, and guides are not side content. They are acquisition infrastructure. The frontend must therefore support credible public exploration: users should be able to browse categories, inspect template/example cards, understand why a template is relevant, and move into onboarding or template-start flows without losing context.

### Scope

**Included In Scope**

- Public template gallery with filterable discovery.
- Public example and category browsing entry patterns.
- ATS-friendly or role/category labels where applicable.
- CTA continuity into signup, template selection, or import flow.

**Out Of Scope**

- Full CMS authoring experience.
- Deep blog/article rendering platform.
- Authenticated builder editing.

### Preconditions

- Public content metadata exists. The public catalog service must already expose published titles, categories, thumbnails, and CTA targets so the frontend can render discovery without touching internal admin data.
- Template/example categorization is approved. A stable taxonomy must be agreed so filter chips, URL slugs, and category pages all reference the same approved categories.
- Public-to-authenticated routing strategy exists. The hand-off points into signup, template selection, and import flows must be defined so CTAs can preserve source context correctly.

### Detailed Workflow

1. Visitor lands on a public template or example page from search, ads, or homepage navigation.
2. The page presents category context, gallery/exemplar cards, and practical next-step CTAs.
3. The visitor filters by style, role, ATS-safety, or document type where supported.
4. The visitor opens a detail or preview state and decides to start from that asset.
5. The app routes them into signup, template selection, or import continuation with source context preserved.

### Functional Requirements

- Public discovery pages must support browsing without requiring account creation first.
- Template and example cards must explain enough to reduce hesitation.
- The same public asset should be able to route into a meaningful next step such as “Use this template”, “Start with this example”, or “Import my resume”.
- Filters and category states should be shareable and URL-stable where practical.
- ATS-friendly or similar trust-relevant labels must be explained, not merely displayed as badges.

### Acceptance Criteria

**AC1 — Public Browsing**  
Given a visitor opens a public discovery page  
When metadata loads  
Then they can browse templates/examples and inspect relevant categories without logging in.

**AC2 — Filterable Discovery**  
Given multiple template/example categories exist  
When the visitor applies supported filters  
Then the gallery updates coherently and the state remains understandable/shareable.

**AC3 — Detail-To-CTA Continuity**  
Given a visitor selects a template or example asset  
When they choose to continue  
Then the next step preserves the chosen source context for onboarding or template start.

**AC4 — Mobile And Search-Funnel Readability**  
Given a visitor arrives on mobile or from a search result page  
When the page renders  
Then core asset value, category context, and CTA hierarchy remain clear.

**AC5 — Honest Empty/Unavailable States**  
Given a category is empty, filtered out, or temporarily unavailable  
When the state is shown  
Then the page handles it gracefully and still offers a productive next action.

### Business Rules

- Public discovery surfaces are conversion infrastructure, not decorative marketing pages only. These pages must actively guide visitors toward a starting point and signup, so every element should serve that funnel intent.
- Category labeling must match actual in-product behavior. If a template is presented as ATS-friendly or role-specific, that label must reflect what the user will actually experience in the product.
- Source-context preservation matters because funnel quality depends on relevance. Losing the visitor's chosen template or example between discovery and signup breaks the relevance that motivated them to continue.

### Validation Rules

- Only published public assets may render in discovery. The frontend must not surface draft or withdrawn assets, even if stale data lingers in a client cache or URL.
- Unsupported filters or stale category slugs must degrade safely. An unknown filter or empty category should render a graceful empty state with alternatives, not a crash or error page.
- CTA destinations must map to valid product entry routes. Every call-to-action must point to a real, working flow so a ready visitor is never stranded on a dead link.

### Error Handling

- If public inventory fails to load, show a fallback discovery state with limited but useful next actions. A degraded catalog should still offer popular categories or a signup path rather than a blank page.
- If a selected template/example becomes unavailable before continuation, explain the change and offer nearby alternatives. Users who clicked through should be told the asset is no longer available and steered to similar options instead of hitting a dead end.

### Security Considerations

- Public pages must not leak internal-only metadata. The frontend must render only the public-safe projection and never expose admin notes, draft states, or internal identifiers even if present in a raw response.
- Query/filter handling must avoid unsafe open redirects or injected route state. Filter and CTA parameters must be validated and sanitized so untrusted URL input cannot trigger redirects to external or malicious destinations.

### Data Requirements

- Public asset id
- Asset type
- Title
- Category metadata
- Preview image/thumbnail
- ATS-friendly label and explanation
- CTA target metadata

### UX Notes

- A new visitor should immediately understand “what kind of help is available here?”
- Browsing should feel useful even before login.

### UI/UX Design Requirements

- Use a polished, conversion-oriented discovery layout that balances inspiration and clarity.
- Template/example cards should feel trustworthy and informative, not like content-farm SEO tiles.
- Keep CTA language specific to the asset and stage of the funnel.

### React UI Implementation Notes

- Separate public discovery state from authenticated app state so caching and routing stay clean.
- Use URL-driven filter state to support search landing pages and shareable category views.
- Reuse template card primitives across public discovery and authenticated template-selection where possible.

### Layout And Responsive Requirements

- Desktop:
  - gallery grid plus contextual header/filter controls
- Mobile:
  - stacked cards with collapsible filters or chip scrollers

### Visual And Interaction Requirements

- Cards need strong preview hierarchy and scannable metadata.
- Category/filter transitions should feel smooth but fast.
- Public pages should feel more editorial and acquisition-focused than the authenticated workspace.

### Definition Of Ready For Engineering

- Public taxonomy and funnel routes are approved.
- Asset metadata contract is approved.
- CTA continuation rules are defined.

### Definition of Done

- Visitors can browse public templates/examples and continue into the product with preserved context.
- Filtering, detail, and fallback states are implemented.
- Responsive behavior and SEO-oriented routing assumptions are validated.
