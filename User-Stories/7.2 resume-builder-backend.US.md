## [RES-BE-001] — Resume Draft ResumeEnhancer.Infrastructure.Persistence And Autosave Orchestration

**Module:** Resume Builder  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Resume Service  
**Dependency:** AUTH-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the resume service,  
I want to persist draft updates, section ordering, visibility states, and version-aware autosave operations,  
so that users can edit resumes safely without losing work or overwriting newer changes.

### Description

This story covers the server-side model and mutation behavior behind the resume builder. The backend must store structured resume data, support partial section updates, preserve deterministic ordering, track versions for conflict detection, and return payloads suitable for fast UI refreshes. It must support autosave patterns rather than assume explicit manual save only.

### Scope

**Included In Scope**

- Resume create/read/update behavior for builder drafts.
- Section-level updates.
- Repeatable item persistence.
- Section and item ordering.
- Visibility flags.
- Optimistic concurrency/version handling.
- Autosave-friendly response behavior.
- Soft deletion where required.

**Out Of Scope**

- Export rendering pipeline itself.
- Multi-user collaborative editing.
- Full restore/version-history UI.
- Cover-letter content model.

### Preconditions

- Authenticated session is valid.
- Resume ownership is resolved.
- Section schemas are defined.
- Template metadata exists for the draft.
- Storage supports transactional or consistency-safe updates.

### Functional Workflow

1. Client requests a resume by ID and receives structured draft data plus version token.
2. Client sends partial section or resume mutations.
3. Service validates mutation against section schema and current version.
4. If valid and current, service persists update and increments version.
5. Service returns updated payload or delta-friendly response.
6. If stale version is submitted, service returns conflict response instead of silently overwriting.

### Functional Requirements

- Resume data must be stored in a structured, queryable form.
- Section ordering must be explicit and stable.
- Partial updates must not require rewriting the entire draft unless architecture intentionally chooses that with safeguards.
- Autosave requests must be safe under rapid repeated submission.
- The service must support soft deletion of sections or items when recoverability is needed.
- Backend validation must remain the final authority, even if the frontend validates first.
- Validation responses must distinguish export-blocking errors from non-blocking quality warnings where business rules support both classes.
- Save responses must support frontend save-state rendering, including success, retry-safe failure, and version-conflict outcomes.
- Mutations that affect preview-relevant layout or visibility must produce deterministic downstream state so the frontend preview remains trustworthy.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid section update request  
When the service processes it  
Then the draft is updated, version metadata changes, and the latest usable resume payload is returned.

**AC2 — Schema Validation**  
Given invalid field structures, unsupported section types, or impossible date ranges  
When the service receives the mutation  
Then it rejects the request with field-scoped validation details.

**AC3 — Concurrency**  
Given the same resume is edited from multiple sessions  
When stale version data is submitted  
Then the service detects the conflict and returns a non-destructive conflict response.

**AC4 — Ordering And Visibility**  
Given a user reorders sections or hides a section  
When the service persists the change  
Then the returned payload preserves deterministic order and visibility state for subsequent reads and renders.

**AC5 — Error Handling**  
Given persistence or downstream refresh fails  
When the mutation runs  
Then the service preserves data integrity and returns a retry-safe outcome.

**AC6 — Validation Severity**  
Given a resume change introduces a content issue  
When validation evaluates the update  
Then the service can distinguish blocking validation from advisory warnings so the frontend can present severity accurately.

### Business Rules

- Resume data is owned by the creating account unless explicitly shared.
- Section order must remain explicit and stable.
- Hidden sections remain in data model unless user explicitly deletes them.
- Soft deletion is preferred over destructive removal where recovery value is meaningful.
- A resume version used for analysis or export should be traceable even as drafts continue to evolve.

### Validation Rules

- Validate per-section schema.
- Enforce supported field lengths and data types.
- Normalize date and location formats where configured.
- Reject unsupported section types unless feature flags permit them.
- Reject mutations with missing or stale version tokens when optimistic concurrency is required.

### Error Handling

- Use optimistic locking or version tokens.
- Make autosave requests idempotent where possible.
- Emit structured conflict responses.
- Preserve prior valid version if a partial mutation fails.
- Return stable status semantics the frontend can map to `saving`, `saved`, `save failed`, and `conflict` states.

### Security Considerations

- Enforce object-level authorization on every mutation.
- Sanitize user-supplied text before storage or rendering.
- Log sensitive operations without exposing resume content unnecessarily.

### Analytics / Tracking

### Data Model

> This section describes the expected entity structure with possible properties. It is a **business-requirements-level starting point** to drive technical modeling discussions, not a final database schema. Types, relationships, and constraints should be refined during technical design.

#### Resume

The top-level document container. One user owns many resumes.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier, immutable |
| `ownerUserId` | string (uuid) | Owning user account |
| `title` | string | User-facing document name, editable |
| `templateId` | string (uuid) | Reference to applied template (style reference, not embedded) |
| `languageCode` | string (ISO 639-1) | Document language for label localization and variant management |
| `status` | enum | `draft`, `ready`, `archived` — lifecycle state |
| `version` | integer | Monotonic counter, incremented on every structural mutation. Used as optimistic concurrency token. |
| `sectionOrder` | string[] | Ordered list of section IDs defining the document's section sequence. Drives preview and export rendering. |
| `createdAt` | datetime | Immutable creation timestamp |
| `updatedAt` | datetime | Auto-set on last mutation |

#### ResumeSection

A typed, structured section within a resume. A resume has many sections. Each section belongs to exactly one resume.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `resumeId` | string (uuid) | Owning resume |
| `type` | string | Section type: `header`, `summary`, `experience`, `education`, `skills`, `projects`, `certifications`, `languages`, `volunteering`, `interests`, `references`, `custom` |
| `label` | string | User-visible section heading (localizable per document language) |
| `isVisible` | boolean | Whether the section renders in preview/export. Hidden sections retain their data; setting to false does not delete content. |
| `order` | integer | Position in the section sequence. Managed by the reorder endpoint. |
| `itemOrder` | string[] | Ordered list of item IDs within repeatable sections. Empty for non-repeatable sections (summary, header). |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

#### ResumeSectionItem

A repeatable entry within a section (e.g., one job in the experience section). A section has zero or more items.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `sectionId` | string (uuid) | Owning section |
| `resumeId` | string (uuid) | Denormalized owning resume for faster query and access control |
| `data` | json | Typed content payload whose shape depends on parent section type — see below |
| `isVisible` | boolean | Hide this individual item without deleting |
| `order` | integer | Position within section. Managed by reorder endpoint. |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

#### Item Data Payloads By Section Type

The `data` field shape varies by parent section type:

| Section Type | Data Properties |
| --- | --- |
| `header` | `fullName`, `email`, `phone`, `location`, `linkedinUrl`, `portfolioUrl`, `professionalTitle` |
| `summary` | `text` (free-text summary paragraph) |
| `experience` | `jobTitle`, `companyName`, `location`, `startDate`, `endDate`, `isCurrent`, `bullets[]` (array of bullet-point strings) |
| `education` | `schoolName`, `degree`, `fieldOfStudy`, `location`, `startDate`, `endDate`, `gpa` (optional) |
| `skills` | `skillName`, `category` (optional), `proficiencyLevel` (optional, e.g., beginner/intermediate/advanced/expert) |
| `projects` | `projectName`, `description`, `url`, `startDate`, `endDate`, `bullets[]` |
| `certifications` | `certificationName`, `issuingOrganization`, `issueDate`, `expirationDate`, `credentialId` (optional) |
| `languages` | `languageName`, `proficiency` (e.g., native/fluent/intermediate/basic) |
| `volunteering` | `organizationName`, `role`, `startDate`, `endDate`, `description`, `bullets[]` |
| `interests` | `interestName` |
| `references` | `referenceName`, `relationship`, `contactInfo`, `note` |

#### Relationships

```text
User (1) ──── (N) Resume
Resume (1) ──── (N) ResumeSection
ResumeSection (1) ──── (N) ResumeSectionItem
Template (N) ──── (1) Resume (via templateId reference)
```

#### Versioning Contract

- Every mutation to a resume, section, or item increments `Resume.version`.
- Clients must send the `version` they last read; the server rejects mutations with stale versions (HTTP 409).
- Conflict responses include the current `version` so the client can re-fetch and re-apply changes.
- Read operations do not require a version token.

#### Design Notes

- Content and design are cleanly separated: resume/sections/items hold content; `templateId` on `Resume` points to style. Changing `templateId` does not touch content.
- Repeatable sections use the `data` json field pattern so new section types can be added without schema migrations.
- `sectionOrder` and `itemOrder` are persisted as arrays on the parent entity, not computed, so reorder operations are deterministic and preview/export always see the same sequence.
- Visibility flags (`isVisible`) allow sections/items to be hidden without data loss — critical for tailoring and A/B resume variants.

### Response Contract Expectations

- Response must include updated version number or token.
- Conflict responses must include enough information for the frontend to decide between refresh or merge.
- Validation responses must map to section and field identifiers.
- Validation payloads should include severity or category metadata where the frontend differentiates blockers from warnings.
- Successful mutation responses should support efficient preview refresh without forcing a full resume reload unless necessary.
