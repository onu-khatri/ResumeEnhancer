## [AUTH-BE-002] — Production Authentication And Authorization Hardening

**Module:** Authentication, Authorization & WebSolution Security  
**Layer:** Backend  
**Priority:** Must Have  
**Persona:** Guest visitor, authenticated user, administrator, and platform operator  
**Depends on:** AUTH-BE-001 — Account Registration And Session Bootstrap  
**Source Classification:** Observed, Inferred, Recommended

### User Story

As a ResumeEnhancer guest, user, administrator, or platform operator, I want authentication and authorization enforced consistently with secure account recovery and password controls, so that public discovery remains available while private data and privileged operations are protected.

### Description

The current AuthModule creates registration sessions and refreshes them, but WebSolution does not configure JWT bearer authentication, does not establish authenticated principals before authorization, and does not apply a fail-closed authorization boundary to module endpoints. Login and password lifecycle operations are also missing.

This story adds the missing security capabilities. Existing /register, /refresh, /logout, /verify-email/resend, and /bootstrap endpoints remain in place and retain their current purpose. Frontend implementation is excluded.

### Scope

**Included**

- Add POST /api/v1/auth/login.
- Replace the custom access-token format with standards-compliant JWT issuance and ASP.NET Core bearer validation.
- Configure authentication and authorization middleware.
- Add a fail-closed fallback policy and explicit anonymous allowlisting.
- Preserve anonymous homepage, onboarding, and approved public discovery.
- Protect private resume, profile, billing, administration, and mutation operations.
- Add role, capability, policy, and resource-ownership authorization.
- Derive identity and audit actors from authenticated principals, not client-controlled IDs.
- Enforce active, verified, non-disabled, non-locked account state.
- Add password change, forgot-password, reset-password, and email-verification completion.
- Prevent reuse of the previous two passwords.
- Harden refresh rotation, revocation, reuse detection, keys, rate limits, ProblemDetails, and security auditing.

**Out of scope**

- Frontend implementation.
- Recreating or redesigning existing Auth endpoints.
- Social login, SSO, external IdPs, or MFA.
- Billing/product-policy redesign beyond authorization enforcement.

### Guest Access Boundary

Anonymous access remains available for:

- Homepage and public discovery content.
- Existing registration, refresh, logout, verification-resend, and bootstrap endpoints.
- New login, email-verification, forgot-password, and reset-password endpoints.
- Approved read-only template/category discovery endpoints.

Resume data, user-owned profile data, billing data, administrative data, and protected mutations require authentication and applicable policies.

### Added API Surface

| Method | Route | Access | Purpose |
| --- | --- | --- | --- |
| POST | /api/v1/auth/login | Anonymous | Validate credentials and issue session |
| POST | /api/v1/auth/password/change | Authenticated | Change password |
| POST | /api/v1/auth/password/forgot | Anonymous | Request reset challenge |
| POST | /api/v1/auth/password/reset | Anonymous | Consume reset challenge |
| POST | /api/v1/auth/verify-email | Anonymous | Consume verification challenge |
| GET | /api/v1/auth/me | Authenticated | Return subject and account state |

### Acceptance Criteria

**AC1 — Login**  
Given an active user with valid credentials, when POST /api/v1/auth/login is called, then the service validates the normalized email/password, creates a refresh-session family, issues a JWT, and returns a safe authentication response.

**AC2 — Safe failures**  
Given unknown email, invalid password, unverified, disabled, or locked account, when login is attempted, then the response does not reveal which condition occurred and no session is created.

**AC3 — JWT validation**  
Bearer tokens must validate issuer, audience, signature, algorithm, subject, session identifier, nbf, iat, exp, and bounded clock skew. Invalid, expired, malformed, unsecured, or algorithm-confusion tokens are rejected.

**AC4 — Middleware**  
Valid tokens populate HttpContext.User before authorization. Missing/invalid tokens on protected routes return 401.

**AC5 — Fail-closed authorization**  
Endpoints without explicit anonymous metadata require authentication through a fallback policy. Authenticated users without the required policy, role, capability, entitlement, or ownership receive 403.

**AC6 — Guest access**  
Approved guest endpoints succeed without JWT. Private and administrative operations remain inaccessible anonymously.

**AC7 — Trusted identity**  
X-User-Id and X-Audit-UserId cannot override the authenticated subject or audit actor.

**AC8 — Account status and email verification**  
Disabled, locked, deleted, and unverified account rules are enforced during login, refresh, and protected access. Applicable sessions are revoked.

**AC9 — Password policy**  
Registration, change, and reset use one server-side policy. Preserve the current minimum 12-character baseline, allow supported special characters, apply breached-password screening where configured, and reject either of the previous two passwords. Do not weaken this to five alphanumeric characters unless explicitly approved as a security exception.

**AC10 — Password change**  
Authenticated change verifies the current password, updates the password and history transactionally, revokes refresh sessions, and audits the event.

**AC11 — Forgot/reset**  
Forgot-password returns the same safe result for known and unknown emails, is rate-limited, and queues only valid-account messages. Reset challenges are hashed, short-lived, single-use, invalidated after use, history-checked, and revoke existing sessions.

**AC12 — Existing refresh behavior**  
Existing refresh continues hashed-at-rest storage, rotation, family revocation on reuse, expiry/revocation checks, and concurrent-use protection.

**AC13 — Key rotation**  
New JWTs use the active key identifier; approved previous keys validate only during configured overlap. Keys come from protected secret management and are never logged or committed.

**AC14 — Abuse controls**  
Login, registration, refresh, verification, password reset/change, and relevant logout operations use distributed rate limits and safe 429 responses without enumeration.

**AC15 — Safe errors and audit**  
All failures use redacted ProblemDetails/ValidationProblemDetails. No password, token, OTP, secret, inner exception, SQL detail, or production stack trace is returned. Login, denial, replay, reset, verification, lockout, disablement, and throttling events are structured and redacted.

**AC16 — Regression**  
Existing register, refresh, logout, verification-resend, bootstrap, idempotency, consent, outbox, and atomic-registration tests pass without endpoint recreation or semantic redesign.

### Definition of Ready

- Guest allowlist and protected endpoint/policy matrix approved.
- JWT issuer, audience, algorithm, lifetime, and clock-skew values approved.
- Key storage/rotation ownership approved.
- Email verification and lockout behavior approved.
- Current 12-character baseline and previous-two-password rule approved; any five-character exception documented.
- Trusted origins and cookie/CSRF strategy approved.
- AUTH-BE-001 contracts and regression tests baselined.

### Definition of Done

Login, password lifecycle, verification completion, JWT middleware, fallback authorization, guest boundaries, ownership checks, account-state enforcement, password history, refresh hardening, key rotation readiness, distributed rate limiting, redacted ProblemDetails, and security auditing are implemented and covered by unit/integration tests. No frontend files are changed.
