## [TRACK-FE-001] — Job Tracker Board And Application Follow-Up Workspace

**Module:** Job Tracking  
**Layer:** Frontend  
**Priority:** Could Have  
**Persona:** Active Job Seeker, Premium User, Returning User  
**Dependency:** TRACK-BE-001, DASH-FE-001, BILL-FE-002  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a job seeker managing multiple opportunities,  
I want a simple application-tracking workspace connected to my resume activity,  
so that I can organize applications, remember next steps, and keep returning to the platform.

### Description

This story covers a lightweight job-tracking board inspired by competitor signals that resume platforms increasingly act as broader job-search workspaces. Novorésumé publicly positions job tracking as a Kanban-style premium capability with card limits (3 free / unlimited premium), which suggests it is both a retention surface and a commercial differentiator. The frontend should focus on practical organization rather than enterprise ATS complexity: track opportunities as cards, move them across defined stages, store simple notes/dates, and connect them to resume variants or job-targeting work.

### Scope

**Included In Scope**

- Personal application board/list workspace.
- Basic stage management: Saved, Applied, Interviewing, Offer, Archived (additional stages post-MVP).
- Job card detail with company, role, link, dates, note, and related resume reference.
- Premium/free limit messaging: proven 3-cards-free / unlimited-premium model must be clearly communicated.

**Out Of Scope**

- Team collaboration.
- Employer-side pipeline management.
- Automated job ingestion from external job boards.

### Preconditions

- User authentication exists.
  The job tracker is a private, account-bound workspace, so the user must be logged in before accessing the board. The tracker must inherit the same session and authorization model as the dashboard, and any session expiry during use should redirect to login with a return path back to the tracker.
- Basic document workspace exists.
  The job tracker lives inside the authenticated workspace shell and depends on the dashboard's navigation, layout, and document-summary infrastructure. Users need the workspace so they can see their list of resumes when associating a job card with a specific resume variant.
- Tracking limits and entitlement policy are defined.
  Product stakeholders must have agreed on the free-tier job-card limit (e.g., 3 cards free / unlimited for premium) and the exact messaging for the upgrade CTA. The frontend relies on this policy to render the usage counter, lock state, and upgrade prompt consistently across the add-card flow and the board header.

### Detailed Workflow

1. User opens job tracker from workspace navigation or premium feature CTA.
2. The app loads current job cards and visible stage columns or filtered list.
3. User adds a new opportunity with company, role, location/link, and optional resume association.
4. User moves the opportunity through stages as the job search progresses.
5. User revisits the board to decide what to follow up on next.

### Functional Requirements

- The tracker must present application progress in a way that is easy to scan.
- Users must be able to add, edit, move, archive, and reopen job entries.
- Each job entry should support a related resume or document reference when available.
- The UI should support both low-card-count users and heavier repeat users without becoming cluttered.
- If the free tier has a card limit, the UI must explain the limit honestly and show the current usage clearly.

### Acceptance Criteria

**AC1 — Board Visibility**  
Given a user opens the job tracker  
When data loads  
Then they can see current opportunities organized by stage or equivalent progress view.

**AC2 — Create And Edit**  
Given the user wants to track a new role  
When they submit the add-job form  
Then the new card appears in the correct stage with editable metadata.

**AC3 — Stage Progression**  
Given an existing opportunity  
When the user moves it to another stage  
Then the UI reflects the change immediately and preserves it after refresh.

**AC4 — Resume Association**  
Given the user has resume variants in the workspace  
When they edit a job card  
Then they can connect the opportunity to the most relevant document.

**AC5 — Limit And Upgrade Handling**  
Given the user reaches the allowed tracker limit  
When they attempt to add another card  
Then the UI explains the limit and offers the correct next step without losing current tracker context.

### Business Rules

- Job tracking is a personal organization surface, not a recruiter system.
  The tracker is designed for the individual job seeker to manage their own applications, not for employers to manage candidates or for teams to collaborate on hiring pipelines. Features like applicant scoring, interview scheduling automation, and multi-user access are intentionally out of scope to keep the experience lightweight and focused.
- Tracking state should be understandable even for users who return after days or weeks.
  The board must clearly show which applications need follow-up, which have been stale, and what stage each opportunity is in, without requiring the user to remember the context from their last visit. Timestamps, stage labels, and summary metadata on each card serve as memory aids for intermittent usage patterns.
- Commercial gating must be transparent if unlimited tracking is premium.
  If the free tier caps the number of job cards (e.g., 3), the UI must show a visible usage indicator (e.g., "2 of 3 jobs used") and explain the limit before the user reaches it. Surprising the user with a paywall only when they try to add the fourth card, without prior warning, creates frustration and feels deceptive.

### Validation Rules

- Required job fields must be minimally sufficient for later recognition.
- Stage values must come from the supported tracker workflow.
- Resume association must reference only user-owned documents.

### Error Handling

- Preserve board context if a card save or stage move fails.
  When a create, update, or stage-move request fails, the board must retain its current visual state — cards should not disappear or snap back to a previous column without explanation. An inline error indicator on the affected card or a toast notification should explain the failure while keeping the rest of the board interactive.
- Allow retry without forcing the user to re-enter all data.
  If a new job card fails to save, the add-job form must retain the user's entered data (company, role, link, notes) so they can retry without retyping. Similarly, if a stage move fails, the card should remain in the target column with a retry affordance rather than being forcibly reverted in a way that loses the user's intent.
- Distinguish entitlement block from general save failure.
  When a user hits the free-tier card limit, the error message must clearly explain that the limit has been reached and link to the upgrade flow — it must not appear as a generic "save failed" error that suggests a technical problem. Conversely, a genuine server or network error must not be mislabeled as an entitlement issue, which would confuse users and erode trust in both the feature and the pricing model.
- If the resume-association lookup fails while editing a job card, allow the card to be saved without a linked resume rather than blocking the entire save operation.
  The resume reference is a secondary field, and its absence should not prevent the user from saving the core job-card data. The UI should save the card with a null resume association and surface a non-blocking warning that the link could not be established.

### Security Considerations

- All tracker data is private user data.
- External job links must be handled safely.
- Resume associations must respect document ownership.

### Data Requirements

- Job id
- Company name
- Role title
- Stage
- Job link
- Applied/follow-up dates
- Notes
- Related resume id

### UX Notes

- The tracker should feel calm and useful, not like another administrative burden.
- The main question the UI should answer is “what should I do next?”

### UI/UX Design Requirements

- Use a compact board or hybrid board/list that keeps stage progression legible.
- Make overdue follow-up or recently updated items easy to notice without turning the page into a warning dashboard.
- Support quick edits from the card surface where practical.

### React UI Implementation Notes

- Keep board layout state separate from job-card data state.
- Model drag/move interactions so keyboard-accessible fallback actions also exist.
- Reuse workspace shell patterns while letting tracker retain its own visual identity.

### Layout And Responsive Requirements

- Desktop:
  - multi-column board preferred
- Tablet/mobile:
  - horizontally scrollable columns or stage-filtered stacked lists acceptable

### Visual And Interaction Requirements

- Stage columns need strong headings and clear card boundaries.
- Resume association should be visible but secondary to job identity.
- Empty states should encourage first use with lightweight guidance.

### Definition Of Ready For Engineering

- Tracker stages and limit policy are approved.
- Data fields for job cards are approved.
- Resume-association behavior is defined.

### Definition of Done

- Users can create, update, move, and review job cards.
- Entitlement or limit states are handled clearly.
- Responsive board behavior is implemented and tested.
