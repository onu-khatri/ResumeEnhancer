# Supporting Information — Review Summary Aggregation And Read-Only Share Link Services

## Suggested Contracts

### Review Summary

```json
{
  "status": "warning",
  "blockers": [],
  "warnings": [
    {
      "code": "missing_metrics",
      "section": "experience",
      "message": "Add measurable impact where possible."
    }
  ],
  "documentVersion": 12,
  "shareState": {
    "active": true
  }
}
```

### Share Link State

```json
{
  "active": true,
  "shareUrl": "https://example.com/share/abc123",
  "mode": "read_only"
}
```

## Suggested Internal Concepts

| Concept | Purpose |
| --- | --- |
| `ReviewSummaryProjection` | normalized final-review payload |
| `DocumentShareLink` | active/revoked share-link state |
| `SharedDocumentProjection` | external read-only representation |

## Edge Cases

- User regenerates share link while old URL is still open elsewhere — if a viewer has the old link open in a browser tab and the owner regenerates it (creating a new token), the old link must immediately resolve to an invalid/expired response. The viewer should see a clear message that the link is no longer available, not a confusing loading state or partial document render.
- Shared link points to a document later deleted or privatized — if the owner deletes the document or changes its privacy setting to restrict external access, any existing share links must stop resolving. The external viewer should receive a generic "link unavailable" response that does not indicate whether the document was deleted, made private, or never existed — this prevents information leakage about the owner's account state.
- Review summary partially stale relative to the most recent draft save — if the user saves changes to the document while the review summary is still computing (or was computed from a prior version), the service must flag the summary as stale via the `freshness` field so the UI can warn the user. The user should have the option to request a fresh computation rather than relying on potentially outdated readiness data.

## Testing Focus

- Ownership enforcement on share management — verify that non-owners receive 403 responses for all share-link CRUD operations, that the error response does not leak whether a share link exists, and that ownership checks occur before any database read or write for share operations.
- External invalid/expired token handling — test that revoked tokens, expired tokens, malformed tokens, and tokens for deleted/privatized documents all return consistent, privacy-safe error responses with no information leakage about the document or its owner.
- Snapshot versus live-state behavior if adopted — if version binding is implemented, verify that the shared projection returns the bound version's content, not the current live version, and that regenerating the link updates the version binding. If live-state is used instead, verify that the projection always reflects the latest document content.

## Developer Notes

- Prefer unguessable share tokens and audit every lifecycle transition — tokens should use `crypto.randomBytes(16).toString('base64url')` or equivalent to produce ~128-bit entropy strings. Every transition (created, revoked, regenerated, accessed) should write an audit log entry with user ID, timestamp, document ID, and action type. This audit trail is essential for investigating "who can see my resume?" support inquiries.
- Keep external projection intentionally smaller than authenticated document payloads — the shared document view must be a separate DTO/serializer that explicitly whitelists which fields are visible. Never reuse the authenticated document response and strip fields; always build the external projection from the ground up to prevent accidental field leakage through future model changes.
