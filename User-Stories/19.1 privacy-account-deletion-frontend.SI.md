# Supporting Information — Privacy, Data Export, And Account Deletion Self-Service Experience

## Suggested Screens

- Privacy/account data section
- Data export request state
- Account deletion explanation and confirmation state
- Privacy support/help state

## Suggested Components

- Privacy action cards
- Consequence summary panel
- Deletion confirmation form
- Support/help callout
- Request accepted state

## Frontend Component Inventory

| Component | Responsibility | Reusability |
| --- | --- | --- |
| `PrivacyActionsPanel` | list of supported privacy actions | shared |
| `DataExportRequestCard` | export-request action and state | shared |
| `DeletionConsequencesPanel` | explain what deletion means | shared |
| `DeletionConfirmationForm` | strong confirmation interaction | shared |
| `PrivacySupportCallout` | escalation/help entry | shared |

## Design Token Guidance

### Typography

- Explanatory copy should be highly readable and plain-language.
- Destructive-action labels should be explicit and unmistakable.

### Color

- Destructive states should use strong semantic styling without panic-inducing design.
- Informational and support areas should remain calm and trustworthy.

### Spacing

- Preserve strong separation between explanation, confirmation, and action buttons.
- Avoid visually compressing high-risk actions.

## API And Entity Map

- APIs: `GET /privacy/options`, `POST /privacy/data-export`, `POST /privacy/account-deletion`
- Entities: `PrivacyRequest`, `User`

## Edge Cases

- User has active subscription while requesting deletion, which means the backend may block the request and the frontend must surface a policy-aware message explaining that the subscription must be canceled first, with a direct path to the billing/cancellation flow.
- Data export requested repeatedly in short time, where the frontend should either prevent rapid resubmission with a throttle or display an existing pending request state instead of creating duplicate requests.
- Deletion policy requires support intervention instead of immediate self-service, meaning the frontend must gracefully redirect the user to a support contact flow rather than showing a generic "failed" error that leaves the user confused about next steps.

## Test Focus

- Consequence clarity must be verified through user testing or heuristic review: can a typical user reading the deletion confirmation understand what will be deleted, what will be retained, and whether the action is reversible?
- Confirmation safety should be tested by attempting to submit the deletion form with empty confirmation fields, partial typed text, or keyboard-only interaction, ensuring the submit action fires only when all requirements are met.
- Fallback to support should be tested across all privacy actions to confirm that when self-service is blocked or unavailable, the user sees a clear support path with visible contact information, not a dead-end error.
- Pending-request state rendering should be tested to confirm that after a successful request submission, the UI shows a stable, reassuring "request accepted" state that persists across navigation.

## Developer Notes

- Keep privacy request state modeling explicit and separate from generic settings save states; a privacy request has a lifecycle (pending → processing → completed/blocked) that is fundamentally different from a simple settings PATCH and needs its own UI state machine.
- Ensure support escalation is always visible for partial self-service models so that if deletion is blocked due to subscription or policy, the user immediately sees a "contact support" path adjacent to the blocked message, never forced to navigate away from the privacy area to find help.
