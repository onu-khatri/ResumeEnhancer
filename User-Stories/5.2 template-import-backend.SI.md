# Supporting Information — Template Catalog And Resume Import Parsing Pipeline

## Proposed APIs

- `GET /templates`
- `GET /templates/{id}`
- `POST /imports/resume`
- `GET /imports/{id}`
- `POST /imports/{id}/create-draft`

## Proposed Entities

- `Template`
  - Represents a selectable resume template in the catalog, carrying identity, category, entitlement gating, and layout compatibility metadata. It is the gallery-facing aggregate that the import and builder flows reference by `templateId`.
- `TemplateVersion`
  - Tracks the layout schema and rendering changes over time so a resume pinned to an older template version continues to render correctly. Versioning decouples live template edits from previously saved documents.
- `ImportJob`
  - Represents a single upload-and-parse workflow from raw file receipt through scanning, parsing, and draft creation. It holds status, scan outcome, parse warnings, and the resulting `createdResumeId`.
- `Resume`
  - The created draft document that the import pipeline produces after review confirmation. It links back to the import job and inherits the parsed section structure.
- `ResumeSection`
  - The structured section data extracted from the source file, such as experience or education, stored in a form the builder can edit. It preserves per-section confidence so the review screen can surface uncertainty.

## Template Metadata Suggestions

| Field | Purpose |
| --- | --- |
| `templateId` | unique identifier used across gallery, builder, and export references |
| `name` | display label shown in the gallery and workspace |
| `category` | gallery filtering value such as professional, creative, or academic |
| `isPremium` | entitlement gate that drives the premium-lock callout |
| `previewImageUrl` | asset used in gallery cards and the preview modal |
| `supportedSections` | the section types the template can render, driving builder compatibility |
| `layoutSchemaVersion` | render compatibility marker so older documents stay stable |

## Suggested Import Job Fields

- `importJobId`
  - Unique identifier used to poll status and locate the review payload.
- `ownerUserId`
  - Ownership key for authorization checks on every subsequent operation.
- `sourceFileName`
  - Original uploaded filename, retained for display and support diagnosis.
- `sourceFileType`
  - Detected format such as `pdf`, `docx`, or `txt`, used to select the parser.
- `status`
  - Current lifecycle state from `queued` through `consumed` or `failed`.
- `scanOutcome`
  - Result of security scanning, kept separate from parse quality.
- `parseWarnings`
  - Human-readable list of uncertain or missing fields surfaced during review.
- `parseConfidence`
  - Aggregate confidence used to badge the review screen.
- `createdResumeId`
  - The resume draft id produced after the user confirms review, null until then.

## Suggested Background Jobs

- File scanning
  - Runs malware and content-inspection checks before parsing so untrusted uploads are never parsed by the application tier.
- Format-specific parsing
  - Extracts text and structure using the parser appropriate to the detected file type, isolating format quirks from the rest of the pipeline.
- Text normalization
  - Cleans and normalizes extracted content so downstream section mapping operates on consistent text.
- Draft creation post-confirmation
  - Builds the `Resume` and `ResumeSection` records only after the user confirms the review, keeping unconfirmed imports out of the document collection.

## Status Model

| Status | Meaning |
| --- | --- |
| `queued` | upload received, awaiting processing |
| `scanning` | security checks running |
| `parsing` | content extraction and mapping running |
| `review_ready` | user can inspect extracted structure |
| `failed` | unrecoverable processing problem |
| `consumed` | parse result used to create a draft |

- The `consumed` state is terminal and idempotency-aware, so a second create-draft call cannot double-create a resume from the same import job.

## Edge Cases

- Image-only PDF
  - A PDF with no text layer produces no extractable content, so the job should fail with an explicit "no extractable text" reason and offer the user an OCR or manual-entry path if supported. This is a parsing failure, not a security block.
- Duplicate uploads
  - Re-uploading the same file should be detected or at least not corrupt state; the system must either deduplicate or treat each upload as an independent job with clear ownership. Repeated uploads must not leak raw files indefinitely.
- Parse succeeds with missing dates
  - The job should reach `review_ready` with warnings rather than failing outright, since partial structure is still usable. Warnings preserve the user's ability to fill gaps during review.
- Create-draft called twice
  - The create-draft endpoint must be idempotent, returning the existing resume rather than creating a second one. Ownership checks must also prevent another user from consuming a job they do not own.

## Test Focus

- Upload rejection reasons
  - Verify unsupported types, oversize files, and scan failures each produce distinct, correct error responses and do not advance the job state.
- Partial parse outputs
  - Assert that parse jobs with missing fields surface warnings and reach review rather than failing wholesale.
- Storage cleanup policy
  - Confirm raw uploads are purged per retention policy while parsed structured data is retained, and that expired files are not recoverable.
- Ownership and idempotency on create-draft
  - Verify a user cannot create a draft from another user's job and that repeated calls return the same resume id.

## Developer Notes

- Use object storage plus durable metadata table for import jobs.
  - Raw files belong in object storage while the job lifecycle lives in a transactional metadata table, keeping large binaries out of the relational database and enabling clean retention and cleanup.
- Keep raw upload retention shorter than parsed structured data retention where policy allows.
  - Once parsing completes and a draft is created, the raw file is no longer needed for product function and can be removed sooner than the structured resume data, reducing storage cost and exposure.
