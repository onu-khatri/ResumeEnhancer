## [IMP-FE-001] — Template Selection And Existing Resume Import

**Module:** Templates & Import  
**Layer:** Frontend  
**Priority:** Must Have  
**Persona:** Job Seeker, Career Changer  
**Dependency:** IMP-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a user starting or modernizing a resume,  
I want to choose a template or upload an existing resume,  
so that I can begin from the path that fits my situation instead of being forced into one creation style.

### Description

This story covers the first content-creation decision after onboarding: start from a template or import an existing resume. The UI must present both options clearly, explain supported formats and premium restrictions, provide template browsing and previewing, handle upload/parse progress, and route the user into a reviewable builder state.

### Scope

**Included In Scope**

- Template gallery browsing and selection.
- Template preview.
- Free vs premium template state.
- Upload flow for supported resume files.
- Parse-progress and parse-review experience.
- Confirmation path into editable resume draft.

**Out Of Scope**

- Template authoring/admin.
- OCR tuning UI.
- Cover letter import.
- Bulk document import.

### Preconditions

- User is authenticated.
  The template gallery and import flows require a valid user session so that draft ownership, entitlement checks, and parse history can be correctly associated with the user's account. Unauthenticated visitors should see a marketing or onboarding surface rather than a broken gallery or upload form.
- Template catalog is available.
  The backend must serve an up-to-date list of templates with their metadata (title, category, preview image, free/premium status, supported sections) so the gallery can render browsable cards. If the catalog endpoint is empty or unreachable, the frontend cannot offer the template-first creation path.
- Import service is reachable.
  The file upload, virus scan, and resume-parsing pipeline must be operational and accepting requests. The frontend should verify service health before allowing the user to begin an upload, rather than letting them invest time in selecting and uploading a file only to discover the service is unavailable.
- Supported file types and size limits are configured.
  Product policy must define exactly which formats are accepted (e.g., PDF, DOCX, TXT) and the maximum file size (e.g., 10 MB). These constraints drive the upload validation UI, the file-picker accept filter, and the pre-upload instructional copy so users know what to expect before they browse for a file.
- Parse result review UI contract is defined.
  The shape of the parsed resume data (sections, confidence scores, warnings, unresolved fields) must be agreed upon between frontend and backend teams. This contract determines how the review screen renders extracted content, which fields are editable, and what confirmation signals are needed before draft creation proceeds.

### Detailed Workflow

1. User lands on a start screen that presents `Choose Template` and `Upload Existing Resume`.
2. If template path is chosen:
   - user browses categories or filters
   - previews a design
   - selects an eligible template
   - starts a new draft
3. If import path is chosen:
   - user uploads a supported document
   - upload progress is shown
   - system scans and parses the file
   - user reviews extracted sections and warnings
   - user confirms creation of a draft from parsed data
4. User enters the builder with either a blank/template-based or parsed draft.

### Functional Requirements

- The UI must make template-first and import-first equally discoverable.
- The system must clearly distinguish free templates from premium templates before the user commits.
- The upload flow must explain supported file types and size limits before the user uploads.
- Parse review must show extracted data plus confidence gaps or unresolved fields.
- The UI must allow the user to correct or accept parse output before entering the builder.
- A selected template must remain associated with the draft even if the user came from an import path and later applies one.

### Acceptance Criteria

**AC1 — Template Path**  
Given a user browses templates  
When they filter, preview, and select a template  
Then they can create a draft with that template and enter the builder without losing the chosen design.

**AC2 — Import Path**  
Given a user uploads a supported resume file  
When parsing completes  
Then the UI shows extracted sections, unresolved issues, and a confirmation path into the builder.

**AC3 — Validation**  
Given the file type is unsupported, the file is too large, or the file is corrupted  
When the user uploads it  
Then the UI blocks continuation and explains the reason clearly.

**AC4 — Premium Lock State**  
Given a template or import-related capability is premium-limited  
When a free user reaches it  
Then the lock state explains value and next action instead of only denying access.

**AC5 — Error Handling**  
Given upload, scanning, or parsing fails  
When the failure occurs  
Then the user sees which step failed, can retry, and can still switch to blank/template-based creation.

### Business Rules

- Users must understand whether they are starting from template or import.
- Free and premium templates must be visually differentiated.
- Imported content must be editable before export.
- A parse result must not auto-overwrite an existing draft without explicit user confirmation.

### Validation Rules

- Allow only configured file formats.
- Enforce maximum upload size.
- Prevent submission of a new parse-confirmation action while a prior draft-creation request is pending.
- Template selection must validate entitlement before draft creation.

### Error Handling

- Keep upload progress and failure states visible.
  The upload progress indicator should show distinct phases (uploading, scanning, parsing, review-ready) so the user always knows which step is in progress and how long they might wait. If a step fails, the failure state must remain anchored to the affected step rather than disappearing and leaving the user unaware of what went wrong.
- Offer retry for parse failures.
  When the parsing service returns an error (timeout, unparseable file, service outage), the UI must display a clear failure message with a retry button. The user should not need to re-upload the file; the already-uploaded file should be resubmitted to the parse pipeline to avoid redundant work and bandwidth consumption.
- Allow fallback to blank or template-based creation.
  If the import path fails irrecoverably (e.g., the file format is permanently unsupported, or repeated parse attempts fail), the user must be offered a clear, one-click transition to the template-based creation flow. Blocking the user at a dead-end import screen with no alternative path creates a frustrating drop-off point.
- Preserve the uploaded-file context when scan succeeds but parse fails partially.
  If the virus scan passes and the file is accepted but the parser can only extract partial data (e.g., name and contact info but not work history), the review screen must show what was successfully parsed alongside clear markers for what could not be extracted. The user should be able to accept the partial result and manually fill in the gaps rather than being forced to start over from a blank document.

### Security Considerations

- Do not render uploaded files directly without sanitization.
- Warn users that imported content may include sensitive personal information.
- Respect file scanning outcomes before any parse review is shown.

### Analytics / Tracking

### API Dependencies

- `GET /templates`
- `GET /templates/{id}`
- `POST /imports/resume`
- `GET /imports/{id}`
- `POST /imports/{id}/create-draft`

### Data Requirements

- Template metadata
- Template entitlement status
- Import job status
- Parse result and confidence markers
- Draft creation result

### UX Notes

- Put template and import paths side by side on the entry screen.
- Use progressive disclosure for parse review instead of dumping raw extracted text.
- Lock states should include benefits and allowed alternatives.

### UI/UX Design Requirements

- The entry experience must clearly present two different user intents:
  - "I want to start fresh"
  - "I already have a resume"
- The design should make both paths feel equally valid, not hide import as a secondary fallback.
- Template browsing must feel editorial and curated rather than like a plain file gallery.
- Parse review must look trustworthy and structured, not like raw machine output.
- Premium template locks should feel aspirational and clear, not frustrating or deceptive.

### React UI Implementation Notes

- Use separate React feature modules for:
  - template gallery
  - template preview
  - import uploader
  - parse review
- Template filters should be stateful and URL-friendly if product wants shareable gallery states later.
- Upload and parse progress should be driven by explicit job-state models rather than ad-hoc booleans.
- Keep parse review editable through controlled form state so corrections can flow naturally into draft creation.

### Layout And Responsive Requirements

- Desktop:
  - start-choice screen can use a dual-card or dual-panel layout
  - template gallery should support responsive card grid
- Tablet:
  - filters may collapse into a drawer or horizontal chip row
- Mobile:
  - stack start choices vertically
  - template cards must remain legible without dense metadata
  - upload area must support tap-first interaction as well as drag-drop where available

### Visual And Interaction Requirements

- Template cards must prioritize preview image, title, category, and entitlement state.
- Hover states should reinforce professionalism, but all key actions must also be obvious without hover.
- Upload states must clearly separate:
  - selected file
  - uploading
  - scanning
  - parsing
  - review ready
- Parse confidence or warning states should use informative labels and helper text, not just colored badges.
- The user should always have a visible fallback path back to template-first creation if import fails.

### Definition Of Ready For Engineering

- Template card metadata contract is approved.
- Import job-state model is approved.
- Parse review schema is approved.

### Definition of Done

- Template browse, preview, and selection work on desktop and mobile.
- Import path handles upload, parsing, review, and builder entry.
- Plan locks and error states are covered by tests.
