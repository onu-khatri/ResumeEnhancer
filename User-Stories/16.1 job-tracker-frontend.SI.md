# Supporting Information — Job Tracker Board And Application Follow-Up Workspace

## Suggested Screens

- Job tracker board
- Add/edit job card dialog or drawer
- Job detail side panel
- Tracker limit / upgrade prompt

## Design Token Guidance

- Give each stage a subtle identifying color or label treatment while keeping the page professional.
- Use surface tokens that make cards feel movable and actionable.
- Follow-up or date-related urgency should use restrained emphasis, not aggressive alert colors everywhere.

## Edge Cases

- User has zero resumes but wants to track jobs.
  - The tracker must remain usable without a linked resume, so the association picker should allow an empty state and not block job creation.
- User deletes a related resume after linking it to a job card.
  - The card must degrade to an unlinked state with a clear indicator rather than pointing at a missing document.
- User reaches tracker limit while editing an imported draft flow.
  - If a card cannot be added due to a limit, the UI must explain the cap and offer an upgrade path without discarding the user's in-progress entry.
- User uses keyboard-only navigation to move cards between stages.
  - Stage moves must be fully achievable via keyboard alternatives to drag-and-drop, with focus preserved after the move.

## Testing Focus

- Stage move persistence.
  - Verify moving a card between stages persists correctly and reflects in the board on reload.
- Small-screen board usability.
  - Confirm stage columns and cards remain navigable on narrow screens without horizontal scroll traps.
- Limit messaging and upgrade continuation.
  - Assert the limit banner appears at the correct threshold and links to an upgrade flow that restores the user's context.
- Accessibility of drag/move interactions.
  - Verify keyboard and screen-reader paths for moving cards are complete and announce changes.

## Developer Notes

- Treat board and list view as presentation modes over the same state model.
  - Keeping a single underlying state model means switching between board and list never forks logic or diverges data.
- Support optimistic move UI with rollback on failure.
  - Moves should update optimistically for responsiveness, then roll back to the persisted stage if the mutation fails.
- Keep date and follow-up logic simple in MVP to avoid accidental calendar-scheduler scope creep.
  - A single next-follow-up date is sufficient initially; full reminder scheduling can be added later without over-engineering now.
