## [ATS-FE-001] — Resume Checker And Job Match Review Workspace

**Module:** ATS Analysis & Job Matching  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** Job Seeker, Premium Subscriber  
**Dependency:** ATS-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a user tailoring a resume for applications,  
I want to see an ATS-style score, missing keywords, and job-match recommendations,  
so that I know what to improve before I apply and can make focused changes instead of guessing.

### Description

This story covers the frontend workspace for resume review, ATS-style analysis, and job-description matching. The UI must let the user select a resume, optionally paste or upload a job description, run an analysis, and inspect results as a structured report rather than a single opaque score.

**Research context:** Novorésumé's ATS checker scores across 5 areas (Job Match / Keywords, Format & Structure, Content Quality, Section Organization, Technical Elements) with per-category sub-scores and concrete fix recommendations. Its job matcher scores across 5 categories (Hard Requirements, Skills Alignment, Seniority Fit, Industry Match, Career Trajectory) with an explicit "honest, not flattering" stance — if a user is not a fit, the tool says so. Both run in ~1 minute. A two-tier funnel (free quick check vs. email-gated complete analysis) is a proven lead-gen pattern. General analysis and job-specific match must be clearly distinct modes.

### Scope

**Included In Scope**

- Analysis launcher for selected resume.
- Job-description paste/input UI.
- Progress state while analysis runs.
- Report view with score breakdowns and recommendation groups.
- Rerun flow after edits.
- Premium gate state where applicable.

**Out Of Scope**

- Full grammar editor.
- Admin scoring-rule UI.
- Recruiting analytics or employer-side features.
- Public shareable analysis reports.

### Preconditions

- A resume exists — the analysis workspace needs at least one saved resume to run against; if the user has no eligible resume, the UI should present an empty state with a clear path to create one rather than a broken launcher.
- Analysis entitlement is available or premium-lock messaging is configured — the frontend must know whether the user's plan allows the requested analysis depth (quick check vs. full report) so it can show the correct free/premium experience up front.
- Analysis response schema is available — the report renderer needs a defined contract for overall score, per-category sub-scores, findings, and recommendations so the workspace can render structured sections instead of a single opaque number.
- Job-description input supports text paste at minimum — the job-match mode must accept plain-text paste as the baseline input method, with any richer inputs (file upload, URL fetch) treated as optional enhancements.

### Detailed Workflow

1. User opens the analysis area and selects a resume.
2. User chooses general resume check or job-tailored match.
3. If job match is selected, user pastes a job description.
4. User starts analysis.
5. UI shows queued/running state and prevents duplicate starts.
6. When results are ready, UI displays:
   - overall score
   - category scores
   - missing keywords
   - recommended actions
   - optional rerun timestamp
7. User edits the resume and reruns analysis to compare changes.

### Functional Requirements

- The UI must make clear whether the current report is a general resume check or a job-specific match.
- Scores must be accompanied by human-readable findings and next actions.
- Recommendations should link conceptually back to sections the user can edit.
- The system must preserve the job description input for reruns unless user clears it.
- The UI must identify stale results if the resume changed after the report was generated.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a user selects a resume and submits a job description  
When analysis completes  
Then the UI shows overall score, category breakdowns, missing keywords, and recommended next actions.

**AC2 — Validation**  
Given the user submits no job description for a job-match run or submits insufficient content  
When they start analysis  
Then the UI blocks the request and explains what is missing.

**AC3 — Error Handling**  
Given analysis fails or times out  
When the failure occurs  
Then the UI preserves inputs, explains the failure, and offers retry without forcing re-entry.

**AC4 — Improvement Loop**  
Given analysis returns fix suggestions  
When the user edits the resume and reruns analysis  
Then the UI clearly identifies the new run and updated results.

**AC5 — Premium And Empty States**  
Given a free user or a user with no eligible resume enters the area  
When prerequisites are missing  
Then the UI shows correct empty or upgrade messaging instead of a broken report view.

### Business Rules

- Scores must be advisory, not promises of hiring success — every report must frame scores and percentages as guidance that can be improved, never as a guarantee of passing an ATS or securing an interview, so the product avoids making misleading claims.
- Findings should separate ATS, content, and job-match perspectives. ATS and job-match must be distinct report modes — general resume checking and job-specific matching are different user intents and must never be merged into one ambiguous report; the UI must clearly label which mode produced the current results.
- Analysis reporting should model the proven categories: ATS = (Keywords/Match, Format, Content Quality, Section Organization, Technical); Job Match = (Hard Requirements, Skills Alignment, Seniority Fit, Industry Match, Career Trajectory) — these named categories give the report structure and match the competitive benchmark the product is modeled on.
- Premium gating may limit detailed results, reruns, or job-specific analysis depth — free users may receive a summary or a limited number of runs while detailed breakdowns or unlimited reruns require a paid plan, and the gating boundary must be clearly communicated.
- Analysis reports must be tied to the resume version used to generate them — a report generated before the user edits their resume must be flagged as stale so the user isn't misled into trusting outdated findings.
- Analysis feedback should be honest, not flattering — if the match is weak, the product says so constructively — the tool must report low fit or missing hard requirements directly rather than inflating scores to keep the user happy.

### Validation Rules

- Job-description text must meet minimum length for match analysis.
- Resume must be in a supported state for analysis.
- Prevent duplicate concurrent analysis runs from the same workspace.
- Block analysis on drafts with critically missing required sections if the engine requires them.

### Error Handling

- Differentiate validation, timeout, and service-unavailable states — a missing job description should show a validation message pointing at the input, a slow run should show an active progress state with reassurance, and a backend outage should show a service-unavailable message with retry, each as a distinct experience rather than one generic error.
- Preserve analysis history per draft where feasible — previous reports and their timestamps should remain accessible so a failed rerun doesn't erase the last known-good results, allowing the user to compare against a prior state.
- Show stale-result labels if a newer run starts or the resume changes afterward — if the resume version changes after a report was generated, the UI must mark the report as out-of-date and prompt a rerun rather than silently displaying results that no longer reflect the current content.

### Security Considerations

- Treat pasted or uploaded job descriptions as untrusted text — any job-description input must be treated as potentially malicious content, rendered with proper output encoding and never executed as script or interpreted as markup, since it originates from external, uncontrolled sources.
- Avoid exposing internal scoring-rule details that enable abuse or gaming beyond intended transparency — the UI should explain what factors affect the score at a high level without revealing the exact weights, thresholds, or rule internals that could let users reverse-engineer and game the system; findings should be actionable but not a complete blueprint of the scoring algorithm.

### Data Requirements

- Resume reference and version
- Job-description input
- Analysis report structure
- Recommendation metadata

### UX Notes

- Use grouped findings with severity and action labels.
- Avoid presenting only one top-line score without explanation.
- Make the path back into editing obvious from every report section.

### UI/UX Design Requirements

- The report screen must feel analytical and trustworthy, not gimmicky or overly gamified.
- The score should be prominent but must not dominate the experience at the expense of actionable findings.
- The layout should support a clear read order:
  - overall result
  - category breakdown
  - prioritized recommendations
  - connection back to editable resume sections
- The report should help the user understand what changed between runs when possible.
- Visual tone should balance coaching and precision rather than judgment.

### React UI Implementation Notes

- Implement the analysis workspace as a set of composable report sections rather than one large rendering component.
- Keep report mode state explicit so the UI can switch language and fields between generic analysis and job match.
- Recommendation cards should be reusable and support future deep-linking back into builder sections.
- Stale-result handling should be driven by resume-version comparison state, not only timestamps.

### Layout And Responsive Requirements

- Desktop:
  - support a summary-first layout with follow-on detail sections
  - recommendation pane or sticky summary can be used if not visually noisy
- Tablet:
  - score and breakdown may stack
- Mobile:
  - report must remain readable as sequential cards or sections
  - charts and score breakdowns must degrade gracefully into simple lists when needed

### Visual And Interaction Requirements

- Use severity and priority styling consistently across findings.
- Keyword-gap and missing-skill patterns should be visually scannable.
- Loading states should communicate that analysis may take time without implying the app froze.
- Rerun states must clearly replace or supersede previous report context.
- Premium summary-only states should still provide enough value to justify the feature.

### Definition Of Ready For Engineering

- Analysis report schema is approved.
- Score category vocabulary is approved.
- Premium-lock behavior is approved.

### Definition of Done

- Analysis flow works from input to report to rerun.
- Key loading, failure, stale-result, and premium states are covered.
- Findings are understandable without claiming proprietary scoring parity.
