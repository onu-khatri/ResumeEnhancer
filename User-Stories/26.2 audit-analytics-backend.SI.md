# Supporting Information — Internal Analytics Summary And Audit Log Retrieval Services

## Proposed APIs

- `GET /admin/analytics/summary`
- `GET /admin/audit-logs`

## Example Audit Row

```json
{
  "id": "aud_123",
  "category": "role_assignment",
  "actorUserId": "adm_1",
  "targetUserId": "usr_22",
  "timestamp": "2026-08-14T14:00:00Z"
}
```

## Proposed Entities

- `AuditLog`
- `AnalyticsSummary`
- `Role`
- `AccessProfile`

## Suggested Technical Controls

- Read-only internal query service: expose no mutation paths, keeping the MVP strictly observational.
- Category/time-range validation: constrain queries to supported categories and bounded time windows to prevent unbounded scans.
- Internal permission gating: enforce role-based access and category-scoped visibility for all retrievals.

## Edge Cases

- Extremely large audit result windows: the service must paginate and enforce limits to avoid excessive loads.
- One summary source delayed while another is available: return stable partial data rather than failing the entire response.
- Operator visibility differs by category: restrict results to the categories the operator is cleared to see.

## Test Focus

- Authorization boundaries: verify operators only receive data within their permitted scope.
- Filter validation: confirm invalid filters and time ranges are rejected cleanly.
- Partial-data behavior: ensure partial availability yields stable, frontend-consumable responses.
- PII minimization: verify summaries and audit rows mask personal fields not needed for diagnosis.

## Developer Notes

- Avoid turning these APIs into generic unrestricted reporting endpoints, keeping the surface curated and scoped.
- Keep summary metrics curated and useful for product operations first, deferring advanced analytics until operator needs are proven.
