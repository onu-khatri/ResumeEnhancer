# Supporting Information — Feature Flag And System Setting Retrieval / Update Services

## Proposed APIs

- `GET /admin/feature-flags`
- `PATCH /admin/feature-flags/{id}`
- `GET /admin/system-settings`
- `PATCH /admin/system-settings/{id}`

## Example Feature Flag Payload

```json
{
  "id": "ff_ai_quick_check",
  "enabled": true,
  "editable": true
}
```

## Proposed Entities

- `FeatureFlag`
- `SystemSetting`
- `AuditLog`

## Suggested Technical Controls

- Approved config allowlist: expose only curated flags and settings, rejecting unknown keys or ids outright.
- Type/range validators: enforce per-item value types and bounds so a boolean flag cannot accept a string.
- Sensitive change audit logging: record both successful and denied change attempts with before/after values.

## Edge Cases

- Concurrent operator edits: detect version conflicts and prevent one operator from silently overwriting another's change.
- Attempt to edit deprecated config item: reject or warn clearly rather than persisting a change to an item no longer active.
- Mixed success across config families not allowed: keep multi-item updates atomic where policy requires, avoiding partial configuration.

## Test Focus

- Editability enforcement: verify protected and view-only items cannot be mutated.
- Type validation: confirm each item is validated against its declared value type.
- Audit completeness: ensure every change attempt is recorded with before/after state.

## Developer Notes

- Keep internal config contracts descriptive enough that frontend can explain item meaning safely, including editability and impact notes.
- Avoid exposing internal runtime or secret-management complexity through these APIs, keeping secrets and infra config out of scope.
