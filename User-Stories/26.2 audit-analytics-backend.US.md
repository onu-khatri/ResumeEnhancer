## [OBS-BE-001] — Internal Analytics Summary And Audit Log Retrieval Services

**Module:** Analytics & Audit  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Observability Service  
**Dependency:** ADM-BE-001, BILL-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the observability service,  
I want to provide authorized internal access to product-level analytics summaries and audit log retrieval,  
so that operators can monitor trust-sensitive product behavior and investigate significant changes safely.

### Description

This story covers backend support for an internal visibility workspace. It includes APIs for high-level product/operational summaries and searchable audit-log retrieval. The service must enforce strict access control, support filtering, and avoid exposing more sensitive data than internal consumers need for diagnosis.

### Scope

**Included In Scope**

- Analytics summary retrieval for approved internal metrics.
- Audit log retrieval with filtering.
- Access control and scope enforcement.

**Out Of Scope**

- Full data warehouse querying.
- Infra telemetry systems.
- Finance reconciliation detail reporting.

### Preconditions

- Audit logging exists in core domains so there is a populated event stream for the retrieval APIs to query.
- Internal metrics summary definitions are approved, constraining which high-level signals are exposed rather than allowing arbitrary queries.
- Admin/operator authorization is available to gate both analytics and audit visibility behind role checks.

### Detailed Workflow

1. Authorized operator requests analytics summary or audit records.
2. Service validates permission scope.
3. Service returns approved metrics summaries and/or filtered audit events.
4. Operator uses the result for support, compliance, or product diagnosis.

### Functional Requirements

- Analytics summary endpoints must expose only approved internal metrics, not raw unrestricted data.
- Audit retrieval must support practical filtering such as category, actor, target, or time window.
- Access to analytics and audit may require different permissions or scopes.
- Payloads should support operational diagnosis without overexposing sensitive personal data.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authorized operator requests internal summaries or audit logs  
When the service processes the request  
Then it returns only approved data within the operator’s scope.

**AC2 — Filtering**  
Given the operator filters by supported parameters  
When the request is processed  
Then the service returns matching audit or summary data predictably and efficiently.

**AC3 — Authorization Boundary**  
Given an operator lacks permission to access the requested data  
When the request is processed  
Then the service denies it without exposing restricted details.

**AC4 — Error Handling**  
Given one data source is temporarily unavailable  
When the request is processed  
Then the service returns stable errors or partial-response semantics that let the frontend render meaningfully.

### Business Rules

- Internal visibility is read-only in MVP, keeping the first iteration focused on understanding before introducing operational actions.
- Audit logs are trust-sensitive operational assets and must be access-controlled, since they reveal who changed what across the platform.
- Summary metrics should support product and support decisions, not become an unbounded reporting API that operators query arbitrarily.

### Validation Rules

- Filters must be limited to supported fields and ranges, rejecting ad hoc query parameters that fall outside the approved set.
- Time windows and category filters must be validated to prevent unbounded scans over the full audit history.
- Operators may have scoped visibility based on role, so some may see billing audit while others see only content or access events.

### Error Handling

- Distinguish unauthorized, invalid filter, unavailable source, and empty-result responses so the frontend renders each distinctly.
- Preserve stable contracts for partial-data conditions where used, so a delayed metric source does not break the whole response.
- Avoid leaking internals in operator-facing error payloads beyond what is useful, keeping messages concise and safe.

### Security Considerations

- Enforce strict internal authorization, treating analytics and audit access as privileged capabilities.
- Minimize PII exposure in summaries and audit records, masking personal fields where they are not needed for diagnosis.
- Ensure audit retrieval itself is auditable if required by policy, so viewing sensitive events can itself be traced.

### Data Model

Analytics and audit visibility are backed by a curated `AnalyticsSummary` for high-level metrics and an `AuditLog` for detailed event retrieval. Access control entities participate because visibility into these records is itself permissioned.

#### AuditLog

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable audit entry identifier. |
| `category` | enum | Event category such as `role_assignment`, `billing`, or `content`. |
| `action` | string | Action performed. |
| `actorUserId` | string | Operator/user who performed the action. |
| `targetType` | string | Kind of entity affected. |
| `targetId` | string | Identifier of the entity affected. |
| `metadata` | json | PII-minimized event details. |
| `timestamp` | datetime | When the event occurred. |

#### AnalyticsSummary

| Property | Type | Description |
| --- | --- | --- |
| `metricKey` | string | Stable metric identifier. |
| `label` | string | Human-readable metric label. |
| `value` | number | Current metric value. |
| `period` | string | Aggregation window such as `24h` or `7d`. |
| `asOf` | datetime | When the summary was computed. |

#### Role

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable role identifier. |
| `name` | string | Role name. |
| `permissions` | string[] | Permission keys for observability access. |

#### AccessProfile

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable access profile identifier. |
| `name` | string | Profile name. |
| `scopeRules` | json | Which metrics/audit categories are visible. |

#### Example JSON

```json
{
  "id": "aud_123",
  "category": "role_assignment",
  "action": "role_assigned",
  "actorUserId": "adm_1",
  "targetUserId": "usr_22",
  "timestamp": "2026-08-14T14:00:00Z"
}
```

#### Relationships

```text
AuditLog * ─── 1 Role/AccessProfile        (scoped visibility)
AnalyticsSummary * ─── 1 AccessProfile     (metric scope)
```

#### Business Notes

- `AuditLog` is append-only in practice; retrieval is read-only and does not mutate history.
- `AnalyticsSummary` entries are pre-aggregated and curated, not raw event streams.
- `Role` and `AccessProfile` determine which categories and metrics an operator can retrieve.
