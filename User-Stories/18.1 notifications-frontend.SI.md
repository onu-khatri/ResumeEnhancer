# Supporting Information — User Notifications And Communication Preferences Experience

## Suggested Screens

- Notification panel or drawer
- Full notification list page
- Notification preferences section

## Suggested Components

- Notification bell or entry point
- Notification item row
- Unread badge
- Empty notification state
- Preferences toggle group

## Frontend Component Inventory

| Component | Responsibility | Reusability |
| --- | --- | --- |
| `NotificationBell` | shell entry point and unread count | shared |
| `NotificationPanel` | compact list surface | shared |
| `NotificationListPage` | full-screen notification history | shared |
| `NotificationItem` | single event summary and action | shared |
| `NotificationPreferencesForm` | communication preference editing | shared |

## Design Token Guidance

### Typography

- Notification titles should be concise and scannable.
- Secondary detail text should support context without becoming verbose.

### Color

- Use subtle status differentiation by category and read state.
- High-priority states should be noticeable but not visually aggressive.

### Spacing

- Notification rows should preserve enough spacing to separate events clearly.
- Preferences section should use calm, form-like spacing similar to settings UI.

## API And Entity Map

- APIs: `GET /notifications`, `PATCH /notifications/{id}`, `PATCH /notifications/preferences`
- Entities: `Notification`, `UserPreference`

## Edge Cases

- Notification target points to an item the user no longer has access to (a deleted document, a revoked export, or a canceled subscription) — the frontend must show a graceful "this item is no longer available" state rather than a raw error or broken deep link.
- Read-state update fails after the user has already opened the destination, leaving the notification visually unread even though the user has acted on it; the UI should retry silently and reconcile local read state optimistically.
- Preferences differ across device sessions (a user disables a category on mobile but the desktop still shows it enabled), requiring the frontend to refresh preferences on mount and surface the most recently persisted state.

## Test Focus

- Read/unread behavior must be tested for both marking a single item and bulk-marking, verifying the unread badge count updates correctly and persists across a page reload.
- Deep-link routing should be tested with valid, stale, and permission-revoked targets to confirm the frontend blocks navigation to inaccessible resources and surfaces a helpful fallback.
- Empty state should render clearly when the user has zero notifications and when notifications have been filtered out by category, with no visual flicker between loading and empty states.
- Preference update success/failure must be tested to confirm that a successful toggle persists, a failed toggle reverts with an inline error, and mandatory categories remain locked and non-editable.

## Developer Notes

- Keep notification-category display mapping centralized in a single shared module (category key → label, icon, and severity) so that the bell, panel, list, and preferences form all render categories consistently and future category additions require a change in only one place.
- Support optional future pagination or lazy loading if notification history grows, designing the list component with a cursor or offset pattern from the start to avoid a costly refactor when notification volume exceeds a single page of results.
