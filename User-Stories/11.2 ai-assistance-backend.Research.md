# Research — AI Assistance Backend (Generate, Rewrite, Tailor)

## Research Basis

The AI assistance domain needs backend support for scoped text generation, rewriting, and job-description-aware tailoring. The selected competitors provide clear signals on what tasks AI should perform and what safety constraints should be enforced, but not on internal provider architecture.

## What The Research Means For The Backend

- AI is not a single `POST /ai/generate` endpoint. It requires **task-specific contracts** (summary, bullet, rewrite, tailor) because each task has different input context, output shape, and guardrail needs.
- Safety must be enforced server-side: the system must prevent fabricated qualifications, metrics, or inflated titles from reaching the user.
- Quota must be tracked reliably (per user, per period, per action type) — free-tier users must see their remaining balance, and requests must be blocked cleanly when exhausted.
- Results must be **version-linked** to the resume content used as input. If the user edits the resume, stale AI suggestions should be flagged (or re-generatable against the new version).
- The backend must handle provider failures (timeout, rate limit, moderation flag) and return distinct error codes so the frontend can surface different messages (retry, quota, moderation, unavailable).

## Requirement Interpretation

| Backend Requirement | Rationale |
| --- | --- |
| Task-specific AI endpoints | Narrow contracts enable targeted prompting, safety filtering, and distinct quotas per action type |
| No-fabrication prompt engineering | System must instruct the model to rephrase/restructure user-provided facts only, not invent credentials, metrics, or job titles |
| Output moderation | Server-side filter for toxic, fabricated, or misleading content before returning to frontend |
| Quota tracking (per user, per period) | Free/premium differentiation and cost control |
| Version-linked results | Stale-suggestion detection when resume content changes |
| Idempotent request handling | Prevent double-usage-counting on retries |
| Provider abstraction | Allows swapping or fallback between AI providers |
| Cost logging | Track AI token/cost usage per request for business analytics |

## Hidden Requirements Inferred

- Prompt templates per action type stored securely (not in client-side code).
- Context-construction logic: which resume sections to include as input for each AI action.
- Moderation pipeline with configurable thresholds (block vs. flag for review).
- Fallback behavior when AI provider is unavailable (graceful degradation, not 500).
- Audit trail: log what was requested, what was generated, and whether the user accepted or rejected.

## Risks If Under-Specified

- Engineers may build one monolithic AI endpoint without task-specific prompt engineering, producing generic output.
- Without explicit no-fabrication rules in the backend, AI may hallucinate credentials, opening trust and reputational risk.
- Quota may be counted incorrectly on retries, causing user frustration or revenue leakage.
- Provider costs may spiral if usage is not metered and capped at the backend level.

## Recommendation To Developers

- Design AI as a pipeline: context extraction → prompt construction → provider call → moderation → response mapping → quota decrement.
- Keep prompt templates and moderation rules in configuration, not hardcoded, so they can be tuned without deploys.
- Treat the "accept" step as important as the "generate" step — log accept/reject to measure AI quality and guide prompt improvement.

## Open Questions

- Which AI provider(s) in MVP?
- What is the exact quota model (per month, per tool, global)?
- Should accepted AI text be flagged as "AI-assisted" in the data model (for analytics but not in user-facing labels unless desired)?
- Do we allow users to provide free-form prompts or only structured context?
