# Research — Multi-Language Resume And Cover Letter Authoring Experience

## Research Basis

Public Novorésumé help-center content explicitly documents multi-language document creation, management, and limitations. This is important because it provides a concrete model (independent language versions, no auto-sync, tags for organization, no RTL yet) that sets both feature expectations and boundary conditions.

## What The Research Means

- Multi-language is **explicitly a manual versioning model**, not automatic translation. This sets realistic user expectations and prevents misleading "it will translate automatically" assumptions.
- Each language version is an **independent, editable document** with its own content and localized labels.
- **No cross-language auto-sync** is the documented behavior — users must explicitly create and maintain each language variant.
- **RTL (Right-to-Left) is not yet supported** even by a market-leading competitor — a realistic constraint for MVP scope.
- Document organization (Views + Tags) is the companion feature needed to make multi-language management usable at scale.

## Product Interpretation

- The model is: "create a new document, choose its language, write in that language, tag it for organization." Not: "translate my resume."
- Section labels should localize based on the document's language setting — but this is UI chrome localization, not content translation.
- Users must be able to visually distinguish language variants quickly (badge, tag, label) to avoid editing the wrong version.
- The document-capacity limit must account for multi-language users who create several variants (e.g., a user with English, Spanish, and German versions uses 3 of their document slots).

## Hidden Requirements Inferred

- Document language as a first-class property (stored, visible, filterable).
- Localized section-label mappings per supported language.
- Document duplication flow (users should create a Spanish resume by duplicating their English one with a new language tag).
- Tag/label system for organization (language tags + purpose tags).
- Capacity planning: document limits must accommodate multi-language users (Novorésumé: 144 docs; 3 languages = 48 docs per language).

## Risks If Under-Specified

- Users may expect automatic translation and become disappointed when it is not provided.
- Users may accidentally edit the wrong language variant if differences are hard to detect.
- RTL or non-Latin character support may be assumed as "just text" by developers, leading to layout breakage on complex scripts.
- Section-label translation may be inconsistently applied if not part of a structured localization system.

## Recommended Scope Interpretation

- MVP: support a finite list of left-to-right languages; document-language metadata; localized section labels; duplication with language tagging; visible language badge.
- Defer: RTL support, automatic machine translation, and full UI localization beyond section labels.
- Design the document model to carry a `languageCode` from day one, even if only one language is implemented initially.

## Open Questions

- How many languages are supported in MVP, and is the list identical for section labels and UI chrome?
- Should the product warn or block RTL languages explicitly, or silently omit them from the language selector?
- Should document limits account for multi-language users (e.g., "you have 10 of 50 documents, 3 of which are language variants")?
