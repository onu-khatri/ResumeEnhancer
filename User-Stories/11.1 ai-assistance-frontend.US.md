## [AI-FE-001] — AI Content Suggestions And Rewrite Controls

**Module:** AI Assistance  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** Job Seeker, Student, Career Changer  
**Dependency:** AI-BE-001  
**Source Classification:** Observed, Documented, Inferred, Recommended

### User Story

As a user improving resume content,  
I want AI suggestions for summaries, bullets, and rewrites inside the builder,  
so that I can create stronger content faster without leaving the resume workflow or losing editorial control.

### Description

This story covers in-context AI assistance inside the resume builder. AI must feel like a scoped assistant, not an uncontrollable auto-writer. The frontend must let users trigger supported AI actions, provide or review context, see progress, inspect suggestions, compare against existing text where relevant, and explicitly accept or reject results.

**Research context:** Novorésumé packages AI as a 10-task toolkit with explicit "never invents qualifications" / "true to your experience" guardrails. Each tool offers one free use — a genuine result, not a blurred preview. Free accounts show a visible AI credit counter (e.g., "2 left this month"). This product must adopt the same stance: AI that assists with discrete, named tasks, preserves user control, and never fabricates credentials, metrics, or experience.

### Scope

**Included In Scope**

- Section-level AI actions such as generate, rewrite, shorten, expand, and improve tone.
- Optional job-description-aware tailoring input.
- Loading, retry, and quota-exhausted states.
- Suggestion preview and accept/reject flow.
- Inline or drawer-based AI interaction model.

**Out Of Scope**

- Autonomous whole-resume rewriting without user control.
- AI-powered chat assistant.
- Admin prompt configuration UI.
- Non-text design-generation features.

### Preconditions

- User is in an editable resume or cover-letter context — AI actions must only appear when the user is actively editing a supported document, so suggestions always have a clear insertion target rather than appearing as disconnected or floating actions.
- AI entitlement and usage state are available — the frontend needs the user's current plan tier, remaining credit count, and quota limits loaded before the AI panel opens so it can warn the user up front instead of failing after they've invested effort writing a prompt.
- The targeted section supports AI actions — each section must declare which AI action types are legal for it (e.g., summary supports rewrite/expand, header does not), and the UI must disable or hide unsupported actions based on that mapping.
- Safety and moderation outcomes can be surfaced meaningfully in UI — the response contract must distinguish between blocked content, provider errors, timeouts, and empty results so the frontend can render an honest, non-technical explanation instead of a generic failure message.

### Detailed Workflow

1. User opens a supported section such as summary or experience.
2. User clicks an AI action such as `Generate`, `Rewrite`, or `Tailor to Job`.
3. UI opens a contextual panel with current text, optional instructions, and quota hint.
4. User submits AI request.
5. UI shows loading and blocks duplicate requests for the same target.
6. Results return as one or more suggestions.
7. User reviews suggestions and chooses `Insert`, `Replace`, `Try Again`, or `Dismiss`.
8. Accepted content is written into local draft state and then persisted through normal builder save flow.

### Functional Requirements

- AI actions must be contextual to the current section and clearly named.
- The user must understand whether AI will create new text or transform existing text.
- The UI must preserve original content until the user accepts a suggestion.
- AI usage limits or paywalls must be visible before the user wastes effort filling prompts.
- Tailoring actions must support pasting a job description when applicable.
- The frontend must distinguish AI-generated but unaccepted text from authored resume content.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a user opens an AI action on a supported section  
When they submit valid context  
Then the UI shows loading, returns suggestions, and allows accept, replace, retry, or dismiss actions.

**AC2 — Context Preservation**  
Given a user already has manual text in a field  
When AI suggestions are returned  
Then the original content remains intact until the user explicitly chooses to replace or insert text.

**AC3 — Validation And Quota**  
Given required context is missing or the user exceeds plan quota  
When they request AI help  
Then the UI explains the issue and offers alternate next steps such as editing manually or upgrading.

**AC4 — Error Handling**  
Given the AI request times out, fails moderation, or the provider is unavailable  
When the failure occurs  
Then the UI preserves draft content, explains the failure type, and supports retry where appropriate.

**AC5 — Accessibility**  
Given the AI workflow is used with keyboard or assistive technology  
When the user navigates prompts, results, and actions  
Then focus handling, labels, and result announcements remain accessible.

### Business Rules

- AI must assist, not silently overwrite user content — generated suggestions are always presented for explicit review and acceptance; no AI action may modify authored resume text until the user confirms an accept/replace decision.
- AI must not fabricate qualifications, metrics, or job titles. Output should rephrase/restructure user-provided facts only — the prompt and moderation layer must enforce a "true to your experience" guardrail so suggestions never invent degrees, employers, dates, or numbers the user did not supply.
- Premium gating must be explicit where applicable — when an action requires a paid plan or consumes a limited credit, the UI must state the cost or lock clearly before the action runs, and must show the remaining balance (e.g., "2 left this month") rather than surprising the user afterward.
- Tailoring actions should accept job-description context when present — when a user pastes a job description, the AI may align language with that description, but only by rephrasing user-provided facts, never by inserting fabricated skills or qualifications to match the posting.
- AI output must remain editable like any other text after acceptance — once a suggestion is accepted into the draft, it becomes ordinary resume content subject to the same editing, validation, and save flow as manually typed text.
- AI usage limits or credit state must be visible to users before they initiate an action — the quota indicator must render up front in the AI panel so users can budget their limited uses and are never forced into a dead-end after submitting a request.

### Validation Rules

- Limit prompt size and supported section contexts.
- Prevent duplicate requests while one is pending for the same target.
- Sanitize pasted job-description input in the UI.
- Block unsupported action types for sections that do not allow them.

### Error Handling

- Maintain draft text during failures — every failure path (timeout, moderation block, provider outage, quota exceeded) must leave the user's current section text untouched and fully recoverable, so a failed AI request never costs the user their existing work.
- Show quota, moderation, and availability issues differently — each failure type needs its own visual treatment and copy: quota issues point to an upgrade path, moderation blocks explain the content policy calmly, and provider outages suggest retry later, avoiding a single confusing generic error.
- Allow retry or manual continue — after any failure, the user must be able to retry the same request with their original prompt preserved, or dismiss the panel and continue editing manually without losing context.
- Never auto-insert partial streamed output unless the product explicitly supports it — if streaming is used, only display intermediate tokens in a clearly-labeled "generating" preview; the actual draft must only be written once the user accepts the completed suggestion.

### Security Considerations

- Warn users not to paste unnecessary sensitive data — the UI should display a brief, non-intrusive notice in the job-description or context input reminding users to avoid sharing PII like addresses, phone numbers, or ID numbers that aren't needed for the rewrite, since this text is transmitted to the AI provider.
- Avoid exposing hidden system prompts or internal provider details — the frontend must never render or log the underlying prompt templates, model parameters, or provider error payloads; it should surface only user-facing explanations so attackers can't probe for prompt-injection weaknesses.
- Respect moderation outcomes and do not display blocked content if policy forbids it — if the backend flags output as policy-violating, the frontend must not render it in any form (including debug views or network panels) and should show the approved explanatory message instead.

### UX Notes

- Keep AI actions inline to the section being improved.
- Use compare-style presentation when suggestions replace existing copy.
- Do not make AI the only path to complete a section.

### UI/UX Design Requirements

- AI must feel like an assistant inside the builder, not a separate chatbot product.
- The UI should reduce fear of losing existing text by visually separating:
  - current content
  - suggested content
  - accepted content
- Suggestion review should feel deliberate and trustworthy.
- The visual language for AI should be distinct enough to signal "generated suggestion" without overwhelming the product’s primary design system.
- Quota and premium messaging must be clear but should not interrupt every edit.

### React UI Implementation Notes

- Implement AI panels as reusable React overlays such as drawers, inline panels, or anchored modals depending on section context.
- Keep accepted text application separate from AI fetch state so users do not lose results during render transitions.
- Suggestion lists should use stable keys and controlled selection state.
- If compare mode is used, isolate diff rendering into its own component rather than mixing it into generic text fields.

### Layout And Responsive Requirements

- Desktop:
  - AI interaction may appear as side drawer or inline contextual panel
- Tablet:
  - drawer or bottom sheet can be used if side space is limited
- Mobile:
  - AI interaction should use a focused single-column review layout
  - accept/reject controls must be large and obvious

### Visual And Interaction Requirements

- Loading state should reassure users that content is being generated without blocking the whole builder.
- Accepted/rejected actions must have immediate feedback.
- For rewrite actions, before/after presentation should make the tradeoff easy to understand.
- Moderation or blocked-output states must be explanatory and calm, not vague.
- Upgrade prompts for AI quota should appear as contextual continuation surfaces, not full-screen dead ends unless necessary.

### Definition Of Ready For Engineering

- Supported AI actions by section are approved.
- Suggestion review pattern is approved by design.
- Usage/quota API shape is available.

### Definition of Done

- AI controls work in core supported sections.
- Acceptance, rejection, retry, quota, and moderation states are tested.
- Accessibility for drawer or modal interaction is verified.
