# Supporting Information — Subscription And Billing Management Experience

## Suggested Screens

- Subscription overview
- Plan-change state
- Cancellation explanation state
- Invoice/history summary state

## Suggested Components

- Current plan summary card
- Status badge
- Included-features list
- Billing action panel
- Invoice list or table
- Support/help callout

## Frontend Component Inventory

| Component | Responsibility | Reusability |
| --- | --- | --- |
| `SubscriptionSummaryCard` | current plan and status | shared billing |
| `PlanFeaturesList` | included capability summary | shared |
| `BillingActionPanel` | upgrade/cancel/manage actions | shared |
| `InvoiceHistoryList` | receipt/invoice summaries | shared |
| `CancellationInfoPanel` | explain post-cancel outcome | shared |

## Design Token Guidance

### Typography

- Current plan and status should be immediately visible.
- Explanatory copy should stay concise and readable.

### Color

- Use neutral and semantic status colors carefully.
- Billing warnings or expiry states should be clear without feeling alarmist.

### Spacing

- Preserve strong separation between status summary and action controls.
- Allow invoice/history rows enough space to scan dates and amounts easily.

## API And Entity Map

- APIs: `GET /billing/subscription`, `GET /billing/invoices`, `POST /billing/cancel`
- Entities: `Subscription`, `Plan`, `Invoice`

## Edge Cases

- Subscription active but entitlement cache stale — the backend may return `status: "active"` but the user's actual feature access (entitlements) may lag behind due to caching or eventual consistency between the billing provider and the application. The UI should display the subscription state as reported by the backend, but if entitlements appear inconsistent (e.g., "Premium" plan but free-tier features), a support path should be visible to flag the discrepancy.
- Pending cancellation with immediate or delayed access loss differences — if the billing model supports end-of-term cancellation, the user's status is `pending_cancellation` but their access continues until the period end. The UI must clearly distinguish between "your access ends now" and "your access continues until [date]" so users don't prematurely stop using the product. The `CancellationInfoPanel` component serves this purpose.
- No invoice history for first-time user — a user who just subscribed (or has never been billed) will receive an empty invoice list from the backend. The UI must handle this gracefully with an empty-state message like "No billing history yet" rather than showing a blank table or error. The empty state should also include a brief note about when the user's first invoice will appear.

## Test Focus

- Current plan summary accuracy — verify that the plan name, status badge, feature list, and timing information exactly match the backend response, that status label colors are semantically correct (active=green, pending_cancellation=yellow, expired=gray), and that the summary updates when the user changes plans.
- Action availability by status — test each subscription status against the `allowedActions` array to confirm that the UI only shows permitted actions: active subscriptions should show "Cancel," pending_cancellation should not show "Cancel" again, expired subscriptions should show "Renew" or "Upgrade," and free users should see "Upgrade" but not "Cancel."
- Cancellation explanation clarity — verify that the `CancellationInfoPanel` correctly communicates whether access ends immediately or at period end, what features are lost, and what data is retained. The language must be unambiguous and tested with non-technical users for comprehension.
- Invoice-history rendering — test that paid invoices render with correct dates, amounts, and currencies; that the receipt URL link works when present; that empty states display appropriately; and that pagination controls appear when the invoice list exceeds one page.

## Developer Notes

- Treat allowed billing actions as backend-driven rather than guessed from status alone — the `SubscriptionSummaryCard` and `BillingActionPanel` components should read the `allowedActions` array from the subscription state response and render buttons accordingly. Hardcoding logic like `if status === 'active' then show cancel button` creates a fragile coupling between frontend and backend business rules that will break when new statuses or billing models are introduced.
- Keep support/help escalation visible for unsupported self-service cases — not all billing scenarios can be handled through self-service (e.g., refund requests, disputed charges, plan grandfathering). The billing page should include a persistent help/support link so users who encounter an unsupported scenario can escalate without hunting for contact information.
