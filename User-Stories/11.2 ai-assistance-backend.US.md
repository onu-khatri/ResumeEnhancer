## [AI-BE-001] — AI Request Orchestration, Safety, And Usage Accounting

**Module:** AI Assistance  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** AI Service  
**Dependency:** RES-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the AI service,  
I want to process generation and rewrite requests with quotas, moderation, cost controls, and auditability,  
so that AI features remain useful, safe, and economically sustainable.

### Description

This story covers the backend orchestration layer that turns builder context into AI suggestions. The service must validate request type, build the correct AI context, enforce plan entitlements and quotas, route to the configured provider, evaluate moderation or safety outcomes, persist usage records, and return structured suggestions to the frontend.

### Scope

**Included In Scope**

- Generation and rewrite request intake.
- Action-type validation.
- Quota and entitlement checks.
- Provider invocation through abstraction layer.
- Moderation and safety handling.
- Structured response formatting.
- Usage accounting and analytics events.

**Out Of Scope**

- Admin prompt-management UI.
- Whole-resume autonomous generation without user segmentation.
- Model-training pipelines.
- Voice or chat interaction.

### Preconditions

- User session and entitlements are valid.
- AI provider configuration is active.
- Moderation policy is defined.
- Usage-record storage exists.

### Functional Workflow

1. Receive AI request with section context and desired action.
2. Validate entitlement, quota, and payload size.
3. Construct action-specific prompt or provider request.
4. Invoke moderation checks before or after generation as policy requires.
5. Call provider through abstraction layer.
6. Normalize provider response into structured suggestions.
7. Store request metadata and usage consumption.
8. Return result to frontend or structured failure.

### Functional Requirements

- The service must support different AI actions without exposing raw provider complexity to clients.
- Entitlement and quota evaluation must happen before expensive provider calls when possible.
- Usage accounting must avoid double charging on retries and failures.
- Moderation outcomes must be expressed in client-safe language.
- Response format must support one or more suggestions plus metadata.
- Response format must support frontend review patterns such as before/after compare, explicit suggestion actions, and remaining usage display.
- Failure categories must be stable enough for the frontend to distinguish quota, moderation, provider, timeout, and validation states.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a valid AI request within quota  
When the service processes it  
Then it returns structured suggestions with request metadata and records usage correctly.

**AC2 — Validation And Entitlements**  
Given an unsupported action, missing required context, or exhausted quota  
When the request arrives  
Then the service rejects it with actionable status codes and does not call the provider unnecessarily.

**AC3 — Safety**  
Given the request or output violates policy or quality thresholds  
When moderation evaluates it  
Then the service blocks or redacts the response and records the decision.

**AC4 — Resilience**  
Given the provider times out, errors, or returns malformed output  
When the call fails  
Then the service returns a retryable failure without charging duplicate usage.

**AC5 — Usage Feedback**  
Given a request succeeds or is rejected due to quota  
When the response is returned  
Then it includes enough usage-state information for the frontend to update visible quota or lock messaging accurately.

### Business Rules

- AI usage must map to plan entitlement.
- Suggestions are advisory and not auto-applied.
- Provider selection must remain abstracted for future switching.
- Cost control must be measurable by user, plan, action type, and provider.

### Validation Rules

- Bound request size and section context length.
- Validate supported action types.
- Reject duplicate idempotency keys for the same request.
- Reject unsupported languages if language support is limited in MVP.

### Error Handling

- Distinguish quota, moderation, provider, validation, and timeout failures.
- Record prompt and response metadata safely.
- Support request replay only when usage/billing state is safe.
- Return structured provider-unavailable states without leaking internal error details.
- Preserve a stable suggestion/result schema even when the provider implementation changes behind the abstraction layer.

### Security Considerations

- Redact sensitive tokens and secrets from logs.
- Apply prompt-injection defenses around pasted job descriptions and user instructions.
- Minimize retained content where policy requires it.

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### AIRequest

Records a single AI generation/rewrite request — its input context, output, and lifecycle state. Used for audit, cost tracking, and support diagnostics.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique request identifier |
| `userId` | string (uuid) | Owning user account |
| `resumeId` | string (uuid) | Resume that provided the context |
| `resumeVersion` | integer | Snapshot: which resume version was used as input (for stale-result detection) |
| `sectionId` | string (uuid) | Target section within the resume |
| `actionType` | string | Scoped AI action: `generate_summary`, `generate_bullets`, `rewrite_section`, `tailor_to_job`, `generate_skills`, `generate_objective` |
| `inputContext` | json | Structured input: existing text, target field, optional job description, section type, action parameters |
| `provider` | string | AI provider identifier (e.g., `openai`, `anthropic`) for cost allocation and failover |
| `status` | enum | `pending`, `processing`, `completed`, `failed`, `moderation_blocked` |
| `suggestions` | json | Structured output: array of `{ text, reasoningSummary, confidence }` objects. Populated when status is `completed` |
| `moderationResult` | json | Outcome of safety/moderation pass: `passed`, `blocked`, `flagged_for_review`, with reason codes |
| `errorCode` | string | Non-null when status is `failed`: `provider_timeout`, `provider_rate_limited`, `provider_error`, `invalid_input`, `internal_error` |
| `tokenUsage` | json | Cost data: `{ promptTokens, completionTokens, estimatedCost }` |
| `idempotencyKey` | string | Client-supplied key; duplicate submissions with the same key return cached result without re-processing or re-decrementing quota |
| `userAccepted` | boolean | Whether the user explicitly accepted the suggestion (tracked for AI quality analytics) |
| `createdAt` | datetime | |
| `completedAt` | datetime | |

#### AIUsage

Tracks consumption per user per period, driving quota enforcement and cost analytics.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | |
| `userId` | string (uuid) | |
| `periodStart` | datetime | Start of the billing/usage period (e.g., first of month) |
| `periodEnd` | datetime | End of the billing/usage period |
| `actionType` | string | Which AI action was consumed (for per-action quotas) |
| `usedCount` | integer | Total requests consumed in this period for this action |
| `quotaLimit` | integer | Maximum allowed requests in this period (from plan entitlement) |
| `lastRequestAt` | datetime | Timestamp of most recent consumption |

#### AI Quota Model

| Plan | Quota Model | Notes |
| --- | --- | --- |
| Free | Per-period credit count (e.g., 2–3 AI actions/month) | Visible counter in UI; exhausted requests prompt upgrade |
| Premium | Extended or per-period high limit (e.g., 50–100/month) | May still have a cap for cost control; communicated transparently |

#### Request Flow

```text
Client → validate entitlement → check quota → moderate input → 
build prompt → call provider → moderate output → store request → 
decrement quota → return suggestions to client
```

If any step fails, the request is marked with the appropriate error code and quota is NOT decremented. The idempotency key prevents double-consumption on retries.

### Definition Of Ready For Engineering

### Definition of Done
