# Research — Notification Event Delivery And Preference Enforcement Service

## Research Basis

Even though public competitor experiences do not market a notification center heavily, the amount of account, billing, export, and support state communicated across public pages strongly implies a structured communication layer behind the product. Users need a reliable way to learn about important state changes, and the system needs a way to differentiate operational communication from optional preference-driven messaging.

## Requirement Interpretation

- Operational event delivery should be treated as a platform service with a stable contract (categories, ownership, read state) rather than a collection of ad-hoc event writes scattered across the codebase, so the frontend always receives consistent, renderable notification data.
- Preference enforcement must still allow required account, billing, and security communication; the distinction between mandatory and optional categories must be modeled explicitly so that a user's marketing opt-out never suppresses a security notice.
- FE needs stable category and destination data, which means BE must model notifications intentionally — with a defined category taxonomy and deep-link metadata — rather than exposing raw event payloads the frontend would have to decode.

## Risks If Under-Specified

- Important events become ad hoc or inconsistent.
- Notification preferences could incorrectly suppress required notices.
- UI may have to infer meaning from raw events not designed for user display.

## Recommended Backend Interpretation

- Build a lightweight but explicit notification service around category, ownership, read state, and optional preference control.
- Keep user-facing notification data intentionally small and safe.
