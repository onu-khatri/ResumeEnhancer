## [THEME-FE-001] — Theme, Appearance, And Custom Layout Editing Experience

**Module:** Builder Customization  
**Layer:** Frontend  
**Priority:** Should Have  
**Persona:** Active Job Seeker, Design-Conscious User, Premium User  
**Dependency:** THEME-BE-001, RES-FE-001, BILL-FE-002  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As a user refining the presentation of my document,  
I want a controlled interface for themes, fonts, visual accents, and layout ordering,  
so that I can personalize my resume without losing content or breaking professional/ATS-safe structure.

### Description

This story covers the dedicated customization experience that sits on top of the core resume builder. The selected research shows that theme and layout control are both strong premium differentiators and sensitive product areas. Users expect to change fonts, color themes, and certain display treatments after entering content, and they expect content to survive those changes. They also expect layout adjustments such as section reordering or item movement to feel deliberate and trustworthy. The frontend must therefore provide a customization panel that is expressive but bounded by design-system and ATS-safe rules.

**Research context:** Novorésumé's documented theme feature offers a tokenized appearance layer: fonts (3 free / 12 premium), color themes (30 free / 74 premium), backgrounds, picture styles, rating styles, and icons. Custom Layout (premium) allows drag-and-drop section reordering. This creates a concrete, explainable premium ladder. ATS-safe constraints must be enforced: certain visual options (e.g., tables, complex graphics, non-standard headings) must be blocked or warned when the user is in an ATS-friendly template mode.

### Scope

**Included In Scope**

- Theme selection and application.
- Font and color customization within approved limits.
- Supported visual style options such as picture/rating/icon styles where product enables them.
- Section and item layout ordering controls beyond basic builder editing.
- Premium-lock handling for advanced customization depth.

**Out Of Scope**

- Pixel-perfect freeform canvas editing.
- User-authored custom template creation from scratch.
- Unbounded drag-anything-anywhere layout system.

### Preconditions

- Builder and preview exist.
  The core resume builder must already be rendering a preview surface that the customization panel can hook into. Without a stable preview, theme changes cannot be visually validated in real time, which defeats the purpose of the customization experience.
- Theme/layout schema exists.
  A structured schema must define which fonts, color tokens, backgrounds, picture styles, rating styles, icon sets, and layout-ordering rules are available per template. The frontend uses this schema to populate controls and to determine which options are safe to render for a given template and ATS-safe mode.
- Premium customization policy is defined.
  Product stakeholders must have approved exactly which customization dimensions are free versus premium, including the numeric limits (e.g., 3 free fonts / 12 premium fonts, 30 free color themes / 74 premium) so that the UI can consistently badge, lock, and upsell without ambiguity.

### Detailed Workflow

1. User opens the customization area from the builder.
2. The UI presents available theme and layout controls based on the active template and entitlements.
3. User previews changes such as font, theme color, section order, or supported style options.
4. The preview updates while preserving document content.
5. The user saves or continues editing with the selected appearance/layout state.

### Functional Requirements

- Customization controls must be visually and conceptually separate from content editing.
- Users must be able to preview supported theme changes before committing mentally to export.
- The UI must clearly distinguish free/default options from premium customization depth.
- Layout ordering controls must remain understandable and reversible.
- The system must explain when a customization option is unavailable due to template limits, ATS-safe mode, or plan entitlements.

### Acceptance Criteria

**AC1 — Theme Preview**  
Given a user opens customization  
When they select a supported theme or font option  
Then the preview updates in a way that reflects the resulting document appearance without altering content.

**AC2 — Layout Control**  
Given the document supports section/item ordering  
When the user reorders supported elements  
Then the visual order updates and persists after refresh.

**AC3 — Premium Differentiation**  
Given some appearance options are premium  
When a free user encounters them  
Then the UI explains the lock clearly and preserves the current editing context.

**AC4 — ATS-Safe Boundaries**  
Given the user is in an ATS-sensitive workflow or using an ATS-friendly template mode  
When a customization would violate approved constraints  
Then the UI prevents or warns about the unsupported visual option appropriately.

**AC5 — Reversible Experimentation**  
Given the user is trying multiple appearance options  
When they switch between them  
Then the experience feels safe, fast, and non-destructive.

### Business Rules

- Content and appearance must remain separated.
  Changing the font, color theme, or icon style must never alter, reorder, or delete the user's written section content. The preview and export pipelines must enforce this separation at every stage so that users feel safe experimenting with visual options without fear of losing text they have already authored.
- Customization is a value layer, not a content-risk layer.
  The customization panel exists to add perceived quality and personalization to the resume, not to introduce risk. If a customization option could cause content loss, layout breakage, or ATS rejection, the system should either block it or surface a clear warning rather than silently applying a harmful change.
- Advanced appearance depth may be monetized, but basic clarity must stay usable.
  Free-tier users must have access to enough fonts, colors, and layout controls to produce a professional-looking document. Premium depth (expanded font libraries, additional color themes, custom backgrounds, drag-and-drop section reordering) can be gated, but the free baseline must never feel deliberately crippled or unusable.

### Validation Rules

- Only template-supported appearance options may render.
- Unsupported combinations must not silently corrupt preview or export assumptions.
- Ordering controls must respect the structured document model.

### Error Handling

- If theme metadata fails to load, preserve builder editing and show a recoverable customization error state.
  The customization panel should degrade gracefully when the theme catalog API is unreachable or returns an error. The user's content editing session must remain untouched, and the panel should display an inline error message with a retry button rather than blocking the builder entirely or showing a blank customization surface.
- If a layout reorder save fails, rollback clearly and allow retry.
  When a drag-and-drop section reorder request fails (e.g., network error, server validation rejection), the UI must revert the visual order to the last known persisted state and show a brief toast or inline notification explaining that the reorder was not saved. The user must be able to retry immediately without re-performing the drag action.
- If a premium option is selected during a network disruption, do not optimistically unlock it.
  The frontend must verify entitlement via the backend before applying a premium-locked theme or font. A transient network failure during this check should keep the lock visible and prompt a retry, rather than briefly showing the premium option as applied and then revoking it, which creates a jarring user experience.

### Security Considerations

- Premium-lock state must not be bypassable client-side.
- Preview assets and theme metadata must not expose internal unpublished template data.

### Analytics / Tracking

- `theme_selected`

### API Dependencies

- `GET /documents/{id}/customization`
- `PATCH /documents/{id}/customization`
- `PATCH /documents/{id}/layout-order`

### Data Requirements

- Theme option set
- Font option set
- Allowed visual styles
- Active layout/order state
- Template capability metadata
- Entitlement visibility state

### UX Notes

- The user should feel invited to refine presentation without feeling they are “editing design code”.
- Preview responsiveness is essential because customization is judged visually.

### UI/UX Design Requirements

- Use a dedicated customization rail, drawer, or side panel separate from section forms.
- Group controls by concept: typography, color, imagery, ratings/icons, layout order.
- Locked premium options should still feel aspirational and understandable, not simply disabled clutter.

### React UI Implementation Notes

- Keep customization state isolated from text-edit form state.
- Support optimistic preview for fast experimentation, but commit persisted state through verified backend responses.
- Reuse builder preview infrastructure instead of mounting a separate rendering system.

### Layout And Responsive Requirements

- Desktop:
  - persistent side panel or dual-pane customization layout preferred
- Mobile:
  - bottom sheet or stepwise customization panels acceptable

### Visual And Interaction Requirements

- Live preview transitions should be smooth and restrained.
- Layout ordering controls need keyboard-accessible alternatives to drag interactions.
- Premium styling options should be visibly grouped from core/default controls.

### Definition Of Ready For Engineering

- Theme and layout capability matrix is approved.
- ATS-safe customization boundaries are defined.
- Premium/free customization policy is approved.

### Definition of Done

- Users can adjust supported appearance and layout settings safely.
- Premium, unsupported, and ATS-constrained states are handled clearly.
- Customization integrates with existing preview and save behavior.
