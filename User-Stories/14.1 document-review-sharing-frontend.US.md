## [REVIEW-FE-001] — Final Review, Share Link, And Export Readiness Experience

**Module:** Document Review And Handoff  
**Layer:** Frontend  
**Priority:** Could Have  
**Persona:** Active Job Seeker, Mentor-Assisted User, Recruiter-Share User  
**Dependency:** REVIEW-BE-001, EXP-FE-001, ATS-FE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As a user preparing to send my application materials,  
I want a final review experience with optional read-only sharing and export-readiness guidance,  
so that I can catch issues, get outside feedback if needed, and hand off a trustworthy final document.

### Description

This story covers the end-of-flow review experience between “editing” and “sending”. The selected competitors emphasize proofread/check behavior, trusted preview, and export quality. Our platform foundation also identified public share links as a likely future capability. The frontend should therefore support a structured final review step that summarizes blockers/warnings, confirms export readiness, and optionally creates a read-only share flow for mentor/recruiter-style feedback or simple external review.

### Scope

**Included In Scope**

- Final review surface before export.
- Consolidated blockers, warnings, and readiness summary.
- Optional read-only share-link creation/management.
- Clear distinction between editable builder state and share/export handoff state.

**Out Of Scope**

- Real-time collaborative editing.
- External reviewer comments system.
- Recruiter-side product portal.

### Preconditions

- Builder validation and export flows exist — the review page depends on upstream features that produce structured validation results, ATS analysis signals, and export-readiness indicators. Without these, the review surface would have no data to display and no useful function beyond a placeholder.
- Backend can produce review summary and optional share-link metadata — the frontend review page is a consumer of the backend aggregation API; it cannot fabricate readiness data locally. The API contract for review summaries and share-link state must be agreed before frontend development can produce meaningful renderings.
- Product policy for public sharing/privacy is approved — the frontend must know whether read-only sharing is enabled at all, what visibility rules govern shared documents, and what version-binding behavior is expected before it can display share controls or explain privacy implications to users.

### Detailed Workflow

1. User chooses to review before export or share.
2. The UI presents a summary of blockers, warnings, freshness, and final preview cues.
3. User resolves issues or proceeds to export if ready.
4. If desired, user creates a read-only share link and copies it safely.
5. User returns to export or editing with full context preserved.

### Functional Requirements

- Final review must show a clear distinction between blocking issues and optional improvements.
- The review page should reuse ATS/export/validation signals rather than inventing a disconnected checklist.
- Share link creation, regeneration, disabling, and copy actions must be understandable and privacy-conscious.
- The UI must make it obvious whether a shared view is editable or read-only.
- Users must be able to continue back to editing or forward to export from the same review context.

### Acceptance Criteria

**AC1 — Readiness Summary**  
Given a user opens final review  
When the review data loads  
Then they see blockers, warnings, and readiness status summarized clearly.

**AC2 — Review-To-Action Continuity**  
Given the document has issues or is ready  
When the user chooses edit or export  
Then the app returns them to the right next step without losing context.

**AC3 — Share Link Clarity**  
Given the user creates a share link  
When the link is shown  
Then the UI explains that it is read-only and what information will be visible externally.

**AC4 — Share Link Controls**  
Given a share link already exists  
When the user revisits review  
Then they can copy, regenerate, or disable it according to product policy.

**AC5 — Privacy-Conscious States**  
Given sharing is unavailable, disabled, or restricted  
When the user attempts to use it  
Then the UI explains why without ambiguous behavior.

### Business Rules

- Final review is a confidence layer before external handoff — this page exists to give users a single place to verify their document is ready before they export or share it. It is not a replacement for the builder or ATS tools but a checkpoint that consolidates their outputs into one actionable view.
- Share links, if supported, are read-only by default — any external viewer who opens a share link must see a non-editable document. The UI must communicate this clearly, and the share-link creation flow must reinforce that sharing does not grant editing access to anyone.
- Sharing must be explicit because resumes contain sensitive personal data — the product defaults to private; creating a share link is an affirmative user action. The UI must not accidentally expose share controls in a way that suggests sharing is expected or automatic.

### Validation Rules

- Blocking issues must be resolved before export if product policy requires it — if the review summary reports blockers that prevent a confident export, the UI must gate the export action and explain which issues must be fixed. The blocking rules must be backend-driven so the frontend does not independently decide what constitutes a blocker.
- Share links must represent a specific document/version context if version binding is required — if the product policy binds a share link to a specific document version, the UI must show which version is shared and warn the user if they have made edits since the link was created. The `PreviewFreshnessBanner` component exists specifically to surface this information.

### Error Handling

- If review summary fails to load, preserve export/edit routes and show a recoverable error — the review page is a convenience, not a gate; if the summary API fails, the user must still be able to reach the export flow or return to editing. The error state should indicate that review data is temporarily unavailable but not block forward progress.
- If share-link creation fails, the user must remain in control of the document and export path — a failed share-link creation must not redirect the user, lock them into a broken state, or obscure the export and edit actions. The failure message should explain what went wrong (e.g., "Unable to create share link — please try again") and keep the document in its current state.

### Security Considerations

- Share-link UI must explain exposure boundaries clearly — before the user copies or shares a link, the interface must use plain language to describe what the recipient will see (full document content, no editing ability) and that anyone with the link can view it. The `ReadOnlyVisibilityNotice` component exists for this purpose.
- Do not reveal the share URL until backend creation succeeds — the UI must not display or pre-render a share URL before the backend confirms the link was persisted. Premature display risks showing a URL that doesn't work or, worse, a URL that was never actually created.
- Copy/regenerate/disable actions must reflect actual backend state — the UI must update share-link controls only after receiving a confirmed backend response. Optimistic updates are dangerous here: showing a link as disabled when it is still active, or showing a new link that wasn't properly created, could lead to unintended document exposure.

### Data Requirements

- Review status
- Blocking and warning summaries
- Preview freshness/version metadata
- Share-link active state
- Share-link visibility policy summary

### UX Notes

- This page should feel like a calm checkpoint, not another noisy dashboard.
- Users need confidence that “this is what others will see”.

### UI/UX Design Requirements

- Use a summary-first layout with clear readiness status at the top.
- Keep share actions clearly secondary to the document-quality review unless the user explicitly enters sharing.
- Use plain-language privacy explanations for sharing.

### React UI Implementation Notes

- Model review-summary state separately from share-link action state.
- Reuse validation and export summary components where possible.
- Keep version/freshness indicators visible if the share or export state may be stale.

### Layout And Responsive Requirements

- Desktop:
  - summary header plus issue list and side action panel preferred
- Mobile:
  - stacked summary and action sections acceptable

### Visual And Interaction Requirements

- Blocking issues need immediate visibility.
- Share-link controls should feel deliberate and privacy-aware.
- Final preview area or preview cue should reinforce handoff confidence.

### Definition Of Ready For Engineering

- Share-link privacy policy is approved.
- Review-summary data contract is defined.
- Export-blocking policy is agreed.

### Definition of Done

- Users can review export readiness and manage a read-only share link if enabled.
- Edit/export continuity is preserved.
- Privacy, stale-state, and failure behaviors are implemented.
