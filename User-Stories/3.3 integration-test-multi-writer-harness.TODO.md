# TODO: Multi-writer integration-test harness

## Purpose

Enable reliable parallel integration-test execution and real concurrency coverage for the Auth and other modules.

## Current limitation

The current integration harness uses one assembly-shared `WebApplicationFactory`, one service provider, and one SQLite in-memory connection (`Data Source=:memory:`). This is useful for deterministic sequential endpoint tests, but it is not a real multi-writer environment. Concurrent requests can contend on the same SQLite connection and a failed test can poison the shared host lifetime.

## Target design

- Use a shared PostgreSQL test database, preferably provisioned with Testcontainers.
- Keep one database instance for the test run, but give every application instance its own `WebApplicationFactory`, service provider, and database connection.
- Configure two independent application instances against the same database.
- Provide deterministic database reset/schema isolation between test cases.
- Keep test data setup and cleanup outside individual theory cases where possible.
- Retain `Theory` and `MemberData` setup objects for scenario matrices.
- Allow parallel execution only for tests with isolated data and independent host fixtures.
- Keep tests that reset shared state in a non-parallel collection.
- Add explicit cancellation and disposal ownership so a factory is disposed only after all tests using that factory complete.

## Required scenarios

### Registration race

- Start two registration requests concurrently through independent application instances.
- Use equivalent normalized email values and distinct idempotency keys.
- Assert exactly one `201 Created` and one `409 Conflict`.
- Assert exactly one identity and one complete registration baseline in the database.
- Assert the losing request does not leave partial consent, preference, entitlement, audit, or outbox records.

### Multi-instance refresh state

- Register through application instance A.
- Refresh the token through application instance B.
- Replay the original refresh token through either instance.
- Assert the replay is rejected using the database-backed session state.

### Queue failure and recovery

- Configure an integration-only side-effect handler that fails predictably.
- Run the outbox dispatcher through multiple attempts.
- Assert retry scheduling, lease ownership, safe audit metadata, and terminal degraded state.
- Verify a later successful attempt marks the message processed and does not duplicate delivery.

### Parallel execution safety

- Run isolated theory cases in parallel using independent databases or schemas.
- Keep shared-database reset tests in a sequential collection.
- Add a repeated-run CI job to detect lifetime and race regressions.
- Verify no `ObjectDisposedException` occurs for `WebApplicationFactory`, `TestServer`, or `IServiceProvider`.

## Acceptance criteria

- Two independent application instances can concurrently write to the same test database.
- Registration race tests pass repeatedly without SQLite-only or host-lifetime assumptions.
- Multi-instance refresh rotation and replay tests pass repeatedly.
- Queue failure/recovery behavior is verified through the integration boundary.
- Parallelizable tests run concurrently without shared-fixture disposal failures.
- Full integration execution remains green, with test counts and execution mode recorded in OpenSpec evidence.

## Suggested implementation order

1. Add the PostgreSQL Testcontainers package and shared database fixture.
2. Add independent application-instance factory builders.
3. Add reset/schema-isolation support.
4. Port registration-race and multi-instance refresh theories.
5. Add queue failure/recovery integration seams.
6. Separate parallel-safe and shared-state test collections.
7. Enable parallel execution incrementally and run repeated CI verification.
