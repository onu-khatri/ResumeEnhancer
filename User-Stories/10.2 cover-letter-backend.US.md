## [CL-BE-001] — Cover Letter Draft Model And Resume-Linked Creation Service

**Module:** Cover Letter  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Cover Letter Service  
**Dependency:** AUTH-BE-001, RES-BE-001, IMP-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the cover-letter service,  
I want to create, persist, and manage editable cover-letter drafts that can optionally derive context from a selected resume,  
so that users can produce a consistent application package with less repeated effort.

### Description

This story covers the backend model and service flows for cover-letter creation and editing. The service must support manual creation, resume-linked creation, and optional resume-context prefill or generation workflows. It should keep cover letters as independent documents while preserving relationship metadata that makes them part of the same user application set.

### Scope

**Included In Scope**

- Cover-letter draft creation.
- Resume-linked cover-letter creation.
- Cover-letter retrieval and update.
- Linkage between a cover letter and source resume where used.
- Template/style metadata support.

**Out Of Scope**

- Human expert review operations.
- Public sharing.
- Billing mechanics beyond entitlement enforcement.

### Preconditions

- Authenticated session is valid.
- Resume ownership can be validated where resume-linked start is used.
- Cover-letter template/style configuration exists.

### Detailed Workflow

1. User requests a new cover-letter draft manually or from an existing resume.
2. Service validates user ownership and optional resume reference.
3. Service creates a new cover-letter draft record.
4. If resume-linked creation is used, service stores the relationship and optional prefill context.
5. User updates the cover-letter draft over time.
6. Draft remains separately editable while preserving resume linkage metadata where relevant.

### Functional Requirements

- Cover letters must be modeled as distinct documents, not hidden extensions of resumes.
- The service must support optional linkage to a source resume for context and package continuity.
- Resume-linked creation must not require the cover letter to mirror resume data permanently once editing begins.
- Template/style metadata should support matching presentation with resume-related flows.
- The service must support normal saved-document lifecycle behavior similar to resumes.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authenticated user creates a cover letter from a selected resume  
When the request is processed  
Then the service creates a cover-letter draft, stores the resume relationship, and returns usable draft data.

**AC2 — Manual Start**  
Given a user starts a cover letter without choosing a resume  
When the request is processed  
Then the service creates an independent editable cover-letter draft without requiring missing resume context.

**AC3 — Authorization**  
Given a user references a resume they do not own  
When cover-letter creation is requested  
Then the service rejects the request and does not expose protected resume metadata.

**AC4 — Editing Continuity**  
Given a resume-linked cover letter has already been edited by the user  
When later updates occur  
Then the draft remains independently editable and does not get silently overwritten by resume-side changes.

**AC5 — Error Handling**  
Given resume-linked prefill or template association fails partially  
When the request completes  
Then the service returns a recoverable state that still allows manual editing when possible.

### Business Rules

- A cover letter is a separate user asset even when created from a resume.
- Resume linkage is contextual, not ownership-transferring.
- Resume-linked creation must reduce work without removing user editorial control.
- Cover-letter drafts should be manageable in the same overall workspace as resumes.

### Validation Rules

- Resume references must be authorized and valid.
- Cover-letter title and content fields must comply with product constraints.
- Matching-style metadata must reference supported template/style combinations only.

### Error Handling

- Distinguish invalid resume reference, authorization failure, missing template/style, and transient service errors.
- Preserve cover-letter independence when resume-linked operations partially fail.
- Allow retry-safe creation flows with idempotency where appropriate.

### Security Considerations

- Enforce object-level authorization on resume-linked start.
- Do not expose unnecessary resume internals in cover-letter payloads.
- Log create/update events in a supportable but privacy-aware way.

### Data Model

> This section describes the expected entity structure with possible properties. It is a business-requirements-level starting point, not a final database schema.

#### CoverLetter

A separate document entity (parallel to Resume) representing a cover-letter draft. Shares many patterns with Resume (save, autosave, versioning, preview, export) but has its own section structure.

| Property | Type | Description |
| --- | --- | --- |
| `id` | string (uuid) | Unique identifier |
| `ownerUserId` | string (uuid) | Owning user |
| `title` | string | User-facing name, e.g., "Cover Letter for Acme Corp" |
| `templateId` | string (uuid) | Applied cover-letter template (style reference) |
| `linkedResumeId` | string (uuid) | The resume this cover letter was created from or linked to. Null if created standalone. Used for resume-aware prefill and "matching set" continuity. |
| `languageCode` | string (ISO 639-1) | Document language |
| `status` | enum | `draft`, `ready`, `archived` |
| `version` | integer | Optimistic concurrency token |
| `content` | json | Structured cover-letter content — see below |
| `sectionOrder` | string[] | Ordered section IDs |
| `createdAt` | datetime | |
| `updatedAt` | datetime | |

| Section Type | Data Properties | Description |

#### Resume-Linked Cover Letter Creation

When a cover letter is created with a linked resume:

1. Ownership of the linked resume is validated.
2. `linkedResumeId` is stored — the cover letter "knows" which resume it was paired with.
3. **Prefill**: sender name, email, and phone are pulled from the linked resume's `header` section into the cover letter's `header` section. The user can edit freely after creation.
4. **Matching template**: if a `pairedCoverLetterId` exists on the resume's template, that cover-letter template is auto-suggested (user can override).
5. After creation, the cover letter is **independently editable** — changes to the linked resume do not automatically update the cover letter, and vice versa.

#### Template Pairing

```json
// Template entity (resume template)
{
  "id": "tpl_resume_executive_01",
  "documentType": "resume",
  "pairedCoverLetterId": "tpl_cover_executive_01"
}

// Template entity (cover-letter template)
{
  "id": "tpl_cover_executive_01",
  "documentType": "cover_letter",
  "pairedResumeTemplateId": "tpl_resume_executive_01"
}
```

#### Relationships

```text
User (1) ──── (N) CoverLetter
Resume (1) ──── (N) CoverLetter (via linkedResumeId — optional, one-to-many)
CoverLetter (1) ──── (N) CoverLetterSection
Template (N) ──── (1) CoverLetter (via templateId)
```
