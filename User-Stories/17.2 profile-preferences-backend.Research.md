# Research — User Profile And Preferences Service

## Research Basis

Public privacy, support, and account-management cues from the selected competitors imply that a real user-service layer is needed for settings-related self-service. Even when detailed settings UIs are not fully public, the product category clearly expects account-based management and privacy-aware supportability.

## Requirement Interpretation

- A current-user API model (`/users/me`) is more appropriate than generic user-id-driven profile management for this product surface, because the settings area is always scoped to the authenticated user and exposing raw user IDs in routes would create unnecessary authorization risk.
- Preferences should be modeled separately enough to avoid accidental identity/profile corruption; a PATCH to `/users/me/preferences` should never be able to modify identity fields like email or display name, and vice versa.
- Settings are not only for convenience; they reinforce trust and self-service legitimacy, which means the backend must provide stable, predictable, and well-documented response contracts that the frontend can rely on across releases.

## Risks If Under-Specified

- Support and privacy actions may become hard to surface cleanly.
- Simple account updates may require unnecessary support intervention.
- Frontend settings UX may become inconsistent due to weak API separation.

## Recommended Backend Interpretation

- Keep editable profile and preference fields explicit and allowlisted.
- Support modular settings UI by offering predictable current-user endpoints and partial updates.
