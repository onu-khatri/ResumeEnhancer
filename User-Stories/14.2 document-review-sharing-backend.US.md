## [REVIEW-BE-001] — Review Summary Aggregation And Read-Only Share Link Services

**Module:** Document Review And Handoff  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Active Job Seeker, External Reviewer, Support Team  
**Dependency:** RES-BE-001, ATS-BE-001, EXP-BE-001  
**Source Classification:** Documented, Inferred, Recommended

### User Story

As the platform,  
I want aggregated review-summary data and controlled read-only share links,  
so that users can verify document readiness and optionally expose a safe external view without opening editing access.

### Description

This story covers backend support for a final-review step and optional read-only sharing. The service must aggregate relevant readiness information from validation, analysis, and export-related checks into a frontend-safe summary. It must also support explicit creation and management of read-only share links under approved privacy rules. This is a handoff capability, not a collaboration system.

### Scope

**Included In Scope**

- Review-summary retrieval.
- Read-only share-link creation and state management.
- External read-only shared document retrieval.
- Optional version or freshness metadata for review/share state.

**Out Of Scope**

- Multi-user comments or annotations.
- Recruiter portals.
- Collaborative editing sessions.

### Preconditions

- Validation and export-readiness signals exist — the review summary must have upstream services (document validation, ATS analysis, export readiness checks) producing structured quality signals that the aggregation layer can consume. Without these, the summary would be empty and misleading.
- Document ownership and authorization exist — the platform must already track which user owns which document and enforce that only the owner can request review summaries or manage share links. Authorization is a prerequisite, not something this story invents.
- Sharing/privacy policy is approved — the product team must have decided whether read-only sharing is a feature at all, what document versions it binds to, and what fields are visible to external viewers before the backend can implement the share-link lifecycle.

### Detailed Workflow

1. Authenticated client requests review summary for a document.
2. Backend aggregates blocking issues, warnings, freshness, and readiness status.
3. User optionally requests creation of a read-only share link.
4. Backend generates and stores the share-link state.
5. External viewer requests the shared document using the issued token or slug.
6. Backend returns a read-only representation or rejects the request if sharing is disabled.

### Functional Requirements

- The review-summary endpoint must provide a normalized readiness payload suitable for final handoff decisions.
- Share links must be explicitly created and revocable.
- Shared views must be read-only and must not expose editing routes or internal metadata.
- If version/freshness binding is part of policy, the service must express that state clearly.
- Ownership rules must be enforced for share-link management actions.

### Acceptance Criteria

**AC1 — Review Summary Retrieval**  
Given a user owns a document  
When they request final review data  
Then the service returns blockers, warnings, and readiness metadata in a stable contract.

**AC2 — Share Link Creation**  
Given sharing is enabled by policy  
When the owner creates a share link  
Then the service returns an active read-only share reference.

**AC3 — Share Link Revocation**  
Given a share link exists  
When the owner disables or regenerates it  
Then previous link behavior follows approved policy and the new state is returned clearly.

**AC4 — External Read-Only Access**  
Given a valid active share link  
When an external viewer opens it  
Then they receive a read-only document representation only.

**AC5 — Unauthorized Management Rejection**  
Given a non-owner attempts to manage a share link  
When the request is processed  
Then the service rejects the action and does not reveal share details.

### Business Rules

- Sharing is explicit and revocable — no document is shareable by default; the owner must take a deliberate action to create a share link, and that link can be disabled at any time. Revocation must take effect immediately, not on a delayed schedule.
- Shared access is read-only by default — external viewers who open a share link see a static, non-editable document projection without any controls that imply they could modify, export, or manage the document. This is the core security boundary of the feature.
- Review summary is a user-facing aggregation layer, not a raw internal diagnostic dump — the service must translate low-level validation results, analysis scores, and freshness metadata into a contract the frontend can render directly without needing to understand internal signal formats. Blockers, warnings, and readiness status must use consistent, documented codes.

### Validation Rules

- Share-link actions require ownership and valid document state — before creating, regenerating, or revoking a share link, the service must verify that the requesting user owns the document and that the document is in a state that permits sharing (not deleted, not archived, not in a restricted privacy mode).
- Review summary must reflect the current or explicitly version-bound document state according to policy — if the product decides that reviews should reflect the latest saved state, the summary endpoint must pull fresh signals each time; if version binding is required, the summary must clearly indicate which version it represents and whether a newer version exists.
- Disabled or expired links must not resolve successfully — any attempt to access a shared document using a revoked or expired token must return a controlled, privacy-safe error that does not reveal whether the document itself still exists or who owns it.

### Error Handling

- If one review sub-signal is temporarily unavailable, return a degraded but explicit summary if product policy allows — the review summary aggregates multiple quality signals, and if one source (e.g., ATS analysis) is temporarily down, the service should return available signals with a clear indication of degradation rather than failing the entire request. The degraded state must be distinguishable from a clean summary.
- If share creation fails, do not leave half-created visible links — the service must ensure atomicity: a share link that fails to persist in the database or whose token generation encounters an error must not produce a visible URL or partial state record. The user should receive a clean failure and be able to retry without side effects.
- External invalid-link responses should be safe and privacy-conscious — when an anonymous viewer follows an invalid, expired, or revoked share link, the response must not reveal whether the document exists, who owns it, or whether the link was ever valid. A generic "this link is not available" response prevents information leakage.

### Security Considerations

- Share tokens/urls must be unguessable — tokens must be generated using a cryptographically secure random number generator with sufficient entropy (minimum 128 bits) so that an attacker cannot enumerate or guess valid share URLs even with knowledge of the document ID scheme.
- Shared payloads must exclude sensitive internal metadata and editing controls — the external projection must strip owner IDs, internal status flags, version history, editing endpoint references, and any administrative metadata that would not be appropriate for an anonymous viewer to see.
- Audit link creation, regeneration, and revocation events — every share-link lifecycle event must be recorded in an audit log with the actor's identity, timestamp, and action type. This provides a trail for investigating abuse, unintended sharing, or support inquiries about who shared what and when.

### Data Model

#### Entity Definitions

**DocumentReviewSummary** — Aggregated readiness snapshot computed from validation, analysis, and export signals.

| Property | Type | Description |
| --- | --- | --- |
| `documentId` | UUID | The owning document identity |
| `ownerId` | UUID | The document owner |
| `status` | enum(`ready`, `warning`, `blocked`) | Overall readiness classification |
| `blockers` | array\<ReviewIssue\> | Issues that prevent confident export or sharing |
| `warnings` | array\<ReviewIssue\> | Improvements recommended but not blocking |
| `documentVersion` | integer | The revision number this summary was computed against |
| `freshness` | enum(`current`, `stale`) | Whether the summary reflects the latest saved state |
| `computedAt` | datetime | When the summary was generated |

**ReviewIssue** — A single quality signal item.

| Property | Type | Description |
| --- | --- | --- |
| `code` | string | Machine-readable issue identifier (e.g., `missing_metrics`) |
| `section` | string | The document section the issue refers to |
| `message` | string | Human-readable description |

**DocumentShareLink** — A revocable, read-only external reference to a document.

| Property | Type | Description |
| --- | --- | --- |
| `id` | UUID | Internal link identifier |
| `documentId` | UUID | The owning document |
| `token` | string | Unguessable share token used in the public URL |
| `mode` | enum(`read_only`) | Access mode — always read-only in this scope |
| `status` | enum(`active`, `revoked`, `expired`) | Current link state |
| `documentVersion` | integer | The version bound when the link was created or last regenerated |
| `createdAt` | datetime | When the link was first created |
| `revokedAt` | datetime \| null | When the link was disabled, if applicable |
| `createdBy` | UUID | The user who created the link |

**SharedDocumentProjection** — The external-facing, stripped-down view of a document returned to non-authenticated viewers.

| Property | Type | Description |
| --- | --- | --- |
| `sections` | array\<DocumentSection\> | The visible document content |
| `lastUpdated` | datetime | The freshness indicator for external viewers |
| `mode` | string | Always `read_only` |


#### Relationships

```
Document ──1:1──> DocumentReviewSummary (computed on demand)
Document ──1:0..1──> DocumentShareLink (explicitly created, at most one active)
DocumentShareLink ──> SharedDocumentProjection (derived view for external access)
ReviewIssue ──> contained within DocumentReviewSummary.blockers[] or .warnings[]
```

- A document may have zero or one active share link at any time; creating a new link revokes the previous one by default.
- The `SharedDocumentProjection` is never persisted — it is derived at read time from the bound document version.
- The `DocumentReviewSummary` is not a persisted entity either; it is computed from live signal sources on each request unless product policy later requires caching/snapshotted summaries.

#### Business-Level Design Notes

- The review summary is a normalization layer, not a raw diagnostic dump. It translates multiple internal quality signals (validation results, ATS analysis, export readiness) into a single frontend-safe contract so the UI never stitches together disparate endpoints.
- Share links are version-aware: if the product chooses version binding, the link records the document version at creation time and the external projection serves that snapshot. If live-state is preferred, the model still records the version for audit but serves the current document state.
- External projections intentionally strip all metadata beyond what an anonymous viewer should see — no owner ID, no internal status flags, no editing routes. This separation prevents accidental information leakage through API responses.
- Tokens must be generated with a cryptographically secure random source and be at least 128 bits of entropy; URLs must not be guessable or enumerable even with knowledge of the document ID.

### Technical Notes

- Keep review aggregation normalized and frontend-safe.
- Strongly separate internal document models from shared external projections.
- Consider whether share links point to live state or snapshot state and document that choice explicitly.
