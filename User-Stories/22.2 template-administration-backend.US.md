## [TPLADM-BE-001] — Template Inventory, Metadata, And Publication Management Services

**Module:** Template Administration  
**Layer:** Backend  
**Priority:** Could Have  
**Persona:** Template Service  
**Dependency:** CONT-BE-001, ADM-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the template service,  
I want to provide authorized internal APIs for template inventory retrieval, template metadata updates, and publication/commercial state management,  
so that the template portfolio can be operated safely and consistently across acquisition, builder, and premium experiences.

### Description

This story covers backend support for template-specific internal operations. Unlike generic content inventory, template administration must account for commercial flags, publication state, and renderer-relevant metadata. The service must support internal retrieval, update, and state transitions for approved fields while protecting against accidental or unauthorized changes.

### Scope

**Included In Scope**

- Template inventory retrieval.
- Template detail retrieval.
- Metadata updates for approved fields.
- Publication and commercial-state updates.
- Audit logging for sensitive changes.

**Out Of Scope**

- Deep template authoring engine.
- Render engine internals.
- Public site rendering.

### Preconditions

- Template model exists, capturing kind, category, premium/public flag, publication state, and ATS metadata so the service has a complete field set to operate on.
- Admin/content authorization exists, ensuring only operators with the correct template-management permissions can reach these endpoints.
- Publication/commercial state rules are defined, specifying the valid transitions and which roles may change premium or public exposure.

### Detailed Workflow

1. Authorized operator requests template inventory or details.
2. Service validates scope and returns template data.
3. Operator updates approved metadata or state.
4. Service validates the update, applies it, and audits the change.

### Functional Requirements

- Template inventory responses must support type, category, premium/public, and publication metadata.
- The service must distinguish resume and cover-letter templates.
- Commercial flags and publication states must be validated against approved policy.
- Sensitive template-state changes must be auditable.
- Retrieval and update contracts should support internal operational UIs without exposing unnecessary render internals.

### Acceptance Criteria

**AC1 — Happy Path**  
Given an authorized operator requests template inventory or a specific template  
When the service processes the request  
Then it returns the requested template summaries or detail metadata within allowed scope.

**AC2 — Metadata Update**  
Given an authorized operator updates an allowed template field  
When the service processes the request  
Then it validates, persists, and returns the updated state.

**AC3 — State Change**  
Given an authorized operator updates publication or premium/public state  
When the service processes the request  
Then it applies the approved transition safely and records an audit event.

**AC4 — Validation And Authorization**  
Given an invalid or unauthorized template change is submitted  
When the service processes the request  
Then it rejects the request without corrupting current template state.

### Business Rules

- Template metadata and commercial state are product-critical operational data, because templates sit at the intersection of acquisition, activation, and premium monetization.
- Resume and cover-letter template families must be distinguishable so operators and downstream rendering logic never conflate the two catalog types.
- State changes affecting public availability or premium positioning must be auditable, capturing who made the change and the before/after values for review and rollback.

### Validation Rules

- Only approved template types, categories, and states may be used, and the service must reject any value outside the approved allowlists.
- Only authorized operators may edit commercial/publication fields, so a general content editor cannot toggle a template to premium without the required role.
- Unknown template ids or unsupported transitions must be rejected with clear, structured errors rather than silently no-oping.

### Error Handling

- Distinguish authorization, validation, not-found, and persistence failures so the frontend can surface the correct message for each failure class.
- Avoid partial state changes when one template update fails, keeping the template in a consistent, known state.
- Return frontend-mappable policy errors for blocked transitions so operators understand exactly why a commercial or publication change was refused.

### Security Considerations

- Protect template-admin APIs with internal authorization, ensuring these mutation endpoints are never reachable from public surfaces.
- Limit exposed data to operationally useful metadata so render internals and internal-only notes do not leak through these contracts.
- Audit commercially sensitive changes, including premium toggles and publication transitions, with attributable before/after records.

### Data Model

Template administration is built around a `Template` entity that carries commercial and publication state, with versioned snapshots for history and rollback. The model deliberately keeps render-internal details out of scope while capturing everything operators need to manage the portfolio.

#### Template

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable template identifier. |
| `kind` | enum | `resume` or `cover_letter`. |
| `name` | string | Human-readable template name. |
| `category` | string | Classification label such as `modern`, `creative`, or `professional`. |
| `isPremium` | boolean | Premium/public commercial flag. |
| `status` | enum | Publication state such as `draft`, `published`, or `archived`. |
| `isAtsFriendly` | boolean | Whether the template is ATS-optimized. |
| `currentVersionId` | string | Points to the active `TemplateVersion`. |
| `updatedAt` | datetime | Last modification timestamp. |

#### TemplateVersion

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable version identifier. |
| `templateId` | string | Owning template. |
| `version` | integer | Monotonic version number. |
| `metadataSnapshot` | json | Frozen copy of template metadata at this version. |
| `createdAt` | datetime | When the version was created. |

#### AuditLog

| Property | Type | Description |
| --- | --- | --- |
| `id` | string | Stable audit entry identifier. |
| `actorId` | string | Operator who performed the change. |
| `action` | enum | `metadata_updated`, `state_changed`, etc. |
| `targetId` | string | Affected template id. |
| `before` | json | Pre-change state snapshot. |
| `after` | json | Post-change state snapshot. |
| `timestamp` | datetime | When the action occurred. |

#### Example JSON

```json
{
  "id": "tpl_123",
  "kind": "resume",
  "name": "Modern Minimal",
  "category": "modern",
  "isPremium": true,
  "status": "published",
  "isAtsFriendly": true
}
```

#### Relationships

```text
Template 1 ─── * TemplateVersion      (version history)
Template 1 ─── * AuditLog             (sensitive changes audited)
```

#### Business Notes

- `isPremium` and `status` are the two most sensitive fields: premium changes affect monetization while status changes affect public discoverability.
- `TemplateVersion` provides a rollback anchor without importing render engine internals.
- Audit entries must capture before/after state for every premium or publication transition.
