## [SUP-BE-001] — Support Entry Metadata And Recovery Guidance Service

**Module:** Support & Recovery  
**Layer:** Backend  
**Priority:** Should Have  
**Persona:** Support Metadata Service  
**Dependency:** AUTH-BE-001, BILL-BE-001  
**Source Classification:** Inferred, Recommended

### User Story

As the support metadata service,  
I want to provide contextual help and recovery-entry metadata for key product workflows,  
so that users can be routed toward the most appropriate self-service or support path during account, billing, export, and workflow issues.

### Description

This story covers the backend support needed for contextual help and recovery routing. The service must not be confused with a full knowledge-base CMS. Its role is to expose stable metadata about supported help categories, context-specific next-step guidance, and available contact/self-service options so the frontend can present a coherent support experience.

### Scope

**Included In Scope**

- Support entry metadata.
- Contextual help mapping by workflow category.
- Contact/self-service option metadata.
- Privacy/help route metadata where relevant.

**Out Of Scope**

- Full article authoring system.
- Ticketing platform implementation.
- Live-chat provider details.

### Preconditions

- Supported help categories are defined with stable machine-readable keys so contextual lookups can match workflow contexts to help entries reliably, not via fuzzy text matching.
- Contact/self-service channels are approved, including the set of allowed channel types (email, phone, chat, help center, privacy page) and their current target URLs.
- Workflow-context taxonomy is defined, mapping each product context (export_failure, billing_question, account_recovery, general) to its identifying key so the frontend can request the correct help entry.

### Detailed Workflow

1. Frontend requests support entry or contextual help data for a workflow state.
2. Service resolves the current workflow category.
3. Service returns approved next-step metadata such as:
   - self-service path
   - contact path
   - policy/help route
4. Frontend presents the best recovery options.

### Functional Requirements

- The service must support context-aware help routing rather than only one generic support payload.
- It must distinguish self-service, contact, and policy/information options.
- Metadata should remain configurable as support policy evolves.
- Fallback support entry data must exist even when no specific contextual mapping is found.

### Acceptance Criteria

**AC1 — Happy Path**  
Given a workflow context such as export failure or billing question  
When the frontend requests contextual help  
Then the service returns approved support-entry metadata appropriate to that context.

**AC2 — Fallback Path**  
Given no specific contextual mapping exists  
When the request is processed  
Then the service still returns a generic but valid help/support entry payload instead of no support path.

**AC3 — Configuration Safety**  
Given support channels or mappings are updated  
When the service serves metadata  
Then it returns only currently approved and valid options.

**AC4 — Error Handling**  
Given the contextual support service encounters transient failure  
When the request is processed  
Then the system returns a stable failure response that allows frontend fallback behavior.

### Business Rules

- Every high-stress workflow (export failure, payment error, account access issue) should have a recoverable support path; the metadata service must provide at minimum a fallback-to-general behavior so no workflow context returns an empty or null response.
- Generic fallback support metadata must always exist as a catch-all entry with `isFallback: true`, ensuring that even unmapped contexts, unknown errors, or misconfigured lookups still produce a usable support payload.
- Support routing should reduce unnecessary contact volume when self-service is adequate, meaning self-service actions should appear first in the ordered actions array and contact actions should only be prominent when the problem genuinely requires human intervention.

### Validation Rules

- Only supported workflow categories may map to contextual help entries, and any request with an unknown context key should return the fallback entry rather than attempting to look up a nonexistent mapping.
- Support channel metadata must be internally consistent and complete before activation; a channel of type "contact" must have a valid `target` URL or label, and an entry with zero actions should be blocked at the configuration level.
- Region/policy variations must be validated if used, ensuring that locale-specific support entries return correct regional contact information rather than defaulting to a single global support address.

### Error Handling

- Distinguish no-context-match (return fallback, HTTP 200) from service failure (return HTTP 503 with a minimal fallback payload if possible) so the frontend can differentiate a temporary outage from a permanent lack of contextual content.
- Preserve safe fallback behavior for the frontend by always including at minimum the generic support contact information in error responses, never returning an empty body or null on failure.
- Avoid exposing internal support configuration details in client payloads; the response should include only user-facing labels, descriptions, and targets, never internal database IDs, configuration keys, or operator-only routing information.

### Security Considerations

- Support metadata responses must not expose privileged internal tooling routes, operator consoles, admin panel URLs, or internal ticketing system identifiers that could be used to target backend infrastructure.
- Privacy/help routes must be restricted to approved public/self-service destinations, with the actions array validated at serve time to ensure no internal-only URLs have been accidentally configured.
- Context resolution should not leak sensitive internal state classifications unnecessarily; the `context` value in responses must be a user-facing workflow key (like "export_failure"), never an internal stack trace or error code that reveals implementation details.

### Analytics / Tracking

- `support_context_requested`
- `support_context_fallback_used`
- `support_metadata_served`

### API Dependencies

- `GET /support/entry-points`
- `GET /support/contextual-help`

### Data Model

#### Entity: SupportEntry

| Property | Type | Description |
| --- | --- | --- |
| `id` | `string (UUID)` | Unique entry identifier |
| `context` | `string` | Workflow context key: `export_failure`, `billing_question`, `account_recovery`, `general` |
| `actions` | `json` | Ordered array of recommended next-step actions |
| `isFallback` | `boolean` | Whether this is the generic catch-all entry |
| `updatedAt` | `datetime` | Last configuration update timestamp |

#### Entity: SupportAction (embedded in SupportEntry.actions[])

| Property | Type | Description |
| --- | --- | --- |
| `type` | `enum` | Action category: `self_service`, `contact`, `policy_info`, `privacy_help` |
| `label` | `string` | User-facing action label |
| `description` | `string` | Brief explanation of what this action provides |
| `target` | `string?` | URL, route, or deep-link target for navigation |

```json
{
  "context": "export_failure",
  "actions": [
    {
      "type": "self_service",
      "label": "Check export blockers",
      "description": "View common reasons exports fail and how to fix them.",
      "target": "/help/exports/troubleshooting"
    },
    {
      "type": "contact",
      "label": "Contact support",
      "description": "Our team typically responds within 24 hours.",
      "target": "/support/contact"
    },
    {
      "type": "policy_info",
      "label": "Export limits",
      "description": "Learn about export quotas and format availability.",
      "target": "/help/exports/limits"
    }
  ],
  "isFallback": false,
  "updatedAt": "2026-08-01T12:00:00Z"
}
```

#### Entity: HelpCategory

| Property | Type | Description |
| --- | --- | --- |
| `id` | `string (UUID)` | Unique category identifier |
| `name` | `string` | Category display name |
| `key` | `string` | Stable machine-readable key for context mapping |
| `sortOrder` | `integer` | Display ordering preference |
| `isActive` | `boolean` | Whether this category is currently published |

#### Entity: SystemSetting (Support Configuration)

| Property | Type | Description |
| --- | --- | --- |
| `key` | `string` | Setting key, e.g. `support.default_contact_email` |
| `value` | `string` | Setting value |
| `updatedAt` | `datetime` | Last update timestamp |

```json
{
  "key": "support.default_contact_email",
  "value": "help@resumeenhancer.com",
  "updatedAt": "2026-07-01T08:00:00Z"
}
```

#### Relationships

```
SupportEntry ───embeds─── SupportAction[0..N]
HelpCategory ───references─── SupportEntry (via context key mapping)
SystemSetting ───(standalone config)───
```

#### Business Notes

- Every `context` value in `SupportEntry` must have a corresponding `general` fallback; if a frontend requests a context that has no specific mapping, the service returns the `isFallback: true` entry instead of an empty response.
- Support action metadata lives outside the codebase and should be configurable via `SystemSetting` or a lightweight admin panel so that contact channels and policy links can be updated without deployments.
- The frontend should cache support metadata responses with a short TTL (e.g., 5–15 minutes) to avoid fetching on every navigation while still reflecting configuration changes within a reasonable window.
- Privacy-help routes embedded in `SupportEntry.actions` must only reference approved public/self-service destinations — never internal ticketing or operator-tool URLs.
